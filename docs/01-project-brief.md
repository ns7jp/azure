# 01. 案件概要・要件定義

## 1. 顧客ヒアリング（架空）

Sample Works社から「社内のお知らせを表示する小さなWebサーバーが欲しい。クラウドは初めてなので、安全で、費用を抑え、障害時に確認できる構成にしたい」と依頼された。

## 2. 曖昧な要望を測れる要件へ変える

| ID | 顧客の言葉 | 技術要件 | 確認方法 |
|---|---|---|---|
| FR-01 | Webページを置きたい | Ubuntu VMにNginxを導入 | HTTP応答またはVM内curl |
| FR-02 | 管理者だけ変更したい | SSHは指定CIDR、鍵認証のみ | 許可元/非許可元で接続試験 |
| NFR-01 | 費用を抑えたい | 学習用の小さいVM、不要時削除 | SKUと課金リソース一覧確認 |
| NFR-02 | 状態を確認したい | CPUアラートとログ基盤を準備 | リソース存在と設定確認 |
| NFR-03 | 再現したい | Bicepでコード化 | What-If、再デプロイ |
| NFR-04 | 誰の環境か知りたい | 共通タグを付与 | Resource Graph/CLIで確認 |

## 3. スコープ

### 対象

- Azure上のリソースグループ、ネットワーク、Linux VM、基本監視
- Bicepによる再現可能な構築
- 構築試験、運用手順、障害一次対応、削除

### 対象外

- 独自ドメイン、TLS証明書、WAF、バックアップ、冗長化、Entra ID認証
- アプリケーション開発、データベース、24時間365日の有人監視
- 本番SLA、負荷試験、実顧客データ

対象外は「不要」ではない。学習用の費用と複雑さを抑えた結果であり、本番化の際は再要件定義する。

## 4. 前提・制約・リスク

| 種別 | 内容 | 対応 |
|---|---|---|
| 前提 | Azure利用権限がある | デプロイ前にアカウントとサブスクリプション確認 |
| 制約 | 学習予算は小さい | 小さいSKU、短時間利用、終了後削除 |
| リスク | Public IPへの攻撃 | SSH接続元制限、鍵認証、HTTP既定閉鎖 |
| リスク | 誤ったサブスクリプションへ作成 | What-Ifと対象IDの指差し確認 |
| リスク | ログ保存で費用増加 | 保持日数と取り込み量を定期確認 |
| リスク | 単一VM停止でサービス停止 | 学習版の受容リスクとして記録 |

## 5. 完了条件

- 設計値とBicepが一致する。
- `az deployment sub what-if` が成功し、想定外リソースがない。
- 実施した試験に日時、結果、証跡、実施者がある。
- 失敗時にRunbookで一次切り分けできる。
- 削除後、対象リソースグループが存在しないことを確認できる。

## 演習

1. 「安全にしてほしい」を3つの測定可能な要件へ分解する。
2. 可用性99.9%が追加された場合、単一VMの何が不足するか説明する。
3. 対象外を1つ選び、本番では必要になる条件を書く。

答えの例は一つではない。設計理由と確認方法がセットなら、案件で説明できる要件になる。
