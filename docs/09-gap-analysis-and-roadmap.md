# 09. 不足点と学習ロードマップ

## 結論

現在の構成には、要件定義、設計、IaC、試験、運用、削除までの流れがあり、未経験者向けの土台として十分な範囲がある。一方、**設計書があること**と**構築できること**と**運用できること**は別である。ポートフォリオとして説得力を上げるには、機能を増やす前に、次の不足を実施結果で埋める。

## 不足点の優先順位

| 優先度 | 不足点 | なぜ必要か | 完了の証拠 |
|---|---|---|---|
| 必須 | 実機での構築・試験証跡 | コードを読めるだけでなく、実行して切り分けた事実を示すため | コミットSHAに対応したWhat-If、デプロイ、正常・異常・削除の記録 |
| 必須 | 要件・設計・実装・試験の追跡 | 「作ったもの」ではなく「要件を満たしたもの」と説明するため | 下記トレーサビリティ表の全必須行にリンクと結果がある |
| 必須 | 初心者向けの段階的な達成判定 | 手順のコピーで終わらず、理解できない箇所を特定するため | 各ステージの説明課題と実技課題を両方完了 |
| 高 | 監視通知とOSログ収集 | 現状はCPUアラートの定義と空のWorkspaceだけで、担当者への通知やsyslog調査ができないため | Action Group通知試験、AMA/DCRの収集クエリと証跡 |
| 高 | バックアップ・復元 | RPO 24時間を記載しているが、現状では達成手段がないため | Backup設計、復元手順、隔離環境での復元試験 |
| 高 | HTTPSと安全な管理経路 | HTTP/Public IP直結は本番想定の保護として不足するため | TLS終端と証明書更新、Bastion/VPN等の比較・採否記録 |
| 中 | コストの実測と上限管理 | 「小さいSKU」だけでは予算超過を検知できないため | 見積内訳、予算、アラート先、利用後の実績差異 |
| 中 | CIのテスト拡充 | 現状のCIはBicep build中心で、設計値や禁止設定の退行を十分検知しないため | lint、パラメーター検証、PSスクリプト解析の自動結果 |
| 発展 | 冗長化・負荷・災害対策 | 単一VMでは可用性要件を保証できないため | SLA前提、障害モード、ゾーン障害試験、RTO/RPO実測 |

> [!IMPORTANT]
> 「高」以降を全部実装する必要はない。未採用項目も、要件、費用、リスクを比較して対象外と判断できれば設計成果になる。実施していない項目を `PASS` と書かない。

## 4ステージの学習順序

### Stage 1: 読んで説明する（目安 2〜4時間）

1. READMEの構成図を紙や自分の言葉で書き直す。
2. `管理者PC → Public IP → NSG → NIC → VM → Nginx` を、各部品の役割とともに説明する。
3. `openHttp=false`、SSH鍵、`adminCidr` の理由を説明する。

達成条件:

- [ ] VNet、Subnet、NSG、NICの違いを資料を見ずに一言で説明できる。
- [ ] 単一VM、Public IP、未収集のOSログという3つの残存リスクを説明できる。
- [ ] 不明な用語を自分の言葉で用語集へ追記した([Azure基礎用語集](11-azure-glossary.md)の16.7を参照)。

### Stage 2: 作る前に予測する（目安 2〜3時間）

1. 自分用パラメーターファイルを作り、秘密情報がないことを確認する。
2. Bicep buildを実行する。
3. What-Ifの前に、作成されるリソース名・種類・個数を予想して記録する。
4. What-If結果と予想の差を記録する。

達成条件:

- [ ] Bicep buildがPASSで、コマンド・日時・コミットSHAが記録されている。
- [ ] What-Ifの差分を「安全そう」ではなく、リソース単位で説明できる。
- [ ] `-Apply` を付けない限り作成されない理由を説明できる。

### Stage 3: 構築して試す（目安 3〜5時間、課金あり）

1. 料金、対象Subscription、削除方法を再確認してデプロイする。
2. 試験仕様書に沿って正常系と異常系を実施する。
3. 少なくとも1件、起きた失敗または意図的な安全な不一致を、仮説→確認→修正→再試験の順で記録する。
4. リソースグループを削除し、残存課金リソースを確認する。

実施順・各フェーズのコマンド・証跡の残し方は [Stage 3 実施ランブック](10-stage3-runbook.md) にまとめている。

達成条件:

- [ ] 構築、SSH、HTTP閉鎖、Nginx、アラート定義、削除の証跡がある。
- [ ] 非許可元SSH試験は代替経路またはセッションを確保して安全に行った。
- [ ] Azure実機で未実施の試験は `NOT RUN` または `BLOCKED` と明記した。

### Stage 4: 1つだけ改善する（目安 4〜8時間）

下記から1つを選ぶ。

- Action GroupとOSログ収集を追加し、通知とKQL検索を試験する。
- Backupを追加し、別名VMまたは隔離環境への復元を試験する。
- Bastion/VPN案とPublic IP案を費用・運用・リスクで比較する。
- GitHub Actionsへlintと安全設定テストを追加する。

達成条件:

- [ ] 変更前の課題と採用理由がDecision Recordにある。
- [ ] 設計、Bicep、試験、Runbookを同じ変更で更新した。
- [ ] 改善の利点だけでなく、追加費用と新しい運用負荷を説明できる。

## 要件トレーサビリティ表

実施時にこの表を証跡ファイルへコピーし、`実装` と `試験結果` を具体的なファイル行、リソース、証跡へ置き換える。

| 要件ID | 設計 | 実装 | 試験ID | 試験結果 | 状態 |
|---|---|---|---|---|---|
| FR-01 | 基本設計「論理構成」 | `infra/cloud-init.yaml` | OS-01, OS-02 | `<証跡リンク>` | NOT RUN |
| FR-02 | 基本設計「セキュリティ」 | NSG規則、VM SSH設定 | NT-01, NT-02 | `<証跡リンク>` | NOT RUN |
| NFR-01 | 基本設計「コスト」 | VM SKU、削除スクリプト | CL-01 | `<証跡リンク>` | NOT RUN |
| NFR-02 | 基本設計「監視」 | Metric Alert、Workspace | MN-01 | `<証跡リンク>` | NOT RUN |
| NFR-03 | 基本設計「信頼性」 | Bicep | ST-01, ST-02, OP-01 | `<証跡リンク>` | NOT RUN |
| NFR-04 | 基本設計「命名・タグ」 | `commonTags` | CT-02 | `<証跡リンク>` | NOT RUN |

判定ルール:

- 要件に試験がなければ、要件を検証できないため未完了。
- 試験がPASSでも証跡がなければ、第三者が追跡できないため未完了。
- 対象外に変更した場合は、理由、承認者、見直し条件を残す。

## 設計判断（Decision Record）テンプレート

改善ごとに以下をIssue、PR、または `docs/decisions/` 配下へ残す。

```markdown
# ADR-NNN: <判断の題名>

- 状態: Proposed / Accepted / Rejected / Superseded
- 日付: YYYY-MM-DD
- 要件・課題: <何を満たしたいか>
- 制約: <予算、期限、スキル、リージョン等>
- 選択肢: <案A / 案B / 何もしない>
- 判断: <採用案>
- 理由: <セキュリティ、信頼性、費用、運用の比較>
- 影響: <得られる効果と新たな欠点>
- 検証: <試験IDと合格条件>
- 見直し条件: <利用者数、SLA、本番化等>
```

## 面接前の最終チェック

- [ ] 60秒で「要件→設計→実装→試験→運用」を説明できる。
- [ ] 自分が変更したBicepを、行ごとではなく設計意図で説明できる。
- [ ] PASS、FAIL、BLOCKED、NOT RUNを正直に区別している。
- [ ] 失敗を1件、原因と再発防止まで説明できる。
- [ ] 構成の弱点を3つ挙げ、予算が増えた場合の改善順を説明できる。
- [ ] 証跡から秘密情報と個人情報を除いている。
- [ ] Azureリソース削除後の確認まで記録している。

このチェックで未完了がある場合、それが次に学ぶ内容である。サービス数よりも、1つの要件を設計・実装・試験・運用まで一貫して説明できることを優先する。

## さらに次の題材を探す場合

上記のStage 1〜4と面接前チェックを終え、単一VM構成の説明に迷いがなくなったら、より複雑な題材で同じ工程(要件定義→設計→構築→試験→運用)を繰り返す発展編が [`docs/advanced/`](advanced/00-overview-requirements.md) にある。Windows Server多層構成(Web/AP/DB + AD DS/DNS)を題材にしており、サービス数を増やす前にこちらの案件で同じ思考プロセスを再現できるかを確認する使い方を想定している。
