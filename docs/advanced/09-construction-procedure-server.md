# 09. 構築手順書(サーバー編)

## この章のポイント

- 本章は、01〜04章で決定した設計内容(全体アーキテクチャ、ネットワーク、サーバー、セキュリティ)を踏まえ、実際に5台の仮想マシン(VM)を作成し、OSの初期設定から役割別ミドルウェア(AD DS/DNS、IIS、SQL Server 2022、ファイル共有等)の導入までを行う**実務手順書**です。番号付きの手順として、実際にそのまま画面操作をなぞれる粒度で解説します。
- Azure Bastion(`bas-sanrise-prod-jpe`)経由でのRDP接続手順を、実際の画面操作に沿って具体的に説明します。
- なぜ`vm-ad01`(AD DS/DNSサーバー)を最初に構築し、VNetのDNS設定を切り替えてから他の4台を構築するのか、という**構築順序の設計思想**を解説します。
- NSG(ネットワークの壁)とWindowsファイアウォール(OS内の壁)という「2つの壁」を両方とも正しく設定しないと通信が通らないという、多層防御構成ならではの落とし穴を整理します。
- 各サーバー構築後に行うべき疎通確認(ping、nslookup、ポート疎通確認、共有フォルダアクセス確認等)の具体的な方法と、初心者が陥りやすい典型的なミス・その対処法を随所に挿入します。

## 1. 本章の目的と位置づけ

### 1.1 何を書く章か

これまでの章は、いずれも「何を、どう作るべきか」という**設計**を扱ってきました。

| 章 | 扱う内容 |
|---|---|
| 01-architecture.md | システム全体構成(3層アーキテクチャ)の設計 |
| 02-network-design.md | VNet・サブネット・NSGルールの設計 |
| 03-server-design.md | 各VMの役割・VMサイズ・ディスク構成の設計 |
| 04-security-design.md | Azure Bastion・ID基盤・暗号化の設計 |

これに対して本章「構築手順書(サーバー編)」は、その設計を**実際にAzure上でどう作るか**という「作業手順」に焦点を当てます。読者が本章の手順を上から順に実施すれば、設計台帳(ledger)に定義された5台のVMが、設計どおりの状態で構築できることをゴールとしています。

なお、VNet・サブネット・NSG・Azure Bastion・Key Vaultといったネットワーク/セキュリティ基盤そのものの作成手順(Azure Portalでの`az network vnet create`相当の操作)は、別冊の「構築手順書(ネットワーク編)」(08-construction-procedure-network.md)で解説する前提とし、本章ではこれらが**すでに構築済みであること**を前提条件とします。本章の対象範囲は、あくまで「その基盤の上に、サーバー(VM)をどう構築するか」に絞ります。

### 1.2 前提となる完成済みリソース(本章の対象外)

本章の手順を開始する前に、以下のリソースが既に構築済みであることを前提とします。いずれも02章・04章で設計した値そのものです。

| リソース種別 | 名前 | 備考 |
|---|---|---|
| リソースグループ | `rg-sanrise-prod-jpe` | Japan East(`japaneast`)リージョン |
| 仮想ネットワーク(VNet) | `vnet-sanrise-prod-jpe`(`10.10.0.0/16`) | 5つのサブネットを含む |
| サブネット | `snet-web-prod-jpe`、`snet-ap-prod-jpe`、`snet-db-prod-jpe`、`snet-mgmt-prod-jpe`、`AzureBastionSubnet` | 02章の値どおり |
| NSG | `nsg-web-prod-jpe`、`nsg-ap-prod-jpe`、`nsg-db-prod-jpe`、`nsg-mgmt-prod-jpe`、`nsg-bastion-prod-jpe` | 各サブネットに関連付け済み。ルール内容は02章参照 |
| Azure Bastion | `bas-sanrise-prod-jpe`(Basic SKU) | `AzureBastionSubnet`(`10.10.5.0/26`)に配置済み |
| Key Vault | `kv-sanrise-prod-jpe` | シークレット保管用。RBACの割当は04章参照 |

> **初心者が陥りやすいミス**:VNet・サブネット・NSG・Bastionの構築が完了する前にVM作成を始めてしまうと、VM作成時のネットワーク選択画面で対象のサブネットが選べず、手順が前後して混乱します。必ず上記の前提条件がすべて揃っていることを、Azureポータルの該当リソースの画面で目視確認してから本章の手順に着手してください。

### 1.3 構築対象と全体順序(なぜこの順番か)

本プロジェクトで構築するVMは、設計台帳のとおり合計5台です。

| 順序 | VM名 | 役割 | 配置サブネット | プライベートIP |
|---|---|---|---|---|
| ① | `vm-ad01` | AD DS(ドメインコントローラ)+ DNSサーバー | `snet-mgmt-prod-jpe` | `10.10.4.4` |
| ② | `vm-db01` | DBサーバー(SQL Server 2022 Standard Edition) | `snet-db-prod-jpe` | `10.10.3.4` |
| ③ | `vm-ap01` | APサーバー(業務アプリケーション) | `snet-ap-prod-jpe` | `10.10.2.4` |
| ④ | `vm-web01` | Webサーバー(IIS) | `snet-web-prod-jpe` | `10.10.1.4` |
| ⑤ | `vm-file01` | ファイルサーバー(部門共有・帳票保管) | `snet-mgmt-prod-jpe` | `10.10.4.5` |

VMは同時並行に作成すること自体は技術的に可能ですが、本書ではあえて上記の順序を推奨します。理由は以下の2点です。

1. **`vm-ad01`を最初に構築する理由**:`vm-web01`・`vm-ap01`・`vm-db01`・`vm-file01`はいずれもドメイン`sanrise.local`に参加し、AD DS/DNSサーバー(`vm-ad01`)による名前解決とドメイン認証に依存します。DNSサーバーが存在しない状態で他のVMを先に構築しても、後からドメイン参加をやり直す二度手間が発生します。また、AD DS昇格が完了した直後に**VNetのDNSサーバー設定を`10.10.4.4`へ切り替える**という重要な作業が発生するため(6.1節で詳述)、これを他のVM作成前に済ませておくことで、以降のVMは作成直後から正しい名前解決の環境で起動できます。
2. **DB→AP→Webの順(業務システムの下流から上流へ)で構築する理由**:3層構成では、Web層はAP層に、AP層はDB層に依存して動作します。下流(DB)から先に構築・疎通確認しておけば、AP層を構築した直後にDB層への接続テストが行え、Web層を構築した直後にAP層への接続テストが行えます。逆にWebから先に作ってしまうと、疎通確認したくてもAP・DBがまだ存在せず、「本当に正しく作れているか」を段階的に確認できません。

`vm-file01`(ファイルサーバー)は業務システムの3層構成から独立した存在であるため、他の4台の構築が一段落してから最後に構築します。

## 2. 構築前の共通準備

### 2.1 使用するAzureイメージ・VMサイズ・ディスク一覧(設計台帳の再掲)

5台のVMはすべて、Azure Marketplaceが提供する**「Windows Server 2022 Datacenter」**イメージ(Gen2、x64)を使用します。設計台帳の値を一覧にまとめます。

| VM名 | VMサイズ | OSディスク | データディスク | 配置サブネット | プライベートIP(静的) |
|---|---|---|---|---|---|
| `vm-ad01` | `Standard_B2ms` | Standard SSD(E10、128 GiB) | なし | `snet-mgmt-prod-jpe` | `10.10.4.4` |
| `vm-web01` | `Standard_B2s` | Standard SSD(E6、64 GiB) | なし | `snet-web-prod-jpe` | `10.10.1.4` |
| `vm-ap01` | `Standard_B2ms` | Standard SSD(E10、128 GiB) | なし | `snet-ap-prod-jpe` | `10.10.2.4` |
| `vm-db01` | `Standard_B4ms` | Standard SSD(OS用) | Premium SSD × 3(データ用・ログ用・tempdb用に分離) | `snet-db-prod-jpe` | `10.10.3.4` |
| `vm-file01` | `Standard_B2s` | Standard SSD(E6、64 GiB、共有データ用ディスクを含む) | なし | `snet-mgmt-prod-jpe` | `10.10.4.5` |

> **補足**:`vm-db01`のデータ/ログ/tempdb用Premium SSDの具体的な容量(GiB数)は設計台帳に定めがなく、実際の受発注・在庫データ量の見積りに応じて別途確定します。本章では「Premium SSDとして3本に分離する」という**設計上決まっている方針**のみを扱い、容量の見積り自体は本パックの対象範囲外とします。

### 2.2 管理者アカウント・パスワードの取り扱い方針(Key Vault活用)

現状課題の1つに「サーバー管理者が固定グローバルIP経由でVMへ直接RDP接続しており、共有の管理者アカウントも常態化していてアクセス統制・監査ログが不十分である」という点がありました。本章のVM構築においても、この反省を踏まえて以下の方針を徹底します。

- **ローカル管理者アカウントのパスワードは、VMごとに異なる強固な値を個別に生成する。** 5台で使い回さないこと。
- **生成したパスワードは、Key Vault(`kv-sanrise-prod-jpe`)にVMごとに異なるシークレット名(例:`vm-ad01-localadmin-password`)で登録する。** 付箋・メモ帳・共有スプレッドシートへの記録は行いません。
- **SQL Serverの`sa`アカウントのパスワードやTDE証明書のバックアップなど、サーバー構築中に発生する秘密情報もすべて同様にKey Vaultへ登録する。**

これは設計台帳のセキュリティ方針(`identityStrategy`)である「各VMのローカル管理者パスワードやSQL Server sa相当アカウントの認証情報はAzure Key Vaultのシークレットとして一元管理し、Azure RBACによりアクセス権を最小権限で払い出す」を、構築作業の現場で具体的に実践するものです。

> **初心者が陥りやすいミス**:「後でまとめて登録すればいい」と考えて、作業中はテキストファイルやメモ帳にパスワードを書き留めてしまうケースが非常に多く見られます。作業端末上に平文のパスワードファイルが残ること自体がセキュリティインシデントの火種になるため、**パスワードを生成したその場でKey Vaultに登録し、ローカルのメモは直ちに削除する**という習慣を徹底してください。

### 2.3 Bastion経由での接続に関する制約(Basic SKUの注意点)

Azure Bastionは`bas-sanrise-prod-jpe`としてBasic SKUで構築されています(04章2.6節参照)。Basic SKUには以下の制約があり、本章の作業に影響するため、事前に理解しておく必要があります。

| 機能 | Basic SKU | Standard SKU以上 |
|---|---|---|
| ブラウザ経由のRDP/SSH接続(Azureポータル上) | ○ 利用可能 | ○ 利用可能 |
| ネイティブクライアント接続(手元PCの「リモートデスクトップ接続」アプリ等を直接使う方式) | × 利用不可 | ○ 利用可能 |
| ファイルのアップロード/ダウンロード | × 利用不可 | ○ 利用可能 |
| クリップボード経由のテキストのコピー&ペースト | ○ 利用可能 | ○ 利用可能 |

本設計はコスト重視のためBasic SKUを採用しているので、**Bastion経由でVMへファイルを直接アップロードすることができません**。そのため、SQL ServerのインストーラーやIISに配置するアプリケーションファイルなど、VM内に持ち込みたいファイルがある場合は、以下のいずれかの方法を用います。

1. VM自身のインターネットへのアウトバウンド通信(各NSGには明示的な拒否ルールがない限りAzureの既定の許可ルールが働くため、VMからインターネットへの発信は既定で可能)を使って、VM内から直接ダウンロードする。
2. あらかじめAzure Storageアカウントにインストーラー等を配置しておき、VM内からPowerShellの`Invoke-WebRequest`やAzure Storage Explorer等でダウンロードする(Azureのバックボーンネットワーク内で完結し、インターネットを経由しないためより安全)。

将来的に管理者の増員やより高度な運用が必要になった場合は、Standard SKUへの切り替えを検討します(04章2.6節参照)。

## 3. VM作成共通手順(Azure Portal)

ここでは、5台すべてのVM作成に共通する手順を、Azureポータルの画面遷移に沿って説明します。以降の6章では、VMごとに異なる値(VM名・サイズ・サブネット・IPアドレス等)だけを示し、「本節の手順に従って作成する」という形で参照します。

1. Azureポータルにサインインし、上部の検索ボックスから「仮想マシン」を検索して開く。
2. 「作成」→「Azure 仮想マシン」を選択する。
3. **[基本] タブ**を以下のとおり設定する。
   - サブスクリプション:プロジェクトで使用するサブスクリプションを選択
   - リソースグループ:`rg-sanrise-prod-jpe`
   - 仮想マシン名:構築対象のVM名(例:`vm-ad01`)
   - リージョン:**Japan East**(`japaneast`)
   - 可用性オプション:**「インフラストラクチャ冗長は必要ありません」**を選択(03章6.3節で解説したとおり、本設計では可用性セット・可用性ゾーンを採用しないため)
   - セキュリティの種類:Standard
   - イメージ:**Windows Server 2022 Datacenter - x64 Gen2**
   - VMアーキテクチャ:x64
   - サイズ:「サイズの変更」から対象のVMサイズ(例:`Standard_B2ms`)を選択
   - 管理者アカウント:ユーザー名・パスワードを入力(2.2節の方針に従い、VMごとに固有の強固なパスワードを設定し、直後にKey Vaultへ登録する)
   - 受信ポートの規則:**「なし」を選択する(最重要)**。RDP(3389)を安易に開放しないこと。VMへの接続はすべてAzure Bastion経由に統一するため、パブリックからの受信ポートは一切開放しません。
   - ライセンスの種類:Azure Hybrid Benefitは使用しない(コスト設計の月額試算はWindows Serverライセンス込みの従量課金を前提としているため)
4. **[ディスク] タブ**を設定する。
   - OSディスクの種類:対象VMに応じたStandard SSD(例:`vm-ad01`ならE10=128 GiB)
   - `vm-db01`の場合のみ、「データディスク」欄で「新しいディスクの作成」を3回行い、いずれもPremium SSDとして追加する(データ用・ログ用・tempdb用。詳細は6.2節)
   - キー管理:プラットフォームマネージドキーを使用(サーバー側の既定の暗号化。04章の`encryptionNotes`に基づく)
5. **[ネットワーク] タブ**を設定する。
   - 仮想ネットワーク:`vnet-sanrise-prod-jpe`
   - サブネット:対象VMの配置サブネット(例:`vm-ad01`なら`snet-mgmt-prod-jpe`)
   - パブリックIP:**「なし」**(最重要。非機能要件「VMには一切パブリックIPアドレスを付与しない」を満たすため)
   - NICネットワークセキュリティグループ:**「なし」**を選択する。本設計ではNSGをサブネット単位でのみ適用する方針(02章)であり、NIC単位でも重ねてNSGを作成すると二重管理になり、想定外の通信ブロックや、逆に想定より緩い通信を招く原因になるためです。
   - プライベートIP:「編集」から**静的(Static)**に変更し、設計台帳どおりの固定IPアドレス(例:`vm-ad01`なら`10.10.4.4`)を入力する
   - 負荷分散:使用しない
6. **[管理] タブ**を設定する。
   - 自動シャットダウン:必要に応じて設定(ledgerに定めなし。検証用途でコストを抑えたい場合の任意設定)
   - Identity:**「システム割り当てマネージドID」をオンにする**。これにより、VMがAzure ADの一種のアイデンティティを持ち、パスワードを使わずにKey Vault上のシークレットへアクセスできるようになります(04章3.5節の「Key Vault Secrets User」ロール割当の前提)。
   - Microsoft Defender for Cloud:サーバー向けプランを有効化(コスト設計の`Microsoft Defender for Cloud`項目に対応)
   - バックアップ:`vm-ad01`・`vm-web01`・`vm-ap01`・`vm-file01`はここで「Azure Backupを有効にする」にチェックし、Recovery Services Vault(`rsv-sanrise-prod-jpe`)とバックアップポリシー(`bkp-sanrise-standard-daily`)を選択する。**`vm-db01`はこの画面でのVM全体バックアップは有効化せず**、SQL Server内ワークロードバックアップ(トランザクションログ含む)を別途構成する(6.2節、詳細は06-backup-dr.md)。
7. **[監視] タブ**は既定値のまま進める(ブート診断は「プラットフォームで管理」のまま)。詳細な監視エージェント導入・アラート設定は05-operations-monitoring.mdで扱います。
8. **[詳細] タブ**は本プロジェクトでは特別な設定を行わず、既定値のまま進める。
9. **[タグ] タブ**は運用管理上、`Environment`・`Owner`等のタグ付けを行うことが一般的に推奨されますが、具体的なタグ運用ルールは設計台帳に定めがないため本書の対象外とし、各社の命名規約に従ってください。
10. **[確認および作成] タブ**で検証に成功していることを確認し、内容をひととおり見直したうえで「作成」をクリックする。
11. デプロイが完了したら、「リソースに移動」をクリックし、作成されたVMの概要画面でプライベートIPアドレスが設計台帳どおりであることを確認する。

### 3.1 よくある初心者のミス

| ミスの内容 | 何が起きるか | 対処法 |
|---|---|---|
| [基本]タブの「受信ポートの規則」でうっかり「RDP (3389)」を許可してしまう | パブリックIPを付与していなくても、この設定自体はNIC側の既定NSGルールに影響するため、意図せず緩い通信経路を作ってしまう可能性がある | 必ず「なし」を選択する。Bastion経由の接続は、対象サブネットのNSG(`nsg-web-prod-jpe`等)側で別途許可されているため、この画面での追加設定は不要 |
| プライベートIPの割り当て方法を「動的(Dynamic)」のままにしてしまう | VMの再起動等のタイミングでIPアドレスが変わる可能性があり、NSGルールやDNSレコード、SQL接続文字列等、固定IPを前提とした設計全体が崩れる | 必ず「静的(Static)」に変更し、設計台帳どおりのIPアドレスを明示的に入力する |
| NICに個別のNSGを追加してしまう | サブネット側のNSGとNIC側のNSGの両方が評価されるようになり、意図しない通信のブロックや、トラブルシュート時にどちらのNSGが原因か分かりにくくなる | NICのNSGは必ず「なし」とし、サブネット単位のNSGのみで通信を統制する |
| 管理者パスワードを全VM共通の値にしてしまう | 現状課題である「共有アカウントの常態化」を、形を変えてAzure上でも再現してしまうことになる | VMごとに固有の強固なパスワードを生成し、Key Vaultへ個別に登録する(2.2節) |

## 4. Azure Bastion経由のRDP接続手順

VM作成後、初回のOS初期設定やソフトウェアのインストールを行うには、Azure BastionからRDP接続を行います。ここでは、Basic SKUのBastionにおける標準的な接続方法(ブラウザ経由)を説明します。

1. Azureポータルで対象のVM(例:`vm-ad01`)のリソース画面を開く。
2. 左側メニューから「接続」→「Bastion」を選択する。
3. 「使用中の Bastion」欄に`bas-sanrise-prod-jpe`が表示されていることを確認する。
4. VMのログオン資格情報を入力する。
   - 初回接続時は、VM作成時に設定したローカル管理者アカウントのユーザー名・パスワードを入力する(Key Vaultから該当のシークレット値をコピーして貼り付ける)
   - ドメイン参加後の2回目以降の接続では、ドメインの管理者アカウント(`SANRISE\ユーザー名`の形式)でもログオン可能
5. 「接続」ボタンをクリックする。
6. ブラウザの新しいタブ(またはポップアップ)にリモートデスクトップ画面が表示されるまで、数秒〜数十秒待つ。
7. 接続が確立すると、ブラウザ内にVMのデスクトップ画面が表示される。

接続後の操作性については、以下の点に留意してください。

- テキストのコピー&ペーストは、ブラウザとVMデスクトップ間で利用可能です(Ctrl+C/Ctrl+Vで通常どおり操作できます)。
- ファイルのアップロード/ダウンロードはBasic SKUでは利用できません(2.3節参照)。
- 接続を終了する際は、VM側で「サインアウト」するか、ブラウザのタブを閉じることでセッションを終了します。

このBastion経由の接続はすべて、Azureポータルへのサインイン(Microsoft Entra ID)を前提としているため、接続の都度「誰が」「いつ」「どのVMに」接続したかが自動的にログとして記録されます(04章2.4節、05章のダッシュボード項目「Azure Bastionの接続ログ」参照)。旧環境の「固定グローバルIP経由の直接RDP接続で証跡が残らない」という課題(現状課題④)は、この接続方式に切り替えることで解消されます。

### 4.1 よくある初心者のミス

| ミスの内容 | 何が起きるか | 対処法 |
|---|---|---|
| VMの「接続」メニューで「RDP」(直接接続用)を選んでしまう | VMにパブリックIPを付与していないため、ダウンロードしたRDPファイルで直接接続しようとしても到達できず、失敗する | 必ず「Bastion」を選択する。「RDP」メニューはパブリックIPを持つVM向けの選択肢であり、本設計では使用しない |
| ローカル管理者パスワードを忘れてBastion画面で入力に詰まる | Key Vaultを確認せず何度もログオンに失敗し、アカウントロックのリスクが生じる | パスワードは必ずKey Vault(`kv-sanrise-prod-jpe`)に保管されているため、そこから正確にコピーする運用を徹底する |
| 接続完了までに時間がかかることに焦って何度も「接続」ボタンを押し直す | 複数の接続セッションが同時に開始され、リソースを無駄に消費したり画面が混乱したりする | Bastion接続の確立には数十秒程度かかることがあるため、1回のクリックで気長に待つ |

## 5. OS初期設定(全VM共通)

Bastion経由で初回ログオンした直後、役割別の設定に入る前に、全VM共通で行うべきOS初期設定です。

1. **タイムゾーンの変更**:Azure VMの既定のタイムゾーンは「(UTC) 協定世界時」です。設定→時刻と言語→日付と時刻から、「**(UTC+09:00) 大阪、札幌、東京**」に変更する。
2. **コンピューター名の確認**:VM作成時に指定した名前(例:`vm-ad01`)がそのままWindowsのコンピューター名になっていることを、システムのプロパティ画面で確認する。
3. **Windows Updateの適用**:設定→Windows Updateから、最新の累積更新プログラムを確認・適用し、必要に応じて再起動する。
4. **NICのDNSサーバー設定の確認**:`ipconfig /all`を実行し、DNSサーバーの設定値を確認する(`vm-ad01`構築直後は既定のAzure提供DNSのままだが、6.1節の手順でVNet全体の設定を`10.10.4.4`に切り替える。`vm-ad01`より後に作成するVMは、作成時点で既にこの設定が反映されているはずである)。
5. **サーバーマネージャーの初期構成ウィザードを閉じる**:既定で起動する「サーバーマネージャー」のダッシュボードを確認し、以降の役割追加作業に備える。

> **初心者が陥りやすいミス**:タイムゾーンの変更を忘れたまま運用を開始してしまうと、イベントログやアプリケーションのログに記録される時刻がすべてUTC(日本時間より9時間遅れ)になり、障害発生時刻の特定やLog Analyticsのログとの突き合わせで混乱を招きます。**OS初期設定の中でも特に忘れやすく、かつ後から気づきにくい**ため、必ずVM作成直後にチェックする習慣をつけてください。

### 5.1 よくある初心者のミス(OS初期設定全般)

| ミスの内容 | 何が起きるか | 対処法 |
|---|---|---|
| Windows Updateを適用しないまま本番運用に入ってしまう | 旧環境の課題であった「OSサポート切れでパッチが当たらない状態」を、形を変えて再現してしまう | VM構築直後に必ず最新の更新プログラムを適用し、以降は05-operations-monitoring.mdで定めるパッチ適用サイクルに乗せる |
| 5台のVMそれぞれでタイムゾーンの設定有無がバラバラになる | 一部のVMだけ日本時間、一部はUTCのままとなり、複数VMをまたいだログ調査(例:Web層とAP層のタイムスタンプ突き合わせ)が困難になる | 5台すべてに対して本節の手順を機械的に実施し、設定漏れのVMがないか一覧でチェックする |

## 6. サーバー別構築・役割設定手順

### 6.1 `vm-ad01`:AD DS/DNSサーバー

#### 6.1.1 VM作成

3章の共通手順に従い、以下のパラメータで`vm-ad01`を作成します。

| 項目 | 値 |
|---|---|
| VM名 | `vm-ad01` |
| VMサイズ | `Standard_B2ms` |
| OSディスク | Standard SSD(E10、128 GiB) |
| 配置サブネット | `snet-mgmt-prod-jpe` |
| プライベートIP(静的) | `10.10.4.4` |

#### 6.1.2 AD DS役割の追加とドメインコントローラーへの昇格

設計台帳の`identityStrategy`には、次のように定められています。

> vm-ad01を既存オンプレミスADドメイン(sanrise.local)の追加ドメインコントローラとしてAzure上に配置し、オンプレ側とサイト間VPNを介して複製する構成を将来フェーズで想定する(本フェーズではAzure内で完結するAD DS環境として構築)。

つまり、将来的にはオンプレミスの`sanrise.local`ドメインとサイト間VPNで接続し、正式な「レプリカドメインコントローラ」として機能させる計画ですが、**本フェーズではオンプレミス環境との接続(サイト間VPN等)を構築しないため**、実際の構築作業では「新しいフォレストを追加する」を選択し、オンプレミスと**同一のドメイン名`sanrise.local`**でAzure内に新規のドメインを作成します。これにより、名前空間をオンプレミスと合わせておき、将来サイト間VPNが構築された際の統合作業をスムーズにするという狙いです。

1. Bastion経由で`vm-ad01`にRDP接続する(4章の手順)。
2. サーバーマネージャーを起動し、「管理」メニューから「役割と機能の追加」を選択する。
3. 「役割ベースまたは機能ベースのインストール」を選択し、「次へ」。
4. 対象サーバーとして`vm-ad01`(自分自身)が選択されていることを確認し、「次へ」。
5. サーバーの役割一覧から「**Active Directory ドメイン サービス**」にチェックを入れる。関連する機能の追加を促すダイアログが表示されるので、「機能の追加」をクリックする(DNSサーバーの役割は、後続のドメイン昇格ウィザードの中で自動的に追加されるため、この時点で個別にチェックする必要はない)。
6. 機能の選択画面は既定のまま「次へ」。
7. AD DSに関する説明画面を確認し、「次へ」。
8. 確認画面の内容を確認し、「インストール」をクリックする。
9. インストール完了後、サーバーマネージャー右上の通知(旗のアイコン)から「**このサーバーをドメイン コントローラーに昇格する**」を実行する。
10. 「配置構成」画面で「**新しいフォレストを追加する**」を選択し、ルートドメイン名に`sanrise.local`と入力する。
11. 「ドメイン コントローラーのオプション」画面で、以下を設定する。
    - フォレストの機能レベル/ドメインの機能レベル:利用可能な最新のレベル(Windows Server 2022環境のため最新でよい)
    - 「ドメイン ネーム システム(DNS)サーバー」:チェック済み(既定)
    - 「グローバル カタログ(GC)」:チェック済み(既定、フォレスト内最初のドメインコントローラーのため必須)
    - ディレクトリ サービス復元モード(DSRM)のパスワードを設定する。このパスワードは、AD DS自体に障害が発生した際の復旧用の特別なパスワードであり、通常のドメイン管理者パスワードとは別物です。**設定後、直ちにKey Vault(`kv-sanrise-prod-jpe`)へシークレットとして登録**する。
12. 「DNSオプション」画面で、委任の作成に関する警告が表示されるが、これは初回構築時に想定される警告であるため、そのまま「次へ」進んでよい。
13. 「追加オプション」画面でNetBIOS名(既定で`SANRISE`)を確認し、「次へ」。
14. 「パス」画面は、データベース・ログファイル・SYSVOLフォルダーの格納先を確認する。本設計ではAD DSのデータ量がOSディスクに収まる規模であるため(03章参照)、既定のパス(OSディスク上)のまま「次へ」進む。
15. 「オプションの確認」画面で設定内容を確認する。
16. 「前提条件のチェック」で警告(初回フォレスト作成時によく出る想定内の警告を含む)が表示された場合は内容を確認し、エラーがなければ「インストール」をクリックする。
17. インストールが完了すると、VMが自動的に再起動される。
18. 再起動後、Bastion経由で再接続し、サーバーマネージャーでAD DSおよびDNSの役割が正常に稼働していることを確認する。

#### 6.1.3 【最重要】VNetのDNSサーバー設定の切り替え

AD DSの昇格が完了しただけでは、他のVM(`vm-web01`等)はまだAzureの既定DNS(`168.63.129.16`)を参照したままであり、`sanrise.local`ドメインの名前解決やドメイン参加ができません。**この手順を忘れると、以降すべてのVMのドメイン参加が失敗します。**

1. Azureポータルで仮想ネットワーク`vnet-sanrise-prod-jpe`のリソース画面を開く。
2. 左側メニューから「DNS サーバー」を選択する。
3. 既定の「既定値(Azure が提供)」から「**カスタム**」に切り替える。
4. DNSサーバーのアドレスとして`10.10.4.4`(`vm-ad01`)を追加する。
5. 「保存」をクリックする。
6. この設定はVNet内の各VMのNICに対してDHCP経由で反映されるため、**既に起動しているVMがある場合は、対象VMを再起動するか、コマンドプロンプトで`ipconfig /release`→`ipconfig /renew`を実行**して新しいDNS設定を反映させる。`vm-ad01`より後に作成するVMは、作成時点でこの設定が既に反映された状態でスタートするため、この再起動作業は不要である。

> **なぜこの手順が必要なのか(設計思想)**:Azure仮想ネットワークは既定で、Azure自身が提供する内部DNS(`168.63.129.16`)を各VMに配布します。このAzure既定DNSは、Azure内部のVM名前解決やインターネット上の名前解決はできますが、`sanrise.local`のような**独自ドメインのAD統合ゾーン**は解決できません。そのため、AD DSを導入したら必ずVNetのカスタムDNS設定をAD DSサーバーのIPアドレスに切り替える、という手順が、Azure上でAD DS環境を構築する際の定石です。本章で構築順序を「`vm-ad01`を最初に」としているのは、まさにこの手順を他のVM構築より先に済ませておくためです(1.3節参照)。

#### 6.1.4 DNSの動作確認

1. `vm-ad01`上で、DNSマネージャー(`dnsmgmt.msc`)を開く。
2. 「前方参照ゾーン」に`sanrise.local`ゾーンが自動的に作成されていることを確認する。
3. コマンドプロンプトで`nslookup sanrise.local`を実行し、`10.10.4.4`が応答として返ることを確認する。

#### 6.1.5 よくある初心者のミス(AD DS構築)

| ミスの内容 | 何が起きるか | 対処法 |
|---|---|---|
| ドメイン名の入力を`sanrise.local`ではなく`sanrise.com`等、別の値で入力してしまう | ドメイン名は昇格後に変更することが極めて困難(実質的に再構築が必要)であり、将来のオンプレミスとの統合(サイト間VPN・信頼関係構築)にも支障が出る | 設計台帳に記載された`sanrise.local`という値を、入力前に必ず指紋合わせのように再確認する |
| VNetのDNSサーバー設定の切り替え(6.1.3節)を忘れる | `vm-web01`等の後続VMがドメインに参加できず、「ドメインが見つかりません」というエラーで数時間ハマる、非常によくある失敗パターン | AD DS昇格が完了したら、他のVMを作らずにまずVNetのDNS設定を確認・変更する習慣をつける |
| DSRMパスワードを設定した記憶がなく、後で聞かれても分からなくなる | AD DSの障害復旧(ディレクトリサービス復元モードでの起動)が必要になった際に対応できなくなる | 設定直後に必ずKey Vaultへ登録し、パスワードをその場限りのものにしない |

### 6.2 `vm-db01`:DBサーバー(SQL Server 2022 Standard Edition)

#### 6.2.1 VM作成

3章の共通手順に従い、以下のパラメータで`vm-db01`を作成します。ディスクタブでは、OSディスクに加えて**データディスクを3本**追加する点が他のVMと異なります。

| 項目 | 値 |
|---|---|
| VM名 | `vm-db01` |
| VMサイズ | `Standard_B4ms` |
| OSディスク | Standard SSD |
| データディスク | Premium SSD × 3本(データ用・ログ用・tempdb用) |
| 配置サブネット | `snet-db-prod-jpe` |
| プライベートIP(静的) | `10.10.3.4` |

> **なぜPremium SSDを3本に分けるのか**:03章5.4節で解説したとおり、OS用の読み書きと業務データの読み書きが同じディスク上で競合すると性能が不安定になること、またデータファイル(ランダムアクセス中心)・ログファイル(順次書き込み中心)・tempdb(一時作業領域で高負荷になりがち)がそれぞれ異なるI/O特性を持つことから、専用のPremium SSDへ分離する設計としています。VM作成時にこの3本を確実に追加し忘れないことが重要です。

#### 6.2.2 データディスクの初期化

Azureポータルでディスクを追加しただけでは、Windows OS上ではまだ「未初期化」の状態であり、そのままでは使用できません。

1. Bastion経由で`vm-db01`にRDP接続する。
2. 「ディスクの管理」(`diskmgmt.msc`)を起動する。
3. 追加した3本のディスクが「オフライン」または「未初期化」として表示されるので、それぞれを右クリックし「オンライン」にする。
4. 続けて各ディスクを右クリックし「ディスクの初期化」を選択、パーティションスタイルは「**GPT**」を選択する。
5. 各ディスクの未割り当て領域を右クリックし「新しいシンプル ボリューム」を作成する。
6. ドライブレターを割り当てる。本書では例として、データ用を`F:`、ログ用を`G:`、tempdb用を`H:`とする(実際の運用では貴社の命名規約に従う)。
7. ファイルシステムはNTFS、アロケーションユニットサイズはSQL Serverの推奨値である**64 KB**を指定してフォーマットする。

> **初心者が陥りやすいミス**:「Azureポータルでディスクを追加したのに、VM内のエクスプローラーに表示されない」という質問は非常によくあるトラブルです。これはAzure側の追加作業とWindows OS側の初期化作業が別工程であるためで、本節の手順(オンライン化→初期化→ボリューム作成)を必ず実施する必要があります。

#### 6.2.3 ドメイン参加

1. システムのプロパティから「ドメインまたはワークグループの変更」を開く。
2. 「ドメイン」を選択し、`sanrise.local`と入力する。
3. ドメイン管理者の資格情報を入力し、参加を完了する。
4. VMを再起動する。

#### 6.2.4 SQL Server 2022 Standard Editionのインストール

1. SQL Server 2022 Standard Editionのインストールメディア(ISOファイル)をマウントし、`setup.exe`を実行する(インストールメディアの入手方法は2.3節参照)。
2. インストールセンターから「新規のSQL Server スタンドアロン インストール...」を選択する。
3. プロダクトキーを入力し(Standard Edition)、「次へ」。
4. 使用条件に同意し、「次へ」。
5. Microsoft Updateの設定を確認し、「次へ」。
6. インストールルールのチェック結果を確認し、警告があれば内容を確認したうえで「次へ」。
7. 「機能の選択」画面で「**データベース エンジン サービス**」にチェックを入れる(SSRS/SSAS等は本設計では使用しないため不要)。
8. 「インスタンスの構成」画面で、既定のインスタンス(`MSSQLSERVER`)を選択する。
9. 「サーバーの構成」画面で以下を設定する。
   - SQL Server エージェントのスタートアップの種類を「**自動**」に変更する(06章のバックアップジョブ等で必要)
   - サービスアカウントには、共有の管理者アカウントではなく専用のドメインサービスアカウントを指定し、そのパスワードもKey Vaultで管理する
10. 「データベース エンジンの構成」画面で以下を設定する。
    - 認証モード:「**混合モード(SQL Server 認証と Windows 認証)**」を選択し、`sa`アカウントのパスワードを設定する。**設定後、直ちにこのパスワードをKey Vault(`kv-sanrise-prod-jpe`)へシークレットとして登録**する(既存アプリケーションがSQL認証で接続する前提のため、混合モードを採用)。
    - 「SQL Server管理者の追加」で、現在のWindowsアカウント(ドメイン管理者等)を追加する。
    - **「データ ディレクトリ」タブ**で、以下のように6.2.2節で作成したドライブを明示的に指定する(最も重要な手順)。
      - ユーザーデータベースディレクトリ:`F:\`
      - ユーザーログディレクトリ:`G:\`
      - tempdbディレクトリ:`H:\`
11. 内容を確認し、「インストール」をクリックする。
12. インストール完了後、Windowsを再起動する。

#### 6.2.5 SQL Serverのネットワーク設定とファイアウォール

1. 「SQL Server 構成マネージャー」を開く。
2. 「SQL Server ネットワークの構成」→「MSSQLSERVER のプロトコル」を開き、**TCP/IPが「有効」になっていることを確認**する(構成によっては既定で無効になっている場合があるため、必ず確認する)。無効の場合は有効化し、SQL Serverサービスを再起動する。
3. コントロールパネルから「Windows Defender ファイアウォール」を開き、「詳細設定」→「受信の規則」→「新しい規則」で、**TCP 1433番ポート**を許可する規則を追加する。

> **なぜOS側のファイアウォールも設定する必要があるのか(多層防御の再確認)**:NSG(`nsg-db-prod-jpe`)側では既に`vm-ap01`からの1433番ポート接続を許可していますが(02章参照)、これはAzureネットワークレベルの制御です。VMのOS内部で動作しているWindows Defenderファイアウォールは、これとは**独立した別レイヤーの壁**であり、既定では1433番ポートの受信を許可していません。NSGとWindowsファイアウォールという「2つの壁」の両方を正しく開けて初めて通信が成立する、という点は、AP層(8443番)・Web層(443番)を含め、本プロジェクトの全サーバーに共通する重要な注意点です。

#### 6.2.6 TDE(透過的データ暗号化)の有効化

設計台帳のとおり、`vm-db01`ではTDEを有効化し、証明書をKey Vaultにバックアップします。SQL Server Management Studio(SSMS)を用いて、以下のT-SQLを順に実行します。

1. `master`データベースにマスターキーを作成する。

```sql
USE master;
CREATE MASTER KEY ENCRYPTION BY PASSWORD = '<強力なパスワード>';
```

2. 証明書を作成する。

```sql
CREATE CERTIFICATE TDECert
WITH SUBJECT = 'Sanrise TDE Certificate for vm-db01';
```

3. 対象データベース(受発注・在庫管理システムのデータベース)にデータベース暗号化キーを作成する。

```sql
USE [対象データベース名];
CREATE DATABASE ENCRYPTION KEY
WITH ALGORITHM = AES_256
ENCRYPTION BY SERVER CERTIFICATE TDECert;
```

4. TDEを有効化する。

```sql
ALTER DATABASE [対象データベース名] SET ENCRYPTION ON;
```

5. **証明書と秘密鍵をファイルにバックアップする(最重要)。**

```sql
BACKUP CERTIFICATE TDECert
TO FILE = 'C:\Temp\TDECert.cer'
WITH PRIVATE KEY (
    FILE = 'C:\Temp\TDECert.pvk',
    ENCRYPTION BY PASSWORD = '<証明書バックアップ用のパスワード>'
);
```

6. 出力された`TDECert.cer`・`TDECert.pvk`の2つのファイルを、Azure Key Vault(`kv-sanrise-prod-jpe`)にシークレット(またはKey Vaultの証明書機能)としてアップロードする。
7. アップロード完了後、`C:\Temp`配下に残っているローカルの証明書ファイルは安全に削除する。

> **なぜ証明書のバックアップが最重要なのか(設計思想)**:TDEを有効化したデータベースは、暗号化に使った証明書がなければ**バックアップからのリストアが一切できなくなります**。万が一`vm-db01`自体が失われ、証明書のバックアップも取っていなかった場合、Recovery Services Vaultにバックアップデータ自体は残っていても、暗号化を解けずデータが永久に読み出せなくなるという致命的な事故につながります。TDEの導入とセットで証明書バックアップを行うことは、暗号化のメリット(データ保護)とリスク(復旧不能化)を正しく両立させるための必須手順です。

#### 6.2.7 よくある初心者のミス(DBサーバー構築)

| ミスの内容 | 何が起きるか | 対処法 |
|---|---|---|
| データディレクトリの指定を忘れ、既定のCドライブ(OSディスク)のままインストールしてしまう | 03章で設計したディスク分離のメリット(I/O競合の回避)が得られず、性能設計が形骸化する | インストールウィザードの「データ ディレクトリ」タブで、必ずF/G/Hドライブを明示的に指定する |
| TDE証明書のバックアップを取らずに運用を開始してしまう | 障害時にバックアップからリストアできない致命的な事態を招く | TDE有効化の直後に必ず証明書バックアップとKey Vaultへの登録をセットで実施する |
| SQL Server構成マネージャーでTCP/IPが無効のまま気づかない | APサーバーからの接続がすべてタイムアウトし、原因調査に時間がかかる | インストール後、必ずTCP/IPの有効化状況を確認する習慣をつける |

#### 6.4.4 HTTPSバインディングの設定

NSG(`nsg-web-prod-jpe`)では、社内イントラネットからの通信としてHTTPS(443番ポート)のみを許可しており、HTTP(80番ポート)は許可されていません(02章参照)。そのためIISの既定のHTTP(80番)バインディングのままでは、社内ユーザーは画面にアクセスできません。

1. IISマネージャーで対象サイトを選択し、「バインドの編集」を開く。
2. 「追加」から、種類「https」、ポート「443」を指定したバインディングを追加する。
3. SSL証明書として、社内のプライベート認証局(内部CA)が発行した証明書、または検証用の自己署名証明書を選択する(証明書の発行・配布手順自体は本書の対象外とし、各社のPKI運用に従う)。
4. 既定のHTTP(80番)バインディングは、社内利用専用であることを踏まえて削除するか、HTTPSへリダイレクトする設定を追加する。

> **なぜこの設定が必要なのか**:「NSGで443番だけ開けたのに画面が表示されない」という質問は非常によくある問い合わせです。原因の多くは、IIS側が既定のHTTP(80番)のままバインドされていることです。NSGはあくまでネットワークレベルの通行許可であり、**アプリケーション(IIS)自体がどのポート・プロトコルで待ち受けているか**は別途設定が必要である、という点を正しく理解することが重要です。

#### 6.4.5 動作確認

1. `vm-web01`上のブラウザで`https://localhost`にアクセスし、IISの既定ページ(または配置済みのアプリケーション画面)が表示されることを確認する。
2. 社内イントラネット(`172.16.0.0/16`)上の端末から`https://vm-web01.sanrise.local`または`https://10.10.1.4`にアクセスし、画面が表示されることを確認する(既存アプリケーションの配置前は、IISの既定ページが表示されれば疎通確認としては成功と判断できる)。

#### 6.5.3 共有フォルダの作成

1. Bastion経由で`vm-file01`にRDP接続する。
2. エクスプローラーでCドライブ直下に、業務用のフォルダ構成を作成する(例:`C:\FileShare\見積書`、`C:\FileShare\納品書`、`C:\FileShare\部門共有`)。

10. 共有一覧に、作成した共有が正しく表示されることを確認する。

#### 6.5.4 よくある初心者のミス(ファイルサーバー構築)

| ミスの内容 | 何が起きるか | 対処法 |
|---|---|---|
| 共有データを一時ディスク(Dドライブ)に保存してしまう | VMの再起動・再作成のタイミングでデータが消失する重大インシデントになる | 共有データは必ず永続化されるディスク(本設計ではOSディスクであるCドライブ)上に作成する |
| 共有権限のみ設定し、NTFS権限の設定を忘れる(またはその逆) | Windowsの共有フォルダは共有権限とNTFS権限の両方が評価され、より厳しい方が適用される。片方だけ緩くしても意図した制御にならない | 「カスタム権限」を選び、共有権限・NTFS権限の両方を意図どおりに設定したことを確認する |
| ドメイン参加前に共有フォルダを作成し、ローカルアカウントに対して権限設定してしまう | ドメイン参加後に権限を設定し直す二度手間が発生する | ドメイン参加を先に完了させてから、ADセキュリティグループを対象に権限設定を行う |

## 7. 構築後の疎通確認(まとめ)

5台すべてのVM構築が完了したら、最後に一連の疎通確認を行い、設計どおりに通信できることを確認します。

### 7.1 各サーバー単体の疎通確認

| 確認項目 | 確認方法 | 確認する内容 |
|---|---|---|
| ドメイン参加状況 | 各VM上で`whoami /fqdn`または`systeminfo`を実行 | `SANRISE\`ドメインのアカウントとして認識されていること |
| 名前解決(正引き) | `nslookup vm-web01.sanrise.local`(`vm-ad01`のDNSサーバーに対して実行) | `10.10.1.4`が返ること(他VMも同様に確認) |
| 名前解決(逆引き) | `nslookup 10.10.1.4` | `vm-web01.sanrise.local`が返ること |
| IPアドレス設定 | `ipconfig /all` | プライベートIPが設計台帳どおりの静的アドレスであること、DNSサーバーが`10.10.4.4`を指していること |
| ネットワーク疎通(ICMP) | `ping vm-ad01.sanrise.local` | 応答があること |

> **ping が通らないときの初心者向けチェックポイント**:pingが失敗すると「ネットワーク設定(NSG)がおかしい」とすぐに疑いがちですが、Windows Serverは既定でWindows Defenderファイアウォールがping(ICMPv4のエコー要求)の受信をブロックしていることがあります。NSG側は明示的にICMPを拒否していないため、まずは対象VMのファイアウォールの受信規則で「ファイルとプリンターの共有 (エコー要求 - ICMPv4-受信)」が有効になっているかを確認してください。

### 7.2 層間の疎通確認(業務システムの通信経路)

02章で設計したとおりの通信のみが通り、それ以外(特にWeb→DBの直接通信)が拒否されることを確認します。PowerShellの`Test-NetConnection`コマンドを使うと、TCPレベルでのポート疎通を簡単に確認できます。

| 確認元 | 確認先 | コマンド例 | 期待結果 |
|---|---|---|---|
| `vm-web01` | `vm-ap01`(8443) | `Test-NetConnection -ComputerName 10.10.2.4 -Port 8443` | `TcpTestSucceeded : True` |
| `vm-ap01` | `vm-db01`(1433) | `Test-NetConnection -ComputerName 10.10.3.4 -Port 1433` | `TcpTestSucceeded : True` |
| `vm-web01` | `vm-db01`(1433) | `Test-NetConnection -ComputerName 10.10.3.4 -Port 1433` | `TcpTestSucceeded : False`(**拒否されることが正しい**。多層防御のルール`Deny-Web-To-Db-Outbound`が機能している証拠) |
| 各VM | `vm-ad01`(53、DNS) | `Resolve-DnsName vm-file01.sanrise.local -Server 10.10.4.4` | 正しくIPアドレスが解決されること |

> **重要**:「Web→DBへの直接通信が失敗すること」も立派な確認項目です。初心者はつい「通信が通ること」ばかりを確認しがちですが、多層防御の設計を検証するうえでは「通ってはいけない通信が、意図どおり拒否されていること」の確認が同じくらい重要です。

### 7.3 役割別の追加確認

| 対象VM | 確認方法 |
|---|---|
| `vm-ad01` | DNSマネージャーで`sanrise.local`ゾーンの存在を確認。「Active Directory ユーザーとコンピューター」でドメイン参加済みの各VMのコンピューターオブジェクトが登録されていることを確認 |
| `vm-web01` | 社内イントラネット端末のブラウザから`https://vm-web01.sanrise.local`にアクセスし、IIS既定ページ(またはアプリ画面)が表示されることを確認 |
| `vm-ap01` | `netstat -an` の結果を8443番ポートで絞り込み、LISTEN状態を確認。`vm-web01`から`Test-NetConnection`で疎通確認 |
| `vm-db01` | SSMSまたは`sqlcmd`で`vm-ap01`から接続テストを実施。TDEが有効なデータベースのプロパティで暗号化状態(「暗号化されています」)を確認 |
| `vm-file01` | 別の端末のエクスプローラーのアドレスバーに`\\vm-file01\FileShare`(または`\\10.10.4.5\FileShare`)を入力し、フォルダ一覧が表示されアクセス権に応じた読み書きができることを確認 |

| 8 | SQL Serverの各データディレクトリがF/G/Hドライブ(Premium SSD)を指している | ☐ |
| 9 | TDEが有効化され、証明書がKey Vaultにバックアップされている | ☐ |

| 11 | すべてのローカル管理者パスワード・サービスアカウントのパスワードがKey Vaultに登録されている | ☐ |

## 8. 設計思想のまとめ・次章への接続

本章で示した構築手順は、いずれも01〜04章で決定した設計を「実際に手で再現するとどうなるか」を具体化したものです。特に強調したいポイントは次の3つです。

1. **構築順序そのものが設計判断である**:AD DS/DNSを最初に構築し、VNetのDNS設定を切り替えてから他のVMを作るという順序は、単なる好みではなく、Azure上でハイブリッドID基盤を成立させるための技術的必然です。
2. **NSGとWindowsファイアウォールという「2つの壁」の両方を意識する**:Azureのネットワークレベルの制御(NSG)と、OS内部の制御(Windowsファイアウォール)は独立したレイヤーであり、多層防御を機能させるには両方を正しく設定する必要があります。
3. **秘密情報はその場でKey Vaultへ**:ローカル管理者パスワード、`sa`パスワード、DSRMパスワード、TDE証明書など、構築作業の過程で次々と発生する秘密情報を、都度Key Vaultへ登録する習慣そのものが、現状課題④(共有アカウントの常態化、証跡管理の不備)を解消する具体的な実践です。

本章で構築したサーバー環境の上に、実際の業務データ移行・アプリケーション配置を行う手順は本パックの対象範囲外とし、構築後の日常運用(パッチ適用、監視、バックアップの運用ルール)は「05-operations-monitoring.md」「06-backup-dr.md」でそれぞれ解説します。また、本章で前提とした基盤(VNet・NSG・Bastion・Key Vault)の作成手順自体は「08-construction-procedure-network.md」を参照してください。

## 理解度チェック

**Q1. なぜ`vm-ad01`(AD DS/DNSサーバー)を最初に構築するのですか。また昇格直後に必ず行うべき作業は何ですか。**
A1. `vm-web01`・`vm-ap01`・`vm-db01`・`vm-file01`はいずれも`sanrise.local`ドメインへの参加とDNS名前解決を`vm-ad01`に依存しているためです。昇格直後には、VNet(`vnet-sanrise-prod-jpe`)のDNSサーバー設定を既定のAzure提供DNSから`vm-ad01`のIPアドレス(`10.10.4.4`)に切り替える必要があります。これを忘れると、以降に作成するVMがドメインに参加できません。

**Q2. VM作成時に「受信ポートの規則」を「なし」にし、「パブリックIP」も「なし」にするのはなぜですか。**
A2. 本設計の非機能要件「VMには一切パブリックIPアドレスを付与しない」を満たすためです。管理アクセスはすべてAzure Bastion(`bas-sanrise-prod-jpe`)経由に一本化しており、VM自体がインターネットから直接到達可能な入口を持たないようにすることで、攻撃対象領域(アタックサーフェス)を最小化しています。

**Q3. NSGで通信を許可しているのに、APサーバー(8443番)やDBサーバー(1433番)への接続が失敗することがあるのはなぜですか。**
A3. NSGはAzureネットワークレベルの制御であり、VMのOS内部で動作するWindows Defenderファイアウォールとは独立した別のレイヤーだからです。既定ではOS側のファイアウォールが該当ポートの受信を許可していないため、NSGとOSファイアウォールの「2つの壁」を両方とも正しく開ける必要があります。

**Q4. ファイルサーバー(`vm-file01`)の共有データを、Azure VMの一時ディスク(Dドライブ)に保存してはいけないのはなぜですか。**
A4. 一時ディスクはVMの再起動・サイズ変更・再作成のタイミングでデータが消去される揮発性の領域だからです。共有データのような永続化すべきデータは、必ずOSディスクや明示的に追加したマネージドディスクなど、永続的なストレージ上に保存する必要があります。

**Q5. `vm-db01`でTDE(透過的データ暗号化)を有効化した際、証明書のバックアップをKey Vaultに保管しなければならないのはなぜですか。**
A5. TDEを有効化したデータベースは、暗号化に使用した証明書がなければバックアップからのリストアが一切できなくなるためです。証明書を紛失すると、Recovery Services Vaultにバックアップデータ自体は残っていても、暗号化を解除できずデータが永久に読み出せなくなる致命的な事態を招くため、証明書のバックアップとKey Vaultへの登録は必須の手順です。
