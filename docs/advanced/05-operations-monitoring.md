# 運用監視設計書

## この章のポイント

- 受発注・在庫管理システムの監視基盤として、**Log Analyticsワークスペース**(`log-sanrise-prod-jpe`)を中心に据え、**Azure Monitor**・アラートルール・**Action Group**(通知先設定)がどのように連携して異常を自動検知するのかを、未経験者にも分かる比喩と図を用いて解説します。
- 設計台帳(ledger)で定義された5種類のアラートルールと8項目の監視ダッシュボードの内容を一覧化し、それぞれ「何を」「どのしきい値で」「誰に」通知するのかを整理します。
- 従来の「担当者の目視確認」に依存した監視体制から、「自動検知→自動通知→人が判断・対応する」体制へ転換する設計思想を明らかにします。
- **Azure Update Manager**(Azure VMのOSパッチ適用を一元管理するサービス)を用いた月次パッチ適用の運用ルール(適用順序・メンテナンスウィンドウ・緊急パッチ対応)を定義します。
- 障害発生時に「誰が」「どの順番で」「何を基準に」対応するのかという一次対応フローと、日次/週次/月次で実施すべき定型運用作業をチェックリスト形式で示します。

## 1. 本章の位置づけと対象範囲

本章「運用監視設計書」は、Azure移行後に本番稼働する受発注・在庫管理システムを、**日々どのように見張り(監視)、どのように保守し(パッチ適用)、何か起きたときにどう動くか(障害対応)**を定義する章です。具体的には次の3本柱で構成します。

1. **監視設計**:Azure Monitor・Log Analytics・アラートルール・ダッシュボードによる自動検知の仕組み(2章・3章)
2. **パッチ適用方針**:Azure Update Managerを用いた計画的なOSパッチ適用の運用ルール(4章)
3. **日常運用ルール**:障害発生時の一次対応フローと、日次/週次/月次の定型作業チェックリスト(5章・6章)

なお、VM間通信を制御するNSG(ネットワークセキュリティグループ)ルールの詳細や暗号化方針は「04-security-design.md」に、バックアップポリシー・RPO/RTOの詳細設計やDR(災害復旧)手順は「06-backup-dr.md」に、月額コストの内訳詳細は「07-cost-design.md」にそれぞれ譲ります。本章はあくまで「稼働開始後、毎日・毎週・毎月どう運用するか」という運用者目線に範囲を絞って解説します。

現行システムが抱えていた課題のうち、本章が直接解決を目指すのは、要件定義書(00-overview-requirements.md)で整理した以下の2点です。

| 現状の課題 | 本章で対応する設計 |
|---|---|
| ⑤ サーバー監視が担当者の目視確認中心であり、CPU/ディスク逼迫や障害の予兆を早期に検知できていない | Log Analyticsによるメトリック・ログの自動収集と、5種類のアラートルールによる自動検知・自動通知体制の整備(2章・3章) |
| ②(部分) OSがWindows Server 2012 R2でメーカーサポートが終了しており、脆弱性対応ができない状態が続いている | Azure Update Managerによる計画的・継続的なパッチ適用サイクルの確立(4章) |

## 2. 監視アーキテクチャの全体像

### 2.1 「なぜ監視の仕組みが3層構造になっているのか」を健康診断に例える

Azureの監視の仕組みは、初めて学ぶ方にとっては「Azure Monitor」「Log Analytics」「アラートルール」「Action Group」と登場人物が多く、混乱しやすいポイントです。ここでは**人間の健康診断・医療の仕組み**に例えて整理します。

| 医療の例え | Azureの仕組み | 役割 |
|---|---|---|
| 体温計・血圧計などのセンサーで日々のバイタル(体温・脈拍等)を測る | **Azure Monitor**(Azure環境全体のメトリック・ログを収集・可視化・分析するための監視基盤の総称。※詳しくは用語集(11-glossary.md)を参照) | 各VMからCPU使用率・ディスク空き容量などの数値データ(メトリック)や、イベントログなどの記録データ(ログ)を収集する仕組み全体を指します |
| 測定結果を書き溜めていく電子カルテ | **Log Analyticsワークスペース**(`log-sanrise-prod-jpe`) | Azure Monitorが集めたメトリック・ログを実際に保存し、検索・分析できる形で蓄積しておくデータベースです。カルテがなければ「先週と比べて数値がどう変化したか」を振り返れないのと同様、ワークスペースがなければ過去の傾向分析や障害調査ができません |
| 「体温が38.5度を超えたら家族に電話する」という取り決め(トリアージ基準) | **アラートルール** | ワークスペースに溜まったデータ、またはAzureが直接収集するメトリックに対して、「CPU使用率が85%を10分超えたら異常」のような条件(しきい値)を定義し、条件が成立したら自動的に次のアクションを起動する設定です |
| 実際に「誰に」「どうやって」連絡するかの緊急連絡網(家族の携帯電話番号、かかりつけ医の番号など) | **Action Group**(`ag-sanrise-ops`) | アラートルールの条件が成立したときに、実際に誰へ・どの手段(メール、Teams通知、SMS等)で知らせるかをまとめた通知先の設定です |

この例えのポイントは、**「センサーで測る(Azure Monitor)」「記録を溜める(Log Analytics)」「異常を判定する(アラートルール)」「人に知らせる(Action Group)」という4つの役割が、それぞれ別のパーツとして分かれている**ことです。従来のサンライズ物産の監視(担当者の目視確認)は、この4つすべてを「人間」が担っていた状態に相当します。Azure移行後は、この一連の流れを自動化することで、担当者が常時画面を見張っていなくても異常を検知できる体制に転換します。

### 2.2 データの流れ(概念図)

上記4つの役割が実際にどうつながっているかを、CPU使用率のアラート(`alert-vm-high-cpu`)を例に図示します。

```mermaid
flowchart LR
    VM["各VM<br/>vm-ad01 / vm-web01 / vm-ap01<br/>vm-db01 / vm-file01"] -->|Azure Monitorエージェントによる収集| LA[("Log Analytics<br/>ワークスペース<br/>log-sanrise-prod-jpe")]
    LA --> RULE["アラートルール<br/>(しきい値判定)<br/>alert-vm-high-cpu"]
    RULE -->|条件成立(CPU 85%超が10分継続)| AG["Action Group<br/>ag-sanrise-ops"]
    AG --> MAIL["運用担当者へ<br/>メール通知"]
    AG --> TEAMS["Teamsチャネルへ<br/>通知"]
```

他の4種類のアラートについても仕組みは同じで、条件(しきい値)と通知先(Action Groupの中身)が異なるだけです。たとえば`alert-vm-unavailable`ではAction Groupの通知先設定として「オンコール担当者へのSMS」が追加され、`alert-disk-low-freespace`では「ITSMツールへの自動チケット起票」が組み合わされます(詳細は3章)。**「収集」「蓄積」「判定」「通知」を分離した部品として組み合わせる**ことで、通知先や条件を後から柔軟に追加・変更できる点が、Azure Monitorのアーキテクチャの優れた点です。

### 2.3 「プラットフォームメトリック」と「ログ・カウンターデータ」の違い(実務上のつまずきポイント)

Azure Monitorには、収集経路が異なる2種類のデータがあり、この違いを理解していないと「なぜこのアラートだけ設定が面倒なのか」で混乱しがちです。

| 種類 | 具体例(本設計での該当アラート) | 収集の仕組み |
|---|---|---|
| プラットフォームメトリック | `Percentage CPU`(CPU使用率、`alert-vm-high-cpu`が参照) | Azure基盤(ホスト)側が自動的に収集する数値データ。VM内にエージェント(常駐ソフト)を入れなくても取得でき、収集自体は追加コストなしで利用可能です |
| ゲストOSレベルのカウンター・ログ | `Logical Disk % Free Space`(ディスク空き容量、`alert-disk-low-freespace`が参照)、Heartbeat(生存確認信号、`alert-vm-unavailable`が参照) | VM内部のOSが持つ情報のため、Azure基盤側からは直接見えません。**Azure Monitor エージェント(AMA:VM内にインストールする収集エージェント)**を各VMに導入し、「何を」「どのくらいの間隔で」収集するかを定義する**データ収集ルール(DCR:Data Collection Rule)**を設定したうえで、収集したデータをLog Analyticsワークスペースへ送信する必要があります |

本設計の5種類のアラートのうち、ディスク空き容量・VM死活監視(Heartbeat)・SQL Server関連のアラートはいずれも後者(エージェント経由)に該当するため、**全VMにAzure Monitor エージェントを導入し、Log Analyticsワークスペース(`log-sanrise-prod-jpe`)へデータを送信する設定を行うことが本設計の前提**になります。エージェントを入れずにプラットフォームメトリックだけで済ませる構成も可能ですが、それでは「ディスクが逼迫している」「VMの応答がない」といった、今回の現状課題(目視確認でしか気づけなかった予兆)に直結する情報が取得できません。**あえてエージェント導入というひと手間をかけてでもLog Analyticsワークスペースを中心に据えている**のは、この予兆検知こそが本プロジェクトの非機能要件(CPU使用率・ディスク空き容量・VM可用性の異常自動検知)の核心だからです。

なお、各VMのサブネット(NSG:ネットワークセキュリティグループ)は、Log Analyticsワークスペースへの送信(アウトバウンドHTTPS 443番)を明示的に拒否するルールを設けていません。このため、Azureが既定で用意している送信規則(インターネット方向への既定許可)を通じて到達する構成としています。将来的な拡張として、Azure Monitor Private Link Scope(プライベートエンドポイント経由でインターネットを経由せずにログを送信する仕組み)を導入し、送信経路をより閉域化することも考えられますが、本フェーズでは監視構成のシンプルさとコスト抑制を優先し、既定の送信経路を採用しています。

## 3. 監視設計の詳細

### 3.1 アラートルール一覧

設計台帳(ledger)で定義されたアラートルールは以下の5種類です。いずれも通知先はAction Group「`ag-sanrise-ops`」を基本としつつ、アラートの性質に応じて通知手段(メール/Teams/SMS/ITSMチケット)を使い分けています。

| アラート名 | 検知条件 | 通知アクション | 対象VM |
|---|---|---|---|
| `alert-vm-high-cpu` | 各VM(vm-ad01, vm-web01, vm-ap01, vm-db01, vm-file01)のCPU使用率(Percentage CPU)が5分平均で85%を超過した状態が10分以上継続 | Action Group「ag-sanrise-ops」経由でインフラ運用担当者へメール通知およびTeamsチャネルへ通知 | 全5台 |
| `alert-disk-low-freespace` | OSディスクまたはデータディスクの空き容量が10%未満(Logical Disk % Free Space) | 運用担当者へメール通知し、ITSM(IT Service Management、社内のIT運用管理)ツールへ自動でチケットを起票 | 全5台 |
| `alert-vm-unavailable` | Log AnalyticsのHeartbeatメトリックが5分間欠落し、VMの応答が確認できない状態を検知 | オンコール担当者へSMS/メールで即時通知し、重大度Sev1としてエスカレーション | 全5台 |
| `alert-backup-job-failure` | Recovery Services Vault(rsv-sanrise-prod-jpe)のバックアップジョブがFailedステータスで完了 | バックアップ管理者へメール通知し、翌営業日の朝会で原因確認を実施 | 全5台(バックアップ対象VM) |
| `alert-sql-high-dtu-or-storage` | vm-db01のSQL Serverプロセスにおけるディスク書き込みレイテンシまたはtempdb格納ディスクの空き容量が閾値(空き容量15%未満)を下回った状態を検知 | DBA担当者へメール通知し、必要に応じてディスク拡張または不要データのアーカイブを実施 | vm-db01のみ |

**なぜこの5種類なのか(設計思想)**:5種類のアラートは、現状課題として挙げられた「CPU/ディスク逼迫や障害の予兆を早期に検知できていない」という課題に直接対応するよう選定しています。特に以下の観点を押さえています。

- **予兆(壊れる前)と障害(壊れた後)の両方をカバーする**:`alert-vm-high-cpu`と`alert-disk-low-freespace`は「まだ動いているが危険な兆候」を検知する予兆系のアラートであり、`alert-vm-unavailable`は「すでに応答がない」という障害発生後の検知です。予兆の段階で気づければ、計画的な対処(ディスク拡張、負荷分散の検討等)で障害そのものを未然に防げます。
- **業務上最も重要なDB層には専用のアラートを追加する**:全VM共通の3種類に加えて、`alert-sql-high-dtu-or-storage`はvm-db01だけを対象にした専用ルールです。受発注・在庫データを保持する唯一のサーバーであるため、他のVMより一段階細かい粒度(I/Oレイテンシ、tempdb使用率)で監視しています。
- **バックアップの失敗そのものを監視対象にする**:`alert-backup-job-failure`は、旧環境で最大の課題だった「リストア検証が未実施でバックアップの実効性が担保されていない」という反省を踏まえたものです。バックアップが取得できていることを日々確認するのではなく、**失敗したときに自動で気づける仕組み**にすることで、いざという時に「実はずっとバックアップが失敗し続けていた」という事態を防ぎます。
- **重大度に応じて通知手段を変える**:全社的な影響が大きい`alert-vm-unavailable`だけがSMSでの即時通知・Sev1(重大度1)エスカレーションという、他より強い通知手段を割り当てています。逆に`alert-backup-job-failure`は即時性より翌営業日の朝会での確認という猶予を持たせた運用にしており、**すべてのアラートを同じ強さで鳴らさない**ことで、真に緊急性の高い通知が埋もれてしまう「アラート疲れ」を防いでいます。

### 3.2 監視ダッシュボード

日常の運用状況を一目で把握できるよう、以下の8項目をダッシュボードとして可視化します。

| No. | ダッシュボード項目 | 目的・見る観点 |
|---|---|---|
| 1 | 各VMのCPU使用率・メモリ使用率の時系列グラフ | 5台のVMの負荷傾向を横並びで確認し、特定のVMだけ負荷が偏っていないかを把握する |
| 2 | 各VMのディスク空き容量(OS/データディスク別) | アラートが発報する前の段階で、ディスク容量が徐々に逼迫していないかのトレンドを確認する |
| 3 | Log Analytics Heartbeatによる全VMの稼働状況(可用性)一覧 | 5台すべてが正常に生存確認信号を送信できているかを一覧で確認する |
| 4 | Azure Bastionの接続ログ(接続元アカウント・接続先VM・接続時刻) | 誰が・いつ・どのVMに管理アクセスしたかを可視化し、意図しないアカウントや深夜帯のアクセスがないかを確認する |
| 5 | NSGフローログのサマリ(拒否された通信の件数推移) | 想定外の通信(攻撃の試行や設定ミスによる不要な通信)が増えていないかを把握する |
| 6 | Recovery Services Vaultのバックアップジョブ成功率・直近失敗ジョブ一覧 | バックアップが確実に取得できているかを日次で確認する |
| 7 | Microsoft Defender for Cloudのセキュリティスコアおよび推奨事項件数 | セキュリティ設定の不備や未対応の脆弱性が増えていないかを継続的に確認する |
| 8 | vm-db01のSQL Serverディスク待機時間(I/Oレイテンシ)およびtempdb使用率 | 業務システム全体のボトルネックになりやすいDB層の性能状態を重点的に確認する |

このダッシュボードは、5章で定義する日次/週次/月次の定型運用チェックリストにおいて、**「まずこの画面を開けば当日確認すべき事項が一通り揃っている」状態を作る**ことを狙いとしています。項目4・5・7はセキュリティ関連の可視化であり、詳細な設計思想は「04-security-design.md」で扱いますが、本設計では**性能監視とセキュリティ監視を同じダッシュボード・同じLog Analyticsワークスペースに統合**しています。これは、運用担当者が複数の画面を行き来する手間を省き、日常点検の負荷を下げるための工夫です。

### 3.3 Log Analyticsワークスペースの保持期間とコストの考え方

Log Analyticsワークスペース(`log-sanrise-prod-jpe`)は、既定の保持期間(30日間)を採用し、それを超えるデータは自動的に削除される設定とします。これは、コスト設計(07-cost-design.md)で見積もっているLog Analyticsの月額費用(従量課金、Pay-As-You-Goプラン想定)を、データ量に応じて無制限に増加させないための方針です。障害調査や傾向分析で30日を超える長期データが必要になった場合は、Azure Storageアカウントへのエクスポート機能等を用いて、必要なデータのみ低コストな場所へ長期保管する拡張を将来検討します。

## 4. パッチ適用方針(Azure Update Manager)

### 4.1 Azure Update Managerとは

**Azure Update Manager**は、Azure VM(および対応するオンプレミスサーバー)に対するOSパッチ(セキュリティ更新プログラム)の適用状況を一元的に可視化し、スケジュールに沿った自動適用を行えるAzureの組み込みサービスです。従来のAutomation Update Management(旧称)と異なり、専用のAutomationアカウントを別途構築する必要がなく、対象VMに拡張機能を有効化するだけで利用を開始できる点が特徴です。

本設計でAzure Update Managerを採用する最大の理由は、現状課題の②「OSがWindows Server 2012 R2でメーカーサポートが終了しており、脆弱性対応ができない状態が続いている」を、Azure移行後に**二度と繰り返さない仕組み**にすることです。旧環境ではパッチ適用そのものが属人的な手順で行われ、いつしか対応が止まってしまいました。Azure Update Managerを使えば、パッチ適用状況(準拠しているか、未適用の更新が何件あるか)がAzureポータル上で常に可視化されるため、「気づいたら何年も放置していた」という事態を構造的に防げます。

### 4.2 パッチ適用のスケジュール設計

Azure Update Managerでは、パッチを適用する対象VM・タイミング・再起動方法などを**メンテナンス構成(Maintenance Configuration)**というリソースにまとめて定義します。本設計では、以下のメンテナンス構成を定義します。

| 項目 | 内容 |
|---|---|
| メンテナンス構成名 | `mc-sanrise-patch-prod-jpe`(CAFの略語規則に沿い、メンテナンス構成を表す`mc-`を使用) |
| 対象VM | vm-ad01, vm-web01, vm-ap01, vm-db01, vm-file01(全5台) |
| 適用スケジュール | 毎月**第3土曜日 01:00〜05:00(JST)**(Microsoft社の月例パッチ公開日、いわゆる「Patch Tuesday」の翌週末を基準に設定) |
| パッチ分類 | セキュリティ更新プログラム(Critical/Important)および重要な更新プログラムを対象。任意の機能更新プログラムは対象外 |
| 再起動設定 | 必要な場合のみ再起動(IfRequired) |
| ウィンドウの上限時間 | 4時間(超過した場合は次回サイクルへ持ち越し、無理に当日中の完了を優先しない) |

**なぜ土曜早朝の時間帯にしたのか**:受発注・在庫管理システムは社内イントラネット経由の平日日中利用が中心であり、休日夜間から早朝にかけては業務アクセスがほぼ発生しません。またMicrosoft社の月例更新プログラムは米国時間の第2火曜日(日本時間では水曜未明)に公開されるため、社内での検証・計画に数日の余裕を持たせたうえで、直近の土曜日に適用することで、万が一のトラブル発生時にも週明けの業務開始までに切り戻し・対処の時間を確保できるようにしています。

### 4.3 適用順序(段階的ロールアウト)によるリスク低減

本設計では、5台のVMに同時にパッチを適用するのではなく、**影響範囲の小さいサーバーから段階的に適用する順序**を定義します。

| 順序 | 対象VM | 適用理由 |
|---|---|---|
| 1 | vm-file01(ファイルサーバー) | 業務システムの中核ではなく、単一VMの一時的な再起動が発生しても受発注業務そのものへの影響が最も小さいため、**パイロット(お試し)適用**の位置づけとする。ここで不具合が出れば他のVMへの適用を一時停止して原因を確認する |
| 2 | vm-ad01(AD DS/DNS) | vm-file01でのパイロット結果に問題がないことを確認したうえで、他の全VMが依存する認証・名前解決の基盤を優先的に最新化する。基盤層に問題があると後続のWeb/AP/DB層の検証自体が正しく行えないため、早い段階で確定させる |
| 3 | vm-web01 → vm-ap01 | Web層・AP層の順に適用する。3層構成の通信フロー(Web→AP→DB)に沿って、下流(AP)より上流(Web)を先に確認する形とし、各層の再起動後は簡易な疎通確認(画面表示・API応答)を行ってから次へ進める |
| 4 | vm-db01(DBサーバー) | 業務データを保持する最重要サーバーであるため、**最後に、かつ最も慎重に**適用する。適用前にAzure Backup(Recovery Services Vault)によるオンデマンドバックアップを追加取得し、万が一パッチ適用後にSQL Serverが正常起動しない場合でも、直前の状態へ復旧できる安全網を用意したうえで適用する |

この段階的な適用順序は、「1台のVMだけを見て良し悪しを判断せず、影響範囲の小さいものから確認しながら進める」という考え方に基づいています。旧環境では手動かつ一括でのパッチ適用(あるいは適用そのものの停止)しか選択肢がありませんでしたが、Azure Update Managerのメンテナンス構成を役割ごとに分けて組む、あるいは同一構成内でも適用順序をあらかじめ運用ルールとして明文化しておくことで、**「パッチを当てたら業務システム全体が同時に止まる」リスクを避ける**設計としています。

### 4.4 緊急パッチ(ゼロデイ脆弱性等)への対応方針

月例の定期パッチとは別に、深刻度の高い脆弱性(内容が公開・悪用され始めている、いわゆるゼロデイ脆弱性や、CVSS基本値が9.0以上の緊急度の高いCVE)が公表された場合は、月次サイクルを待たずに**緊急パッチ**として対応します。

- **検知経路**:Microsoft Defender for Cloud(脆弱性評価機能)の推奨事項、またはMicrosoft社のセキュリティ情報(MSRC)を通じて検知します。
- **対応期限**:検知から**72時間以内**に、Azure Update Managerの「今すぐの更新プログラムのインストール」機能を用いてオンデマンドで適用します。定期サイクルのような段階的ロールアウトの猶予は取らず、パイロット確認とAD層確認は簡略化(疎通確認のみ)したうえで、全VMへ速やかに展開します。
- **事後対応**:適用結果と対応時間を記録し、翌月の月次レビュー(6.3節)で振り返りを行います。

### 4.5 パッチ適用状況と監視の連携

Azure Update Managerが評価するパッチ準拠状況(何件のセキュリティ更新プログラムが未適用か)は、Microsoft Defender for Cloudの推奨事項にも反映されます。3.2節のダッシュボード項目7(Defender for Cloudのセキュリティスコアおよび推奨事項件数)を確認することで、**「パッチが計画通り適用され、脆弱性が放置されていないか」を監視ダッシュボード上からも継続的に確認できる**構成としています。これにより、パッチ適用(4章)と監視(2章・3章)という2つの柱が、Defender for Cloudというひとつの可視化画面を介して連動する設計になっています。

## 5. 障害発生時の一次対応フロー

### 5.1 検知の入り口

障害の検知経路は、大きく分けて2種類あります。

1. **アラートによる自動検知**:3章で定義したアラートルールがAction Group(ag-sanrise-ops)を通じて自動的に通知するケース
2. **利用者からの問い合わせ**:社内イントラネット(172.16.0.0/16)を利用する社員から「受発注画面が開けない」等の連絡がヘルプデスクや情報システム部門に直接入るケース

どちらの入り口であっても、対応する運用担当者はまず監視ダッシュボード(3.2節)とLog Analyticsワークスペースを確認し、**「感覚」ではなくデータに基づいて状況を把握する**ことを一次対応の原則とします。これは、旧環境の「担当者の目視確認」に依存した属人的な対応から脱却するための重要な考え方です。

### 5.2 重大度(Severity)の分類

障害の影響度に応じて、以下の3段階の重大度(Severity、略してSev)を定義し、対応の緊急性を判断します。

| 重大度 | 定義 | 該当する典型例 | 初動対応の目標時間 |
|---|---|---|---|
| Sev1(重大) | 業務システム全体または特定サーバーが停止し、全社的に業務が継続できない状態 | `alert-vm-unavailable`の発報(VM応答なし)、DBサーバー停止、Web画面への全社アクセス不可 | 検知から15分以内にオンコール担当者が着手 |
| Sev2(中度) | 一部機能が低下しているが、業務は継続可能な状態 | `alert-vm-high-cpu`や`alert-sql-high-dtu-or-storage`など、性能劣化の兆候を示すアラート | 営業時間内であれば1時間以内、営業時間外は翌営業日の始業直後までに着手 |
| Sev3(軽微) | 業務への直接的な影響がない、または単発的な事象 | `alert-backup-job-failure`が単発で発生(継続的な失敗ではない)、ディスク空き容量アラートが発報したが緊急性は低いケース | 翌営業日以降に計画的に対応(朝会等での確認) |

### 5.3 一次対応〜エスカレーションのフロー

```mermaid
flowchart TD
    A["アラート発報 または 利用者からの問い合わせ"] --> B["ダッシュボード / Log Analyticsで状況確認"]
    B --> C["影響範囲・再現性の切り分け"]
    C --> D{"重大度(Sev1〜Sev3)を判定"}
    D -->|Sev1: 全社影響・VM停止| E["オンコール担当へ即時招集(15分以内)"]
    D -->|Sev2: 一部機能に影響| F["営業時間内に一次対応者が対応(1時間以内)"]
    D -->|Sev3: 軽微・影響なし| G["翌営業日以降に計画的に対応"]
    E --> H["暫定対処を実施(VM再起動・ネットワーク切り離し等)"]
    F --> H
    H --> I{"暫定対処で復旧したか"}
    I -->|復旧した| J["事後報告・恒久対策の検討"]
    I -->|未復旧(30分超)| K["二次対応へエスカレーション<br/>(保守ベンダー/情報システム部門責任者)"]
    K --> L["原因調査・本格的な復旧作業を実施"]
    L --> J
    G --> J
```

### 5.4 エスカレーション体制

| 段階 | 対応者 | 主な役割 | エスカレーション条件 |
|---|---|---|---|
| 一次対応 | インフラ運用担当者(当番制のオンコール担当を含む) | ダッシュボードでの状況確認、影響範囲の切り分け、再起動等の暫定対処 | 30分以内に自力で復旧できない、または原因が特定できない場合に二次対応へ引き継ぐ |
| 二次対応 | 保守ベンダー(構築・保守を担当するSIer等)、または情報システム部門の上位責任者 | より深い原因調査、ベンダーサポート(Microsoftサポート等)への問い合わせ、恒久対策の立案 | Sev1で長時間(目安2時間以上)復旧しない場合、経営層・業務部門への状況共有が必要と判断される場合 |
| 経営層・業務部門への共有 | 情報システム部門長 | 業務影響の大きい障害について、経営層・関係部門(受発注業務の現場責任者等)へ状況と見込みを報告 | Sev1が長時間化し、業務停止が顧客対応(取引先スーパーマーケット・ドラッグストア等)にまで影響し得る場合 |

**なぜ「30分」「2時間」という目安時間を明文化するのか**:旧環境では管理が属人化しており、障害対応が誰の判断で、どのタイミングでエスカレーションされるかが曖昧でした。目安時間をあらかじめ明文化しておくことで、担当者個人の裁量に頼らず、**「抱え込みすぎて対応が遅れる」事態を防ぐ**ことがねらいです。なお、Sev1(`alert-vm-unavailable`)については、RTO(Recovery Time Objective:目標復旧時間)4時間以内という非機能要件(06-backup-dr.mdで詳述)を満たす必要があるため、二次対応への引き継ぎやリストア判断(バックアップからの復旧に切り替えるか)は、この4時間という制約から逆算して早め早めに判断する運用とします。

## 7. 設計思想のまとめ(なぜこの運用監視設計にしたのか)

本章で解説してきた運用監視設計の判断は、突き詰めると次の3つの考え方に集約されます。

1. **「目視」から「自動検知」への転換**:Log Analyticsワークスペースを中心に、プラットフォームメトリックとゲストOSレベルのデータの両方を収集し、5種類のアラートルールで自動的に異常を検知する体制を構築しました。これは、現状課題「サーバー監視が担当者の目視確認中心」を構造的に解消するための設計です。
2. **「壊さない」ための計画的なパッチ適用と、「気づけなかった」を無くす仕組み化**:Azure Update Managerによる月次パッチ適用に、影響範囲の小さいサーバーから確認しながら進める段階的ロールアウトを組み合わせることで、旧環境で発生した「パッチ適用そのものが止まってしまう」問題と、「一括適用による全体障害」の両方のリスクに同時に備えています。
3. **重大度に応じたメリハリのある対応体制**:すべての異常を同じ強さで通知・対応するのではなく、Sev1〜Sev3という重大度分類と、それに応じた通知手段(SMS/メール/Teams/ITSMチケット)・対応時間の目安を明文化することで、限られた運用担当者のリソースを本当に緊急性の高い事象に集中させる設計としています。

これらの判断はいずれも、要件定義書(00-overview-requirements.md)の非機能要件「CPU使用率・ディスク空き容量・VM可用性の異常を自動検知し、運用担当者へ通知できる監視体制を整備する」を出発点としています。次章以降では、こうした日常運用を支えるバックアップ・DR体制(06-backup-dr.md)や、月額コストの詳細な内訳(07-cost-design.md)を解説します。

## 理解度チェック

**Q1. Azure Monitor・Log Analyticsワークスペース・アラートルール・Action Groupは、それぞれどのような役割を担っていますか。**
A1. Azure Monitorは各VMからメトリック・ログを収集する監視基盤全体、Log Analyticsワークスペース(log-sanrise-prod-jpe)は収集したデータを蓄積・分析するためのデータベース、アラートルールは蓄積されたデータが特定のしきい値を超えたかどうかを自動判定する仕組み、Action Group(ag-sanrise-ops)はアラート発報時に実際に誰へ・どの手段(メール、Teams、SMS等)で通知するかをまとめた通知先設定です。

**Q2. `alert-vm-unavailable`と`alert-backup-job-failure`では、通知の緊急性にどのような違いがありますか。またそれはなぜですか。**
A2. `alert-vm-unavailable`はオンコール担当者へSMS/メールで即時通知し重大度Sev1としてエスカレーションする一方、`alert-backup-job-failure`はメール通知のうえ翌営業日の朝会で原因確認するという、猶予を持たせた対応です。VMの応答停止は全社的な業務停止に直結する緊急事態であるのに対し、バックアップジョブの単発失敗は直ちに業務へ影響しないため、重大度に応じて通知の強さを意図的に変えています。

**Q3. Azure Update Managerによるパッチ適用で、なぜ5台のVMに同時ではなく段階的な順序で適用するのですか。**
A3. 一括適用すると、万が一パッチに不具合があった場合に業務システム全体が同時に影響を受けるリスクがあるためです。本設計では、影響が最も小さいvm-file01をパイロットとして最初に適用し、次に基盤であるvm-ad01、その後Web層・AP層、最後に最重要のvm-db01(適用前にオンデマンドバックアップを取得)という順序で、影響範囲の小さいものから確認しながら進めることでリスクを低減しています。

**Q4. 障害発生時の重大度(Severity)はどのように分類されていますか。Sev1に該当する典型例を1つ挙げてください。**
A4. Sev1(重大、業務全体が停止)・Sev2(中度、一部機能に影響)・Sev3(軽微、業務への直接影響なし)の3段階に分類されています。Sev1の典型例は、`alert-vm-unavailable`が発報するようなVM応答なし(死活監視の異常)や、DBサーバーの停止による全社的な業務停止です。

**Q5. 本設計でLog Analyticsワークスペースの保持期間を既定の30日間としているのはなぜですか。**
A5. 収集するデータ量が多いほどLog Analyticsの従量課金コストが増加するため、月額運用コストを抑制する制約条件と両立させるためです。30日を超える長期データが必要な場合は、Azure Storageへのエクスポート等による低コストな長期保管を将来の拡張として検討する方針です。
