# サーバー設計書

## この章のポイント

- 受発注・在庫管理システムを構成する5台の仮想マシン(VM:Virtual Machineの略。物理サーバーの上でソフトウェア的に再現された仮想的なコンピューター。※詳しくは用語集(11-glossary.md)を参照)について、役割・OS・VMサイズ・配置サブネット・IPアドレス・ディスク構成を設計台帳の値に基づき一覧化します。
- AD DS/DNS、IIS Webサーバー、APサーバー、SQL Server DBサーバー、ファイルサーバーという5つの役割を、未経験者にも分かるように1つずつ解説します。
- Azure VMのサイズ体系(vCPU・メモリ・シリーズ)と、本プロジェクトで採用したBシリーズ(バースト可能インスタンス)の仕組みを解説し、「なぜこのVMサイズを選んだのか」という判断根拠を示します。
- マネージドディスク(Azureが管理するVM用のディスクリソース)の種類(Standard SSD/Premium SSD等)の違いと、DBサーバーでディスクを分離した設計理由を説明します。
- 可用性セット・可用性ゾーンという可用性向上の仕組みを紹介したうえで、本設計ではあえて採用しなかった理由と、将来の拡張案を整理します。

## 1. 本章の位置づけと対象範囲

本章「サーバー設計書」は、全体アーキテクチャ設計書(01-architecture.md)で示したシステム全体構成のうち、**個々の仮想マシン(VM)の設計**にフォーカスした章です。具体的には、次の4つの観点を扱います。

1. 各VMがどのような役割(AD DS/DNS、Web、AP、DB、ファイルサーバー)を担うか
2. 各VMにどのOS・VMサイズ(コンピューティング性能)を割り当てるか、その根拠
3. 各VMにどのようなディスク(記憶領域)を割り当てるか、その根拠
4. VMの可用性(壊れにくさ・止まりにくさ)をどう考えるか

なお、VM間の通信を制御するネットワーク構成(VNet・サブネット・NSGルール)の詳細は「02-network-design.md」「04-security-design.md」に、監視・アラートやWindows Updateなど日常のOS運用ルールの詳細設計は「05-operations-monitoring.md」に、バックアップ・災害復旧(DR)の詳細設計は「06-backup-dr.md」にそれぞれ譲ります。本章はあくまで「サーバーというモノ(VM)自体の設計」に範囲を絞って解説します。

## 3. 各サーバーの役割解説

ここでは、上記5台のVMがそれぞれ何をしているサーバーなのかを、未経験者の方にも分かるように1台ずつ解説します。

### 3.1 vm-ad01(AD DS/DNSサーバー)

**AD DS(Active Directory Domain Services)とは**、Windows環境において「誰が」「どのコンピューターを使って」「何にアクセスできるか」を一元管理するディレクトリサービス(組織内のユーザー・コンピューター・権限などの情報をデータベースとして管理する仕組み)です。企業内のPCやサーバーが1つの「ドメイン」に参加することで、社員は1つのアカウントで複数のシステムにログインでき、管理者はアカウントや権限を一括管理できます。**DNS(Domain Name System)**は、`vm-web01`のようなコンピューター名やドメイン名を、実際の通信に使うIPアドレス(例:10.10.1.4)に変換する「名前解決」の仕組みです。AD DSとDNSは実務上セットで運用されることが多く、本設計でも1台のVMに両方の役割を集約しています。

本設計のvm-ad01は、既存のオンプレミスADドメイン`sanrise.local`の**レプリカドメインコントローラ**(既存ドメインの複製を持つ追加のドメインコントローラ)としてAzure上に構築します。これにより、Azure上のvm-web01・vm-ap01・vm-db01・vm-file01も、オンプレミスと同じ`sanrise.local`ドメインの一員として認証・名前解決を受けられます。本フェーズではAzure内で完結する構成としていますが、将来的にはこのVMに**Entra Connect**(オンプレミスAD DSとMicrosoft Entra IDのアカウント情報を同期させるツール)を同居させ、ハイブリッドID基盤(オンプレミスとクラウドの両方の認証基盤を組み合わせた仕組み)へ段階的に移行する構想です。

Web/AP/DB各層のVMは、vm-ad01に対してDNS(53番ポート)、Kerberos認証(88番ポート、Windows環境の標準的な認証プロトコル)、LDAP(389番ポート、ディレクトリ情報の問い合わせに使うプロトコル)、SMB(445番ポート、後述するファイル共有等に使うプロトコル)で通信し、名前解決とドメイン認証を行います。これらの通信ルールの詳細は「02-network-design.md」「04-security-design.md」で解説します。

### 3.2 vm-web01(Webサーバー、IIS)

**Webサーバー**とは、ブラウザ(Webページを表示するソフトウェア)からのリクエストを受け取り、画面(HTMLページ)を返す役割を持つサーバーです。本設計では**IIS(Internet Information Services、Windows Server標準のWebサーバー機能)**のバージョン10.0上で、既存の受発注・在庫管理システムのフロントエンド(利用者が実際に操作する画面部分)を稼働させます。

社内の各拠点(大阪本社・東京支店・福岡支店)の社員は、社内イントラネット(172.16.0.0/16)からHTTPS(443番ポート、暗号化されたWeb通信のプロトコル)でこのvm-web01にアクセスし、受発注・在庫管理システムの画面を利用します。vm-web01自体にはパブリックIPアドレスを付与しないため、インターネットから直接この画面にアクセスすることはできません。あくまで社内利用者専用の画面という位置づけです。画面上で入力された操作(受注登録、在庫照会など)は、vm-web01からvm-ap01へAPI呼び出し(8443番ポート)という形で引き継がれ、実際の業務ロジックの処理はAP層に委ねられます。

3層構成において、Webサーバーの役割を「画面表示に専念させ、業務ロジックやデータベースへの直接アクセスを持たせない」ことは、後述する多層防御の考え方の土台になっています。万が一Web層が外部から侵害されても、業務ロジック(AP層)やデータ(DB層)へ直接被害が及ばない構造にする狙いです。

### 3.3 vm-ap01(APサーバー)

**APサーバー(アプリケーションサーバー)**とは、業務上の処理ロジック(受注登録時の在庫引き当て計算、与信チェック、伝票番号の採番など)を実行するサーバーです。本設計では、.NET Framework(マイクロソフト製のアプリケーション開発・実行基盤)で作られた既存の業務アプリケーションを、そのままvm-ap01上で稼働させます。

vm-ap01は、Web層(vm-web01)からのAPI呼び出しを8443番ポートで受け付け、必要な業務ロジックを処理したうえで、DB層(vm-db01)へSQL接続(1433番ポート、SQL Serverの既定の通信ポート)を行い、受発注・在庫データの読み書きを行います。Web層とDB層の間に必ずAP層を挟む構成にすることで、「画面(Web)がデータベース(DB)に直接触れられない」という制御を実現しています。これは、画面側の不具合や侵害が直接データ破壊につながらないようにするための設計上の工夫です。

### 3.4 vm-db01(DBサーバー、SQL Server 2022)

**DBサーバー(データベースサーバー)**とは、業務データ(受注データ、在庫データ、取引先マスタなど)を保存・管理する役割を持つサーバーです。本設計では、Windows Server 2022 Datacenter上に**SQL Server 2022 Standard Edition**(マイクロソフト製のリレーショナルデータベース管理システム。※詳しくは用語集を参照)を搭載し、受発注・在庫管理システムの全データを一元管理します。

vm-db01は、業務上唯一データを保持する重要なサーバーであるため、次のようなセキュリティ・堅牢性の工夫を施しています。

- **通信の限定**:APサーバー(vm-ap01)からの1433番ポート接続のみを許可し、Web層や他の層からの直接接続は一切許可しません。
- **TDE(透過的データ暗号化、Transparent Data Encryption)の有効化**:データベースファイル自体をディスク上で暗号化する機能です。万が一ディスクの中身が第三者の手に渡っても、暗号化キーがなければデータを読み取れません。暗号化に使う証明書はAzure Key Vault(kv-sanrise-prod-jpe)にバックアップし、証明書の紛失によって暗号化データそのものが復元不能になる事態を防いでいます。
- **ディスクの分離**:OS用ディスクとは別に、データ/ログ/tempdb(SQL Serverが並べ替えや一時計算などに使う作業用の一時データベース)用のディスクをPremium SSD(高性能なマネージドディスク)として分離しています。詳細は5章で解説します。

DBサーバーは業務システム全体のボトルネック(処理速度の律速要因)になりやすいため、VMサイズも他のサーバーより余裕を持たせた`Standard_B4ms`を採用しています(4章で詳述)。

### 3.5 vm-file01(ファイルサーバー)

**ファイルサーバー**とは、複数の利用者が共有して使うファイル(文書、表計算シート、PDFなど)を格納し、ネットワーク経由でアクセスできるようにするサーバーです。本設計のvm-file01は、見積書・納品書等の帳票データや、部門をまたいで共有する各種業務データを、**SMB共有**(Server Message Block。Windows標準のファイル共有プロトコルで、Windowsのエクスプローラーから「ネットワークドライブ」として利用できる仕組み)により提供します。

株式会社サンライズ物産は大阪本社・東京支店・福岡支店の複数拠点を持つ企業ですが、本設計では単一拠点(Azure上の1台のVM)にファイルサーバー機能を集約する構成としており、複数拠点のファイルサーバーを1つの名前空間に見せる**DFS(Distributed File System)**は採用していません。これは、複数拠点にまたがるファイル同期・レプリケーションの仕組みを持ち込むと構成・運用が複雑化し、本プロジェクトの「コスト・運用負荷を抑制する」という方針に反するためです。各拠点からは、Azure ExpressRouteやVPN等のオンプレミス接続(本ポートフォリオの対象範囲外)を経由してこの1台のファイルサーバーへアクセスする想定とし、まずはシンプルな一元管理構成でリスクとコストのバランスを取っています。vm-file01も他のVMと同様、Recovery Services Vault(rsv-sanrise-prod-jpe)による自動バックアップの対象です。

## 4. VMサイズの選定

### 4.1 Azure VMサイズ体系の基礎

Azureの仮想マシンには、あらかじめ性能(vCPU数・メモリ量など)が定義された「VMサイズ」という規格が多数用意されており、利用者はその中から用途に合ったものを選びます。VMサイズの名前は「`Standard_<シリーズ記号><数字><接尾辞>`」という形式になっており、たとえば`Standard_B2ms`であれば「Bシリーズ・2の数字・msという接尾辞」を意味します。

VMサイズを選ぶうえでまず理解すべき基本要素は、以下の3つです。

| 要素 | 説明 |
|---|---|
| vCPU(仮想CPU) | VMに割り当てられる処理能力の単位。物理CPUのコアを仮想化して割り当てたもので、数が多いほど同時に処理できる量が増えます。 |
| メモリ(RAM) | VMが一時的にデータを保持しながら処理を行うための作業領域の容量。アプリケーションやOSが同時に扱えるデータ量に直結します。 |
| シリーズ | 用途特性ごとに分類されたVMのグループ。バースト可能インスタンス(Bシリーズ)、汎用(Dシリーズ等)、メモリ最適化(Eシリーズ等)、ストレージ最適化、GPU搭載など多数の系統があります。 |

VMサイズを選ぶ際は、単に「性能が高いものを選ぶ」のではなく、「そのサーバーがどのような負荷パターンで使われるか」を見極め、コストとのバランスを取ることが実務上重要です。

### 4.2 バースト可能インスタンス(Bシリーズ)の仕組み

本プロジェクトでは、制約条件「ポートフォリオとしての検証用途のため、月額運用コストを抑制する目的でVMサイズはBシリーズを基本とする」に基づき、全5台のVMサイズにBシリーズを採用しています。

**Bシリーズ(バースト可能インスタンス)**とは、普段は決められた低め・中程度の性能(ベースライン性能)で動作し、その代わりに一定のCPU使用率を下回っている間は「CPUクレジット」という利用権のようなものを貯めておき、業務が集中して負荷が上がった瞬間にそのクレジットを消費して一時的にベースラインを超える性能へ引き上げられる(バーストする)、という仕組みのVMシリーズです。常時100%近い高負荷が続く用途には不向きですが、「普段は余裕があり、たまに負荷が上がる」という一般的な社内業務システムの利用パターンとは非常に相性がよく、汎用シリーズ(Dシリーズ等)より安価に運用できます。

本設計で使用しているBシリーズ各サイズの一般的な仕様は、以下のとおりです(Microsoft社が公開しているVMサイズ仕様に基づく参考値であり、最新の正確な値は都度Microsoft Learnの公式ドキュメントをご確認ください)。

| VMサイズ | vCPU数 | メモリ | ベースラインCPU性能の目安 | 本設計での用途 |
|---|---|---|---|---|
| Standard_B2s | 2 | 4 GiB | 1 vCPUあたり約40% | vm-web01、vm-file01 |
| Standard_B2ms | 2 | 8 GiB | 1 vCPUあたり約60% | vm-ad01、vm-ap01 |
| Standard_B4ms | 4 | 16 GiB | 1 vCPUあたり約90% | vm-db01 |

「ベースラインCPU性能」とは、CPUクレジットを消費していない通常時に発揮できるCPU性能の割合です。たとえばStandard_B2sは2 vCPUに対してそれぞれ約40%のベースライン性能となり、平常時は控えめな処理能力で稼働しつつ、負荷が上がった瞬間にクレジットを使って100%近くまで性能を引き上げられます。B2ms・B4msとサイズが上がるほど、ベースライン性能そのものも高くなっていく点が特徴です。

### 4.3 本設計でのVMサイズ選定と理由

| VM名 | 役割 | VMサイズ | 選定理由 |
|---|---|---|---|
| vm-web01 | Webサーバー(画面表示のみ) | Standard_B2s | 画面表示中心の処理であり、業務ロジックやデータ処理を持たないため、CPU・メモリともに最も軽量なサイズで十分。イントラネット限定の社内アクセスであり、外部からの大量アクセスも想定しないためコスト最優先で選定。 |
| vm-ap01 | APサーバー(業務ロジック実行) | Standard_B2ms | 業務ロジックの処理はWebサーバーより負荷が高くなりやすいため、vm-web01よりメモリを2倍(8 GiB)確保できるB2msを選定。受注処理や在庫引き当て計算等でメモリを要するケースを想定。 |
| vm-db01 | DBサーバー(SQL Server) | Standard_B4ms | SQL Serverはデータのキャッシュ(バッファプール)にメモリを多く使う特性があり、CPU・メモリ要求がシステム内で最も高い。5台の中で唯一vCPU数4・メモリ16 GiBというワンランク上のサイズを選定し、業務システムとして最低限必要な性能を確保。 |
| vm-ad01 | AD DS/DNS | Standard_B2ms | ドメイン認証・名前解決は全VMからの要求を捌く基盤的な役割であり、瞬間的な認証要求の集中(始業時のログインラッシュ等)に備えて、vm-web01よりメモリに余裕のあるB2msを選定。将来のEntra Connect同居も見据えた余裕確保。 |
| vm-file01 | ファイルサーバー | Standard_B2s | ファイル共有(SMB)は読み書きの多くがディスクI/O(入出力)に依存し、CPU・メモリへの要求はWebサーバー同様に軽量であるため、最も軽量なB2sを選定。 |

このように、単純に「全部同じサイズにする」のではなく、**各サーバーが実際にどのような処理特性を持つか(CPU中心か、メモリ中心か、I/O中心か)**を踏まえてサイズを段階的に使い分けている点が、本設計における「なぜその設計にしたのか」のポイントです。

### 4.4 D/Eシリーズ等の汎用・メモリ最適化シリーズとの比較検討

Bシリーズ以外の代表的な選択肢として、以下のシリーズも比較検討しました。

| シリーズ | 特徴 | 本プロジェクトで採用しなかった理由 |
|---|---|---|
| Dシリーズ(汎用) | ベースライン性能というバースト特有の制約がなく、常に安定したCPU性能を発揮できる汎用シリーズ | 24時間365日にわたる安定した高負荷を前提とする用途ではないため、常時高性能を維持できる分のコストが本プロジェクトの目的に対して過剰(オーバースペック)であり、月額コスト抑制という制約条件に反するため見送り |
| Eシリーズ(メモリ最適化) | vCPU数に対してメモリの割当比率が特に高く、大量データのインメモリ処理やメモリを大量消費するデータベースワークロードに適したシリーズ | 本システムの受発注・在庫データの規模は中堅商社の業務システムとしては比較的小規模であり、Eシリーズが想定するような大規模データベース向けの潤沢なメモリまでは必要とせず、コスト効率で劣後するため見送り |

将来、事業拡大やデータ量の増加によってBシリーズのベースライン性能では処理が追いつかなくなった場合は、まずは同一VM内でのサイズ変更(スケールアップ)により、BシリーズからDシリーズやEシリーズへ切り替える、あるいはBシリーズ内のより上位サイズ(例:Standard_B8ms)へ変更するといった対応が考えられます。Azure VMはサイズ変更が比較的容易であるため、「まずは小さく始めて、必要になったら引き上げる」という段階的なアプローチを取りやすい点も、初期構成でBシリーズを選択した理由の1つです。

## 5. ディスク設計

### 5.1 マネージドディスクの種類と特性

Azureの仮想マシンが使用するディスク(記憶領域)は、**マネージドディスク**(Azureがディスクの配置・冗長化・管理を代行してくれる仕組み)として提供され、性能・コストの異なる複数の種類(ディスクの種類のことを「SKU」と呼びます)から選択します。代表的な種類の特性は以下のとおりです。

| ディスクの種類 | 特性 | 主な用途 |
|---|---|---|
| Standard HDD | 磁気ディスク(回転する円盤)を用いた最も安価な種類。IOPS(1秒あたりの読み書き回数)・応答速度(レイテンシ)ともに他の種類より劣る | バックアップデータの保管など、頻繁なアクセスを必要としない用途 |
| Standard SSD | フラッシュメモリ(SSD)を用いた種類で、HDDより安定した低遅延・高IOPSを実現しつつ、Premium SSDより安価 | 業務上の常時高負荷を伴わないWeb/APサーバーや、一般的な社内システムのOSディスク |
| Premium SSD | Standard SSDよりもさらに高いIOPS・高いスループット(単位時間あたりの転送量)・低い遅延を実現する高性能な種類 | データベースなど、I/O性能がシステム全体の応答速度に直結するワークロード |
| Ultra Disk | 最高クラスの性能を持ち、ディスクサイズとは切り離してIOPS・スループットを個別に細かく指定できる種類 | 非常に高いI/O性能が要求される大規模データベース等(本プロジェクトでは未使用) |

本設計では、コストと性能のバランスを踏まえ、**OSディスクや軽量なサーバーはStandard SSD、I/O性能が業務全体に直結するDBサーバーのデータ関連ディスクのみPremium SSD**という使い分けを行っています。Ultra Diskは本プロジェクトの規模・予算に対して過剰な性能であるため採用していません。

### 5.2 ディスクサイズの単位(設計台帳の「E6」「E10」の意味)

設計台帳のディスク種別欄に記載されている「Standard SSD(E6)」「Standard SSD(E10)」といった表記は、Azureのマネージドディスクにおけるサイズ区分(SKU名)を表しています。Azureのマネージドディスクは、ディスクの種類(Standard HDDなら「S」、Standard SSDなら「E」、Premium SSDなら「P」)とサイズ区分の番号を組み合わせて呼ばれ、番号が大きいほど大容量になります。本設計に関連する範囲のStandard SSDのサイズ区分は以下のとおりです。

| サイズ区分 | ディスク容量 |
|---|---|
| E1 | 4 GiB |
| E2 | 8 GiB |
| E3 | 16 GiB |
| E4 | 32 GiB |
| E6 | 64 GiB |
| E10 | 128 GiB |

すなわち、vm-web01・vm-file01に割り当てる「Standard SSD(E6)」は容量64 GiBのディスク、vm-ad01・vm-ap01に割り当てる「Standard SSD(E10)」は容量128 GiBのディスクを意味します。AD DS/DNSやAPサーバーはWebサーバー・ファイルサーバーよりもやや多くのソフトウェア(ミドルウェアや業務アプリケーション本体)を格納するため、ワンランク大きいE10を割り当てています。

### 5.3 本設計でのディスク構成

| VM名 | OSディスク | データディスク | 選定理由 |
|---|---|---|---|
| vm-ad01 | Standard SSD(E10、128 GiB) | なし | AD DS/DNSのデータベース(NTDS.dit等)はOSディスク内に収まる規模であり、追加のデータディスクは不要と判断 |
| vm-web01 | Standard SSD(E6、64 GiB) | なし | 画面表示用の静的ファイル・IISの構成ファイルのみを保持する軽量な用途のため、OSディスクのみで十分 |
| vm-ap01 | Standard SSD(E10、128 GiB) | なし | 業務アプリケーション本体と実行時の一時ファイルを保持するため、vm-web01よりやや大きいE10を選定 |
| vm-db01 | Standard SSD(OS用) | Premium SSD(データ用・ログ用・tempdb用に個別のディスクとして分離) | I/O性能がシステム全体の応答速度に直結するため、OS用と業務データ用のディスクを明確に分離(詳細は5.4節) |
| vm-file01 | Standard SSD(E6、64 GiB、共有データ用ディスクを含む) | ― | 帳票・共有データの保管が主目的であり、常時高いI/O性能までは要求しないためStandard SSDで十分と判断 |

### 5.4 DBサーバー(vm-db01)におけるディスク分離設計

vm-db01では、OSディスクとは別に、SQL Serverが使用する**データファイル**(実際の業務データを格納するファイル)、**ログファイル**(データベースへの変更履歴を記録するトランザクションログファイル)、**tempdb**(並べ替えや一時的な計算結果の保持など、SQL Serverが内部処理で一時的に使用する作業用データベース)を、それぞれ別のPremium SSDディスクとして分離しています。これはSQL Serverの構築における一般的なベストプラクティス(推奨される実践方法)であり、以下のような設計上の狙いがあります。

- **I/O競合の回避**:OS自体の読み書き(Windows Updateの適用時など)と、業務データの読み書きが同じディスク上で発生すると、互いの処理が待ち合いになり性能が不安定になります。ディスクを分離することで、OS側の入出力と業務データ側の入出力が競合しない構成にしています。
- **性能特性の違いへの対応**:データファイルへのアクセスはランダムアクセス(データベース内のあちこちを読み書きする)が中心である一方、ログファイルへの書き込みは順次書き込み(記録を追記していく)が中心という、異なるI/O特性を持ちます。ディスクを分けることで、それぞれの特性に応じた性能を確保しやすくなります。
- **tempdbの独立**:tempdbは一時的な作業領域であるため、頻繁かつ大量の書き込みが発生しがちです。専用ディスクに分離することで、tempdbの高負荷が本来の業務データ(データファイル)の性能に影響を与えないようにしています。
- **Premium SSDの採用**:これらのディスクにはStandard SSDではなくPremium SSD(低遅延・高IOPSの高性能ディスク)を採用しています。OSディスクはStandard SSDのままとし、業務システムの応答速度に直結する部分にだけ性能投資を行うことで、コストと性能のバランスを取っています。

なお、Premium SSDを利用するには、VM側もPremium Storageに対応したサイズである必要があります。本設計で採用している`Standard_B4ms`をはじめ、名前の末尾に「s」を含むBシリーズのVMサイズ(B2s、B2ms、B4msなど)はいずれもPremium Storageに対応しており、この点でも矛盾のない組み合わせとなっています。

## 6. 可用性セット・可用性ゾーンの考え方

### 6.1 可用性セットとは

**可用性セット(Availability Set)**とは、複数台のVMを、物理的な障害の影響を受けにくいように意図的に分散配置するための論理的なグループです。Azureのデータセンター内部では、VMは「フォールトドメイン」(電源やネットワークスイッチなどのハードウェアを共有するグループ)と「アップデートドメイン」(Azure基盤側のメンテナンス(再起動を伴う更新作業)が同じタイミングで行われるグループ)という単位に分かれています。可用性セットを組んだ複数のVMは、これらのドメインが分散するように自動的に配置されるため、1つの物理ラックの電源障害や、Azure側のメンテナンスが原因で複数VMが同時に停止する事態を避けやすくなります。ただし、可用性セットの効果が発揮されるのは「同じ役割を持つVMが2台以上ある場合」に限られ、1台だけのVMに可用性セットを設定しても冗長化のメリットはありません。

### 6.2 可用性ゾーンとは

**可用性ゾーン(Availability Zone)**とは、Azureのリージョン内に用意された、電源・冷却・ネットワークが物理的に独立した複数のデータセンター群です。Japan East(japaneast)リージョンは複数の可用性ゾーンを提供しており、異なるゾーンに複数台のVMを分散配置することで、1つのデータセンター施設全体が停止するような大規模障害が発生しても、他のゾーンのVMでサービスを継続できます。可用性セットが「同じデータセンター内でのラック単位の分散」であるのに対し、可用性ゾーンは「データセンター施設そのものを分散させる」より大きな粒度の冗長化と言えます。一般的に、可用性セットのみの構成は99.95%、複数の可用性ゾーンにまたがる構成は99.99%といった、より高いSLA(Service Level Agreement、Azureが保証する稼働率の目標値)が案内されています。

### 6.3 本設計での位置づけ

本設計では、可用性セット・可用性ゾーンのいずれも**採用していません**。理由は以下のとおりです。

- **各役割が1台構成であること**:6.1節で述べたとおり、可用性セットや可用性ゾーンによる冗長化は、同じ役割のVMが複数台存在して初めて効果を発揮します。本設計ではvm-web01・vm-ap01・vm-db01・vm-ad01・vm-file01のいずれも各役割1台構成であり、そのままではゾーン分散のメリットを活かせません。
- **コスト制約との整合**:制約条件により月額運用コストの抑制が求められており、各役割を2台以上に冗長化するとVMの台数が単純に倍増し、コストも大きく増加します。ポートフォリオとしての検証用途であることを踏まえ、本フェーズでは冗長化よりもコスト効率を優先しています。
- **バックアップによる代替**:VM単体の障害に対しては、可用性の仕組みで「止まらないようにする」のではなく、Recovery Services Vaultによる自動バックアップから「素早く復旧する」という方針で対応しています。非機能要件で定めるRTO 4時間以内(VM全体のリストアによる復旧)は、この方針を前提とした目標値です。バックアップ・DRの詳細な設計は「06-backup-dr.md」で解説します。

つまり本設計は、「VMが壊れないようにする(可用性ゾーン等による予防)」よりも、「VMが壊れても短時間で復旧できるようにする(バックアップによる事後対応)」ことを優先したコスト効率重視の可用性設計であると言えます。

### 6.4 将来拡張案

将来、事業拡大や利用者数の増加により、より高い可用性(ダウンタイムの一層の短縮)が求められる場合は、以下のような拡張が考えられます。

| 対象 | 拡張案 | 概要 |
|---|---|---|
| Web層・AP層 | 可用性ゾーンをまたいだ水平スケール(スケールアウト) | vm-web01・vm-ap01をそれぞれ複数台に増設し、異なる可用性ゾーンへ分散配置したうえで、Azure Load Balancer(通信を複数のVMへ振り分けるサービス)やApplication Gatewayを前段に配置し、1台が停止しても他のVMで処理を継続できる構成へ発展させる |
| DB層 | SQL Server Always On 可用性グループ、またはAzure SQL Managed Instanceのゾーン冗長構成 | vm-db01を複数台構成にし、SQL Serverのレプリケーション機能によってデータベースを常時同期させる、あるいは将来のPaaS化検討にあわせてAzure SQL Managed Instance等のマネージドサービスへ移行し、ゾーン冗長オプションを利用する |
| AD DS/DNS | 追加ドメインコントローラの可用性ゾーン分散 | vm-ad01が単一障害点(1点が壊れると全体が止まってしまう箇所)にならないよう、別ゾーンに2台目のドメインコントローラを追加し、認証・名前解決の可用性を高める |

これらはいずれも、「将来的なPaaS化・DX推進の足がかりとする」というプロジェクトゴールとも整合する拡張の方向性です。本フェーズではまずIaaS中心のリフト&シフトで安定稼働を実現し、事業要件の変化に応じて段階的に可用性投資を積み増していく方針とします。

## 7. 設計思想のまとめ(なぜこの構成にしたのか)

本章で解説してきたサーバー設計の判断は、突き詰めると次の3つの考え方に集約されます。

1. **役割ごとにサーバーを分離し、それぞれの負荷特性に見合ったサイズを充てる**:Web/AP/DB/AD・DNS/ファイルサーバーという役割ごとにVMを分け、CPU・メモリの要求が大きいDBサーバーだけをワンランク上のサイズ(Standard_B4ms)にするなど、一律ではなくメリハリのある選定を行っています。
2. **性能とコストのバランスを、部分最適ではなく用途単位で判断する**:VMサイズは全体としてBシリーズ(コスト重視)で統一しつつ、ディスクだけはDBサーバーのI/O性能が業務全体のボトルネックになりやすい部分に限ってPremium SSDへ投資するなど、「どこにコストをかけ、どこを抑えるか」を明確に切り分けています。
3. **「壊れないようにする」より「壊れても素早く戻せるようにする」を選ぶ**:可用性セット・可用性ゾーンによる常時冗長化はコスト増を伴うため本フェーズでは見送り、代わりに自動バックアップとRTO/RPO目標に基づく復旧体制で可用性要件に応えるという、コスト制約下での現実的な設計判断を行っています。

これらの判断はいずれも、要件定義書(00-overview-requirements.md)で整理した機能要件・非機能要件・制約条件、特に「月額運用コストを抑制する」という制約条件C-01と、「RPO 24時間以内・RTO 4時間以内」という非機能要件NF-03を出発点としています。次章「02-network-design.md」「04-security-design.md」では、これらのサーバー間をどのような通信ルールで結ぶかを解説します。

## 理解度チェック

**Q1. 本プロジェクトのVMは何台構成で、それぞれどのような役割を担っていますか。**
A1. 合計5台です。vm-ad01(AD DS/DNS)、vm-web01(Webサーバー、IIS)、vm-ap01(APサーバー、業務アプリケーション)、vm-db01(DBサーバー、SQL Server 2022)、vm-file01(ファイルサーバー)の5つの役割にそれぞれ1台ずつVMを割り当てています。

**Q2. vm-db01だけが他のVMより大きいVMサイズ(Standard_B4ms)を採用しているのはなぜですか。**
A2. SQL Serverはデータのキャッシュ(バッファプール)にメモリを多く使う特性があり、システム全体の中でCPU・メモリ要求が最も高いためです。他のVMがStandard_B2s/B2msであるのに対し、vm-db01のみvCPU数4・メモリ16 GiBというワンランク上のサイズを選定し、業務システムとして最低限必要な性能を確保しています。

**Q3. Bシリーズ(バースト可能インスタンス)の仕組みを一言で説明してください。**
A3. 普段は決められたベースライン性能(低め・中程度のCPU性能)で動作し、CPU使用率がベースラインを下回っている間に貯めた「CPUクレジット」を消費することで、負荷が上がった瞬間に一時的に性能を引き上げられる(バーストする)仕組みのVMシリーズです。常時高負荷ではない一般的な社内業務システムと相性がよく、コストを抑えられます。

**Q4. vm-db01でOSディスクとデータ/ログ/tempdb用ディスクを分離しているのはなぜですか。**
A4. OS自体の読み書きと業務データの読み書きが同じディスク上で発生すると、処理が競合して性能が不安定になるためです。またデータファイル(ランダムアクセス中心)、ログファイル(順次書き込み中心)、tempdb(一時作業領域で高負荷になりがち)はそれぞれ異なるI/O特性を持つため、専用ディスクに分離しPremium SSD(高性能ディスク)を採用することで、業務全体の応答速度に直結するI/O性能を確保しています。

**Q5. 本設計で可用性セット・可用性ゾーンを採用しなかった理由と、代わりに何で可用性要件に応えていますか。**
A5. 各役割が1台構成であり、可用性セット・可用性ゾーンによる冗長化は同じ役割のVMが複数台あって初めて効果を発揮するためです。また冗長化するとVM台数が増えコストも増加し、月額運用コストを抑制する制約条件に反します。代わりに、Recovery Services Vaultによる自動バックアップと、RPO 24時間以内(DBは15分以内)・RTO 4時間以内という目標値に基づく「壊れても素早く復旧する」方針で可用性要件に応えています。
