# 11. 用語集(初心者向け)

**この章のポイント**

- 本パック(00章〜10章)に登場する専門用語を、**ネットワーク系/コンピューティング系/セキュリティ系/運用系/バックアップ系/IaC系/その他**の7カテゴリに分け、合計64語を収録します。
- 各用語は「**一言でいうと**(まず結論だけ知りたいとき用)」→「**もう少し詳しく**(実務でどう使うか・本設計でなぜ採用したかまで理解したいとき用)」の2段階で解説し、読者の理解度に合わせて必要なところだけ読める構成にしています。
- 各用語がどの章の設計内容と結びついているかを「登場する章」列に明示し、本パック全体を横断できる**索引**として機能させます。
- 単なる単語カードの寄せ集めにせず、「増分バックアップと差分バックアップは何が違うのか」「なぜルートテーブルを独自に作らなかったのか」といった、初心者がつまずきやすい**比較・設計判断の理由**もあわせて解説します。
- 章末の理解度チェックで、代表的な用語の理解度をセルフチェックできます。

## 1. この章の使い方・用語集を設けた理由

### 1.1 なぜ独立した章として用語集を用意したのか(設計思想)

00章〜10章の各設計書では、専門用語が初めて登場する箇所に「(〇〇という意味。※詳しくは用語集(11-glossary.md)を参照)」という形で簡単な注釈を入れる方針を徹底してきました。これは、実務の設計書でも、読み手(発注者・他部署の担当者・後任の運用者など、必ずしもインフラの専門家とは限らない人たち)が読みながら迷子にならないための一般的な配慮です。

ただし、各章の注釈はあくまで「読み進める邪魔にならない程度の一言」に留めています。そのため、「一言だけでは物足りない、実務でどう使うのか・なぜこの設計で採用したのかまで理解したい」という段階になったときに立ち戻れる場所が別途必要になります。本章はその**受け皿**として設けたものであり、以下の2つの読み方を想定しています。

1. **辞書的な使い方**:他の章を読んでいて「※詳しくは用語集を参照」と出てきたら、本章の該当カテゴリを開いて確認する。
2. **通読による体系的な学習**:面接や書類選考の前に、本章だけを通しで読み、Azureインフラ構築の基礎用語を一通り棚卸しする。

## 2. ネットワーク系用語

本プロジェクトでは、VNet(仮想ネットワーク)を1つだけ作成し、その内部をWeb層・AP層・DB層・管理層・Bastion層という5つのサブネットに細かく分割しています(詳細は02章)。これは、旧環境の現状課題④「サーバー管理者が固定グローバルIP経由でVMへ直接RDP接続しており、アクセス統制・監査ログが不十分である」を踏まえ、「ネットワークの入口を1か所(Azure Bastion)に絞り、層と層の間の通信も業務上必要な最小限に絞る」という多層防御の設計思想を、IPアドレス設計とアクセス経路の両面から実現するためです。以下の用語は、この構成を正しく読み解くための基礎知識です。

| 用語 | 一言でいうと | もう少し詳しく | 登場する章 |
|---|---|---|---|
| VNet(Virtual Network、仮想ネットワーク) | Azure上に作る、自社専用の仮想的なネットワーク空間 | オンプレミスの社内LANに相当するもので、Azure上のVM同士やサブネット同士が通信するための土台になります。本設計では`vnet-sanrise-prod-jpe`(`10.10.0.0/16`)を1つだけ作成し、その中をサブネットで分割する方針を採っています。複数のVNetを連携させる大規模構成(後述のハブ&スポーク構成)を組むほどの規模ではないため、単一VNetでシンプルに構成し、将来の拡張余地は`/16`という十分広いアドレス空間の確保で担保しています。 | 00章、01章、02章 |
| サブネット(Subnet) | VNetの中をさらに小さく区切った、用途別の区画 | 1つのVNetを、役割ごと(Web/AP/DB/管理/Bastion)に分割した単位です。サブネットを分けることで、区画ごとに異なるNSG(通信の許可・拒否ルール)を割り当てられるようになり、「Web層が攻撃を受けてもDB層には直接届かない」といった被害の局所化が可能になります。本設計では5つのサブネット(`snet-web-prod-jpe`等)に分割しています。**注意点**:サブネットは一度VMなどのリソースを配置すると、範囲の変更・縮小が難しくなるため、設計段階で余裕を持ったCIDR設計をしておくことが重要です。 | 02章、03章 |
| CIDR(Classless Inter-Domain Routing) | IPアドレスの範囲を「◯◯.◯◯.◯◯.◯◯/数字」という形で表す記法 | 末尾の数字(プレフィックス長)が大きいほど、含まれるIPアドレスの範囲は狭くなります。たとえば`/24`は256個、`/26`は64個のIPアドレスを表します。ただしAzureでは、各サブネットにつきネットワークアドレス・デフォルトゲートウェイ・DNS用途2個・ブロードキャストアドレスの合計5個を予約するため、実際に使える数は理論値より5個少なくなります(`/24`なら251個、Bastion専用の`/26`なら59個)。本設計のVNet全体は`10.10.0.0/16`、各業務層サブネットは`/24`、Bastion専用サブネットは仕様上`/26`以上と定められています。 | 02章 |
| NSG(Network Security Group、ネットワークセキュリティグループ) | サブネットやNIC単位で「どの通信を許可・拒否するか」を定義するファイアウォールのようなルール集 | 「方向(Inbound/Outbound)」「優先度(数字が小さいほど先に評価)」「プロトコル」「送信元/宛先」「許可/拒否」の組み合わせで1件ずつルールを定義します。本設計ではサブネットごとに専用のNSG(`nsg-web-prod-jpe`等)を割り当て、Web→AP→DBという業務上必要な通信のみを許可し、Web→DBの直接通信のように不要な経路は明示的に拒否ルールで塞ぐ、多層防御の要になっています。NSGの通信ログを集計したものが「NSGフローログ」(本カテゴリ内で別掲)です。 | 02章、04章、08章 |
| DNS(Domain Name System) | コンピューター名(ホスト名)とIPアドレスを対応づける、名前解決の仕組み | 人間が覚えやすい名前(例:`vm-db01.sanrise.local`)を、実際の通信に必要なIPアドレスへ変換する仕組みです。本設計では、オンプレミスADドメイン`sanrise.local`を運用するため、Azure標準のDNSではなく、`vm-ad01`(`10.10.4.4`)をVNetのカスタムDNSサーバーとして設定しています。ドメイン参加した各VMは、まず`vm-ad01`に名前解決を問い合わせ、社外のホスト名を調べたい場合は`vm-ad01`のフォワーダー設定を経由してAzure提供DNS(`168.63.129.16`)へ転送される構成です。 | 00章、02章、03章、08章、09章 |
| ルートテーブル(Route Table、UDR:User Defined Routes) | 通信がどの経路を通ってVNet内外へ届くかを、既定の経路から変更したいときに使う設定 | Azureは何も設定しなくても「同じVNet内は直接届く」「インターネットへはAzureの既定ゲートウェイ経由」といった基本的な経路(システムルート)を自動的に用意しています。ルートテーブルは、たとえばAzure Firewallや仮想アプライアンス(NVA)を経由させたい場合など、この既定経路をあえて上書きしたいときに使う仕組みです。**なぜ本設計では作成していないのか(設計思想)**:本設計はNSGによる通信制御だけで多層防御の要件(NF-02)を満たせており、Azure Firewall等のNVAを経由させる特別な通信経路も不要なため、Azureの既定のシステムルートのままで問題ないと判断し、独自のルートテーブルは作成していません。将来Azure Firewallを導入する場合などに、あらためて検討対象となる項目です。 | 02章 |
| Azure Bastion | インターネットに公開せず、Azureポータル経由でVMへ安全にRDP/SSH接続できるマネージドの踏み台サービス | 旧環境では管理者が固定グローバルIP経由でVMへ直接RDP接続していましたが、本設計ではVMへのパブリックIP付与を全廃し、`bas-sanrise-prod-jpe`(専用サブネット`AzureBastionSubnet`、`10.10.5.0/26`)を経由した接続に一本化しています。Azureポータルへのサインイン(Microsoft Entra ID)を前提とするため、「誰が」「いつ」「どのVMに」接続したかが自動的にログとして残る点も、旧環境の証跡不足という課題の解決につながっています。コスト重視の構成のためBasic SKUを採用しており、同時接続数などに制約がありますが、本システムの規模(サーバー5台・少人数の管理者)であれば十分と判断しています。 | 00章、01章、02章、04章、08章、09章 |
| VPN(Virtual Private Network) | インターネット回線の上に、暗号化された仮想的な専用線を構築する技術 | 旧環境では、管理者がVPN経由で社内ネットワークへ接続したうえで各サーバーへRDP接続する運用でしたが、接続経路自体は暗号化されていても、「一度VPNに入ってしまえば内部のどのサーバーにも直接RDPできてしまう」というアクセス統制の甘さが課題でした。本設計ではAzure Bastionへの一本化によってこの課題を解消しつつ、将来的にはオンプレミスADとのサイト間VPN(拠点間を結ぶVPN)による複製構成も見据えています。 | 00章、02章 |
| RDP(Remote Desktop Protocol) | Windowsサーバー・PCへ遠隔操作(画面転送)で接続するための通信プロトコル(既定ポート3389) | 旧環境では、管理者の端末からVMへ直接この3389番ポートで接続していたため、VM側にパブリックIPと3389番ポートの受信許可が必要でした。本設計では、VMへのパブリックIPを全廃し、RDP接続はAzure Bastion経由でのみ、かつ送信元をBastion専用サブネット(`10.10.5.0/26`)からのみに限定するNSGルール(`Allow-Bastion-Rdp-Inbound`)で許可しており、インターネットから直接3389番ポートが見える状態を作らない設計になっています。 | 00章、02章、04章 |
| パブリックIP / プライベートIP | インターネットから直接届く住所(パブリックIP)と、VNet内部だけで通用する住所(プライベートIP) | 各VMには、VNet内部専用の**プライベートIP**(例:`vm-web01`は`10.10.1.4`)のみが割り当てられ、インターネットから直接アクセスできる**パブリックIP**は一切付与していません。これは非機能要件(VMには一切パブリックIPアドレスを付与しない)を満たすための最も基本的な設計判断であり、外部からの攻撃対象領域(アタックサーフェス)を最小化する効果があります。パブリックIPを持つのは、利用者の性質上インターネットからの着信が必須なAzure Bastion(Standard SKUのパブリックIP)のみです。 | 00章、02章、04章 |
| ハブ&スポーク構成(Hub-Spoke) | 中心となる共有ネットワーク(ハブ)から、複数の業務用ネットワーク(スポーク)を放射状につなぐ、大規模組織向けのVNet設計パターン | 複数の部門・複数のシステムが、共通のセキュリティ機能(Azure Firewallなど)やオンプレミス接続をハブ側に集約し、各スポークからそれを共有する構成です。本プロジェクトはJapan East単一リージョン・単一の業務システムが対象であり、この構成を組むほどの規模ではないと判断し、単一VNet内をサブネットで分割するシンプルな構成を採用しています。会社の拠点(東京・福岡支店を含む)が今後増え、複数システムが並行稼働するようになった場合の拡張オプションとして紹介するに留めています。 | 02章 |
| サービスタグ(Service Tag) | 「Storage」「AzureActiveDirectory」など、AzureのサービスをまとめたIPアドレス範囲の別名 | Azureの各サービスが実際に使用するIPアドレス範囲は変動する場合があるため、NSGルールの送信元/宛先に個別のIPアドレスを直接書く代わりに、Azureが管理する「サービスタグ」という名前で指定できます。本設計では、DBサーバーからAzure Backupのストレージへの通信を許可するルールで宛先に`Storage`タグを、Entra Connectのディレクトリ同期通信を許可するルールで宛先に`AzureActiveDirectory`タグを使用しており、Azure側でIP範囲が変わってもルールを書き換える必要がない、保守性の高い書き方になっています。 | 02章、06章 |
| NSGフローログ(NSG Flow Logs) | NSGを通過した(または拒否された)通信の記録を、時系列で残す仕組み | NSGのルール自体は「今この瞬間、この通信を通すか止めるか」を判定するだけですが、フローログを有効にしておくと「いつ・どのIPから・どのポートへ・許可されたか拒否されたか」という通信の履歴を後から確認できます。本設計では、監視ダッシュボードの項目の1つとして「NSGフローログのサマリ(拒否された通信の件数推移)」を可視化し、想定外の通信が増えていないかを継続的にチェックする方針としています。 | 05章 |

## 3. コンピューティング系用語

本プロジェクトのVM構成は、「老朽化した物理サーバー(Web/AP/DBの3層構成)を、できる限りそのままの構成でAzureへ移行する(リフト&シフト)」という要件定義書のゴールと、「ポートフォリオとしての検証用途のため、月額運用コストを抑制する目的でVMサイズはBシリーズを基本とする」という制約条件(C-01)の両方を満たすように設計されています(詳細は03章)。以下の用語は、この考え方を理解するための基礎知識です。

| 用語 | 一言でいうと | もう少し詳しく | 登場する章 |
|---|---|---|---|
| VM(Virtual Machine、仮想マシン) | 1台の物理サーバーの上で、ソフトウェア的に再現された仮想的なコンピューター | Azure上では、CPU・メモリ・ディスク・ネットワークを持つ独立したサーバーとして、VMを自由に作成・削除できます。本設計では、旧物理サーバーの役割(AD/Web/AP/DB/ファイルサーバー)をそのまま5台のVM(`vm-ad01`・`vm-web01`・`vm-ap01`・`vm-db01`・`vm-file01`)に対応させ、OS・ミドルウェアのみWindows Server 2022へ刷新するリフト&シフトを行っています。 | 00章、03章、09章 |
| VMサイズ(VM Size) | VMのCPUコア数・メモリ量・性能グレードを決める「サイズ表」のようなもの | Azureには数多くのVMシリーズ・サイズが用意されており、用途に応じて選択します。本設計では、コスト制約からBシリーズ(次項)を中心に選定しており、DBサーバー(`vm-db01`)はSQL Serverを稼働させるためやや大きめの`Standard_B4ms`、Webサーバー(`vm-web01`)・ファイルサーバー(`vm-file01`)は負荷が小さいため`Standard_B2s`、AD/APサーバー(`vm-ad01`・`vm-ap01`)は中間の`Standard_B2ms`を採用しています。VMサイズは後から変更(スケールアップ/ダウン)も可能ですが、変更時にはVMの再起動が必要になる点に注意が必要です。 | 03章、07章、09章 |
| 可用性セット(Availability Set) | 同じ役割のVMを複数台配置するとき、物理的な障害の影響が同時に及ばないように自動的に分散配置する仕組み | Azureのデータセンター内部の「フォールトドメイン(電源・ネットワークスイッチを共有する単位)」と「アップデートドメイン(Azure側のメンテナンスが同時に行われる単位)」を分散させることで、1つのラック障害やメンテナンスで同じ役割のVMが同時に停止する事態を避けます。**本設計での採用状況**:各役割が1台構成であるため、可用性セットの効果(同じ役割のVMが複数台あって初めて発揮される)を活かせず、採用していません。 | 03章 |
| 可用性ゾーン(Availability Zone) | リージョン内に複数用意された、電源・冷却・ネットワークが物理的に独立したデータセンター群 | 可用性セットが「同じデータセンター内でのラック単位の分散」であるのに対し、可用性ゾーンは「データセンター施設そのものを分散させる」、より大きな粒度の冗長化です。Japan Eastリージョンは複数の可用性ゾーンを提供しています。**本設計での採用状況**:コスト制約と各役割1台構成という前提から採用しておらず、「VMが壊れないようにする(予防)」よりも「VMが壊れても短時間で復旧できるようにする(バックアップによる事後対応)」を優先する設計判断を行っています。将来、可用性要件がさらに高まった場合の拡張オプションです。 | 01章、03章 |
| マネージドディスク(Managed Disk) | ディスクの実体(ストレージアカウント等)の管理をAzureに任せられる、VM用の仮想ディスク | 旧世代の「非マネージドディスク」ではストレージアカウントの管理をユーザー側が行う必要がありましたが、マネージドディスクではAzureが可用性・暗号化・バックアップ連携などを内部で管理してくれます。性能・コストの異なる複数の種類(Standard HDD、Standard SSD、Premium SSD等)があり、本設計ではOSディスクや負荷の小さいVMにStandard SSD、DBサーバー(`vm-db01`)のデータ/ログ/tempdb用ディスクにはI/O性能が求められるためPremium SSDを分離して採用しています。ディスクを分離しているのは、OSの入出力とデータベースの入出力が競合してパフォーマンスが劣化するのを防ぐためです。 | 03章、07章 |

## 4. セキュリティ系用語

本設計が目指すのは、「社内ネットワークの中にいるから安全」「一度ログインしたら何でもできる」という暗黙の信頼を置かない、**ゼロトラストに近い最小権限モデル**です。具体的には、①管理アクセスの統制(Azure Bastionへの一元化)、②ID・権限の最小化(RBAC)、③秘密情報の一元管理(Key Vault)、④データの暗号化、という4本の柱で構成されています(詳細は04章)。以下の用語は、この4本柱を理解するための基礎知識です。

## 5. 運用系用語

## 6. バックアップ系用語

旧環境の現状課題⑥「バックアップが磁気テープによる手動運用であり、リストア検証やDR訓練が実施できておらず復旧の実効性が担保されていない」を解決するのが、本カテゴリの用語群です(詳細は06章)。「バックアップは取得しているが、実際に戻せるかは試したことがない」という状態を、Azure Backupによる自動化と10章のテスト仕様書によるリストア検証で二度と繰り返さない、というのが設計の狙いです。

| 用語 | 一言でいうと | もう少し詳しく | 登場する章 |
|---|---|---|---|
| Recovery Services Vault | Azure Backupのバックアップデータを保管・管理するための箱(コンテナ)にあたるAzureリソース | 本設計では`rsv-sanrise-prod-jpe`として構築し、5台すべてのVMのバックアップをここに集約管理しています。バックアップポリシー`bkp-sanrise-standard-daily`(毎日02:00の日次バックアップ+週次・月次の長期保持)を適用し、旧環境の磁気テープによる手動運用から、スケジュールに沿った自動運用へ切り替えています。 | 00章、01章、06章、09章 |
| フルバックアップ(Full Backup) | ある時点の全データを、まるごと1回分コピーするバックアップ方式 | 復旧時に必要なデータがこの1回分に完結しているため理解しやすい反面、データ量が多いほど取得に時間がかかり、保存先の容量も多く必要になります。本設計では、DBサーバー(`vm-db01`)のSQL Serverワークロードバックアップにおいて、週1回のフルバックアップを起点とし、そこに日次の差分バックアップ(次項)とトランザクションログバックアップ(後述)を組み合わせる方式を採用しています。 | 06章 |
| 増分バックアップ(Incremental Backup) | 直前の(フルまたは増分)バックアップ以降に変更があった部分だけを取得するバックアップ方式 | フルバックアップに比べてデータ量・取得時間を抑えられる一方、復旧時にはフルバックアップと、それ以降のすべての増分バックアップを順番に適用する必要があります。**本設計での使われ方**:Azure Backup(Recovery Services Vault)によるVMレベルのバックアップ(`vm-ad01`・`vm-web01`・`vm-ap01`・`vm-file01`が対象)は、初回にフルバックアップを取得した後、以降は変更されたブロックのみを取得する増分方式で動作する仕組みになっており、Azure側が裏側で世代管理・合成(リストア時にフル相当へ組み立てる処理)を自動的に行います。 | 06章 |
| 差分バックアップ(Differential Backup) | 直近の**フルバックアップ**からの変更分だけを取得するバックアップ方式(増分バックアップとの違いに注意) | **増分バックアップと混同しやすいポイント**:増分バックアップが「直前のバックアップ(フルでも増分でもよい)からの差分」を取るのに対し、差分バックアップは常に「直近のフルバックアップからの差分」を取り続けます。そのため復旧に必要なのは「フルバックアップ+最新の差分バックアップ1つ」だけで済み、増分方式より復旧の組み立てはシンプルになりますが、日を追うごとに1回あたりのデータ量は増えていきます。本設計では、DBサーバー(`vm-db01`)のSQL Serverワークロードバックアップにおいて、週1回のフルバックアップに対し、日次でこの差分バックアップを取得する方式(Azure Backup SQL Server内ワークロードバックアップの標準的な方式)を採用しています。 | 06章 |
| トランザクションログバックアップ(Transaction Log Backup) | データベースへの更新履歴(トランザクションログ)を、短い間隔で継続的にバックアップする方式 | フル/差分バックアップだけでは「前回のバックアップ時点」までしか戻せませんが、トランザクションログバックアップを組み合わせることで、「障害発生の直前」に近い時点まで復旧する**ポイントインタイムリストア**が可能になります。本設計では、受発注・在庫データを扱うDBサーバー(`vm-db01`)に対してのみ、15分間隔でこのバックアップを取得し、15日間保持することで、非機能要件のRPO 15分以内という厳しい目標を実現しています。 | 00章、06章 |
| GRS(Geo-Redundant Storage、地理冗長ストレージ) | 保存したデータを、地理的に離れたペアリージョンへ自動的に複製するAzureストレージの冗長化オプション | Japan Eastリージョンのペアリージョンは西日本(Japan West)であり、GRSを使うとバックアップデータが自動的にJapan Westへ複製されます。本設計では、コスト重視の構成のためAzure Site Recovery(次項)による本格的なリージョン間フェイルオーバーは導入していませんが、Recovery Services VaultのGRSによってバックアップデータだけは地理的に保全しており、大規模障害時には西日本リージョンへ新規VMを構築し、GRS化されたリカバリーポイントからリストアする簡易DR手順を運用マニュアルに定める方針です。 | 01章、06章 |
| Azure Site Recovery(ASR) | VMをリージョン間で常時レプリケーション(複製)しておき、災害時に短時間でフェイルオーバー(切り替え)できるようにするDR(災害復旧)サービス | 常時レプリケーション用の複製リソース(実質的にレプリカVM相当の待機環境)を維持し続ける必要があるため、平常時から追加コストが発生し続けます。本設計では、コスト制約からASRは本フェーズでは導入せず、前項のGRSによる最低限の地理的保全と、簡易的な手動DR手順で代替しています。将来的に事業が拡大し、より厳しいRTO要件が求められるようになった場合の拡張オプションとして位置づけています。 | 01章、06章 |
| DR(Disaster Recovery、災害復旧) | 地震・水害・大規模障害などでシステムが利用できなくなった際に、どう復旧するかを定めた考え方・体制 | 旧環境は自社データセンターの単一拠点運用であり、災害時の事業継続(BCP、次カテゴリで解説)の観点で大きな課題を抱えていました。本設計では、コスト制約を踏まえ、可用性ゾーン冗長化やAzure Site Recoveryといった本格的なDR基盤ではなく、Recovery Services VaultのGRSと簡易的な手動リストア手順という「コスト効率を優先した現実的なDR」を採用しています。 | 00章、06章 |

## 7. IaC系用語

本パックは、要件定義から設計・構築・運用までを一貫して示すことを目的としているため、「設計書に書いたとおりに、再現性を持って構築できること」を重視しています。08章・09章では、Azureポータルでの手動構築手順と対になる形で、`infra/advanced`配下にBicepによるコード一式を用意する方針としています。以下の用語は、この「構成をコードで管理する(IaC)」という考え方の基礎知識です。

|---|---|---|---|
| IaC(Infrastructure as Code) | サーバーやネットワークなどのインフラ構成を、手作業ではなくコード(定義ファイル)として記述し、実行することで構築・変更する手法 | 手順書を見ながらポータルを1画面ずつクリックしていく方法は、人為的な入力ミスが起きやすく、同じ環境をもう一度再現するのも大変です。IaCでは、構成をコードとして残すことで、①同じ環境を何度でも正確に再現できる、②Gitなどのバージョン管理システムで変更履歴・レビューが可能になる、というメリットが得られます。本パックでは、まずポータル操作(08章・09章)で「何が作られるか」を体で理解し、実務ではBicepを正として再現性のある構築・変更管理を行う、という学習の流れを想定しています。 | 00章、01章、08章 |

## 理解度チェック

**Q1. Azure Bastion専用サブネット`AzureBastionSubnet`(`10.10.5.0/26`)には、理論上何個のIPアドレスが含まれ、Azureの予約分を除くと実際に使えるのは何個ですか。**

A. 理論上は64個(`/26`)です。Azureは各サブネットでネットワークアドレス・デフォルトゲートウェイ・DNS用途2個・ブロードキャストアドレスの合計5個を予約するため、実際に使える数は64から5を引いた59個になります。

**Q2. 「増分バックアップ」と「差分バックアップ」の違いを、本設計の具体例を挙げて説明してください。**

A. 増分バックアップは「直前のバックアップ(フルでも増分でもよい)からの変更分」を取得する方式で、`vm-ad01`・`vm-web01`・`vm-ap01`・`vm-file01`のAzure Backup(VMレベルのバックアップ)がこの方式で動作します。一方、差分バックアップは「直近のフルバックアップからの変更分」を毎回取得する方式で、DBサーバー(`vm-db01`)のSQL Serverワークロードバックアップは、週1回のフルバックアップに対し日次でこの差分バックアップを取得しています。

**Q3. 本設計でルートテーブル(UDR)を独自に作成していないのはなぜですか。**

A. 本設計はNSGによる通信制御だけで、多層防御の非機能要件(Web/AP/DB層間の通信を最小限のポートに限定する)を満たせており、Azure Firewallのような仮想アプライアンス(NVA)を経由させる特別な通信経路も必要ないためです。そのため、Azureが自動的に用意する既定のシステムルートのままとし、独自のルートテーブルは作成していません。

**Q4. 「べき等性」とは何ですか。IaC(Bicep)においてなぜ重要ですか。**

A. べき等性とは、同じ操作を何度実行しても結果(最終的な状態)が変わらないという性質です。IaCにこの性質があることで、デプロイに失敗しても安心して同じコマンドを再実行できる(安全な再試行)ほか、誰かが手動で設定を変えてしまった場合でも、コードを再適用するだけで本来あるべき状態に戻せる(構成ドリフトの是正)というメリットが得られます。

**Q5. 本設計でVMがKey Vault上のシークレットへアクセスする際、なぜパスワードを使わずに済むのですか。ここに関わる用語を2つ挙げて説明してください。**

A. 関わる用語は「システム割り当てマネージドID」と「RBAC」です。各VMにシステム割り当てマネージドID(パスワードを使わずにAzureリソースとして認証される仕組み)を持たせたうえで、そのIDに対してRBACの「Key Vault Secrets User」ロールのみを付与しているため、VMはパスワードを介さずに、かつ必要最小限の権限(シークレットの読み取りのみ)でKey Vaultへアクセスできます。これは最小権限の原則をID面で実装した具体例です。
