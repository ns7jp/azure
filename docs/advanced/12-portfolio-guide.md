# 12. ポートフォリオ活用ガイド

## この章のポイント

- この設計書パック(00〜11番)を、転職活動・面接の場で**実際にどう説明するか**を、STAR形式(状況・課題・行動・結果)のトークスクリプト例として具体化します。
- 「なぜAzureを選んだのか」「NSG設計で工夫した点は何か」「コスト意識はどう持ったか」など、未経験からのインフラ・サーバー構築エンジニア志望者が聞かれやすい**想定面接質問と回答例を12問**用意します。
- このポートフォリオが「未経験可」のインフラ/サーバー構築エンジニア求人でどう刺さるのかを、**求人票でよく見る表現とアピールできる具体的スキルの対応表**として整理します。
- Terraform化・CI/CDパイプライン化・マルチリージョンDR・コンテナ化など、**今後の発展課題(伸びしろ)**を提示し、「作って終わり」ではなく学習の継続性をアピールする材料にします。
- GitHubリポジトリとして公開する際の**README構成・図の見せ方・スクリーンショット追加のコツ**をまとめ、採用担当者が数分で価値を理解できる見せ方を解説します。

---

## 1. 本章の目的:設計書を「転職活動の武器」に変える

### 1.1 なぜこの章が必要か

00〜10番の設計書は、株式会社サンライズ物産という架空の卸売業企業を題材に、老朽化した基幹サーバー(受発注・在庫管理システム)をAzureへリフト&シフトする、という一連の設計・構築プロセスを実務さながらに documentation したものです。しかし、**どれほど作り込んだ設計書でも、それを「自分の言葉で語れる」状態にしなければ転職活動における武器にはなりません**。書類選考の担当者やエンジニア面接官は、設計書そのものの完成度と同じくらい、あるいはそれ以上に「この人は自分が何を考えてこの設計にしたのかを理解し、説明できるか」を見ています。

本章は、00〜10番で積み上げてきた設計内容を棚卸しし、以下の3つの形に「翻訳」し直すことを目的とした、実務でそのまま使える活用ガイドです。

1. **面接で1分〜3分にまとめて話せるトークスクリプト**(STAR形式)
2. **深掘り質問に対する回答例の引き出し**(Q&Aのストック)
3. **GitHub上での見せ方**(採用担当者が最初の数分で価値を理解できる導線)

### 1.2 想定読者と使い方

本章の想定読者は、本設計書パック全体と同じく「未経験からサーバー構築/インフラエンジニアを目指している人」です。その中でも特に、書類選考を通過し、いよいよ技術面接・カジュアル面談に臨む段階の方を想定しています。使い方としては、以下のような順序を推奨します。

| ステップ | やること | 参照節 |
|---|---|---|
| ① 全体像を1分で語れるようにする | 2.2節の短縮版トークスクリプトを暗記ではなく「自分の言葉」に置き換えて練習する | 2.2節 |
| ② 深掘りに備える | 2.3節の詳細版STARで、各要素の裏にある数値・固有名詞(リソース名等)を頭に入れる | 2.3節 |
| ③ 想定質問に答える練習をする | 3節のQ&Aを声に出して練習し、回答例を丸暗記ではなく理解の上で再構成する | 3節 |
| ④ 求人票と自分のスキルを結び付ける | 4節の対応表を使い、応募先の求人票の文言と本ポートフォリオの該当箇所を事前にマッピングしておく | 4節 |
| ⑤ 「伸びしろ」を語れるようにする | 5節の発展課題を1〜2個選び、「本当に取り組んでいる/取り組む予定である」と言えるようにしておく | 5節 |
| ⑥ GitHubを整える | 6節を参考にREADMEと図を整備し、面接前に必ずURLを送れる状態にしておく | 6節 |

> **設計思想メモ**:本章をあえて「面接想定問答集」ではなく「ポートフォリオ活用ガイド」という章タイトルにしたのは、丸暗記した回答をそのまま話す人と、設計思想を理解した上で自分の言葉に変換して話す人とでは、面接官への伝わり方がまったく違うためです。以降のスクリプトや回答例は、**そのまま暗唱する台本ではなく、自分の経験に合わせて言い換えるための「型」**として使ってください。

## 2. STAR形式で語る:面接トークスクリプト例

### 2.1 STAR形式とは

**STAR形式**(状況・課題・行動・結果を順番に語る面接での説明フレームワーク。Situation〈状況〉・Task〈課題〉・Action〈行動〉・Result〈結果〉の頭文字。※詳しくは用語集(11-glossary.md)を参照)は、実務経験の浅い方が「何をどうやって、どんな結果を出したのか」を論理的に説明するために広く使われる型です。実務経験がまだない、あるいは浅い方の場合、実際の職務経験の代わりに**個人で作り込んだポートフォリオの設計プロセスをSTAR形式に当てはめて語る**ことで、実務経験者に近い説得力を持たせることができます。

| 要素 | 意味 | 本ポートフォリオでの対応 |
|---|---|---|
| S(Situation:状況) | どんな背景・状況だったか | 株式会社サンライズ物産の老朽化した基幹サーバーという架空シナリオの設定(00-overview-requirements.md) |
| T(Task:課題) | 何を解決する必要があったか | ハードウェア保守切れ・OSサポート終了・アクセス統制不備・監視不足・バックアップ未検証という6つの課題(00-overview-requirements.md) |
| A(Action:行動) | 課題に対して具体的に何をしたか | ネットワーク設計・サーバー設計・セキュリティ設計・監視設計・バックアップ設計・コスト設計という一連の設計プロセス(01〜07番) |
| R(Result:結果) | どんな成果・アウトプットになったか | 12本の設計書一式、構築手順書、試験計画書という実務水準のドキュメント一式(08〜10番、本章) |

### 2.2 短縮版トークスクリプト(自己紹介・1分で話す場合)

面接冒頭の自己紹介やポートフォリオ紹介で「1分程度でお願いします」と言われた場合を想定した短縮版です。太字部分は特に強調して話すことを意識してください。

> 「私が今回作成したポートフォリオは、**卸売業の企業が2012年に構築した老朽化した基幹サーバーをAzureへ移行する**、という設定のインフラ設計プロジェクトです。ハードウェア保守切れとOSサポート終了という現実によくある課題に対して、単にAzure上にサーバーを建て直すだけでなく、**VMへのパブリックIP付与を廃止してAzure Bastion経由の管理アクセスに統制する**、**Web/AP/DB層の間の通信をNSGで必要最小限に絞り込む**、**Key VaultとMicrosoft Entra IDでID・秘密情報を一元管理する**といった、セキュリティを軸にした設計にこだわりました。また、ポートフォリオとしての検証コストを抑えるため、VMサイズの選定理由やコスト内訳まで説明できるように、月額約16.8万円という試算根拠も含めてドキュメント化しています。要件定義から、ネットワーク・サーバー・セキュリティ・監視・バックアップ・コストの各設計書、構築手順書、試験計画書まで一式を作成し、GitHubで公開しています。」

### 2.3 詳細版トークスクリプト(深掘りされた場合に話す内容)

「詳しく教えてください」と深掘りされた場合に備えて、S・T・A・Rそれぞれをもう一段詳しく話せるようにしておきます。実際の口頭説明では、以下を丸ごと話すのではなく、聞かれた要素だけを話せるように部品化して覚えておくのがコツです。

#### S(状況)

> 「題材にしたのは、大阪に本社を置く従業員約182名の卸売業の企業、株式会社サンライズ物産という設定です。加工食品・日用雑貨をスーパーやドラッグストアに卸す会社で、受発注・在庫管理システムを2009年に自社データセンター内の物理サーバー上にWeb/AP/DBの3層構成で構築し、10年以上運用してきました。しかしそのサーバーのハードウェア保守契約が2026年9月末で終了予定で、かつOSもWindows Server 2012 R2でメーカーサポートが切れている、という『更新期限が迫っている老朽化システム』というよくある状況を出発点にしました。」

#### T(課題)

> 「現状には大きく6つの課題がありました。1つ目はハードウェア保守切れ、2つ目はOSサポート終了によるセキュリティパッチ未適用、3つ目は自社データセンターの単一拠点運用によるBCP(事業継続計画)上のリスク、4つ目は管理者が固定グローバルIP経由でVMへ直接RDP接続し、しかも共有の管理者アカウントが常態化していてアクセス統制・監査ログが不十分だった点、5つ目はサーバー監視が目視中心で障害の予兆を検知できていなかった点、6つ目は磁気テープによる手動バックアップでリストア検証もDR訓練も未実施だった点です。これらを解決しつつ、Azure移行を機に可用性・セキュリティ・運用性を底上げすることが課題でした。」

#### A(行動)

> 「まずネットワーク設計として、Japan Eastリージョンに`vnet-sanrise-prod-jpe`という単一のVNet(10.10.0.0/16)を作り、Web層・AP層・DB層・管理層・Bastion専用の5つのサブネットに分割しました。単に分割するだけでなく、NSG(ネットワークセキュリティグループ)を各層に設定して、Web層からDB層への直接通信を明示的にDenyするなど、多層防御を意識した設計にしています。サーバー設計では、AD DS/DNSサーバー、Webサーバー、APサーバー、SQL Serverを搭載したDBサーバー、ファイルサーバーの5台をWindows Server 2022で構築する設計とし、コストを抑えるためBシリーズ(バースト可能インスタンス)を基本のVMサイズに選定しました。セキュリティ設計では、VMへのパブリックIP付与を一切廃止し、Azure Bastion経由でのみ管理者が接続できるようにした上で、各層間の通信ポートをアプリケーションが実際に使う最小限(WebからAPへは8443番、APからDBへは1433番など)に絞り込みました。さらにローカル管理者パスワードやSQL Serverの認証情報はAzure Key Vaultで一元管理し、Azure基盤の管理操作はMicrosoft Entra IDのRBACとMFAで統制する設計にしました。監視設計ではLog Analyticsワークスペースを構築し、CPU使用率・ディスク空き容量・VM死活監視・バックアップ失敗などをアラートで検知できるようにし、バックアップ設計ではRecovery Services Vaultで日次・週次・月次のバックアップに加え、DBサーバーだけはトランザクションログバックアップを15分間隔で取得することでRPOを最大15分に抑える設計にしました。最後にコスト設計として、各リソースの費用内訳を積み上げ、月額概算168,000円という数字を根拠付きで説明できるようにしています。」

#### R(結果)

> 「最終的に、要件定義書からネットワーク設計・サーバー設計・セキュリティ設計・監視設計・バックアップ設計・コスト設計、さらにネットワークとサーバーそれぞれの構築手順書、試験計画書、用語集まで、実務でそのまま使えるレベルの設計書一式(12ドキュメント)を作成しました。単なる技術メモではなく、『なぜこの設計にしたのか』という設計思想を毎回言語化することを徹底したので、面接でどの部分を深掘りされても、根拠を持って説明できる状態になっています。」

### 2.4 深掘り質問への橋渡し

上記のRの最後の一文は意図的に「どこを深掘りされても答えられる」という布石にしています。実際に面接官がここから深掘りしてくる典型的な切り口が、次の3節でまとめる想定質問です。次節に進む前に、**S・T・A・Rの各要素と、それを裏付ける固有名詞(リソース名・数値)がすぐに口から出るか**を一度自己チェックしておくことをお勧めします。

## 3. 想定面接質問と回答例

以下は、未経験からのインフラ/サーバー構築エンジニア志望者が本ポートフォリオを提示した際に、実際に聞かれやすい質問とその回答例です。回答例はあくまで型であり、面接では自分の言葉に言い換えて話してください。

### Q1. なぜAWSやGCPではなくAzureを選んだのですか?

**回答例**:「今回題材にした株式会社サンライズ物産は、既存の社内AD DS(sanrise.local)というオンプレミスのActive Directory基盤を持っている、という設定にしました。オンプレミスのActive DirectoryとのハイブリッドID連携(Microsoft Entra Connectによる同期)や、Windows Server・SQL Serverといった既存資産との親和性を考えると、同じMicrosoft製品であるAzureを選ぶのが自然だと考えたためです。また将来的にMicrosoft Entra IDへ段階的に移行していくという設計思想とも一貫性が取れると考えました。特定のクラウドへの強いこだわりというより、『既存のWindows Server資産を持つ中堅企業が最初に検討しやすい現実的な選択肢』としてAzureを選んでいます。」

### Q2. VMへのパブリックIP付与を廃止してAzure Bastionにした理由、NSG設計で工夫した点は何ですか?

**回答例**:「現行環境では管理者が固定グローバルIP経由で各サーバーに直接RDP接続しており、しかも共有の管理者アカウントが常態化していて、誰がいつどのサーバーに接続したのかという証跡が残らない状態でした。これを解決するために、まずVMには一切パブリックIPアドレスを付与しない方針にし、管理アクセスは必ずAzure Bastionという踏み台サービスを経由させることにしました。Bastion自体もAzure公式の必須ルール(HTTPS 443番の受信許可やBastionホスト間の内部通信許可など)に沿ってNSGを組んだ上で、各層のNSGでは『Bastionが配置されているサブネット(10.10.5.0/26)からの3389番ポートのみ許可』という形で管理経路を一本化しています。工夫した点は、単に許可ルールを積むだけでなく、Web層からDB層への通信を明示的にDenyするルールをあえて優先度200番などで追加している点です。既定のNSGはサブネット内の同一VNet通信を暗黙に許可してしまうため、多層防御の考え方に基づいて『本来通信してはいけない経路』を明示的に遮断することで、設定ミスや将来のルール追加時の事故を防ぐ設計にしています。」

### Q3. NSGルールの優先度(priority)の付け方に何かルールを設けましたか?

**回答例**:「基本方針として、実際に通す必要がある許可ルールを100番台の若い番号で先に定義し、多層防御のための明示的な拒否ルールをそれより大きい番号(200番台や4000番台)で後ろに配置しています。これは、NSGが番号の小さい順に評価され、最初にマッチしたルールが適用される、という評価順序の仕様を踏まえた設計です。また、Azure Bastionサブネットについては、Microsoft公式のBastion運用に必須とされる受信・送信ルール(HTTPS、GatewayManager、AzureLoadBalancer、Bastionホスト間通信など)を100番台で漏れなく定義し、最後に優先度4096番の明示的な全拒否ルールを置くことで、『許可されていない通信は必ず拒否される』という状態を目に見える形にしています。」

### Q4. コスト意識はどのように持ちましたか?具体的な工夫を教えてください。

**回答例**:「今回はポートフォリオとしての検証用途という前提を最初に置き、月額運用コストを抑制する目的でVMサイズはBシリーズ(バースト可能インスタンス。普段は低い性能で動作し、必要なときだけCPUクレジットを使って性能を引き上げられるVMシリーズ)を基本に選定しました。5台のVM合計で月額約85,000円、マネージドディスク・Bastion・バックアップ・監視・Key Vault・ネットワーク・Defender for Cloudまで含めた全体の月額概算は約168,000円になる、という内訳を積み上げで算出しています。単に安いVMを選ぶだけでなく、DBサーバーだけはデータ・ログ・tempdb用のディスクにPremium SSDを分離するなど、コストと性能要件のバランスを項目ごとに判断したことがポイントです。また、検証が終わったらリソースグループごと削除する、自動シャットダウンを設定するといった、実際に自分の財布で検証する際に必要なコスト管理の運用面まで意識してドキュメント化しました。」

### Q5. なぜBシリーズを選んだのですか?性能面のデメリットはありませんか?

**回答例**:「Bシリーズはベースライン性能を超えた分をCPUクレジットで賄う、いわゆるバースト可能インスタンスで、常時高負荷がかかり続けるワークロードには不向きというデメリットがあります。ただ、今回のシステムは実際の卸売業の受発注ピーク時間帯のように負荷が変動するワークロードを想定しており、かつポートフォリオとしての検証用途でコストを抑える制約があったため、Bシリーズを採用しました。実際の本番導入を仮定する場合は、Azure MonitorでCPU使用率の推移を継続的に観察し、CPUクレジットが慢性的に枯渇するようであれば汎用インスタンス(Dsv5シリーズなど)への切り替えを検討する、という運用上の見直し方針もあわせて設計書に明記しています。」

### Q6. バックアップ・DR設計の考え方、RPO/RTOはどう決めましたか?

**回答例**:「業務システム全体としてRPO(目標復旧時点。データがどの時点まで復旧できればよいかの目安)24時間以内、RTO(目標復旧時間。障害発生からどれくらいの時間でサービスを復旧させるかの目安)4時間以内という目標を置きました。日次のVMバックアップだけでは受発注データが最大24時間分失われるリスクがあるため、DBサーバーだけはAzure BackupのSQL Serverワークロードバックアップを使い、フルバックアップを週1回、差分バックアップを日次、そしてトランザクションログバックアップを15分間隔で取得することで、DBに関してはRPOを最大15分に抑える設計にしています。DR(災害復旧)については、可用性ゾーンの冗長化やAzure Site Recoveryによるリージョン間フェイルオーバーはコスト面から今回は見送り、その代わりにRecovery Services VaultのGeo冗長ストレージ(GRS)でバックアップデータをJapan Westへ自動レプリケーションする、という最低限の地理的保全にとどめています。これは『コスト重視の検証環境として妥当な落としどころはどこか』を自分なりに判断した結果であり、本番運用に引き上げる場合はAzure Site Recoveryの導入を追加検討する、という将来課題としても明記しています。」

### Q7. Key VaultやEntra IDをどう使い分けましたか?セキュリティ設計の全体像を教えてください。

**回答例**:「大きく2つのレイヤーで整理しています。1つ目はAzureリソースそのものの管理者権限の統制で、こちらはMicrosoft Entra IDの条件付きアクセスとMFA(多要素認証)を必須にした上でAzure RBAC(ロールベースアクセス制御)により最小権限で払い出す設計にしています。2つ目は業務アプリケーションのユーザー認証で、こちらは既存のオンプレAD DS(sanrise.local)をそのまま継続利用し、将来的にEntra Connectでハイブリッド同期してSSO基盤へ段階移行する方針としました。この2つを混同せず整理して説明できることが、ゼロトラストに近い最小権限モデルを理解しているかどうかの分かれ目だと考えています。Key Vaultについては、各VMのローカル管理者パスワードやSQL Server相当の認証情報、DBサーバーのTDE(透過的データ暗号化)証明書のバックアップなど、コードや構成ファイルに直接書いてはいけない秘密情報を一元管理する場所として位置づけ、アクセス権はAzure RBACで最小権限に絞っています。」

### Q8. これは実際に構築したものですか?それとも設計だけですか?

**回答例**:「正直にお伝えすると、これは実際の企業案件ではなく、架空の卸売業企業を題材にした設計ポートフォリオです。ただし、単なる机上の空論にならないよう、Microsoft Cloud Adoption Frameworkの命名規則に沿ったリソース名・実在するVMサイズ・実際のNSGルールの優先度や送信元/宛先まで、実務でそのまま使えるレベルの粒度で設計・ドキュメント化することにこだわりました。構築手順書(08・09番)や試験計画書(10番)まで作成しているのは、設計を『絵に描いた餅』で終わらせず、実際にAzure環境へデプロイして検証できるところまで落とし込んだことを示すためです。今後は自分のAzureサブスクリプション上で実際にこの設計を構築し、スクリーンショットや実際の動作結果をポートフォリオに追加していく予定です。」(※実際に構築済みの場合は、この回答を「実際にAzure上で構築し、Azure Bastion経由の接続やバックアップジョブの成功をポータル上で確認済みです」という体験ベースの回答に置き換えてください。)

### Q9. もし本番環境で障害が発生したら、どう対応する設計にしていますか?

**回答例**:「監視設計として、Log Analyticsワークスペース(`log-sanrise-prod-jpe`)にVMのメトリック・ログを集約し、CPU使用率が5分平均で85%を超えて10分以上継続した場合や、ディスク空き容量が10%を切った場合、Heartbeatメトリックが5分間途絶えてVMの応答が確認できない場合など、5種類のアラートルールを定義しています。特にVM応答不可の検知は重大度Sev1としてオンコール担当者へSMS・メールで即時エスカレーションする設計にしており、目視確認に頼っていた現状の課題(予兆を検知できない)を、自動検知・自動通知に置き換えることを重視しました。バックアップジョブの失敗もアラート対象にしているのは、『バックアップを取っているつもりが実は失敗していた』という、テープ運用時代にありがちだった問題を防ぐためです。」

### Q10. 実務未経験なのに、なぜここまで詳細な設計ができたのですか?

**回答例**:「実務経験がないことは事実なので、そこは正直にお伝えしています。その上で、Microsoft Learnや公式ドキュメント、Cloud Adoption Frameworkの命名規則などの一次情報を調べながら、『なぜその設計が推奨されているのか』を自分の言葉で説明できるまで理解することを意識して取り組みました。特にAzure Bastionの必須NSGルールのように、公式ドキュメントで明確に定義されている仕様については正確に踏襲しつつ、Web/AP/DB間の通信をどこまで絞り込むか、Bシリーズをどこまで採用するかといった『トレードオフを伴う判断』については、要件と制約条件を踏まえて自分なりの根拠を持って決めるようにしました。実務経験の不足は、今後現場で経験を積むことでしか埋められない部分だと理解していますが、設計の背景にある考え方を自分の言葉で説明できることは、実務未経験であっても示せる強みだと考えています。」

### Q11. このポートフォリオで一番苦労した点、工夫した点は何ですか?

**回答例**:「一番苦労したのは、Web層・AP層・DB層それぞれのNSGルールを、許可すべき通信と拒否すべき通信の両方を漏れなく洗い出すところでした。許可ルールだけを積み重ねると『動けばいい』設計になってしまいますが、多層防御という考え方を理解してからは、Web層からDB層への通信のように、本来発生してはいけない経路を明示的にDenyルールとして書き出すことを意識しました。この作業を通じて、NSGは単なる通信の許可リストではなく、『このシステムのどこからどこへ、何が流れることを想定しているか』を可視化するドキュメントでもある、ということを実感できたのが一番の学びです。」

### Q12. 今後さらに発展させるとしたら、何から着手しますか?

**回答例**:「まずは現在Bicep(Azure専用のIaCツール)による構築を前提としている設計を、GitHub ActionsによるCI/CDパイプラインに載せて、`what-if`によるデプロイ前検証やコードレビューを経てから環境が更新される流れを実装したいと考えています。その次のステップとして、Terraformへの書き換えにも挑戦し、特定クラウドに依存しないIaCの経験も積みたいです。」(詳細は5節を参照してください。)

### 6.2 アーキテクチャ図の見せ方

- **最初に全体構成図を1枚見せる**:01-architecture.mdで作成したMermaid記法の構成図(Web/AP/DB層、管理サブネット、Bastionサブネット、各層間の許可された通信経路)を、README冒頭に埋め込みます。GitHub上ではMermaid記法のコードブロック(` ```mermaid `)がそのまま図としてレンダリングされるため、画像ファイルを別途用意しなくても見た目の良い図をREADMEに直接埋め込める点が実務上のメリットです。
- **「何が許可され、何が拒否されているか」を図に書き込む**:単なるネットワーク構成図ではなく、Web→AP(8443番)、AP→DB(1433番)、Web→DB(明示的にDeny)のように、矢印に許可/拒否の情報を添えることで、04-security-design.mdの多層防御の思想が図だけで伝わるようにします。
- **CAF命名規則を図中にも反映する**:`vnet-sanrise-prod-jpe`、`snet-web-prod-jpe`のように、実際のリソース名をそのまま図中のラベルに使うことで、「命名規則を意識して設計している」ことが図を見ただけで伝わります。
- **図は詳細図と全体図の2段階で用意する**:README用には5層構成が一目で分かるシンプルな全体図、02-network-design.mdや04-security-design.md本文にはNSGルールの詳細まで書き込んだ詳細図、という形で使い分けると、読み手の負荷を上げずに情報量を確保できます。

### 6.3 スクリーンショットを追加する場合の提案

このポートフォリオを実際に自分のAzureサブスクリプション上に構築した場合は、以下のようなスクリーンショットを`screenshots/`フォルダに格納し、READMEおよび該当する設計書からリンクすることを強く推奨します。文字だけの設計書よりも、実際に動いている証拠があるポートフォリオの方が圧倒的に説得力が増します。

## 理解度チェック

**Q1. STAR形式の4つの要素とは何ですか?**
A1. Situation(状況)・Task(課題)・Action(行動)・Result(結果)の4つです。本ポートフォリオでは、Situationを株式会社サンライズ物産の背景設定、Taskを老朽化サーバーが抱える6つの課題、Actionをネットワーク・サーバー・セキュリティ・監視・バックアップ・コストの各設計プロセス、Resultを12本の設計書一式に対応付けて語ります。

**Q2. 面接で「なぜAzure Bastionを導入したのか」と聞かれたら、中心に据えるべきキーワードは何ですか?**
A2. 「VMへのパブリックIP付与の廃止」と「管理アクセスの経路の一本化・証跡の確保」です。現行環境が固定グローバルIP経由の直接RDP接続と共有管理者アカウントの常態化という課題を抱えていたことを踏まえ、Bastionを唯一の管理経路にすることでアクセス統制と監査性を高めた、という文脈で説明します。

**Q3. 求人票の「IaC(Infrastructure as Code)の経験」という要件に対して、本ポートフォリオの何を根拠に答えられますか?**
A3. 現時点ではBicepによる構築を前提とした設計・手順書(01・08・09番)を根拠に、IaCの考え方を理解して構築プロセスを設計できることを説明します。加えて、5節で挙げたTerraform化やCI/CDパイプライン化という今後の学習計画を添えることで、単発の知識でなく継続的にIaCスキルを伸ばす意欲を示せます。

**Q4. GitHubのREADMEに最低限含めるべき要素を3つ挙げてください。**
A4. 例えば「①プロジェクト概要(何を題材にした設計か)」「②アーキテクチャ図(全体構成が一目で分かる図)」「③設計書一覧(00〜12番へのリンク)」の3つが最低限必要です。これに加えて、設計のこだわり・工夫点や今後の展望を含めると、より採用担当者に刺さる構成になります。

**Q5. 「実務未経験なのに、なぜここまで詳細な設計ができたのか」と聞かれたら、どう答えるのが望ましいですか?**
A5. 実務経験がないこと自体は正直に伝えた上で、公式ドキュメントやCloud Adoption Frameworkの命名規則といった一次情報を根拠に、設計判断の理由を自分の言葉で説明できることを強みとして伝えます。丸暗記ではなく「なぜその設計にしたのか」を理解している姿勢を示すことが、実務未経験というギャップを補う最も効果的な方法です。
