# 00. 案件概要・要件定義書

**この章のポイント**

- このドキュメントパックが想定する架空クライアント「株式会社サンライズ物産」の企業概要と、老朽化した基幹システムが抱える具体的な課題を整理します。
- 本ポートフォリオを作成した目的(未経験からインフラエンジニアを目指す立場として何をアピールしたいか)を明確にします。
- 要件定義書の本体として、機能要件・非機能要件・制約条件を設計台帳(ledger)の値に基づき表形式で整理します。
- 「現状の課題」と「要件」がどう対応しているか(トレーサビリティ)を示し、設計判断の根拠を説明します。
- 実務における要件定義の進め方について、未経験者向けにコラム形式で解説します。
- 本パック全体(全12章+IaC)の構成をドキュメント一覧表として案内します。

---

## 1. このポートフォリオの目的

このドキュメントパックは、未経験からサーバー構築/インフラエンジニアへの転職・キャリアチェンジを目指す筆者が、**架空の中堅企業「株式会社サンライズ物産」を題材にした仮想案件**を通じて、Azure(マイクロソフトのクラウドサービス)を用いたインフラ設計・構築の一連の工程を実務レベルで疑似体験し、その成果を設計書という形でまとめたものです。

実務未経験者がインフラエンジニアの採用選考でよく直面する課題として、次のようなものが挙げられます。

- 資格(例:AZ-900、AZ-104など)は取得したが、「実際にシステムを設計・構築した経験」を語れる材料がない
- 個人学習で作ったAzure環境はあっても、断片的な検証止まりで「なぜその設計にしたのか」を説明できない
- 要件定義から設計・構築・運用まで、一連の工程を通しで経験したことがない

そこで本パックでは、あえて**実在しそうな企業の背景・課題・要件を設定**し、そこから逆算する形でネットワーク構成、サーバー構成、セキュリティ設計、監視設計、バックアップ/DR(Disaster Recovery:災害復旧、※詳しくは用語集(11-glossary.md)を参照)設計、コスト試算までを一貫して作成しました。単なる技術要素の寄せ集めではなく、「顧客の課題 → 要件 → 設計判断とその理由 → 構築 → 運用」という実務の流れを再現することで、以下をアピールすることを目的としています。

1. **要件定義から運用まで通しで設計できる基礎力があること**
2. **ゼロトラスト(社内外を問わずすべての通信を信用せず都度検証するセキュリティの考え方、※詳しくは用語集を参照)に近い最小権限設計や、CAF(Cloud Adoption Framework、マイクロソフトが提唱するクラウド導入の標準的な指針・命名規則、※詳しくは用語集を参照)準拠のリソース命名など、実務で評価される設計作法を理解していること**
3. **「なぜこの構成にしたのか」を自分の言葉で説明できること**(採用面接でよく問われる「設計の意図」に答えられる状態を作ること)

なお、本パックに登場する企業名・人物・数値等はすべて学習目的で作成した架空の設定であり、実在の企業・団体とは一切関係ありません。

## 2. 案件概要

### 2.1 クライアント企業プロフィール

| 項目 | 内容 |
|---|---|
| 企業名 | 株式会社サンライズ物産(架空企業) |
| 業種 | 卸売業(加工食品・日用雑貨卸売) |
| 事業内容 | 加工食品・日用雑貨を中心に、全国のスーパーマーケット・ドラッグストアへの卸売を行う |
| 設立 | 1978年創業 |
| 従業員数 | 約182名 |

### 2.2 現行システムの背景

株式会社サンライズ物産では、受発注・在庫管理システムを2009年に自社データセンター内の物理サーバー(Windows Server 2012 R2)上に構築し、Web/AP/DB(それぞれWebサーバー/アプリケーションサーバー/データベースサーバーの略。※詳しくは用語集を参照)の3層構成で長年運用してきました。しかし、対象サーバーは導入から10年以上が経過し、以下のような状況に至っています。

- ハードウェア保守契約が**2026年9月末で終了予定**であり、故障時の交換部品調達・修理対応ができなくなる
- OS(Windows Server 2012 R2)はメーカーサポートがすでに終了しており、新たに発見される脆弱性に対してセキュリティパッチを適用できない状態が続いている
- サーバー管理者はVPN(Virtual Private Network、インターネット上に構築する仮想的な専用線。※詳しくは用語集を参照)経由で各サーバーへ直接RDP(Remote Desktop Protocol、Windowsのリモートデスクトップ接続に使われる通信プロトコル。※詳しくは用語集を参照)接続しており、アクセス管理・操作証跡の管理が担当者個人のノウハウに依存(属人化)している
- バックアップは磁気テープによる手動運用であり、リストア(復元)検証も実施されていないため、いざという時に本当に復旧できるかが確認できていない

これらの状況から、事業継続性(BCP:Business Continuity Plan、事業継続計画。※詳しくは用語集を参照)およびセキュリティの両面でリスクが高まっており、ハードウェア保守契約の終了というタイムリミットを機に、基幹システムの刷新が経営課題として浮上しました。

### 2.3 現状の課題(As-Is)

現行システムが抱える課題を整理すると、以下の6点に集約されます。

| No. | 課題領域 | 課題の内容 |
|---|---|---|
| 1 | ハードウェア老朽化 | 基幹サーバー(受発注・在庫管理)のハードウェア保守契約が2026年9月に終了予定で、更新時期を迎えている |
| 2 | OSサポート切れ | OSがWindows Server 2012 R2でメーカーサポートが終了しており、脆弱性対応ができない状態が続いている |
| 3 | 事業継続性(BCP) | 自社データセンターの単一拠点運用のため、地震・水害等の災害時における事業継続対策が不十分である |
| 4 | アクセス統制・監査 | サーバー管理者が固定グローバルIP経由でVMへ直接RDP接続しており、共有の管理者アカウントも常態化していてアクセス統制・監査ログが不十分である |
| 5 | 監視体制 | サーバー監視が担当者の目視確認中心であり、CPU/ディスク逼迫や障害の予兆を早期に検知できていない |
| 6 | バックアップ・DR | バックアップが磁気テープによる手動運用であり、リストア検証やDR訓練が実施できておらず復旧の実効性が担保されていない |

### 2.4 プロジェクトのゴール

老朽化した基幹サーバーの更新時期に合わせ、受発注・在庫管理システムをAzure(IaaS:Infrastructure as a Service、仮想マシン等のインフラをサービスとして利用する形態。※詳しくは用語集を参照)中心に**リフト&シフト**(既存システムをほぼそのままの構成でクラウドへ移行する手法。※詳しくは用語集を参照)し、以下を実現することを本プロジェクトのゴールとします。

- 可用性・セキュリティ・運用性の向上
- VMへのパブリックIP付与を廃止し、Azure Bastion(踏み台サーバー機能をマネージドサービスとして提供する仕組み。※詳しくは用語集を参照)経由の統制された管理アクセスへの切り替え
- Key Vault(秘密情報を安全に一元管理するサービス。※詳しくは用語集を参照)とMicrosoft Entra ID(旧Azure AD。マイクロソフトのクラウドID管理サービス。※詳しくは用語集を参照)を活用した、ゼロトラストに近い最小権限のセキュリティモデルの確立
- Log Analytics(ログ・メトリックを収集し分析するAzureのサービス。※詳しくは用語集を参照)による予兆監視と、Recovery Services Vault(Azure Backupのバックアップデータを保管する管理単位。※詳しくは用語集を参照)による自動バックアップ体制の整備
- 将来的なPaaS(Platform as a Service。※詳しくは用語集を参照)化・DX(デジタルトランスフォーメーション)推進の足がかりづくり

## 3. 要件定義

要件定義とは、「これから作るシステムが満たすべき条件」を、発注者(クライアント)と開発・構築側の双方が合意できる形で明文化する工程です。本章では、株式会社サンライズ物産の現状課題(2.3節)を踏まえ、機能要件・非機能要件・制約条件の3つに分類して整理します。

### 3.1 機能要件

機能要件とは、「システムが実現すべき業務上の機能」を指します。

| No. | 機能要件 |
|---|---|
| F-01 | 既存の受発注・在庫管理業務アプリケーション(Web/AP/DBの3層構成)をAzure VM上へリフト&シフトする |
| F-02 | 社内AD DS/DNS基盤をAzure上に拡張し、オンプレミスADとのハイブリッド構成(将来のEntra Connect同期を含む)を実現する |
| F-03 | 見積書・納品書等の帳票や部門共有データを格納するファイルサーバーをAzure上に提供する |
| F-04 | 社内ユーザーが従来と同様にイントラネット経由で受発注・在庫管理システムの画面にアクセスできること |

- **AD DS**(Active Directory Domain Services):Windows環境におけるユーザー・コンピューターの認証や管理を行うディレクトリサービス。※詳しくは用語集を参照
- **DNS**(Domain Name System):ドメイン名とIPアドレスを紐づける名前解決の仕組み。※詳しくは用語集を参照
- **Entra Connect**:オンプレミスのAD DSとMicrosoft Entra IDを同期させるためのツール。※詳しくは用語集を参照

### 3.2 非機能要件

非機能要件とは、「性能・セキュリティ・可用性・運用性」など、機能そのものではなく品質やシステムの特性に関わる要件を指します。実務では、機能要件よりも非機能要件のすり合わせ不足がトラブルの原因になりやすいため、特に丁寧に定義します。

| No. | 分類 | 非機能要件 |
|---|---|---|
| NF-01 | アクセス統制 | サーバー管理者はAzure Bastion経由でのみ各VMに接続でき、VMには一切パブリックIPアドレスを付与しない |
| NF-02 | ネットワークセキュリティ | Web層/AP層/DB層間の通信を業務上必要な最小限のポート・プロトコルのみに限定する多層防御(ゼロトラストに近い最小権限)構成とする |
| NF-03 | 可用性・DR | RPO 24時間以内(DBサーバーはトランザクションログバックアップにより15分以内)、RTO 4時間以内を満たすバックアップ・DR体制を整備する |
| NF-04 | 監視 | CPU使用率・ディスク空き容量・VM可用性の異常を自動検知し、運用担当者へ通知できる監視体制を整備する |
| NF-05 | 秘密情報管理 | SQL接続文字列やサービスアカウントのパスワード等の秘密情報は、コードや構成ファイルに直接記載せずAzure Key Vaultで一元管理する |
| NF-06 | ID・認証基盤 | 認証はMicrosoft Entra ID(旧Azure AD)と社内AD DSを組み合わせたハイブリッドID基盤とする |

- **RPO**(Recovery Point Objective:目標復旧時点):障害発生時に「どの時点のデータまで復旧できればよいか」を示す指標。値が小さいほどデータ損失の許容範囲が狭く、厳しい要件になります。※詳しくは用語集を参照
- **RTO**(Recovery Time Objective:目標復旧時間):障害発生から「どのくらいの時間でシステムを復旧させるか」を示す指標。※詳しくは用語集を参照
- RPO/RTOの具体的な数値と、それを実現するバックアップ方式の詳細は「06-backup-dr.md」で解説します。

### 3.3 制約条件

制約条件とは、予算・期間・技術方針など、設計の自由度を制限する前提条件です。

| No. | 分類 | 制約条件 |
|---|---|---|
| C-01 | コスト | ポートフォリオとしての検証用途のため、月額運用コストを抑制する目的でVMサイズはBシリーズ(バースト可能インスタンス、※詳しくは用語集を参照)を基本とする |
| C-02 | リージョン | 利用リージョンはJapan East(japaneast)単一リージョンに限定する |
| C-03 | 命名規則 | リソース名はMicrosoft Cloud Adoption Framework(CAF)の略語規則(rg-, vnet-, snet-, nsg-, vm-, kv-, log-, rsv- 等)に準拠する |
| C-04 | 移行方針 | 既存業務アプリケーションの改修は最小限とし、原則としてOS・ミドルウェアをWindows Server 2022へ載せ替えるのみに留める(アプリケーション自体の再設計・PaaS化は本フェーズの対象外とする) |

> **補足**:C-02について、本来であればBCP強化のためにリージョン間の冗長化(マルチリージョン構成)も検討対象となりますが、本ポートフォリオではコストと学習範囲のバランスを考慮し、単一リージョン+バックアップのGRS(Geo冗長ストレージ)による地理的保全に留めています。将来フェーズでの拡張方針は「06-backup-dr.md」で扱います。

### 3.4 課題と要件のトレーサビリティ(なぜこの設計にしたのか)

要件定義において重要なのは、要件が「思いつき」ではなく、現状課題から論理的に導かれていることです。以下に、2.3節で整理した現状課題と、それに対応する要件・後続章での設計対応をまとめます。

| 現状課題(As-Is) | 対応する要件 | 設計での対応(概要) | 詳細章 |
|---|---|---|---|
| ① ハードウェア保守契約終了(2026年9月) | F-01 | Azure VMへのリフト&シフトによりハードウェア資産を保有しないIaaS化 | 01-architecture.md, 03-server-design.md |
| ② OSサポート切れ(Windows Server 2012 R2) | C-04 | Windows Server 2022へ載せ替え、以降はAzure側でOSパッチ適用サイクルを継続運用 | 03-server-design.md, 05-operations-monitoring.md |
| ③ 単一拠点運用によるBCP不足 | NF-03 | Recovery Services VaultのGRSによるJapan Westへの自動レプリケーションと簡易DR手順の整備 | 06-backup-dr.md |
| ④ 属人化した直接RDP接続・共有管理者アカウント | NF-01, NF-02, NF-06 | Azure Bastion経由アクセスへの一本化(パブリックIP廃止)、Entra IDによるRBACとMFA必須化 | 04-security-design.md |
| ⑤ 目視中心の監視体制 | NF-04 | Log Analyticsワークスペースへのログ集約とアラートルールによる自動検知・通知 | 05-operations-monitoring.md |
| ⑥ 磁気テープ手動バックアップ・リストア未検証 | NF-03 | Recovery Services Vaultによる自動バックアップとポリシー化されたリストア手順の整備 | 06-backup-dr.md |

このように、「課題 → 要件 → 設計」を一直線につなげておくことで、設計書のどの記述にも「なぜそうしたのか」という根拠を示せるようにしています。これは実務の要件定義書でも同様に重視される考え方であり、次章以降の各設計書でも、個々の設計判断の理由を明記する方針で統一しています。

## 4. コラム:実務における要件定義の進め方

> **このコラムのねらい**:未経験者向けに、実務での要件定義がどのような流れで進むのか、なぜそれが重要なのかを解説します。

インフラ構築の実務経験がないと、「要件定義書は最初に一度作って終わり」という印象を持ちがちですが、実際には次のような反復的なプロセスで進みます。

1. **現状分析(As-Is整理)**
   顧客への ヒアリングや既存システムの構成調査を通じて、現状の課題を洗い出します。本章2.3節のように、課題を箇条書きで具体的に言語化することがスタート地点です。「なんとなく古いから直したい」ではなく、「ハードウェア保守契約がいつ切れるのか」「OSサポート切れによる具体的なリスクは何か」まで掘り下げることが重要です。

2. **要件の分類・整理**
   洗い出した課題をもとに、「機能要件」「非機能要件」「制約条件」に分類します。特に非機能要件(可用性・セキュリティ・性能・運用性など)は顧客側が明確に言語化できていないことが多く、エンジニア側から具体的な数値(RPO/RTOなど)まで踏み込んで提案・合意形成する姿勢が求められます。

3. **要件の優先順位付けとトレードオフの調整**
   予算・期間・技術的制約の中で、すべての要望を満たせるとは限りません。本案件でも「コスト抑制のためBシリーズVMを採用する」代わりに「性能面のマージンは小さくなる」といったトレードオフが発生しています。こうした判断の理由を明文化しておくことが、後工程での手戻りや認識齟齬を防ぎます。

4. **要件定義書としての合意形成**
   整理した要件を文書化し、顧客(またはプロジェクト関係者)と合意を取ります。この合意プロセスを経ずに設計・構築を進めてしまうと、「言った・言わない」のトラブルや、完成後の手戻りにつながります。

5. **後続工程(設計・構築・テスト・運用)へのトレーサビリティ確保**
   要件定義書の内容は、以降の基本設計・詳細設計・構築・テストの各工程で「この設計は、どの要件を満たすためのものか」を常に参照される起点になります。本パックの3.4節で示したトレーサビリティ表のような形で、要件と設計の対応関係を明示しておくことは、実務でも品質管理や仕様変更時の影響範囲特定に直結する重要な習慣です。

未経験の方が学習を進める際は、技術要素(VMの立て方やネットワークの組み方)の習得に意識が向きがちですが、実務で評価されるのは「なぜその技術要素を選んだのか」を要件から説明できる力です。本パックでは、あえてこの要件定義の工程を最初の章に置き、以降のすべての設計判断がこの要件に紐づく構成としています。

## 理解度チェック

**Q1. 株式会社サンライズ物産の現行システムが抱える課題のうち、今回のプロジェクトの直接的な発端(タイムリミット)となっているものは何ですか?**
A1. 基幹サーバーのハードウェア保守契約が2026年9月末で終了予定であること。あわせてOS(Windows Server 2012 R2)のサポートも終了しており、セキュリティ上のリスクが放置できない状態になっていることが背景です。

**Q2. 非機能要件と機能要件の違いを一言で説明してください。**
A2. 機能要件は「システムが実現すべき業務上の機能」(例:受発注・在庫管理業務ができること)を指し、非機能要件は「性能・セキュリティ・可用性・運用性」など機能以外の品質特性(例:RPO/RTO、アクセス統制の方式)を指します。

**Q3. 本プロジェクトでVMサイズに主にBシリーズを採用している理由は何ですか?**
A3. 本案件がポートフォリオとしての検証用途であり、月額運用コストを抑制する必要があるためです(制約条件C-01)。Bシリーズはバースト可能インスタンスであり、常時高負荷でない用途において費用対効果に優れます。

**Q4. RPOとRTOの違いを説明してください。**
A4. RPO(目標復旧時点)は「障害発生時にどの時点のデータまで復旧できればよいか」を示す指標で、値が小さいほどデータ損失の許容範囲が狭くなります。RTO(目標復旧時間)は「障害発生からどのくらいの時間でシステムを復旧させるか」を示す指標です。本案件ではRPO 24時間以内(DBはログバックアップにより15分以内)、RTO 4時間以内を要件としています。

**Q5. 「課題 → 要件 → 設計」のトレーサビリティを明示することが実務でなぜ重要ですか?**
A5. 各設計判断の根拠を明確にすることで、仕様変更が発生した際の影響範囲の特定や、レビュー時の妥当性確認が容易になるためです。また、「なぜその設計にしたのか」を説明できることは、実務でもポートフォリオの評価でも重視されるポイントです。
