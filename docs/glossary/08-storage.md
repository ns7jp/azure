# 8. ストレージとディスク

[用語集トップ](../11-azure-glossary.md) ・ 前: [7. コンピューティング(仮想マシン)](07-compute.md) ・ 次: [9. ID・アクセス管理とセキュリティ](09-identity-security.md)

Azureの保存領域は、大きく2種類に分かれます。1つはVMに取り付けて使う**ディスク**、もう1つはVMとは独立して単体で使える**ストレージアカウント**系のサービスです。この2つを混同すると「VMを消したらファイルも消えた」「ディスクにBlobを置こうとした」といった事故につながります。サーバー構築エンジニアは、Azure側でディスクを足したあとにLinux側で何をするかまで通しで言えることが求められます。

## 8.2 用語解説

### 8.2.1 マネージドディスク(Managed Disk、管理ディスク)

- **一言でいうと**: ディスクの置き場所や壊れにくさの管理をAzureに任せられる、VM用の仮想ディスクです。
- **たとえると**: 賃貸マンションです。建物の耐震や配管の面倒はオーナー側が見てくれ、住人は部屋の使い方だけを考えます。
- **もう少し詳しく**: Azureのディスクは1つのリソースとして独立して存在し、VMに取り付けたり外したりできます。冗長化や既定の暗号化はAzure側が持つため、利用者は「種類」と「容量」を決めるだけで済みます。VMを削除してもディスクを残す設定にでき、逆に残ったディスクは使っていなくても課金対象になります。
- **この案件では**: Linux VMのOSディスクを`infra/modules/workload.bicep`で`StandardSSD_LRS`、`diskSizeGB: 30`と宣言しています。
- **覚え方**: manageは「管理する、面倒を見る」。マネージドと付いたサービスは**面倒な部分をAzureが持つ**という目印です。
- **つまずきポイント**: VMを消せばディスク代も止まると思いがちですが、実際は取り残されたディスクが課金され続けることがあります。削除時はディスクの残骸も確認します。
- **関連**: OSディスク / データディスク / ディスクの種類

### 8.2.2 OSディスク(OS Disk)

- **一言でいうと**: OS本体とシステム領域が入っている、VMに必ず1本だけ付くディスクです。
- **たとえると**: パソコンのCドライブです。これがないとそもそも起動しません。
- **もう少し詳しく**: VMを作るとき選んだイメージ(Ubuntuなどの雛形)がOSディスクへ書き込まれ、そこから起動します。Linuxでは通常`/`(ルート)としてマウントされています。容量はイメージの既定値より大きく指定でき、あとから拡張もできますが、縮小はできません。OS障害の調査で、OSディスクを別のVMに付け替えて中身を読む「復旧用の付け替え」もよく使う手です。
- **この案件では**: Ubuntuイメージから作成した1本のOSディスクだけで動く構成です。
- **覚え方**: **VMの頭はOSディスク、体はデータディスク**。頭は1つしか付けられない、と覚えます。
- **つまずきポイント**: OSディスクに業務データを置いても動きますが、拡張や退避が絡む場面で不自由になります。データは別ディスクへ分けるのが原則です。
- **関連**: データディスク / 一時ディスク / VMイメージ

### 8.2.3 データディスク(Data Disk)

- **一言でいうと**: 業務データやログを置くために、必要な数だけ後から追加できるディスクです。
- **たとえると**: 机の横に足す引き出しです。中身が増えたら引き出しを増やし、要らなくなれば外します。
- **もう少し詳しく**: VMへ取り付けると、OSからは新しいブロックデバイスとして見えます。取り付けただけでは使えず、Linux側でフォーマットとマウントが必要です。同時に取り付けられる本数はVMサイズごとに上限があるため、大きな容量が必要ならVMサイズの選定も一緒に検討します。OSとデータを分けておくと、OS入れ替え時にデータディスクを付け替えるだけで済みます。
- **この案件では**: 基礎編の構成一覧にデータディスクは含まれておらず、Nginxの配信ファイルもOSディスク上にあります。
- **覚え方**: **OSは建て替え、データは引っ越し**。分けておけば片方だけ入れ替えられる、という動作イメージで覚えます。
- **つまずきポイント**: Azureポータルやコマンドで追加すれば使えると思いがちですが、実際はOS側の作業が終わるまで書き込めません。
- **関連**: OSディスク / Linuxでのディスク追加手順 / ファイルシステム

### 8.2.4 一時ディスク(Temporary Disk、リソースディスク、temp / エフェメラル)

- **一言でいうと**: VMが動いているホストの内蔵ストレージを借りた、消えることが前提の作業領域です。
- **たとえると**: 新幹線の座席テーブルです。乗車中は物を置けますが、降りたら何も残せません。
- **もう少し詳しく**: Linuxでは通常`/mnt`にマウントされます。VMの停止(割り当て解除)、サイズ変更、ホスト側のメンテナンスで**中身は失われます**。スワップや一時ファイルの置き場には向きますが、業務データを置いてはいけません。VMサイズによっては一時ディスクを持たないものもあるため、あることを前提にした設計は避けます。
- **覚え方**: 一時ディスク=`/mnt`=**マウントできるが、残らない**。「いちじ」の「じ」は「じきに消える」と結び付けます。
- **つまずきポイント**: 名前が似た「エフェメラルOSディスク」はOSディスク自体をホスト側の領域に置く別機能で、こちらも再作成で中身が失われます。どちらも「ホストに置いた分は残らない」と押さえます。
- **関連**: OSディスク / データディスク / VMサイズ

### 8.2.5 ディスクの種類(Standard HDD / Standard SSD / Premium SSD / Ultra Disk)

- **一言でいうと**: 速さと安定性、そしてコストが違う4段階の選択肢で、用途に合わせて選びます。
- **たとえると**: 鉄道の各駅停車、快速、特急、新幹線です。目的地は同じでも、速さと運賃が変わります。
- **もう少し詳しく**: Standard HDDは磁気ディスク基盤で最も安く、検証や低頻度アクセス向けです。Standard SSDはSSD基盤で、軽い本番用途や開発に向きます。Premium SSDは安定した性能が必要な本番向けで、利用にはPremium対応のVMサイズが必要です。Ultra Diskは最高性能帯で、リージョンやVMサイズなどの条件があり、データディスクとしてのみ使えます。ほかにPremium SSD v2もあります。
- **この案件では**: 学習コストを抑えつつSSDの安定性を取る判断として`StandardSSD_LRS`を選んでいます。
- **覚え方**: **HDD → SSD → Premium → Ultra**の4段の階段。上に行くほど速く高い、と1本の線で覚えます。
- **つまずきポイント**: 上位を選べば必ず速いと思いがちですが、実際はVMサイズ側の上限で頭を打つことがあります。ディスクとVMは対で選びます。
- **関連**: IOPSとスループット / マネージドディスク / VMサイズ

### 8.2.6 IOPSとスループット(IOPS / Throughput)

- **一言でいうと**: ディスクの性能を、1秒あたりの処理回数と1秒あたりのデータ量という2つの角度で表した指標です。
- **たとえると**: 宅配便です。IOPSは1日に何件配れるか、スループットは合計で何トン運べるかにあたります。
- **もう少し詳しく**: IOPSはInput/Output Per Secondの略で、小さな読み書きが大量に発生するデータベースなどで効きます。スループットは`MB/s`で表され、大きなファイルのコピーやバックアップで効きます。実際に出る性能は**ディスク側の上限とVMサイズ側の上限の小さいほう**で決まります。Standard系やPremium SSDは容量の段階が上がると上限も上がるため、容量を増やすと速くなる場合があります。
- **覚え方**: **IOPSは回数、スループットは量**。「件数か、トン数か」と宅配便で言い換えます。
- **つまずきポイント**: 遅い原因をディスクだけに求めがちですが、実際はVMサイズの上限やCPU待ちが原因のこともあります。両方の上限を並べて確認します。
- **関連**: ディスクの種類 / VMサイズ / メトリック

### 8.2.7 ディスクスナップショット(Disk Snapshot)

- **一言でいうと**: ある時点のディスクの中身を丸ごと写し取った、読み取り専用のコピーです。
- **たとえると**: 健康診断の記録です。その日の状態を1枚に残し、あとから見比べたり、そこへ戻す判断材料にします。
- **もう少し詳しく**: スナップショットはディスクとは別のリソースとして保存され、そこから新しいディスクを作ってVMへ取り付けられます。変更差分だけを保存する増分方式も選べます。作業前に取っておけば、失敗時の切り戻しが現実的になります。ただし複数ディスクをまたぐ整合性やスケジュール管理は自分で面倒を見る必要があり、業務のバックアップにはAzure Backupのような専用の仕組みを使います。
- **この案件では**: バックアップは未実装の発展課題です。まず手作業の切り戻し手段としてスナップショットを理解しておくと、次の課題につながります。
- **覚え方**: snap(パチッと)+shot(撮る)=**その瞬間の1枚**。動画ではなく写真だから、取ったあとの変更は写らない、と覚えます。
- **つまずきポイント**: スナップショットがあればバックアップは済んだと思いがちですが、実際は世代管理も復元試験もありません。取得しただけで安心しないことが大事です。
- **関連**: マネージドディスク / Azure Backup / 冗長構成

### 8.2.8 ディスクの暗号化(SSE / Azure Disk Encryption、ADE)

- **一言でいうと**: 保存されているデータを、正しい鍵を持たない相手には読めない形に変換しておく仕組みです。
- **たとえると**: 金庫と、金庫の鍵をどこで管理するかの話です。中身を守るだけでなく、鍵の持ち主を決めることが本題です。
- **もう少し詳しく**: SSEはServer Side Encryptionの略で、マネージドディスクは保存時に既定で暗号化されています。鍵はプラットフォーム管理キーが既定で、Key Vaultに置いた顧客管理キーへ切り替えることもできます。ADE(Azure Disk Encryption)はゲストOSの機能を使う暗号化で、Linuxではdm-crypt、WindowsではBitLockerを利用します。SSEは外側、ADEはOSの内側という役割の違いです。
- **覚え方**: **SSEはServer Side=外から自動、ADEはOSの中から自前**。「外は既定、中は追加」と対比で覚えます。
- **つまずきポイント**: 暗号化を有効にしていないから丸見えだと思いがちですが、実際はマネージドディスクの保存時暗号化は既定で有効です。論点は「有効か」ではなく「鍵を誰が持つか」です。
- **関連**: Key Vault / マネージドディスク / 転送時の暗号化

### 8.2.9 Linuxでのディスク追加手順(パーティション、フォーマット、マウント)

- **一言でいうと**: 追加したディスクをLinuxで使えるようにするまでの、認識から自動マウント登録までの一連の作業です。
- **たとえると**: 空き地に建物を建てる流れです。土地を確認し、区画を切り、建物を建て、住所を割り当て、台帳に登録します。
- **もう少し詳しく**: 流れは5段です。1)`lsblk`で新しいデバイスを確認、2)`parted`や`fdisk`で区画を作成、3)`mkfs.ext4`や`mkfs.xfs`でフォーマット、4)`mkdir`でマウント先を作り`mount`で接続、5)`blkid`で確認したUUIDを`/etc/fstab`へ書き、`mount -a`と`df -h`で検証します。デバイス名は接続順や再起動で変わることがあるため、必ず`lsblk`で現物を確認してから作業します。
- **覚え方**: **見る、切る、作る、つける、書く**。この5語を口に出して覚えれば、手順書がなくても筋道を思い出せます。
- **つまずきポイント**: `mount`しただけで完了と思いがちですが、実際は再起動でマウントが消えます。`/etc/fstab`への登録までが1セットです。
- **関連**: データディスク / ファイルシステム / `/etc/fstab`

### 8.2.10 ファイルシステム(ext4 / XFS)と`/etc/fstab`

- **一言でいうと**: ディスクの中身をどう並べて記録するかの規格と、どこに何を自動でマウントするかを書いた設定表です。
- **たとえると**: 図書館の分類ルールと、書架の配置図です。並べ方の規格が決まり、配置図があるから毎朝同じ棚に本が並びます。
- **もう少し詳しく**: ext4はUbuntuなどで広く使われる既定寄りの選択肢、XFSは大容量や並列I/Oに強く、RHEL系で既定に採用されています。XFSは拡張(`xfs_growfs`)はできますが縮小はできません。`/etc/fstab`は1行6項目で、デバイス指定、マウント先、種類、オプション、dump、起動時チェック順を書きます。デバイス指定はUUIDを使うのが安全で、記述を誤ると起動に失敗することがあるため、`nofail`オプションの併用も検討します。
- **この案件では**: OSはUbuntuのため、追加ディスクを扱う場合もext4が素直な選択になります。
- **覚え方**: fstabは**f**ile**s**ystem+**tab**le=「ファイルシステムの表」。表だから1行=1マウント、と形で覚えます。
- **つまずきポイント**: `/dev/sdc1`のように書けば十分と思いがちですが、実際はデバイス名が入れ替わって別のディスクをマウントする事故が起きます。UUIDで書きます。
- **関連**: Linuxでのディスク追加手順 / データディスク / OSディスク

### 8.2.11 ストレージアカウント(Storage Account)

- **一言でいうと**: Blobやファイル共有などを内側にまとめて置ける、VMとは独立した保存サービスの入れ物です。
- **たとえると**: マンション1棟です。棟の名前は世の中で一意で、その中に部屋(コンテナーや共有)が並びます。
- **もう少し詳しく**: 1つのアカウントの中に、Blob、ファイル共有、キュー、テーブルといった保存の種類を持てます。アカウント名はAzure全体で一意である必要があり、そのままアクセス用のホスト名の一部になります。冗長構成、アクセス層の既定値、ネットワーク制限、暗号化の鍵といった設定はアカウント単位で決まるため、用途が違うデータは別アカウントに分ける設計もよく取られます。
- **覚え方**: **棟(アカウント)→部屋(コンテナー)→荷物(Blob)**の3階層。住所を上から下へたどる形で覚えます。
- **つまずきポイント**: VMのディスクと同じものだと思いがちですが、実際はVMがなくても存在し、HTTPS越しに使う別サービスです。
- **関連**: Blob Storage / Azure Files / データの冗長構成

### 8.2.12 Blob Storage(コンテナーとBlob)

- **一言でいうと**: 画像でもログでもzipでも、種類を問わずファイルを置けるクラウド上の巨大な倉庫です。
- **たとえると**: 宅配の倉庫です。棚(コンテナー)に段ボール(Blob)を積み、伝票番号(名前)で1個ずつ取り出します。
- **もう少し詳しく**: BlobはBinary Large OBjectの略で、ストレージアカウントの中にコンテナーを作り、その中へBlobを置きます。コンテナーの中は本当は平らな並びで、名前に含めた`/`がフォルダのように見えているだけです。用途別にブロックBlob、追加Blob、ページBlobがあり、通常のファイルやバックアップはブロックBlobを使います。公開設定は既定で非公開で、匿名アクセスは明示的に許可しない限り効きません。
- **覚え方**: **B-L-OB=Binary Large OBject**。「大きなかたまり」なので中身の形式を問わない、と語源から意味を引き出します。
- **つまずきポイント**: フォルダを作って整理していると思いがちですが、実際は名前の一部にすぎません。命名規則が実質のフォルダ設計になります。
- **関連**: ストレージアカウント / アクセス層 / SASトークン

### 8.2.13 アクセス層(Access Tier、ホット / クール / アーカイブ)

- **一言でいうと**: 取り出す頻度に応じて、Blobの保存コストと取り出しコストの比率を切り替える段階設定です。
- **たとえると**: 家の中の置き場所です。よく使う物は手元の棚、季節物は押し入れ、思い出の箱は貸倉庫へ預けます。
- **もう少し詳しく**: ホットは頻繁に読む前提で保存料が高め、取り出しは安めです。クールは逆で、保存料が安く取り出しは高めになります。アーカイブは最も安く保存できますが**オフライン**で、読むにはリハイドレート(オンラインへ戻す操作)が必要で時間がかかります。クールやアーカイブには最低保存期間があり、早く削除すると早期削除の扱いになります。ライフサイクル管理ルールで、一定日数後に自動で層を下げる運用が定番です。
- **覚え方**: **温度が下がるほど安く、遅い**。ホット、クール、アーカイブを温度計の目盛りとして一列に並べて覚えます。
- **つまずきポイント**: アーカイブでもダウンロードできると思いがちですが、実際はリハイドレートしないと読めません。復元に時間の余裕がない用途では選びません。
- **関連**: Blob Storage / ストレージアカウント / コスト管理

### 8.2.14 Azure Files(SMBファイル共有)

- **一言でいうと**: Windowsのネットワークドライブと同じ感覚で複数台から共有できる、クラウド上のファイル共有です。
- **たとえると**: 会社の共有フォルダをそのままクラウドへ移したものです。部署の全員が同じパスを見に行けます。
- **もう少し詳しく**: ストレージアカウント内にファイル共有を作り、SMBプロトコル(TCP 445番)でマウントします。Linuxからも`cifs`でマウントでき、NFSに対応したオプションもあります。認証はストレージアカウントキーのほか、ディレクトリサービスと連携したID認証も選べます。標準とPremiumの性能帯があり、複数VMから同じデータを読み書きしたい場合の第一候補になります。
- **覚え方**: **Blobは倉庫、Filesは共有フォルダ**。アプリからAPIで置くならBlob、OSからパスで開くならFiles、と入口の違いで覚えます。
- **つまずきポイント**: どこからでもマウントできると思いがちですが、実際はTCP 445番の外向き通信が事業者やファイアウォールで遮断されていて社外から繋がらない例があります。
- **関連**: ストレージアカウント / Blob Storage / ストレージのネットワーク制限

### 8.2.15 データの冗長構成(LRS / ZRS / GRS / RA-GRS)

- **一言でいうと**: データのコピーを何個作り、どのくらい離れた場所に置くかを決める選択肢です。
- **たとえると**: 大事な書類の控えをどこに置くかです。同じ部屋か、別の建物か、別の都市かで、耐えられる災害の規模が変わります。
- **もう少し詳しく**: LRSは同一リージョン内の1か所で3つのコピーを保持します。ZRSは同一リージョン内の3つの可用性ゾーンへ分散し、データセンター単位の障害に耐えます。GRSはLRSに加えて離れたペアリージョンへ非同期で複製し、合計6つのコピーになります。RA-GRSはGRSの複製先を読み取り専用で参照できるようにしたものです。ペアリージョンは`japaneast`なら西日本にあたります。
- **この案件では**: OSディスクの指定`StandardSSD_LRS`の末尾`LRS`がこの冗長構成を表しています。用語を知っていれば、SKU名から冗長性まで読み取れます。
- **覚え方**: 頭文字を分解します。**L=Local(同じ場所)、Z=Zone(ゾーン分散)、G=Geo(地理的に遠く)、RA=Read-Access(読める)、S=Storage**。距離が伸びる順にL→Z→Gと並べます。
- **つまずきポイント**: GRSなら複製先をすぐ読めると思いがちですが、実際は読み取りにはRA-GRSが必要です。GRSのままでは障害時のフェールオーバー操作が前提になります。
- **関連**: ストレージアカウント / リージョンとペアリージョン / 可用性ゾーン

### 8.2.16 SASトークン(SAS、Shared Access Signature、共有アクセス署名)

- **一言でいうと**: 権限と期限を絞ったうえで、URLの形で一時的にアクセスを許可する引換券です。
- **たとえると**: 期限付きの合鍵です。玄関の鍵そのものを渡さず、今日だけ開く鍵を貸します。
- **もう少し詳しく**: 対象のリソース、読み取りや書き込みといった権限、開始と失効の時刻、許可するIP範囲やプロトコルを署名付きのクエリ文字列として埋め込みます。アカウントキーを配らずに外部へファイルを渡せるのが利点です。一方でURLを持つ人は誰でも使えるため、失効時刻は必要最小限にし、共有アクセスポリシーを使って後から失効できる形にしておくのが安全です。
- **覚え方**: **S=Shared(共有)、A=Access(アクセス)、S=Signature(署名)**。「署名した合鍵」と読み替えると、鍵本体ではないことが腹に落ちます。
- **つまずきポイント**: 発行したSASは消せると思いがちですが、実際はポリシーに紐付けていない場合、キーを再生成するまで有効なままです。
- **関連**: ストレージアカウント / Blob Storage / アクセスキー

### 8.2.17 ストレージのネットワーク制限(ファイアウォール / プライベートエンドポイント)

- **一言でいうと**: 鍵を持っているかどうかの前に、どの経路からのアクセスを通すかを絞る設定です。
- **たとえると**: マンションのオートロックです。部屋の鍵を持っていても、まず建物の入口を通れなければ辿り着けません。
- **もう少し詳しく**: ストレージアカウントは既定でインターネット経由の公開エンドポイントを持ちます。ファイアウォール設定で、許可したIP範囲や指定したVNetのサブネットからだけ許す形に絞れます。さらにプライベートエンドポイントを使うと、アカウントに対してVNet内のプライベートIPが割り当てられ、インターネット経路を使わずに到達できます。公開アクセス自体を無効化し、プライベート経路だけ残す構成が、本番設計での定石です。
- **覚え方**: **経路を絞る(ネットワーク)→ 誰かを確かめる(認証)→ 何ができるか(権限)**の3段の関門。手前から順に締める、と動作イメージで覚えます。
- **つまずきポイント**: キー管理さえ厳しくすれば十分と思いがちですが、実際はキーやSASが漏れた瞬間に世界中から使えてしまいます。経路の制限が最後の砦になります。
- **関連**: SASトークン / VNetとサブネット / NSG

## 8.3 このセクションの覚え方まとめ

まず「VMに付く物」と「単体で立つ物」の2本立てで整理します。

```text
VMに付く       : OSディスク(頭) + データディスク(体) + 一時ディスク(消える)
単体で立つ     : ストレージアカウント → コンテナー/共有 → Blob/ファイル
選ぶ順番       : 種類(HDD→SSD→Premium→Ultra) → 容量 → 冗長構成(L→Z→G)
```

- 冗長構成は頭文字だけ覚えます。**L=Local、Z=Zone、G=Geo、RAは読めるGeo**。
- ディスクを足したら**見る、切る、作る、つける、書く**。最後の「書く」は`/etc/fstab`で、ここを飛ばすと再起動で消えます。
- `/mnt`の一時ディスクは残らない、`StandardSSD_LRS`の`LRS`は冗長構成。この2つを言えれば、このセクションは自分の言葉になっています。
