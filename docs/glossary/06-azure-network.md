# 6. Azureのネットワークサービス

[用語集トップ](../11-azure-glossary.md) ・ 前: [5. ネットワークの基礎(Azure以前に必要な知識)](05-network-basics.md) ・ 次: [7. コンピューティング(仮想マシン)](07-compute.md)

本セクションはこの教材の中心分野です。サーバーが置けるだけでは仕事にならず、`管理者PC → Public IP → NSGの判定 → NIC → VM → Nginx`という経路のどこで通信が止まるかを説明できて、はじめて構築を任せられます。覚える順番は、VNetとサブネットで住所を決める、NSGで通す通信を決める、必要なら経路を曲げるの3段階です。本案件で実際に作るのはVNet、サブネット、NSG、Public IP、NICの5つで、残りは次に学ぶ選択肢として整理します。

## 6.2 用語解説

### 6.2.1 VNet(Virtual Network、仮想ネットワーク)

- **一言でいうと**: Azureの中に自分専用に区切って作る、社内LANのような閉じたネットワークです。
- **たとえると**: マンションを1棟まるごと借りるイメージです。棟の中の住所の付け方は自分で決められます。
- **もう少し詳しく**: VNetはリージョンとリソースグループに属し、この中に置いたリソース同士はプライベートIPで通信できます。VNetの外とは、Public IPやゲートウェイ、ピアリングといった出入口を明示的に作らないとつながりません。サブネット、NSG、ルートテーブルはすべてVNetの上に載るため、ネットワーク設計はVNetから始めます。
- **この案件では**: `vnet-`で始まる名前のVNetを1つだけ作り、アドレス空間は`10.20.0.0/16`です。
- **覚え方**: V=Virtual(仮想)、Net=Network。「クラウドの中の自社LAN」と言い換えて覚えます。
- **つまずきポイント**: 作れば外から見えると思いがちですが、実際は既定で閉じており、出入口は自分で設計します。
- **関連**: アドレス空間 / サブネット / VNetピアリング

### 6.2.2 アドレス空間(Address Space)

- **一言でいうと**: そのVNetで使えるプライベートIPアドレスの範囲を、CIDR表記でまとめて宣言したものです。
- **たとえると**: マンションの敷地に割り当てられた「何丁目何番地」という住所の枠です。
- **もう少し詳しく**: `10.20.0.0/16`のようにCIDRで指定し、1つのVNetに複数のCIDRを持たせることもできます。サブネットはこの範囲の内側からしか切り出せないため、最初に広めに取るのが定石です。他のVNetやオンプレミスと範囲が重複するとピアリングやVPNで接続できないため、社内で台帳管理します。`/16`は65,536アドレス、`/24`は256アドレスです。
- **この案件では**: `10.20.0.0/16`です。将来サブネットを追加しても足りるよう広く確保しています。
- **覚え方**: 数字が小さいほど範囲が広い。`/16`は「先頭16ビットだけ固定=残りは自由」と読むと、`/24`より広いことが計算せずに分かります。
- **つまずきポイント**: 後から自由に広げられると思いがちですが、実際は既存のサブネットや接続先と重複しない範囲しか追加できません。
- **関連**: VNet / サブネット / VNetピアリング

### 6.2.3 サブネット(Subnet)

- **一言でいうと**: VNetのアドレス空間を用途ごとに区切った小さな区画で、リソースを実際に置く場所です。
- **たとえると**: マンションの階です。1階は店舗、2階以上は住居のように、階ごとに入退館ルールを変えられます。
- **もう少し詳しく**: NICはサブネットに接続され、NSGとルートテーブルはサブネット単位で関連付けられます。役割ごとにサブネットを分ければ、Web層とDB層で別のルールを当てられ、侵害の被害を局所化できます。Azure BastionやApplication Gateway、Azure Firewallのように、決まった名前の専用サブネットを要求するサービスもあります。
- **この案件では**: サーバー用サブネット`10.20.1.0/24`が1つで、ここにVMのNICを置きます。
- **覚え方**: Sub(下位の)+net(ネットワーク)。「VNetは棟、サブネットは階」で上下関係を覚えます。
- **つまずきポイント**: あとで広げればよいと思いがちですが、実際はリソース配置後の範囲変更は難しいため、設計時に余裕を持たせます。
- **関連**: アドレス空間 / NSG / NIC

### 6.2.4 Azureがサブネットで予約する5つのIP

- **一言でいうと**: どのサブネットでも先頭4つと末尾1つのアドレスはAzureが押さえるため、使える数は理論値より5個少なくなります。
- **たとえると**: 各階に必ずある管理室や配電盤のような共用部で、住人が部屋として使うことはできません。
- **もう少し詳しく**: 内訳はネットワークアドレス、既定ゲートウェイ、Azure DNSのマッピング用2つ、ブロードキャストアドレスの計5つです。`10.20.1.0/24`なら`10.20.1.0`、`10.20.1.1`、`10.20.1.2`、`10.20.1.3`、`10.20.1.255`が予約され、使えるのは`10.20.1.4`から`10.20.1.254`の251個です。`/29`は8アドレスなので3個しか残らず、サブネットを小さく切りすぎると足りなくなります。
- **この案件では**: VMのプライベートIPは`10.20.1.4`以降から払い出されます。
- **覚え方**: 「先頭4つ+末尾1つ=5つ」。`/24`なら256-5=251と、引き算1回で答えが出ます。
- **つまずきポイント**: `/29`で8台置けると思いがちですが、実際は3台分しか使えません。
- **関連**: サブネット / プライベートIPの割り当て / Azure DNSとプライベートDNSゾーン

### 6.2.5 NIC(Network Interface Card、ネットワークインターフェイス)

- **一言でいうと**: VMをサブネットへつなぐネットワークの差込口で、IPアドレスを持つ独立したAzureリソースです。
- **たとえると**: 部屋の壁にあるLANポートです。部屋であるVMと、建物の配線であるサブネットをつなぎます。
- **もう少し詳しく**: NICはIP構成を持ち、そこにプライベートIPと、必要ならPublic IPリソースを結び付けます。NSGはサブネットにもNICにも付けられ、両方あれば両方が評価されます。NICはVMとは別のリソースなので、VMを作り直してもNICとIPを残すことができます。
- **この案件では**: `nic-`で始まるNICを1つ作り、サブネット`10.20.1.0/24`とPublic IPをVMへ結び付けています。
- **覚え方**: Network Interface Cardの頭文字です。物理サーバーのLANカードがそのままリソースになったと考えます。
- **つまずきポイント**: IPアドレスはVMが持つと思いがちですが、実際に持っているのはNICです。
- **関連**: サブネット / パブリックIPアドレスリソース / NSG

### 6.2.6 プライベートIPの割り当て(動的・静的)

- **一言でいうと**: VNet内部だけで通じる住所を、Azureに自動で選ばせるか、自分で固定するかの選択です。
- **たとえると**: 社内の内線番号です。総務が空き番号を割り振るか、部署が希望の番号を予約しておくかの違いです。
- **もう少し詳しく**: `Dynamic`はサブネットの空きから自動で払い出し、VMの割り当てを解除すると変わる可能性があります。`Static`はサブネット範囲内の指定アドレスに固定します。DNSサーバーやドメインコントローラーのように他から住所で名指しされる役は`Static`、ロードバランサーや名前解決を経由して届く役は`Dynamic`で足りることが多いです。
- **この案件では**: `privateIPAllocationMethod`は`Dynamic`です。SSHとHTTPはPublic IP側から届くため、内部の住所を固定する必要がありません。
- **覚え方**: 動的はAzureが決める、静的は人が決める。「動くのは番号、静かなら固定」と対で覚えます。
- **つまずきポイント**: `Dynamic`は毎回変わると思いがちですが、実際はVMが動いている間は同じアドレスを保持します。
- **関連**: NIC / Azureがサブネットで予約する5つのIP / Azure DNSとプライベートDNSゾーン

### 6.2.7 パブリックIPアドレスリソース(Public IP Address、SKUと割り当て方法)

- **一言でいうと**: インターネット側から届く住所を、Azureの独立したリソースとして確保したものです。
- **たとえると**: 郵便が届く公道側の番地です。マンションの部屋番号にあたるプライベートIPとは別に必要になります。
- **もう少し詳しく**: SKUはサービスのグレードを表し、`Standard`SKUでは割り当て方法が`Static`に固定されるため、VMを再起動してもアドレスが変わりません。NICやロードバランサー、Bastionのフロントに関連付けて使います。`Standard`SKUのPublic IPは既定で受信を通さず、NSGで明示的に許可した通信だけが届きます。
- **この案件では**: `pip-`で始まるPublic IPを`Standard`SKU、`Static`で作り、NIC経由でVMへ関連付けます。
- **覚え方**: SKUは「グレード」、割り当て方法は「固定か浮動か」。`Standard`は「標準で静的」と2語で覚えます。
- **つまずきポイント**: Public IPを付ければ通信できると思いがちですが、実際はNSGの許可がなければ届きません。
- **関連**: NIC / NSG / NAT Gateway

### 6.2.8 NSG(Network Security Group、ネットワークセキュリティグループ)

- **一言でいうと**: サブネットやNICに付けて、通す通信と止める通信を一覧表で判定させるAzure側のフィルターです。
- **たとえると**: マンションのオートロックです。誰がどの入口から入れるかを、管理人室の名簿で決めます。
- **もう少し詳しく**: ルールは優先度の小さい順に評価され、最初に一致した1本で許可か拒否が確定し、それ以降は見ません。ステートフルなので、許可した通信の戻りには別途ルールが不要です。サブネットNSGとNIC NSGの両方がある場合、受信はサブネットからNICの順、送信はNICからサブネットの順に評価され、どちらかが拒否すれば通りません。VM内のOSファイアウォールとは別物なので、切り分けでは両方を確認します。
- **この案件では**: `nsg-`で始まるNSGをサーバー用サブネットへ関連付け、入口で通信を絞っています。
- **覚え方**: N=Network、S=Security、G=Group。「ネットワークの入場者名簿」と言い換えます。
- **つまずきポイント**: 拒否ルールを足せば安全になると思いがちですが、実際は受信は既定で拒否済みで、足すべきは最小限の許可です。
- **関連**: NSGルールの5要素 / 既定のセキュリティ規則 / ASG

### 6.2.9 NSGルールの5要素(優先度・方向・プロトコル・送信元/宛先・許可拒否)

- **一言でいうと**: NSGのルール1本は、優先度、方向、プロトコル、送信元と宛先、許可か拒否の5点だけで決まります。
- **たとえると**: 入館申請書の5つの欄です。何番目に見るか、入るのか出るのか、どの手段か、誰がどこへ、通すか止めるか。
- **もう少し詳しく**: 優先度はカスタムルールで`100`から`4096`まで指定でき、数字が小さいほど先に評価されます。方向は`Inbound`と`Outbound`。プロトコルは`Tcp`、`Udp`、`Icmp`、すべてを表す`*`など。送信元と宛先はIPやCIDR、サービスタグ、ASGで指定し、それぞれポート範囲も添えます。許可拒否は`Allow`と`Deny`です。
- **この案件では**: SSHの許可は優先度`100`、方向`Inbound`、プロトコル`Tcp`、送信元`adminCidr`、宛先ポート`22`、動作`Allow`という1本で表現されています。HTTPは`openHttp=false`のためルールを作らず、既定の受信拒否によって80番が閉じたままになります。`openHttp=true`にしたときだけ、優先度`110`、`Inbound`、`Tcp`、送信元`Internet`、宛先ポート`80`、`Allow`のルールが追加されます。
- **覚え方**: 「順番・向き・手段・相手・可否」の5語を声に出します。順番=優先度、向き=方向、手段=プロトコル、相手=送信元と宛先、可否=許可拒否です。
- **つまずきポイント**: 優先度は数字が大きいほど強いと思いがちですが、実際は小さいほうが先に評価されて勝ちます。
- **関連**: NSG / サービスタグ / 実効セキュリティ規則

### 6.2.10 既定のセキュリティ規則(Default Security Rules)

- **一言でいうと**: NSGを作った時点で最初から入っている、削除できない土台のルール群です。
- **たとえると**: 建物の消防法上の決まりです。入居者が勝手に消せない、最後の砦にあたります。
- **もう少し詳しく**: 受信には`AllowVnetInBound`、`AllowAzureLoadBalancerInBound`、`DenyAllInBound`、送信には`AllowVnetOutBound`、`AllowInternetOutBound`、`DenyAllOutBound`があり、優先度は`65000`以降です。カスタムルールは`100`から`4096`なので必ず先に評価され、既定より優先します。出発点は「VNet内は通る、インターネットからの受信は拒否、インターネットへの送信は通る」の3点です。
- **この案件では**: HTTPの許可ルールを作らない状態でも80番が閉じているのは、この`DenyAllInBound`が最後に効いているためです。
- **覚え方**: 「内は通す、外からは拒否、外へは通す」の3行で唱えます。列の最後には必ず`DenyAll`が待っていると覚えます。
- **つまずきポイント**: 何も設定しなければ全部通ると思いがちですが、実際はインターネットからの受信は既定で拒否されています。
- **関連**: NSG / NSGルールの5要素 / システムルート

### 6.2.11 実効セキュリティ規則(Effective Security Rules)

- **一言でいうと**: サブネットNSGとNIC NSGを合算して、あるNICに実際に効いているルールを一覧化した結果です。
- **たとえると**: 建物の入館ルールと部署の入室ルールを重ねて作った、「この席に座る人の最終ルール一覧」です。
- **もう少し詳しく**: NSGを2枚重ねると、片方だけを見ても通るか止まるかは分かりません。実効セキュリティ規則はNICを起点に、サブネット側とNIC側、カスタムと既定、さらにサービスタグが展開したIP範囲まで含めて示すため、通信できないときの一次資料になります。Network Watcherの診断機能やAzure CLIから取得できます。
- **覚え方**: 実効=実際に効く、と漢字を分解します。「ルール表ではなく答え合わせの表」を見る機能です。
- **つまずきポイント**: NSGのルール一覧を見れば十分と思いがちですが、実際は2枚の重ね合わせを見ないと原因に届きません。
- **関連**: NSG / Network Watcher / ASG

### 6.2.12 サービスタグ(Service Tag)

- **一言でいうと**: AzureサービスのIPアドレス範囲にMicrosoftが付けた別名で、NSGルールの送信元や宛先に書けます。
- **たとえると**: 宅配業者の営業所リストです。個々の住所を書き写す代わりに「あの運送会社の全営業所」と1語で指定します。
- **もう少し詳しく**: `Internet`、`VirtualNetwork`、`AzureLoadBalancer`、`Storage`、`Sql`、`AzureCloud`などが用意されています。範囲はMicrosoftが更新するため、対象サービスのIPが変わってもルールを書き換える必要がありません。タグによってはリージョンを限定した指定もできます。
- **この案件では**: HTTPを開ける場合の許可ルールで、送信元に`Internet`タグを使っています。
- **覚え方**: 「IPの束に貼ったラベル」。サービス名を書けばIP一覧表を持たなくてよい、と動作で覚えます。
- **つまずきポイント**: 好きな名前を自分で付けられると思いがちですが、実際はAzureが定義した名前しか使えません。
- **関連**: NSGルールの5要素 / サービスエンドポイント / Azure Firewall

### 6.2.13 ASG(Application Security Group、アプリケーションセキュリティグループ)

- **一言でいうと**: 複数のNICをひとまとめにして名前を付け、NSGルールの送信元や宛先にその名前を書ける仕組みです。
- **たとえると**: 会社の組織名です。「田中と佐藤と鈴木」ではなく「経理部」と書けば済むのと同じです。
- **もう少し詳しく**: NICをASGへ所属させ、ルールにはグループ名を書きます。サーバーが増えてもASGへ入れるだけでルールは変えずに済み、IPアドレスを固定する必要もありません。ASGが対象にできるのはVNet内のNICで、ルールの両側にASGを使う場合は同じVNet内に限られます。
- **覚え方**: A=Application、S=Security、G=Group。NSGは「ルールの束」、ASGは「NICの束」と対比します。
- **つまずきポイント**: サブネットに付けるものと思いがちですが、実際はNICに貼る役割ラベルです。
- **関連**: NSG / NIC / サービスタグ

### 6.2.14 システムルート(System Routes)

- **一言でいうと**: 何も設定しなくてもAzureが自動で用意している、通信の行き先を決める既定の経路表です。
- **たとえると**: 引っ越した初日から使える最寄り駅までの道です。自分で舗装しなくても最初から通れます。
- **もう少し詳しく**: VNetのアドレス空間宛ては同じVNet内へ直接、`0.0.0.0/0`宛てはインターネットへ、といった経路が最初から入っています。ピアリングやVPN Gatewayを作ると、その宛先の経路も自動で追加されます。システムルートは削除できないため、変えたい場合はUDRで上書きします。
- **この案件では**: 独自のルートテーブルは作らず、システムルートのままです。VMからのパッケージ更新などの送信通信は、既定経路でインターネットへ出ます。
- **覚え方**: システム=Azureが用意、ルート=経路。「道は最初から通っている」と覚えます。
- **つまずきポイント**: 経路設定は必須と思いがちですが、実際は小規模構成では何も作らなくても通信できます。
- **関連**: UDRとルートテーブル / VNetピアリング / Azure Firewall

### 6.2.15 UDR(User Defined Route、ユーザー定義ルート)とルートテーブル

- **一言でいうと**: 既定の経路をあえて書き換えて、通信を指定した装置経由に曲げるための設定です。
- **たとえると**: 工事のときに立てる迂回路の看板です。目的地は同じでも、通る道を強制的に変えます。
- **もう少し詳しく**: ルートテーブルというリソースにUDRを並べ、サブネットへ関連付けます。UDR1本は宛先CIDRと次ホップの種類の組で、次ホップには仮想アプライアンス、仮想ネットワークゲートウェイ、VNet、インターネット、なしを選べます。宛先が複数一致する場合はより長いプレフィックスが勝ち、同じ宛先ならUDRがシステムルートより優先されます。代表例は`0.0.0.0/0`をAzure Firewallへ向け、外向き通信を1か所で検査させる構成です。
- **この案件では**: 単一VMでFirewallを経由させる要件がないため、ルートテーブルは作成していません。
- **覚え方**: UDR=User Defined Route、つまり「人が決めた道」。既定はSystem、上書きはUserと対で覚えます。
- **つまずきポイント**: NSGと同じものと思いがちですが、NSGは通すかどうか、UDRはどこへ通すかで役割が違います。
- **関連**: システムルート / Azure Firewall / NSG

### 6.2.16 VNetピアリング(VNet Peering)

- **一言でいうと**: 2つのVNetを直接つないで、プライベートIPのまま相互に通信できるようにする機能です。
- **たとえると**: 隣り合うビルをつなぐ連絡通路です。いったん外に出て公道を歩かずに行き来できます。
- **もう少し詳しく**: ゲートウェイもインターネット経由も不要で、同一リージョン同士だけでなくリージョンをまたぐグローバルピアリングもできます。アドレス空間が重複するVNet同士はピアリングできません。ピアリングは推移しないため、AとB、BとCをつないでもAとCは通信できず、必要ならAとCを直接つなぐか、ハブ側のアプライアンスを経由させます。
- **覚え方**: peerは「対等な相手」。「対等な2棟を廊下でつなぐ、3棟目には抜けられない」と図で覚えます。
- **つまずきポイント**: つなげば全体が網の目になると思いがちですが、実際は1対1の関係が積み重なるだけです。
- **関連**: アドレス空間 / UDRとルートテーブル / VPN Gateway

### 6.2.17 VPN Gateway(Virtual Private Network Gateway)

- **一言でいうと**: インターネット回線の上に暗号化トンネルを張り、拠点や個人端末とVNetをつなぐ出入口です。
- **たとえると**: 公道を走る現金輸送車です。道は誰でも通れる公共のものでも、中身は箱ごと施錠されています。
- **もう少し詳しく**: VNet内に`GatewaySubnet`という名前の専用サブネットを用意して配置します。接続形態は、拠点とVNetを結ぶサイト間、個人端末から接続するポイント対サイト、VNet同士を結ぶものがあります。IPsecやIKEで暗号化しますが、経路はインターネットなので帯域や遅延は回線品質に左右されます。SKUによって性能と対応機能が変わります。
- **覚え方**: VPN=Virtual Private Network、Gateway=出入口。「仮想の専用線に置く関所」と分解します。
- **つまずきポイント**: 専用線と同等の品質だと思いがちですが、実際は公衆網を通るため品質は保証されません。
- **関連**: ExpressRoute / VNetピアリング / Azure Bastion

### 6.2.18 ExpressRoute

- **一言でいうと**: 通信事業者の閉域回線でオンプレミスとAzureを直結し、インターネットを経由しない接続方式です。
- **たとえると**: 会社と倉庫を結ぶ専用の引き込み線です。一般道の渋滞や事故の影響を受けません。
- **もう少し詳しく**: 接続事業者と契約して回線を用意し、Azure側にはExpressRoute回線とゲートウェイを構成します。公衆網を通らないため、安定した帯域と低い遅延、経路の秘匿性が得られます。大量データの移送や、監査上インターネット経由を避けたい場合に選びます。物理回線の契約と開通作業が伴うため、期間と費用は早めに見積もります。
- **覚え方**: Express=急行、Route=経路。VPNは一般道、ExpressRouteは専用の急行線と、鉄道でたとえます。
- **つまずきポイント**: Azure側の設定だけで使えると思いがちですが、実際は事業者との契約と物理的な開通が前提です。
- **関連**: VPN Gateway / システムルート / Azure Firewall

### 6.2.19 Azure Bastion

- **一言でいうと**: VMにPublic IPを付けずに、ブラウザー経由で安全にSSHやRDP接続できるマネージドの踏み台です。
- **たとえると**: 管理人が常駐するマンションの受付です。各部屋に外からの勝手口を作らず、必ず受付を通します。
- **もう少し詳しく**: VNet内に`AzureBastionSubnet`という名前の専用サブネットを`/26`以上で作って配置します。管理者はAzureへサインインしてから接続するため、誰がいつどのVMへ入ったかを追跡しやすくなります。VM側のNSGでSSHの22番やRDPの3389番をインターネットへ開ける必要がなくなり、攻撃を受ける面が小さくなります。
- **この案件では**: 未実装の発展課題です。学習版は`adminCidr`限定でPublic IP経由のSSHを行い、本番想定ではBastionやプライベート接続へ切り替える方針を基本設計に記載しています。
- **覚え方**: bastionは城の稜堡、日本語なら踏み台サーバー。「城門を1か所に絞る」動作で覚えます。
- **つまずきポイント**: 高機能なVPNだと思いがちですが、実際は管理接続を1か所へ集約する専用の入口です。
- **関連**: パブリックIPアドレスリソース / NSG / VPN Gateway

### 6.2.20 NAT Gateway(Network Address Translation Gateway)

- **一言でいうと**: サブネット内のVMが外へ出るときの送信元IPをまとめて代表させる、送信専用の出口サービスです。
- **たとえると**: 会社の代表電話です。社員がどの内線からかけても、相手には代表番号が表示されます。
- **もう少し詳しく**: サブネットへ関連付け、`Standard`SKUのPublic IPやIPプレフィックスを出口アドレスとして使います。VMごとにPublic IPを付けずに済み、外向き通信の送信元IPが安定するため、相手側の許可リストに登録しやすくなります。受信は一切開かないため、外から入る経路にはなりません。
- **覚え方**: NAT=Network Address Translation、つまりアドレス変換。「出るときだけ名札を代表に付け替える」と覚えます。
- **つまずきポイント**: 双方向の入口にもなると思いがちですが、実際は送信専用で受信は通しません。
- **関連**: パブリックIPアドレスリソース / システムルート / Azure Firewall

### 6.2.21 Azure Load Balancer(ロードバランサー)

- **一言でいうと**: 同じ役割の複数VMへ、TCPやUDPの通信を振り分ける第4層のロードバランサーです。
- **たとえると**: 銀行の番号札発行機です。空いている窓口へ順に案内し、閉じた窓口へは回しません。
- **もう少し詳しく**: フロントエンドIP、バックエンドプール、正常性プローブ、負荷分散規則の4点で構成します。プローブが応答しないVMは振り分け対象から自動的に外れるため、1台の障害で全体が止まるのを防げます。インターネット向けのパブリックと、VNet内部向けの内部ロードバランサーがあります。HTTPの中身を見た振り分けはできません。
- **この案件では**: 単一VM構成のため未実装です。可用性要件が出た場合に、可用性ゾーンと複数VMとあわせて検討します。
- **覚え方**: Load(負荷)をBalance(均す)。「窓口を増やして待ち行列を分ける」動作で覚えます。
- **つまずきポイント**: URLごとの振り分けができると思いがちですが、実際の判断材料はIPとポートまでです。
- **関連**: Application GatewayとWAF / パブリックIPアドレスリソース / サービスタグ

### 6.2.22 Application GatewayとWAF(Web Application Firewall)

- **一言でいうと**: HTTPの中身を見て振り分ける第7層のロードバランサーと、そこへ追加するWebアプリ専用の防御機能です。
- **たとえると**: 郵便物を開けて宛先部署へ回す受付と、その手前に立つ不審物検査の係です。
- **もう少し詳しく**: URLのパスやホスト名による振り分け、TLSの終端、Cookieによるセッション維持などができ、配置には専用サブネットが必要です。WAFはSQLインジェクションやクロスサイトスクリプティングのようなWebアプリを狙う攻撃パターンを検査し、記録だけを行うモードと実際に遮断するモードを選べます。
- **この案件では**: 未実装の発展課題です。HTTPS化と本番想定の公開構成へ進む段階で、Public IP直結をやめて導入を検討します。
- **覚え方**: Load Balancerは「宛先を見る窓口」、Application Gatewayは「中身を読む窓口」、WAFは「Webの門番」と3語で並べます。
- **つまずきポイント**: NSGがあればWAFは不要と思いがちですが、NSGはポート単位、WAFはリクエスト内容単位で守る層が違います。
- **関連**: Azure Load Balancer / Azure Firewall / NSG

### 6.2.23 Azure Firewall

- **一言でいうと**: VNetの出入口に置いて、通信をまとめて検査し記録するマネージドのファイアウォールサービスです。
- **たとえると**: 会社の正門にある警備室です。全員がここを通り、入退場が台帳に残ります。
- **もう少し詳しく**: `AzureFirewallSubnet`という名前の専用サブネットに配置し、UDRで通信をここへ向けて経由させます。IPとポートによるネットワークルールに加え、宛先のFQDNで許可するアプリケーションルールも書けます。SKUによって使える機能が異なります。NSGはリソースの近くを守る細かい網、Azure Firewallは境界を一括で守る太い網という関係です。
- **この案件では**: 未実装です。単一VNet・単一VMでは、NSGによる最小許可で要件を満たせると判断しています。
- **覚え方**: 「NSGは各部屋の鍵、Azure Firewallは正門の警備室」。守る位置の違いで区別します。
- **つまずきポイント**: NSGの上位互換だと思いがちですが、実際は併用が前提で、置き換えではありません。
- **関連**: UDRとルートテーブル / NSG / Application GatewayとWAF

### 6.2.24 Azure DNSとプライベートDNSゾーン(Private DNS Zone)

- **一言でいうと**: 名前とIPアドレスの対応をAzure上で管理する仕組みで、外部に公開する用と、VNet内部だけで引く用があります。
- **たとえると**: 電話帳です。誰でも見られる職業別電話帳と、社内だけに配る内線表の2種類があるイメージです。
- **もう少し詳しく**: VNet内のVMは既定でAzure提供のDNSを使い、その参照先は`168.63.129.16`です。公開ドメインのレコードはAzure DNSのパブリックゾーンで管理します。プライベートDNSゾーンはVNetへリンクして使い、自動登録を有効にするとVM名のレコードが自動で作られます。プライベートエンドポイントの名前解決にも使います。VNetにカスタムDNSサーバーを指定すれば、社内のDNSへ問い合わせを寄せることもできます。
- **覚え方**: DNS=Domain Name System、「名前をIPに直す係」。パブリックは外向き電話帳、プライベートは内線表と対比します。
- **つまずきポイント**: 名前が引けたら通信できると思いがちですが、実際は名前解決とNSGの許可はまったく別の話です。
- **関連**: プライベートエンドポイント / Azureがサブネットで予約する5つのIP / サブネット

### 6.2.25 サービスエンドポイント(Service Endpoint)

- **一言でいうと**: サブネットからAzureのPaaSへの通信をAzure内の経路に寄せ、サービス側でそのサブネットだけを許可する仕組みです。
- **たとえると**: 取引先の受付に「うちの社員証を持つ人だけ通してください」と事前に伝えておく運用です。
- **もう少し詳しく**: まずサブネット側で対象サービスのエンドポイントを有効にし、次にストレージなどサービス側のネットワーク設定で、そのVNetとサブネットからのアクセスだけを許可します。有効化はサブネット単位です。接続先の名前とIPはパブリックのまま変わらないため、DNSの追加設定は要りません。
- **覚え方**: 「相手の受付に自分の身分を登録する」。次の項目との違いは、接続先の住所が変わらない点です。
- **つまずきポイント**: 完全な閉域になると思いがちですが、実際は接続先はパブリックの名前とIPのままです。
- **関連**: プライベートエンドポイント / サービスタグ / サブネット

### 6.2.26 プライベートエンドポイント(Private Endpoint)

- **一言でいうと**: PaaSサービスに自分のサブネット内のプライベートIPを1つ与え、VNetの内側から呼べるようにする仕組みです。
- **たとえると**: 取引先の窓口を自社ビルの空き部屋に招いて常駐させ、社内から内線で呼べるようにするイメージです。
- **もう少し詳しく**: 指定したサブネットにNICが作られ、そこへプライベートIPが割り当てられます。Azure Private Linkの機能で、通信はVNet内のIP宛てになるためパブリック経路を使いません。サービス名がそのプライベートIPを返すよう、プライベートDNSゾーンをあわせて構成するのが定番です。サービス側でパブリックアクセスを無効化すると、より閉じた構成になります。
- **この案件では**: 未実装の発展課題です。本番想定でPublic IP直結をやめる際の候補として、基本設計の将来構成に挙げています。
- **覚え方**: サービスエンドポイントは「相手の受付に登録」、プライベートエンドポイントは「相手を自社に招く」。招くほうが閉じている、と対比します。
- **つまずきポイント**: 有効化すれば名前も自動で切り替わると思いがちですが、実際はDNSの構成が別途必要です。
- **関連**: サービスエンドポイント / Azure DNSとプライベートDNSゾーン / NIC

### 6.2.27 Network Watcher(接続のトラブルシューティング)

- **一言でいうと**: つながらない原因を切り分けるために用意された、Azureネットワーク専用の診断ツール群です。
- **たとえると**: 健康診断のセットです。問診、レントゲン、血液検査のように、目的別の検査項目が束になっています。
- **もう少し詳しく**: 実際に通信を試して結果を返す接続のトラブルシューティング、指定した通信がNSGで許可されるか判定するIPフロー検証、宛先への次の転送先を示すネクストホップ、NICに効いているルールを見る実効セキュリティ規則、通信の履歴を残すフローログなどがあります。NSGか経路かOSかを、当て推量ではなく検査結果で切り分けられます。
- **この案件では**: `管理者PC → Public IP → NSGの判定 → NIC → VM → Nginx`の順路を逆からたどる切り分けと組み合わせると、原因の特定が速くなります。
- **覚え方**: Network(ネットワーク)をWatch(見張る)。「ネットワークの健康診断センター」と言い換えます。
- **つまずきポイント**: 常時動かす監視サービスだと思いがちですが、実際は障害時に呼び出す検査キットとしての使い方が中心です。
- **関連**: 実効セキュリティ規則 / NSG / システムルート

## 6.3 このセクションの覚え方まとめ

```text
[土台]     VNet -> アドレス空間 -> サブネット(先頭4つ+末尾1つは予約)
[接続口]   NIC -> プライベートIP / パブリックIP
[門番]     NSG(順番・向き・手段・相手・可否)+ 既定規則 / サービスタグ / ASG
[道案内]   システムルート -> UDRとルートテーブル
[外への橋] VNetピアリング / VPN Gateway / ExpressRoute / Bastion / NAT Gateway
[受付]     Load Balancer(L4) -> Application GatewayとWAF(L7) -> Azure Firewall(境界)
[名前と閉域] Azure DNS -> サービスエンドポイント -> プライベートエンドポイント
[検査]     Network Watcher -> 実効セキュリティ規則
```

- 順番で覚える: 土台、接続口、門番、道案内、外への橋、受付、名前と閉域、検査。設計もこの順で決めます。
- NSGは5語で唱える: 「順番・向き・手段・相手・可否」。本案件のSSH許可は`100`・`Inbound`・`Tcp`・`adminCidr`から`22`番へ・`Allow`の1本だけです。
- 数字は1つだけ覚える: サブネットの予約は5個。`/24`なら256-5=251個、先頭は`10.20.1.4`から。
- 対比で覚える: NSGは通すか、UDRはどこへ通すか。Load Balancerは宛先、Application Gatewayは中身。サービスエンドポイントは相手に登録、プライベートエンドポイントは相手を招く。
