# 7. コンピューティング(仮想マシン)

[用語集トップ](../11-azure-glossary.md) ・ 前: [6. Azureのネットワークサービス](06-azure-network.md) ・ 次: [8. ストレージとディスク](08-storage.md)

コンピューティングは、Azureの中で実際に処理を動かす部分です。この案件の主役は`vm-`から始まるLinux仮想マシン1台で、その上でNginxが動きます。ここでは、VMを1台作るときに何を決めるのかを順番に並べ、最後に初心者が最もつまずく「止めたのに課金が続く」問題を整理します。

## 7.2 用語解説

### 7.2.1 仮想マシン(VM、Virtual Machine、仮想サーバー)

- **一言でいうと**: 物理サーバーの中身をソフトウェアで再現した、自分専用の1台のサーバーです。
- **たとえると**: 1棟のビルを間仕切りして貸す賃貸オフィスです。建物の設備は大家(Azure)が持ち、部屋の中の使い方は借り主が決めます。
- **もう少し詳しく**: CPU、メモリ、ディスク、ネットワークを組み合わせて作ります。OSより上は利用者の責任範囲で、パッチ適用もミドルウェア設定も自分で行います。この形態を**IaaS**と呼びます。機器の調達が不要で、数分で作って壊せるのがクラウドのVMの強みです。
- **この案件では**: Ubuntu VMを1台だけ作り、その上でNginxを動かします。名前は`vm-`から始まる規則で付けます。
- **覚え方**: Virtual(仮想の)+Machine(機械)。「機械のフリをしたソフト」と語源で分解します。
- **つまずきポイント**: 作ってしまえば管理はAzureに任せられると思いがちですが、実際はOSの更新もバックアップも利用者の仕事です。
- **関連**: IaaS / NIC / マネージドディスク

### 7.2.2 VMサイズとシリーズ(VM Size / VM Series)

- **一言でいうと**: VMの性能と用途の傾向を、あらかじめ用意された型番の一覧から選ぶ仕組みです。
- **たとえると**: レンタカーの車種表です。軽・セダン・トラックという系統(シリーズ)があり、その中に排気量の違い(サイズ)があります。
- **もう少し詳しく**: 名前は`Standard_B1s`のように、シリーズを表す文字、vCPU数、機能を表す接尾辞の組み合わせで読みます。**B**はバースト可能、**D**は汎用、**E**はメモリ重視、**F**はコンピューティング重視という傾向です。サイズは後から変更できますが、変更にはVMの再起動が必要です。
- **この案件では**: 既定を`Standard_B1s`とし、学習費用を抑えています。値は`infra/main.bicep`のパラメーター`vmSize`で変更します。
- **覚え方**: 頭文字で「B=バースト、D=だいたい汎用、E=メモリ重視、F=速いCPU(Fast)」。
- **つまずきポイント**: 大きいほど良いと思いがちですが、実際は負荷の形に合っているかが重要で、常時暇なVMを大きくしても無駄になります。
- **関連**: vCPUとメモリ / Bシリーズ / SKU

### 7.2.3 vCPUとメモリ(仮想CPU / RAM)

- **一言でいうと**: VMの計算力を表すvCPUの数と、作業用の一時記憶の大きさを表すメモリ量です。
- **たとえると**: vCPUはレジの台数、メモリは商品を広げる作業台の広さです。台数が多ければ同時にさばけ、台が広ければ一度に多くを並べられます。
- **もう少し詳しく**: vCPUは物理CPUのコアを仮想化して割り当てた単位で、`Standard_B1s`のようにサイズ名の数字がvCPU数に対応するシリーズが多くあります。メモリが足りないとOSがディスクへ退避してから急激に遅くなり、vCPUが足りないと処理待ちの行列ができます。原因が違えば対処も違うため、監視では両方を見ます。
- **この案件では**: CPU使用率のメトリックアラートを作り、平均が5分間にわたり`80`パーセントを超えたら発報する設定にしています。
- **覚え方**: 「vCPUは手の数、メモリは机の広さ」。遅いときは、手が足りないのか机が狭いのかで切り分けます。
- **つまずきポイント**: CPU使用率だけを見て足りていると判断しがちですが、実際はメモリ不足が原因の遅さも同じくらい多くあります。
- **関連**: VMサイズとシリーズ / Bシリーズ / メトリックアラート

### 7.2.4 Bシリーズ(バースト可能VM、B-series burstable)

- **一言でいうと**: 普段は控えめな性能で安く動き、必要なときだけ性能を引き上げられるVMの系統です。
- **たとえると**: 貯金です。使わない日にこつこつ貯め、必要な日にまとめて取り崩します。
- **もう少し詳しく**: **CPUクレジット**という考え方で動きます。CPU使用率が基準を下回っている間はクレジットが貯まり、負荷が上がった局面でそれを消費して基準以上の性能を出します。クレジットを使い切ると基準の性能まで戻るため、常時高負荷が続く用途には向きません。負荷が断続的な小規模Webサーバーや学習用途と相性が良いシリーズです。
- **この案件では**: 既定の`Standard_B1s`がこのBシリーズで、常時高負荷ではない社内向けWebサーバーという前提に合わせた選択です。
- **覚え方**: BはBurst(噴き出す)とBudget(予算)の2つのB。「安いが息継ぎがある」。
- **つまずきポイント**: 表示された性能が常に出ると思いがちですが、実際はクレジットが尽きると性能が落ちます。
- **関連**: VMサイズとシリーズ / vCPUとメモリ / Spot VM

### 7.2.5 SKU(Stock Keeping Unit、在庫管理単位)

- **一言でいうと**: 同じサービスの中で、性能や機能の違いを区別するために付けられた型番です。
- **たとえると**: コンビニの商品バーコードです。「お茶」ではなく「あの銘柄の500ml」まで一意に決めます。
- **もう少し詳しく**: 元は小売業の在庫管理単位ですが、Azureでは「どの等級を選んだか」を表す語として広く使われます。Public IPのBasicとStandard、マネージドディスクのStandard HDD/Standard SSD/Premium SSD、VMサイズそのものもSKUの一種です。SKUによって使える機能や料金が変わるため、設計書ではSKU名まで書き切るのが基本です。
- **この案件では**: Public IPは`Standard`、OSディスクは`StandardSSD_LRS`、Log AnalyticsのSKUは`PerGB2018`をBicepで明示しています。
- **覚え方**: 「S=商品、K=管理、U=単位」の頭文字。日本語の「型番」に置き換えると迷いません。
- **つまずきポイント**: サービス名が同じなら中身も同じと思いがちですが、実際はSKU違いで使える機能が変わります。
- **関連**: VMサイズとシリーズ / Public IP / マネージドディスク

### 7.2.6 VMイメージとAzure Marketplace(VM Image / Marketplace)

- **一言でいうと**: VMを作るときの中身の原型を、あらかじめ用意された配布物から選ぶ仕組みです。
- **たとえると**: 賃貸の「家具付きプラン」です。素の部屋か、家電まで入った部屋かを入居前に選びます。
- **もう少し詳しく**: イメージは**publisher(発行元)、offer(製品)、sku(版)、version(版数)** の4点で指定します。Azure Marketplaceには、OSだけのイメージからミドルウェア導入済みのイメージまで多数が並びます。自分で整えたVMを原型として量産したい場合は、Azure Compute Galleryのカスタムイメージにする方法もあります。
- **この案件では**: publisher`Canonical`、offer`ubuntu-24_04-lts`、sku`server`、version`latest`を指定しています。
- **覚え方**: 「発行元・製品・版・版数」の4段で、住所のように上から下へ絞り込みます。
- **つまずきポイント**: `latest`にしておけば安心と思いがちですが、実際は再デプロイのたびに中身が変わるため、再現性を重視する場面では版数を固定します。
- **関連**: OSの選択 / 世代 / カスタムデータとcloud-init

### 7.2.7 OSの選択(Ubuntu / Windows Server)

- **一言でいうと**: VMの上で動かす基本ソフトを決める、後戻りが最も難しい選択です。
- **たとえると**: 職場の共通語をどちらにするかです。使う道具も、集めやすい人材も、この決定に引きずられます。
- **もう少し詳しく**: Linux(Ubuntuなど)はSSHとコマンドで運用し、Webサーバー用途で広く使われ、OSのライセンス費用がかからないディストリビューションもあります。Windows ServerはRDPと画面操作で運用し、Active DirectoryやIISなどMicrosoft製品と組み合わせやすい一方、ライセンスの扱いが加わります。既存アプリの動作要件と、運用担当者が慣れている側を軸に決めます。
- **この案件では**: Ubuntuを選び、SSH公開鍵認証だけで接続します。パスワード認証は`disablePasswordAuthentication`により無効です。
- **覚え方**: 「Linuxは鍵とコマンド、Windowsは画面とドメイン」と対比で覚えます。
- **つまずきポイント**: 後から入れ替えられると思いがちですが、実際はOSの変更はVMの作り直しに近い作業です。
- **関連**: SSH / RDP / VMイメージとAzure Marketplace

### 7.2.8 世代(Generation 2、Gen2、第2世代)

- **一言でいうと**: VMの仮想ハードウェアの世代で、起動方式と使える機能が変わります。
- **たとえると**: 建物の電気設備の規格です。同じ家電でも、古い規格の建物では使えない機能があります。
- **もう少し詳しく**: 第1世代(Gen1)はBIOSで起動し、第2世代(Gen2)はUEFIで起動します。Gen2ではセキュアブートや仮想TPMを使うTrusted Launch、大きなOSディスクからの起動などに対応します。世代は選んだイメージとVMサイズの対応で決まり、作成後に世代だけを切り替えることはできません。新規構築では、対応するイメージがある限りGen2を選ぶのが一般的です。
- **この案件では**: Bicepで世代を明示せず、指定したUbuntuイメージのSKUに従います。
- **覚え方**: 「Gen1はBIOS、Gen2はUEFI」。1は古い起動、2は新しい起動と数字で対応させます。
- **つまずきポイント**: 後から世代を変えられると思いがちですが、実際は作り直しが必要です。
- **関連**: VMイメージとAzure Marketplace / VMサイズとシリーズ / マネージドディスク

### 7.2.9 カスタムデータとcloud-init(Custom Data / cloud-init)

- **一言でいうと**: VMが初回起動する瞬間に、決めておいた初期設定を自動で実行させる仕組みです。
- **たとえると**: 新人の初日に渡す作業指示書です。出社した本人が、指示書どおりに自分で環境を整えます。
- **もう少し詳しく**: カスタムデータはVM作成時に渡すテキストで、Linux側の**cloud-init**がこれを読み取り、パッケージ導入、ファイル配置、コマンド実行を行います。Bicepでは`customData`にBase64化して渡します。手作業のセットアップをコードにできるため、同じサーバーを何度でも同じ状態で作れます。
- **この案件では**: `infra/cloud-init.yaml`で`nginx`を導入し、`/var/www/html/index.html`を配置して、`systemctl enable --now nginx`でNginxを起動します。
- **覚え方**: cloud-**init**は「初期化(initialize)」。Linuxの`init`と同じ語で、最初の1回だけ働くと覚えます。
- **つまずきポイント**: ファイルを直せば動いているVMにも反映されると思いがちですが、実際は初回起動時の処理なので、作り直すか個別に適用します。
- **関連**: VM拡張機能 / VMイメージとAzure Marketplace / 起動診断

### 7.2.10 VM拡張機能(VM Extensions、VM拡張)

- **一言でいうと**: 稼働中のVMへ、Azure側から機能や設定を後付けするための小さな部品です。
- **たとえると**: スマートフォンへ後から入れるアプリです。本体を買い替えずに機能を足せます。
- **もう少し詳しく**: VM内の**Azure VMエージェント**が窓口となり、Azureからの指示で拡張機能を導入・実行します。スクリプト実行、監視エージェント導入、ログ収集設定などが代表例です。Bicepやポータルから宣言的に管理できるため、後から足した設定も構成として記録に残ります。エージェントが動いていないVMには拡張機能を配れません。
- **この案件では**: `provisionVMAgent`を有効にしており、拡張機能を使う準備は整っています。監視のためのAzure Monitor Agent(AMA)の導入は未実装の発展課題です。
- **覚え方**: 「初回はcloud-init、あとからはExtensions」。入り口が違うと対比で覚えます。
- **つまずきポイント**: 作成時にしか設定できないと思いがちですが、実際は稼働後も追加・更新できます。
- **関連**: カスタムデータとcloud-init / Azure Monitor Agent / Log Analytics

### 7.2.11 起動診断(Boot Diagnostics、ブート診断)

- **一言でいうと**: VMが起動しないときに、画面のスクリーンショットと起動時のログをAzure側から見られる機能です。
- **たとえると**: ドライブレコーダーです。走れなくなった後で、止まる直前の様子を確認できます。
- **もう少し詳しく**: SSHやRDPで入れない状態でも、外から見える情報を残します。OSが起動途中で止まっている、ファイルシステムの確認待ちで停止している、ネットワーク設定を壊して到達できないといった切り分けに使います。有効化していないと、障害時に読める情報が大きく減ります。
- **この案件では**: Bicepの`bootDiagnostics`を有効にしており、起動しない事象の初動調査に使えます。
- **覚え方**: 文字どおり「起動の診断」。健康診断と同じで、平常時に受けておくから異常時に比べて読めます。
- **つまずきポイント**: 障害が起きてから有効化すればよいと思いがちですが、実際は事前に有効化していないと当時の記録が残りません。
- **関連**: シリアルコンソール / VM拡張機能 / メトリックアラート

### 7.2.12 シリアルコンソール(Serial Console)

- **一言でいうと**: ネットワーク経由で入れなくなったVMへ、Azureの画面から直接文字を打てる非常口です。
- **たとえると**: 電子錠が動かなくなった建物の、管理人だけが使える物理鍵の裏口です。
- **もう少し詳しく**: VMの仮想シリアルポートへつないでOSのコンソールを操作します。SSH設定やネットワーク設定を壊して接続できなくなった場合の復旧に使えます。利用には起動診断が有効である必要があり、さらにOS側にログインできる資格情報が必要です。ネットワークを通らない経路のため、NSGのルールには左右されません。
- **この案件では**: SSHは公開鍵認証のみでパスワードを持たないため、シリアルコンソールから操作するにはOS側でログイン手段を別途用意する必要があります。
- **覚え方**: シリアルは「1本の線で直結」。ネットワークの迂回路ではなく、そもそも別の線と覚えます。
- **つまずきポイント**: 有効にすればいつでも入れると思いがちですが、実際はOS側のログイン手段がなければ画面が見えるだけです。
- **関連**: 起動診断 / SSH / NSG

### 7.2.13 停止と停止(割り当て解除)の違い(StoppedとStopped deallocated)

- **一言でいうと**: 電源を切っただけの状態と、計算資源そのものを手放した状態は別物で、かかる費用が変わります。
- **たとえると**: 駐車場の車です。エンジンを切るだけでは駐車料金が続き、出庫して枠を返して初めて料金が止まります。
- **もう少し詳しく**: OSの中から`shutdown`しただけのVMは「停止(Stopped)」で、ホスト上の実行枠を確保したままです。この状態ではコンピューティングの課金が続きます。Azure側から割り当てを解除すると「停止(割り当て解除)」となり、枠を返すためコンピューティングの課金が止まります。ただしOSディスクなどのディスクと、`Static`で確保したPublic IPは残るため、その分は課金対象のままです。Azure CLIでは`az vm stop`が前者、`az vm deallocate`が後者にあたります。割り当て解除後は、`Dynamic`で割り当てたプライベートIPが変わる可能性がある点にも注意します。実際の金額はリージョン・契約・時期で変わるため、Azure Pricing CalculatorとCost Managementで確認します。
- **この案件では**: 学習を中断するときは割り当て解除まで行い、学習を終えたときは`scripts/remove.ps1`でリソースグループごと削除します。Public IPは`Static`のため、割り当て解除後も同じアドレスが残ります。
- **覚え方**: 「止める」と「返す」は別。エンジンを切る(停止)か、駐車枠を返す(割り当て解除)かの2択で覚えます。
- **つまずきポイント**: OS内でシャットダウンすれば費用が止まると思いがちですが、実際は枠を返すまでコンピューティングの課金が続きます。ここが初心者の請求事故で最も多い原因です。
- **関連**: Spot VM / マネージドディスク / Public IP

### 7.2.14 可用性セットと障害ドメイン・更新ドメイン(Availability Set / Fault Domain / Update Domain)

- **一言でいうと**: 同じ役割のVMを複数台置くとき、それらが同時に止まらないよう自動で分散配置する仕組みです。
- **たとえると**: 同じ部署の担当者を、1つの島に固めず別の島へ分けて座らせることです。片方の島で停電しても業務が続きます。
- **もう少し詳しく**: **障害ドメイン**は電源やネットワーク機器を共有する単位で、ここを分けるとラック単位の故障で全台が同時に落ちる事態を避けられます。**更新ドメイン**はAzure側の計画メンテナンスで同時に再起動される単位で、ここを分けると更新が順番に行われます。可用性セットはVM作成時に指定するもので、既存のVMを後から入れることはできません。
- **この案件では**: 単一VM構成のため使用していません。台数を増やす段階で初めて検討します。
- **覚え方**: 「障害ドメインは事故で落ちる範囲、更新ドメインは工事で止まる範囲」。事故と工事の2種類に分けます。
- **つまずきポイント**: 可用性セットに入れれば1台でも守られると思いがちですが、実際は複数台に分散して初めて意味を持ちます。
- **関連**: 可用性ゾーンへの配置 / 仮想マシンスケールセット / 単一障害点

### 7.2.15 可用性ゾーンへの配置(Availability Zones、AZ、可用性ゾーン)

- **一言でいうと**: 同じリージョンの中で、建物ごと分かれたデータセンターへVMを分けて置く冗長化です。
- **たとえると**: 支店を同じビルの別フロアではなく、別の街に置くことです。停電や水害の影響が同時には及びません。
- **もう少し詳しく**: 可用性セットが1つのデータセンター内の分散であるのに対し、可用性ゾーンは電源・冷却・ネットワークが独立した施設単位の分散です。VMは作成時にゾーンを指定し、後からゾーンだけを変更することはできません。ゾーンをまたぐ構成では、Load Balancerやゾーン冗長のPublic IPなど、前面の部品もゾーン対応にそろえる必要があります。
- **この案件では**: 学習費用を抑える判断から単一VMとし、ゾーン配置は行っていません。冗長化は未実装の発展課題です。
- **覚え方**: 「セットは同じ建物の中、ゾーンは建物ごと別」。内と外で対比します。
- **つまずきポイント**: ゾーンを指定すれば自動で複数台になると思いがちですが、実際は台数を増やして別ゾーンへ配置するのは設計者の仕事です。
- **関連**: 可用性セット / 仮想マシンスケールセット / リージョン

### 7.2.16 仮想マシンスケールセット(VMSS、Virtual Machine Scale Sets)

- **一言でいうと**: 同じ構成のVMを1つの群として扱い、台数の増減を自動化できる仕組みです。
- **たとえると**: 行列の長さでレジの台数を変えるスーパーです。1人ずつ雇うのではなく、必要な台数だけ開けます。
- **もう少し詳しく**: 1台ずつ手で作るのではなく、モデルとなる構成と台数を指定して群を管理します。CPU使用率などの条件で台数を増減させる自動スケールを組めば、負荷の波に追従できます。ゾーンをまたいだ配置にも対応するため、可用性とスケールを同時に確保する手段になります。前面にLoad Balancerを置き、どのVMへ振り分けても同じ結果になるようアプリを作ることが前提です。
- **この案件では**: 単一VM構成のため使用していません。台数を自動で増やす構成は発展課題です。
- **覚え方**: 「1台を育てるのではなく、群を増やす」。1台を大事に手入れする発想との対比で覚えます。
- **つまずきポイント**: VMSSにすれば既存のVMがそのまま増えると思いがちですが、実際は同じ構成をいつでも自動で作り直せる状態にしておく必要があります。
- **関連**: 可用性ゾーンへの配置 / カスタムデータとcloud-init / App ServiceとVMの使い分け

### 7.2.17 Accelerated Networking(高速ネットワーク)

- **一言でいうと**: VMのネットワーク処理をハードウェア側へ寄せ、遅延とCPU負荷を下げる機能です。
- **たとえると**: 荷物を毎回受付に通さず、専用の搬入口から直接倉庫へ入れることです。
- **もう少し詳しく**: 通常はホスト側の仮想スイッチがパケットを処理しますが、この機能を有効にするとVMがネットワークアダプターへ直接アクセスでき、経路が1段短くなります。遅延とそのばらつきが小さくなり、同じ通信量でもCPUの消費が下がります。設定はNIC単位で、対応するVMサイズとOSの組み合わせが必要なため、小さなサイズでは選べないことがあります。
- **この案件では**: 既定の`Standard_B1s`は小さなサイズであり、この機能を前提にした設計にはしていません。
- **覚え方**: Accelerateは「加速」。動作イメージは「経路の寄り道を1つ減らす」。
- **つまずきポイント**: どのVMでも有効にできると思いがちですが、実際はサイズとOSの対応条件があります。
- **関連**: NIC / VMサイズとシリーズ / VNet

### 7.2.18 予約インスタンスとSavings Plan(Reserved Instances / Savings Plan for compute)

- **一言でいうと**: 一定期間の利用を先に約束することで、従量課金より単価を下げる契約の仕組みです。
- **たとえると**: 定期券と回数券です。毎日乗ると分かっているなら、定期のほうが1回あたりが安くなります。
- **もう少し詳しく**: 予約インスタンスは1年または3年の期間で、対象や地域を決めて容量の利用をコミットする形です。Savings Planは同じ期間の枠組みで、1時間あたりの利用金額をコミットし、対象となるコンピューティングサービスの範囲で柔軟に適用されます。構成が固まって長く動かすものには効きますが、途中でやめる前提の学習環境には向きません。割引率や適用条件は契約と時期で変わるため、Azure Pricing CalculatorとCost Managementで確認します。
- **この案件では**: 短期間で作って壊す学習用途のため、いずれも使いません。費用は削除手順で抑えます。
- **覚え方**: 「予約は席を押さえる、Savings Planは金額を押さえる」。押さえる対象が違うと覚えます。
- **つまずきポイント**: 契約すれば何にでも自動で安くなると思いがちですが、実際は対象範囲と期間の条件があります。
- **関連**: Spot VM / Cost Management / Azure Hybrid Benefit

### 7.2.19 Spot VM(スポット仮想マシン)

- **一言でいうと**: Azureで余っている容量を安く借りる代わりに、いつ止められても困らない用途だけに使う方式です。
- **たとえると**: 飛行機の空席待ちです。空いていれば安く乗れますが、正規の予約が入れば席を譲ります。
- **もう少し詳しく**: 容量が必要になったとき、または設定した上限価格を超えたときに、Azure側からVMが退去させられます。退去時の動作は割り当て解除か削除のどちらかを選べます。中断しても再実行できるバッチ処理、検証、レンダリングなどに向き、止まると業務が止まるサーバーには使えません。
- **この案件では**: Webサーバーは常時応答する前提のため使用しません。
- **覚え方**: Spotは「その場限り」。安さの対価は中断だと1対1で結び付けます。
- **つまずきポイント**: 安いのだから本番でも使えると思いがちですが、実際は中断が前提のため、止まってはいけない用途には使えません。
- **関連**: 予約インスタンスとSavings Plan / Bシリーズ / 停止と停止(割り当て解除)の違い

### 7.2.20 Azure Hybrid Benefit(AHB、Azureハイブリッド特典)

- **一言でいうと**: すでに持っているサーバーOSやデータベースのライセンスをAzureへ持ち込んで使える仕組みです。
- **たとえると**: 引っ越し先で、いま使っているエアコンを持ち込み、備え付けを借りない選択です。
- **もう少し詳しく**: 対象は、ソフトウェアアシュアランス付きのWindows ServerやSQL Serverのライセンス、およびRHELやSLESといった有償Linuxのサブスクリプションです。適用するとVMの料金からライセンス相当分が外れます。対象と条件が細かいため、適用の前に自社の契約内容を確認する必要があります。
- **この案件では**: OSがUbuntuでライセンス費用が発生しないため、この特典の対象ではありません。
- **覚え方**: Hybridは「手元とクラウドの合わせ技」、Benefitは「特典」。ひとことで「持ち込み割引」。
- **つまずきポイント**: どのOSでも使えると思いがちですが、実際は対象のライセンスを持っている場合に限られます。
- **関連**: OSの選択 / 予約インスタンスとSavings Plan / SKU

### 7.2.21 App ServiceとVMの使い分け(App Service、IaaSとPaaSの選択)

- **一言でいうと**: OSまで自分で面倒を見るか、アプリだけに集中するかという、担当範囲の選択です。
- **たとえると**: 一戸建て(VM)と、管理会社付きの賃貸マンション(App Service)です。設備の面倒を誰が見るかが違います。
- **もう少し詳しく**: App ServiceはWebアプリの実行環境を提供する**PaaS**で、OSの更新やミドルウェアの管理をAzure側が担い、デプロイと台数増減の仕組みも用意されています。一方VMは、OS設定やミドルウェアの選択が自由で、既存の作りをそのまま動かせます。自由度を取るならVM、運用の手間を減らすならApp Serviceという軸で選び、Webサイト単体ならApp Serviceで足りることが多くあります。
- **この案件では**: サーバー構築の基礎を学ぶことが目的のため、あえてVM上にNginxを構築しています。実務でWebサイトだけを載せるなら、App Serviceの検討が先になります。
- **覚え方**: 「IaaSはOSから、PaaSはアプリから」。責任の線がどこに引かれるかで覚えます。
- **つまずきポイント**: VMのほうが本格的で優れていると思いがちですが、実際は要件次第で、運用負荷を含めて考えるとPaaSが有利な場面が多くあります。
- **関連**: IaaSとPaaS / コンテナー / 仮想マシンスケールセット

### 7.2.22 コンテナー(AKS / Container Apps)との違い

- **一言でいうと**: OSごと借りるVMに対し、アプリと必要な部品だけを軽く箱詰めして動かす方式です。
- **たとえると**: 引っ越しトラック(VM)と宅配便の箱(コンテナー)です。箱はどのトラックに載せ替えても中身が変わりません。
- **もう少し詳しく**: コンテナーはOSのカーネルを共有するため起動が速く、同じイメージをどの環境でも同じように動かせます。多数のコンテナーの配置・再起動・スケールを自動で管理する代表的な仕組みが**Kubernetes**で、そのマネージドサービスがAKS(Azure Kubernetes Service)です。Container Appsは、Kubernetesの運用を意識せずにコンテナーを動かせるサービスです。学習コストは上がるため、まずVMやApp Serviceで足りるかを先に見極めます。
- **この案件では**: 使用していません。まずVMでOS、Webサーバー、通信制御の基礎を押さえる段階です。
- **覚え方**: 「VMは家ごと、コンテナーは荷物だけ」。運ぶ単位の大きさで対比します。
- **つまずきポイント**: コンテナーにすれば運用が楽になると思いがちですが、実際はイメージ管理や基盤の運用という別の仕事が増えます。
- **関連**: App ServiceとVMの使い分け / 仮想マシンスケールセット / VMイメージとAzure Marketplace

## 7.3 このセクションの覚え方まとめ

```text
VMを1台作るときの決定チェックリスト(7項目)
1. 置き場所 : リージョン / リソースグループ / 可用性ゾーン
2. 器       : シリーズとVMサイズ / vCPUとメモリ / 世代
3. 中身     : VMイメージ / OS / ディスクのSKU
4. 入り口   : NIC / Public IP / NSG / SSHの鍵
5. 仕込み   : カスタムデータ(cloud-init) / VM拡張機能
6. 見張り   : 起動診断 / メトリックアラート / Log Analytics
7. お金     : 停止か割り当て解除か / 予約かSpotか / 削除手順
```

- 順番は「置く・盛る・詰める・つなぐ・仕込む・見張る・払う」の7語で思い出します。
- 最重要は7番です。エンジンを切るだけの「停止」ではコンピューティングの課金が続き、「停止(割り当て解除)」で枠を返して初めて止まります。
- 迷ったら「1台で足りるか」を先に問います。足りないなら台数の話(可用性セット、可用性ゾーン、VMSS)、手間を減らしたいならPaaSの話(App Service、コンテナー)へ進みます。
- この案件の単一VMは学習費用を抑えるための割り切りであり、冗長化・自動スケール・バックアップは未実装の発展課題だと説明できるようにしておきます。
