# 13. IaCと開発ツール

[用語集トップ](../11-azure-glossary.md) ・ 前: [12. コスト管理](12-cost.md) ・ 次: [14. 現場でよく使う仕事の言葉](14-workplace.md)

Azureの構成は、ポータルをクリックして作ることもできます。操作そのものはActivity Logに残りますが、なぜその値にしたのかという意図と差分は残りません。この案件では構成をBicepのコードで書き、What-Ifで予測を見てから作り、GitとGitHub Actionsで履歴とチェックを残します。このセクションの用語は、`infra/main.bicep`の実際の行を読めるようになるための道具です。手を動かす前に、コードの読み方と安全装置の名前を覚えてください。

## 13.2 用語解説

### 13.2.1 IaC(Infrastructure as Code、コードとしてのインフラ)

- **一言でいうと**: サーバーやネットワークの構成を、画面操作ではなくコードで書き、それを実行して作る進め方です。
- **たとえると**: 料理を口伝えでなく、レシピカードで配る形です。誰が作っても同じ味になります。
- **もう少し詳しく**: 手作業は速く始められますが、同じ環境をもう一度作ると必ずどこかが違います。コードにすれば何度でも再現でき、差分をレビューでき、履歴が残ります。
- **この案件では**: 構成はすべて`infra/main.bicep`とモジュール`infra/modules/workload.bicep`にあり、値を1か所直せば再構築できます。
- **覚え方**: 名前を分解します。Infrastructure(インフラ)as(として)Code(コード)。それだけです。
- **つまずきポイント**: IaCは上級者の道具と思いがちですが、実際は初心者ほど恩恵が大きいです。操作の記録はActivity Logにも残りますが、押し間違いを差分として見比べ、レビューして戻せるのはコードだけです。
- **関連**: Bicep / 宣言型と命令型 / べき等性

### 13.2.2 宣言型と命令型(Declarative / Imperative)

- **一言でいうと**: 宣言型は「最終的にこうなっていてほしい」を書き、命令型は「この順でこう操作せよ」を書く書き方です。
- **たとえると**: カーナビに目的地だけ入れるのが宣言型、「次の信号を右」と指示し続けるのが命令型です。
- **もう少し詳しく**: BicepとARMテンプレートは宣言型で、あるべき状態を書くと現在との差分をAzure側が埋めます。`az`コマンドの並びは命令型で、実行順と現在の状態に強く依存します。宣言型は再実行しやすく、命令型は細かい手順制御が得意です。
- **この案件では**: 構成はBicep(宣言型)、実行の段取りは`scripts/deploy.ps1`(命令型)と役割を分けています。
- **覚え方**: 対比で覚えます。**宣言型は完成写真、命令型は組立手順書**。家具を買ったとき、どちらを渡されるかの違いです。
- **つまずきポイント**: 宣言型なら順番を考えなくてよいと思いがちですが、実際は依存関係は必要で、Bicepが参照関係から自動で判断します。
- **関連**: IaC / べき等性 / デプロイモード

### 13.2.3 ARMテンプレート(ARM Template、JSON形式のデプロイ定義)

- **一言でいうと**: Azure Resource Managerが直接受け取れるJSON形式の構成定義ファイルです。
- **たとえると**: 役所に出す正式な申請書です。下書きのメモではなく、決まった書式の紙が受理されます。
- **もう少し詳しく**: AzureのリソースはすべてAzure Resource Manager経由で作られ、その入力形式がARMテンプレート(JSON)です。JSONは人が読み書きするには冗長なため、Bicepが生まれました。Bicepは実行前にこの形式へ変換されて送られます。
- **この案件では**: `scripts/deploy.ps1`が`az bicep build`でJSONへ変換できるかを先に確かめ、それからWhat-Ifへ進みます。
- **覚え方**: 動作イメージで覚えます。「Bicepで書く → JSONへ翻訳 → Azureへ提出」の3段です。
- **つまずきポイント**: 古い形式だから使わないと思いがちですが、実際はBicepを使っていても内部では常にこの形式です。
- **関連**: Bicep / リソース宣言とAPIバージョン / IaC

### 13.2.4 Bicep(バイセップ、Azure向けIaC言語)

- **一言でいうと**: ARMテンプレートと同じことを、はるかに短く読みやすく書けるAzure専用の言語です。
- **たとえると**: 手書きの申請書を、入力補助つきのアプリで作る形です。書類は同じでも負担が減ります。
- **もう少し詳しく**: 拡張子は`.bicep`で、リソース定義、パラメーター、変数、出力、モジュール、条件やループを簡潔に書けます。エディターの補完が効くため、初心者でも書き間違いに気づけます。Azure専用である代わりに、Azureのサービスを最も素直に表現できます。
- **この案件では**: 入口が`infra/main.bicep`、実体の大半がモジュール`infra/modules/workload.bicep`です。
- **覚え方**: 語源で覚えます。bicepは上腕二頭筋、つまり**腕(ARM)を曲げる筋肉**です。ARMを動かす筋肉と結びつけます。
- **つまずきポイント**: Bicepを覚えればARMテンプレートは不要と思いがちですが、実際は変換後のJSONを読む場面が残ります。
- **関連**: ARMテンプレート / リンター / モジュール

### 13.2.5 リソース宣言とAPIバージョン(resource / API Version)

- **一言でいうと**: `resource`は「Azureに何を作るか」の宣言で、`@`のあとの日付はどの版の仕様で作るかの指定です。
- **たとえると**: 申請書の様式番号と改訂年月です。何年版の様式かで書く欄が変わります。
- **もう少し詳しく**: 書式は`resource シンボル名 '種別@APIバージョン' = { ... }`です。シンボル名は内部で参照する名札、種別は`プロバイダー/リソース種類`、APIバージョンは日付です。版を明示するので、Azureの仕様が更新されても既存コードの挙動は変わりません。
- **この案件では**: 実例は`infra/main.bicep`の`Microsoft.Resources/resourceGroups@2024-11-01`です。
- **覚え方**: 数字で覚えます。1行に必要な情報は**3つ**、名札・種別・日付です。
- **つまずきポイント**: APIバージョンは新しければよいと思いがちですが、実際は種別ごとに提供される版が違い、存在しない日付はエラーです。
- **関連**: ARMテンプレート / Bicep / モジュール

### 13.2.6 パラメーター(param)とパラメーターファイル(.bicepparam)

- **一言でいうと**: `param`は外から値を差し込む受け口で、`.bicepparam`はその値を環境ごとにまとめるファイルです。
- **たとえると**: レシピと買い物メモの関係です。作り方は共通で、人数や辛さだけ差し替えます。
- **もう少し詳しく**: `param`には型、既定値、`@allowed`、`@secure()`を付けられます。`@secure()`の値は履歴やログに出ません。ファイル側は冒頭の`using`で対象のBicepを指定します。
- **この案件では**: `infra/main.bicep`は`location`など9個を受け取り、`sshPublicKey`は`@secure()`、`environment`は`dev`と`test`のみ`@allowed`、`openHttp`の既定値は`false`です。
- **覚え方**: **paramは受け口、.bicepparamは差し込む値**。コンセントとプラグの関係です。
- **つまずきポイント**: 既定値があるから省けると思いがちですが、実際は`owner`など既定値のないものは必須です。
- **関連**: 変数と出力 / シークレットをコミットしない / モジュール

### 13.2.7 変数(var)と出力(output)

- **一言でいうと**: `var`はコード内で使い回す計算結果の置き場、`output`はデプロイ後に外へ返す結果の置き場です。
- **たとえると**: `var`は下書き用のメモ、`output`は完了報告書です。メモは自分だけが見ます。
- **もう少し詳しく**: `var`は命名規則やタグの塊をまとめるのに向き、同じ文字列を何度も書くミスを防ぎます。`output`はデプロイ後に確認したい値を返します。秘密の値は履歴から読めるため、鍵やパスワードは返しません。
- **この案件では**: `var suffix`から`rg-${suffix}`が作られます。`output`は`resourceGroupName`、`vmName`、`publicIpAddress`、`sshCommand`の4つです。
- **覚え方**: 向きで覚えます。**varは内向き、outputは外向き**。矢印を内と外に描くと迷いません。
- **つまずきポイント**: `output`は単なるログと思いがちですが、実際は呼び出し側から参照できる正式な戻り値です。
- **関連**: パラメーターとパラメーターファイル / モジュール / シークレットをコミットしない

### 13.2.8 モジュール(module、部品化したBicep)

- **一言でいうと**: 別のBicepファイルを部品として呼び出し、値を渡して実行させる仕組みです。
- **たとえると**: 会社の組織です。社長が全部やらず、部署に依頼書を渡し、部署から報告を受け取ります。
- **もう少し詳しく**: 書式は`module シンボル名 'パス' = { name: ..., scope: ..., params: { ... } }`です。`params`で子へ値を渡し、`シンボル名.outputs.項目名`で結果を受け取ります。役割ごとに分けられるのでレビュー範囲も絞れます。
- **この案件では**: `infra/main.bicep`が`module workload 'modules/workload.bicep'`に`scope: resourceGroup`を渡して中身を任せます。
- **覚え方**: 親が渡すのは`params`、子が返すのは`outputs`。**渡して、返る**の往復1セットです。
- **つまずきポイント**: 分割すると難しくなると思いがちですが、実際は詳細を子に隠せるので読みやすくなります。
- **関連**: デプロイのスコープ / 変数と出力 / コードレビューの観点

### 13.2.9 デプロイのスコープ(Deployment Scope、対象範囲)

- **一言でいうと**: そのデプロイをAzureのどの階層に対して行うかという、対象範囲の指定です。
- **たとえると**: 住所の階層です。国、都道府県、市区町村のどこ向けかで、できることが変わります。
- **もう少し詳しく**: Azureの階層はテナント、管理グループ、サブスクリプション、リソースグループの順に細かくなります。Bicepでは冒頭の`targetScope`で宣言し、既定はリソースグループです。リソースグループ自体を作るには、外側のサブスクリプションスコープが必要です。
- **この案件では**: `infra/main.bicep`の1行目が`targetScope = 'subscription'`で、`scripts/deploy.ps1`は`az deployment sub`系を使います。
- **覚え方**: 大きい順に4段、**テ・カ・サ・リ**(テナント、管理グループ、サブスクリプション、リソースグループ)。
- **つまずきポイント**: どのスコープでも同じコマンドで通ると思いがちですが、実際は書き方から変わります。
- **関連**: モジュール / リソースグループ / デプロイモード

### 13.2.10 デプロイモード(増分 / 完全、Incremental / Complete)

- **一言でいうと**: コードに書いていない既存リソースを残すか消すかを決める、デプロイ時の動作の切り替えです。
- **たとえると**: 部屋の片付けです。増分は「リストの物を置くだけ」、完全は「ない物は捨てる」です。
- **もう少し詳しく**: 増分モードが既定で、書かれたものを作成または更新し、書かれていない既存リソースには触れません。完全モードはコードにないリソースを削除します。なお完全モードを選べるのはリソースグループスコープのデプロイだけで、サブスクリプションより外側のスコープは増分モードのみです。
- **この案件では**: `infra/main.bicep`はサブスクリプションスコープなので、選択の余地なく増分モードで動きます。消すときは`scripts/remove.ps1`でリソースグループ名を二重に指定します。
- **覚え方**: **増分は足し算だけ、完全は引き算つき**。引き算がある方が怖いのです。
- **つまずきポイント**: 完全モードのほうが実物と揃うと思いがちですが、実際は削除を伴うため事前の確認が要ります。
- **関連**: What-If / べき等性 / ドリフト

### 13.2.11 べき等性(Idempotency、何度実行しても同じ)

- **一言でいうと**: 同じコードを何回実行しても、結果が同じ状態に落ち着く性質です。
- **たとえると**: エレベーターの階数ボタンです。3階を10回押しても、3階に着くだけです。
- **もう少し詳しく**: 宣言型のBicepは「あるべき状態」を書くため、2回目の実行では差がない部分は何もしません。通信が切れて途中で止まっても同じコマンドを再実行できます。誰かが画面から設定を変えても、コードを再適用すれば本来の状態へ戻せます。
- **この案件では**: `scripts/deploy.ps1`は毎回`az bicep build`とWhat-Ifから始まるため、何度実行しても構成は`infra/main.bicep`の内容に収束します。
- **覚え方**: 漢字で分解します。「べき」は累乗の冪、1は何乗しても1です。**1のべき乗**を思い出します。
- **つまずきポイント**: 何度実行しても完全に無害と思いがちですが、実際はVMの再起動を伴う変更などは実行時に影響が出ます。
- **関連**: 宣言型と命令型 / What-If / ドリフト

### 13.2.12 What-If(変更予測、変更の事前確認)

- **一言でいうと**: 実際には作らずに、今このコードを適用したら何がどう変わるかを一覧で出す機能です。
- **たとえると**: 健康診断の結果説明です。まだ治療はしていませんが、どこを直すべきかが先に分かります。
- **もう少し詳しく**: 現在のAzureの状態とコードを突き合わせ、作成、変更、削除、変更なしの区分で予測を表示します。特に見るべきは削除と変更で、意図しない削除が並んでいたら実行してはいけません。予測なので実物との完全一致は保証されませんが、事故の大半はここで止まります。
- **この案件では**: `scripts/deploy.ps1`は既定でWhat-Ifだけを実行し、`-Apply`を明示しない限りリソースを作りません。`adminCidr`が`0.0.0.0/0`の場合はWhat-If以前に止まります。
- **覚え方**: 直訳がそのまま意味です。**やる前に、もしもを見る**と唱えます。
- **つまずきポイント**: What-Ifを実行すると作られてしまうと思いがちですが、実際は何も作りません。
- **関連**: デプロイモード / べき等性 / コードレビューの観点

### 13.2.13 ドリフト(Drift、手作業による差異)

- **一言でいうと**: コードに書いた構成と、Azure上の実物がずれてしまった状態です。
- **たとえると**: 船が錨を下ろさずに潮に流されるのと同じです。動かしたつもりはないのに位置が違います。
- **もう少し詳しく**: 障害対応中に画面から一時的にルールを開ける作業が原因の大半です。コードが正のはずなのに実物が違うと、次のデプロイで設定が突然戻り、原因不明の障害に見えます。防ぎ方は3つ、緊急変更を記録する、落ち着いたらコードへ反映する、定期的にWhat-Ifで差分を見る、です。
- **この案件では**: 学習中に画面からNSGのルールを足すと、次に`scripts/deploy.ps1`を実行したときWhat-Ifに変更予定として現れます。
- **覚え方**: 動作イメージで覚えます。**コードは真っすぐ、実物が滑った**と絵にすると、どちらを直すべきかも見えます。
- **つまずきポイント**: 小さな手直しならコードに戻さなくてよいと思いがちですが、実際は次のデプロイで消えます。
- **関連**: べき等性 / What-If / コードレビューの観点

### 13.2.14 リンター(Linter、静的な書き方チェック)

- **一言でいうと**: 実行しなくても分かる書き方の問題を、コードを読むだけで指摘してくれる検査役です。
- **たとえると**: 提出前に文書を見てくれる先輩です。内容の是非より前に、書式のほころびを拾います。
- **もう少し詳しく**: Bicepにはリンターが組み込まれており、`az bicep build`などの際に警告として表示されます。使われていないパラメーターや変数、推奨されない書き方が対象です。`bicepconfig.json`を置けば規則の有効無効や深刻度を調整できます。文法エラーと違って処理は止まりません。
- **この案件では**: CIとローカルの両方で`az bicep build`が走るため、書いた直後に指摘を受け取れます。
- **覚え方**: 語源で覚えます。lintは衣類につく糸くずや毛玉のこと。**コードの毛玉取り**と覚えます。
- **つまずきポイント**: 警告が出てもビルドできたから問題なしと思いがちですが、実際は警告は将来の事故の予告です。
- **関連**: CI/CD / Bicep / コードレビューの観点

### 13.2.15 Terraform(テラフォーム、マルチクラウド対応のIaCツール)

- **一言でいうと**: Azureだけでなく複数のクラウドを同じ書き方で扱える、代表的なIaCツールです。
- **たとえると**: 共通規格のドライバーセットです。1本で複数のねじに対応でき、専用工具ほどはなじみません。
- **もう少し詳しく**: HashiCorp社が開発し、HCLという記法で構成を書きます。宣言型で、`terraform plan`が変更内容を事前に見せる点はWhat-Ifと同じ発想です。大きな違いは自分で状態ファイルを持って現状を管理することで、その置き場と共有方法が実務の論点になります。
- **覚え方**: 対比で覚えます。**BicepはAzure専用の母国語、Terraformは多クラウドの共通語**です。
- **つまずきポイント**: どちらが優れているかの勝負と思いがちですが、実際は対象範囲と組織の事情で選ぶ話です。
- **関連**: Bicep / What-If / IaC

### 13.2.16 Git・ブランチ・プルリクエスト(Git / Branch / Pull Request)

- **一言でいうと**: 変更の履歴を残し、作業用の枝で試し、本線へ取り込む前に他人の確認を通す仕組みです。
- **たとえると**: 鉄道の路線です。本線を止めずに支線で試運転し、安全確認が済んでから合流させます。
- **もう少し詳しく**: Gitは変更をコミット単位で記録する仕組みで、いつ誰が何を変えたかを追えます。ブランチは本線から分けた作業用の枝で、失敗しても本線は無傷です。プルリクエストは枝を本線へ取り込む依頼で、差分、レビュー、自動チェックの結果がここに集まります。
- **この案件では**: `.github/workflows/validate.yml`はプルリクエストとmainへのpushで動くため、本線へ入れる前に自動検査が回ります。
- **覚え方**: 3語で覚えます。**記録するのがコミット、分けるのがブランチ、頼むのがプルリクエスト**。
- **つまずきポイント**: 1人開発ならブランチは不要と思いがちですが、実際は作業単位を分けると差分が読みやすくなります。
- **関連**: CI/CD / コードレビューの観点 / シークレットをコミットしない

### 13.2.17 CI/CD(Continuous Integration / Continuous Delivery、GitHub Actions)

- **一言でいうと**: 変更を入れるたびに検査や配布を自動で走らせ、壊れた状態が本線に入るのを防ぐ仕組みです。
- **たとえると**: 工場の自動検品機です。人の目に頼らず、毎回同じ基準で全数を検査します。
- **もう少し詳しく**: CIは変更を頻繁に統合して毎回自動検査すること、CDはその成果物を継続的に届けることです。GitHub Actionsは`.github/workflows/`配下のYAMLに、いつ動くかと何をするかを書きます。インフラでは静的検査だけでも効きます。
- **この案件では**: `.github/workflows/validate.yml`が`az bicep build`、`az bicep build-params`、Markdownリンク、`git diff --check`の4つを検査します。
- **覚え方**: 頭文字を開きます。CIは**継続的に統合**、CDは**継続的に届ける**です。
- **つまずきポイント**: CIが通れば本番でも動くと思いがちですが、見ているのは書式と整合性だけです。
- **関連**: リンター / Git・ブランチ・プルリクエスト / What-If

### 13.2.18 シークレットをコミットしない(Secrets、.gitignoreの役割)

- **一言でいうと**: 秘密鍵やパスワード、実在のIPやIDをGitに入れない鉄則と、それを守らせる仕組みです。
- **たとえると**: 合鍵をコピーして掲示板に貼るようなものです。剥がしても写真が残れば同じです。
- **もう少し詳しく**: Gitは履歴を保存するので、一度コミットした値はファイルを消しても過去に残ります。公開リポジトリなら流出と同義で、対応は鍵の無効化と再発行です。`.gitignore`は条件に合うファイルを管理対象から外す指定です。
- **この案件では**: `.gitignore`が`infra/parameters/*.bicepparam`を無視し、`!infra/parameters/*.example.bicepparam`で例だけを追跡対象に戻します。
- **覚え方**: 数字で覚えます。**取り消せない回数は1回**。送信ボタンと同じです。
- **つまずきポイント**: あとで削除すれば大丈夫と思いがちですが、実際は履歴に残るため正解は入れないことだけです。
- **関連**: パラメーターとパラメーターファイル / Git・ブランチ・プルリクエスト / コードレビューの観点

### 13.2.19 コードレビューの観点(Code Review Checklist)

- **一言でいうと**: 他人のインフラコードを見るとき、感想ではなく決まった軸で確認するための着眼点です。
- **たとえると**: 車の点検です。気になった所を眺めるのではなく、点検表の項目を順に見ていきます。
- **もう少し詳しく**: インフラのレビューは、動くかどうかより危なくないかを見ます。中心は6点、名前が命名規則に沿っているか、通信の穴が広すぎないか、秘密の値が混ざっていないか、既定値が安全側か、What-Ifに意図しない削除がないか、タグが揃っているかです。
- **この案件では**: `adminCidr`が`/32`など十分に狭いか、`openHttp`が`false`のままか、`sshPublicKey`に公開鍵しか入っていないか、`commonTags`が付いているかを見ます。
- **覚え方**: **名前・穴・秘密・既定・消える・札**。語呂で口に出すと順に出てきます。
- **つまずきポイント**: レビューは詳しい人の仕事と思いがちですが、実際は初心者が分からないと書くだけでも欠陥が見つかります。
- **関連**: What-If / シークレットをコミットしない / CI/CD

## 13.3 このセクションの覚え方まとめ

このセクションは、コードを書く順番でそのまま覚えられます。

```text
書く      : param で受ける → var で組む → resource で宣言 → module に任せる → output で返す
確かめる  : リンター → az bicep build(JSON化) → What-If → -Apply
守る      : 増分が既定 / べき等だから再実行できる / ドリフトはコードへ書き戻す
残す      : ブランチで作業 → プルリクエスト → CIが自動検査 → レビューで6点確認
```

覚える柱は3本だけです。1本目は**宣言型**、完成形を書けばAzureが差分を埋める。2本目は**べき等性**、だから何度でも安全に実行できる。3本目は**What-If**、それでも実行前に必ず予測を見る。この3本が繋がると、`infra/main.bicep`と`scripts/deploy.ps1`が何を守っている仕組みなのかが読めるようになります。

そして最後に、覚え方より優先する1行があります。**秘密の値はコミットしない**。他はやり直せますが、これだけはやり直せません。
