# 13. IaCと開発ツール

[用語集トップ](../11-azure-glossary.md) ・ 前: [12. コスト管理](12-cost.md) ・ 次: [14. 現場でよく使う仕事の言葉](14-workplace.md)

Azureの構成は、ポータルをクリックして作ることもできますが、それでは「誰が何をどう変えたか」が残りません。この案件では構成をBicepのコードで書き、What-Ifで予測を見てから作り、GitとGitHub Actionsで履歴とチェックを残します。このセクションの用語は、`infra/main.bicep`の実際の行を読めるようになるための道具です。手を動かす前に、コードの読み方と安全装置の名前を覚えてください。

## 13.2 用語解説

### 13.2.1 IaC(Infrastructure as Code、コードとしてのインフラ)

- **一言でいうと**: サーバーやネットワークの構成を、画面操作ではなくコードで書き、それを実行して作る進め方です。
- **たとえると**: 料理を口伝えで教えるのをやめて、レシピカードを配るようなものです。誰が作っても同じ味になり、味を変えたければカードを直します。
- **もう少し詳しく**: 手作業は速く始められますが、同じ環境をもう一度作るとき必ずどこかが違います。コードにしておくと、同じものを何度でも再現でき、変更の差分をレビューでき、履歴が残ります。インフラを扱う仕事がアプリ開発と同じ道具で回せるようになる、という点が本質です。
- **この案件では**: 構成はすべて`infra/main.bicep`とモジュール`infra/modules/workload.bicep`に書かれています。設計書とコードが対応しているので、値を1か所直せば再構築できます。
- **覚え方**: 名前をそのまま分解します。Infrastructure(インフラ)as(として)Code(コード)。「インフラを、コードとして扱う」以上の意味はありません。
- **つまずきポイント**: IaCは上級者の道具と思いがちですが、実際は初心者ほど恩恵が大きいです。押し間違いを記録に残せるのはコードだけです。
- **関連**: Bicep / 宣言型と命令型 / べき等性

### 13.2.2 宣言型と命令型(Declarative / Imperative)

- **一言でいうと**: 宣言型は「最終的にこうなっていてほしい」を書き、命令型は「この順番でこう操作せよ」を書く書き方です。
- **たとえると**: カーナビに目的地だけ入れるのが宣言型、同乗者に「次の信号を右」と指示し続けるのが命令型です。
- **もう少し詳しく**: BicepとARMテンプレートは宣言型です。あるべき状態を書くと、現在との差分をAzure側が判断して埋めます。一方でシェルスクリプトや`az`コマンドの並びは命令型で、実行順と現在の状態に強く依存します。宣言型は途中で失敗しても再実行しやすく、命令型は細かい手順制御が得意です。
- **この案件では**: 構成そのものはBicep(宣言型)、実行の段取りは`scripts/deploy.ps1`(命令型)と役割を分けています。
- **覚え方**: 対比で覚えます。**宣言型は「完成写真」、命令型は「組立手順書」**。家具を買ったとき、写真だけ渡されるか手順書を渡されるかの違いです。
- **つまずきポイント**: 宣言型なら順番を考えなくてよいと思いがちですが、実際は依存関係(サブネットができてからNICを作る等)は必要で、Bicepはそれを参照関係から自動で判断します。
- **関連**: IaC / べき等性 / デプロイモード

### 13.2.3 ARMテンプレート(ARM Template、JSON形式のデプロイ定義)

- **一言でいうと**: Azure Resource Managerが直接受け取れるJSON形式の構成定義ファイルです。
- **たとえると**: 役所に出す正式な申請書です。人間が下書きしたメモではなく、決まった書式に落とし込んだ紙が最終的に受理されます。
- **もう少し詳しく**: AzureのリソースはすべてAzure Resource Manager経由で作られ、その入力形式がARMテンプレート(JSON)です。JSONは波かっことカンマが多く、人が読み書きするには冗長でした。そこでBicepが生まれ、Bicepは実行前にARMテンプレートへ変換されてから送られます。つまりBicepとARMテンプレートは対立する選択肢ではなく、下書きと提出物の関係です。
- **この案件では**: `scripts/deploy.ps1`が`az bicep build`を実行し、JSONへ変換できるかを先に確かめてからWhat-Ifへ進みます。
- **覚え方**: 動作イメージで覚えます。「Bicepで書く → JSONへ翻訳 → Azureへ提出」。翻訳をサボると提出できない、と考えると`az bicep build`の意味も腑に落ちます。
- **つまずきポイント**: 古い形式だから使わないと思いがちですが、実際はBicepを使っていても内部では常にこの形式が使われています。エラーメッセージがJSON寄りの表現で出るのはそのためです。
- **関連**: Bicep / リソース宣言とAPIバージョン / IaC

### 13.2.4 Bicep(バイセップ、Azure向けIaC言語)

- **一言でいうと**: ARMテンプレートと同じことを、はるかに短く読みやすく書けるAzure専用の言語です。
- **たとえると**: 手書きの申請書を、入力補助つきの申請アプリで作るようなものです。出てくる書類は同じでも、書く負担が大きく減ります。
- **もう少し詳しく**: 拡張子は`.bicep`で、リソース定義、パラメーター、変数、出力、モジュール、条件分岐やループを簡潔に書けます。Azureの新しいリソース種別にも追随しやすく、エディターの補完が効くため初心者でも書き間違いに気づけます。Azure専用である代わりに、Azureのサービスを最も素直に表現できます。
- **この案件では**: 入口が`infra/main.bicep`、実体の大半がモジュール`infra/modules/workload.bicep`です。まずこの2ファイルを読めれば、設計書の値がどこに効くかが分かります。
- **覚え方**: 語源で覚えます。bicepは上腕二頭筋、つまり**腕(ARM)を曲げる筋肉**です。ARMテンプレートを動かす筋肉、と結びつけると忘れません。
- **つまずきポイント**: Bicepを覚えればARMテンプレートは不要と思いがちですが、実際は変換後のJSONを読む場面が残ります。両方の存在を知っておくと調査が速くなります。
- **関連**: ARMテンプレート / リンター / モジュール

### 13.2.5 リソース宣言とAPIバージョン(resource / API Version)

- **一言でいうと**: `resource`は「Azureに何を作るか」の宣言で、`@`のあとの日付はその種別のどの版の仕様で作るかの指定です。
- **たとえると**: 申請書の様式番号と改訂年月です。同じ「住民票の申請」でも、令和何年版の様式かで書く欄が変わります。
- **もう少し詳しく**: 書式は`resource シンボル名 '種別@APIバージョン' = { ... }`です。シンボル名はBicep内部で参照するための名札、種別は`プロバイダー/リソース種類`、APIバージョンは日付形式です。版を明示するので、Azure側の仕様が更新されても既存コードの挙動が勝手に変わりません。
- **この案件では**: `infra/main.bicep`に`resource resourceGroup 'Microsoft.Resources/resourceGroups@2024-11-01'`があり、`infra/modules/workload.bicep`には`resource nsg 'Microsoft.Network/networkSecurityGroups@2024-05-01'`があります。種別が違えばAPIバージョンも別に管理されると分かります。
- **覚え方**: 数字で覚えます。1行に必要な情報は**3つ**、名札・種別・日付です。この3点が揃っていない`resource`行はありません。
- **つまずきポイント**: APIバージョンは新しければよいと思いがちですが、実際は種別ごとに提供されている版が違い、存在しない日付を書くとエラーになります。
- **関連**: ARMテンプレート / Bicep / モジュール

### 13.2.6 パラメーター(param)とパラメーターファイル(.bicepparam)

- **一言でいうと**: `param`はコードの外から値を差し込む受け口で、`.bicepparam`はその値を環境ごとにまとめて書くファイルです。
- **たとえると**: レシピ本文と買い物メモの関係です。作り方は共通で、人数や好みの辛さだけメモを差し替えます。
- **もう少し詳しく**: `param`には型、既定値、`@allowed`などの制約、`@secure()`を付けられます。`@secure()`の値はデプロイ履歴やログに出力されません。パラメーターファイルは冒頭の`using`で対象のBicepを指定するため、対応関係が壊れていれば変換時に検出できます。
- **この案件では**: `infra/main.bicep`が`location`、`environment`、`projectName`、`owner`、`sshPublicKey`、`adminCidr`、`openHttp`、`vmSize`、`adminUsername`を受け取ります。`sshPublicKey`は`@secure()`、`environment`は`dev`と`test`のみ`@allowed`、`openHttp`の既定値は`false`です。例は`infra/parameters/dev.example.bicepparam`で、1行目が`using '../main.bicep'`です。
- **覚え方**: 対比で覚えます。**paramは受け口、.bicepparamは差し込む値**。コンセントとプラグの関係で、形が合わなければ挿さりません。
- **つまずきポイント**: 既定値があるから書かなくてよいと思いがちですが、実際は`owner`や`adminCidr`のように既定値のないものは必須で、指定しないとデプロイが始まりません。
- **関連**: 変数と出力 / シークレットをコミットしない / モジュール

### 13.2.7 変数(var)と出力(output)

- **一言でいうと**: `var`はコード内で使い回す計算結果の置き場、`output`はデプロイ後に外へ返す結果の置き場です。
- **たとえると**: `var`は下書き用のメモ、`output`は完了報告書です。メモは自分だけが見て、報告書は依頼者に渡します。
- **もう少し詳しく**: `var`はパラメーターを組み合わせた命名規則やタグの塊をまとめるのに向き、同じ文字列を何度も書くミスを防ぎます。`output`はデプロイ後に確認したい値を返すもので、次の作業のコマンドをそのまま組み立てて返すこともできます。`output`に秘密の値を入れると履歴から読めてしまうため、鍵やパスワードは返しません。
- **この案件では**: `var suffix = '${projectName}-${environment}-${regionCode}-001'`が命名の土台で、そこから`rg-${suffix}`が作られます。`output`は`resourceGroupName`、`vmName`、`publicIpAddress`、そして`ssh ${adminUsername}@...`という形の`sshCommand`の4つです。
- **覚え方**: 向きで覚えます。**varは内向き、outputは外向き**。矢印を内側と外側に描くと、どちらに何を書くか迷いません。
- **つまずきポイント**: `output`は単なるログと思いがちですが、実際は呼び出し側から参照できる正式な戻り値で、モジュールの`output`は親から読み出して使います。
- **関連**: パラメーターとパラメーターファイル / モジュール / シークレットをコミットしない

### 13.2.8 モジュール(module、部品化したBicep)

- **一言でいうと**: 別のBicepファイルを部品として呼び出し、値を渡して実行させる仕組みです。
- **たとえると**: 会社の組織です。社長が全部やるのではなく、部署に依頼書(パラメーター)を渡し、部署から報告(出力)を受け取ります。
- **もう少し詳しく**: 書式は`module シンボル名 'パス' = { name: ..., scope: ..., params: { ... } }`です。`params`で子へ値を渡し、`シンボル名.outputs.項目名`で結果を受け取ります。役割ごとにファイルを分けられるので、1ファイルが長くなりすぎず、レビューの範囲も絞れます。
- **この案件では**: `infra/main.bicep`はリソースグループを作り、`module workload 'modules/workload.bicep'`に`scope: resourceGroup`を指定して中身の構築を任せます。親側の`output vmName string = workload.outputs.vmName`が、子の出力を受け取っている実例です。
- **覚え方**: 動作イメージで覚えます。親が渡すのは`params`、子が返すのは`outputs`。**渡して、返る**の往復1セットがモジュールです。
- **つまずきポイント**: 分割すると難しくなると思いがちですが、実際は親が「どこに何を作らせるか」だけを持ち、詳細を子に隠せるので読みやすくなります。
- **関連**: デプロイのスコープ / 変数と出力 / コードレビューの観点

### 13.2.9 デプロイのスコープ(Deployment Scope、対象範囲)

- **一言でいうと**: そのデプロイをAzureのどの階層に対して行うかという対象範囲の指定です。
- **たとえると**: 住所の階層です。国、都道府県、市区町村、番地のどこに向けた手続きかで、できることが変わります。
- **もう少し詳しく**: Azureの階層はテナント、管理グループ、サブスクリプション、リソースグループの順に細かくなります。Bicepではファイル冒頭の`targetScope`で宣言し、既定はリソースグループです。リソースグループそのものを作りたい場合は、より外側のサブスクリプションスコープが必要になり、使うコマンドも変わります。
- **この案件では**: `infra/main.bicep`の1行目が`targetScope = 'subscription'`です。リソースグループ`rg-portfolio-dev-jpe-001`をコード側で作るため外側から始め、中身はモジュールに`scope: resourceGroup`を渡します。`scripts/deploy.ps1`が`az deployment sub`系を使うのはこのためです。
- **覚え方**: 大きい順に4段、**テ・カ・サ・リ**(テナント、管理グループ、サブスクリプション、リソースグループ)。頭文字を階段状に並べて覚えます。
- **つまずきポイント**: どのスコープでも同じコマンドで通ると思いがちですが、実際はスコープが違うとコマンドも書き方も変わり、取り違えるとリソースグループが見つからないという趣旨のエラーになります。
- **関連**: モジュール / リソースグループ / デプロイモード

### 13.2.10 デプロイモード(増分 / 完全、Incremental / Complete)

- **一言でいうと**: コードに書いていない既存リソースを残すか消すかを決める、デプロイ時の動作の切り替えです。
- **たとえると**: 部屋の片付けです。増分は「リストの物を置くだけ」、完全は「リストにない物は捨てる」です。
- **もう少し詳しく**: 増分モードが既定で、コードに書かれたものを作成または更新し、書かれていない既存リソースには手を触れません。完全モードは対象範囲内でコードに書かれていないリソースを削除するため、意図しない消失が起こりえます。完全モードを使う場面はありますが、初心者のうちは増分のままにし、消したいものは削除手順で明示的に消すのが安全です。
- **この案件では**: モードを指定していないため増分で動きます。学習後に消すときは`scripts/remove.ps1`でリソースグループ名を二重に指定して削除します。
- **覚え方**: 対比と記号で覚えます。**増分は足し算だけ、完全は引き算つき**。引き算がある方が怖い、と覚えれば選択を間違えません。
- **つまずきポイント**: 完全モードのほうがコードと実物が揃うので良いと思いがちですが、実際は削除を伴うため、What-Ifで削除予定を確認せずに使うと事故になります。
- **関連**: What-If / べき等性 / ドリフト

### 13.2.11 べき等性(Idempotency、何度実行しても同じ)

- **一言でいうと**: 同じコードを何回実行しても、結果が同じ状態に落ち着く性質です。
- **たとえると**: エレベーターの階数ボタンです。3階を10回押しても、11階へ行ったり3つ止まったりはせず、3階に着くだけです。
- **もう少し詳しく**: 宣言型のBicepは「あるべき状態」を書くため、2回目の実行では差がない部分は何もしません。この性質があるので、通信が切れて途中で止まっても同じコマンドを安心して再実行できます。さらに、誰かが画面から設定を変えてしまっても、コードを再適用すれば本来の状態へ戻せます。本教材が「怖くない」のは、この性質が土台にあるからです。
- **この案件では**: `scripts/deploy.ps1`は毎回`az bicep build`とWhat-Ifから始まるため、同じパラメーターで何度実行しても構成は`infra/main.bicep`の内容に収束します。
- **覚え方**: 漢字で分解します。「べき」は累乗の冪、1は何乗しても1です。**1のべき乗**を思い出せば「何回やっても同じ」が出てきます。
- **つまずきポイント**: 何度実行しても完全に無害と思いがちですが、実際はVMの再起動を伴う変更などは実行時に影響が出ます。無害なのは「状態が同じなら何もしない」部分だけです。
- **関連**: 宣言型と命令型 / What-If / ドリフト

### 13.2.12 What-If(変更予測、変更の事前確認)

- **一言でいうと**: 実際には作らずに、「今このコードを適用したら何がどう変わるか」を一覧で出す機能です。
- **たとえると**: 健康診断の結果説明です。まだ治療はしていませんが、どこをどう直す必要があるかが先に分かります。
- **もう少し詳しく**: 現在のAzureの状態とコードを突き合わせ、作成、変更、削除、変更なしといった区分でリソースごとに予測を表示します。特に見るべきは削除と変更で、意図しない削除が並んでいたらそのまま実行してはいけません。予測なので実物と完全一致は保証されませんが、事故の大半はここで止まります。IaCの安全装置として最も費用対効果が高い手順です。
- **この案件では**: `./scripts/deploy.ps1 -ParameterFile ...`は既定でWhat-Ifだけを実行して停止し、`-Apply`を明示しない限りリソースを作りません。加えて`adminCidr`が`0.0.0.0/0`の場合や、例の公開鍵が置き換えられていない場合、秘密鍵らしい文字列が含まれる場合は、What-If以前に処理を止めます。
- **覚え方**: 直訳がそのまま意味です。What if I run this、「もしこれを実行したら」。**やる前に、もしもを見る**と唱えます。
- **つまずきポイント**: What-Ifを実行すると作られてしまうと思いがちですが、実際は何も作りません。逆に、What-Ifが成功したから本番も必ず成功するとも限りません。
- **関連**: デプロイモード / べき等性 / コードレビューの観点

### 13.2.13 ドリフト(Drift、手作業による差異)

- **一言でいうと**: コードに書いた構成と、Azure上の実物がずれてしまった状態です。
- **たとえると**: 船が錨を下ろさずに潮に流されるのと同じです。動かしたつもりはないのに、いつのまにか位置が違います。
- **もう少し詳しく**: 障害対応中に画面から一時的にルールを開ける、といった作業が原因の大半です。コードが正であるはずなのに実物が違うと、次のデプロイで設定が突然戻り、原因不明の障害に見えます。防ぎ方は3つ、緊急変更を記録する、落ち着いたらコードへ反映する、定期的にWhat-Ifで差分を見る、です。
- **この案件では**: 学習中に画面からNSGのルールを足すと、次に`scripts/deploy.ps1`を実行したときWhat-Ifに変更予定として現れます。この差分がドリフトの正体です。
- **覚え方**: 動作イメージで覚えます。ドリフトは車が横滑りすること。**コードは真っすぐ、実物が滑った**と絵にすると、どちらを直すべきかも見えます。
- **つまずきポイント**: 小さな手直しならコードに戻さなくてよいと思いがちですが、実際は次のデプロイで消えるため、消えて困る変更ほどコードへ書き戻す必要があります。
- **関連**: べき等性 / What-If / コードレビューの観点

### 13.2.14 リンター(Linter、静的な書き方チェック)

- **一言でいうと**: 実行しなくても分かる書き方の問題を、コードを読むだけで指摘してくれる検査役です。
- **たとえると**: 提出前に文書を見てくれる先輩です。内容の是非より前に、書式のほころびを拾ってくれます。
- **もう少し詳しく**: Bicepにはリンターが組み込まれており、`az bicep build`などの際に警告として表示されます。使われていないパラメーターや変数、推奨されない書き方、秘密の値の扱いなどが対象です。`bicepconfig.json`を置けば規則の有効無効や深刻度を調整できます。文法エラーと違って処理は止まりませんが、警告を放置すると読みにくいコードが積み上がります。
- **この案件では**: CIとローカルの両方で`az bicep build`が走るため、コードを書いた直後に指摘を受け取れます。
- **覚え方**: 語源で覚えます。lintは衣類につく糸くずや毛玉のこと。**コードの毛玉取り**と覚えれば、役割も強さも想像できます。
- **つまずきポイント**: 警告が出てもビルドできたから問題なしと思いがちですが、実際は警告は将来の事故の予告です。件数を0に保つ習慣が効きます。
- **関連**: CI/CD / Bicep / コードレビューの観点

### 13.2.15 Terraform(テラフォーム、マルチクラウド対応のIaCツール)

- **一言でいうと**: Azureだけでなく複数のクラウドを同じ書き方で扱える、代表的なIaCツールです。
- **たとえると**: 共通規格のドライバーセットです。1本で複数のねじに対応でき、代わりに専用工具ほど手にはなじみません。
- **もう少し詳しく**: HashiCorp社が開発し、HCLという独自の記法で構成を書きます。宣言型で、`terraform plan`が変更内容を事前に見せる点はWhat-Ifと同じ発想です。大きな違いは、Terraformが自分で状態ファイルを持って現状を管理することで、この状態ファイルの置き場と共有方法が実務での論点になります。求人票で併記されることが多いので、名前と立ち位置は知っておく価値があります。
- **覚え方**: 対比で覚えます。**BicepはAzure専用の母国語、Terraformは多クラウドの共通語**。1社でよいなら専用、複数を跨ぐなら共通語です。
- **つまずきポイント**: どちらが優れているかの勝負と思いがちですが、実際は対象範囲と組織の事情で選ぶ話で、両方を使う現場もあります。
- **関連**: Bicep / What-If / IaC

### 13.2.16 Git・ブランチ・プルリクエスト(Git / Branch / Pull Request)

- **一言でいうと**: 変更の履歴を残し、作業用の枝で試し、本線へ取り込む前に他人の確認を通す仕組みです。
- **たとえると**: 鉄道の路線です。本線を止めずに支線で試運転し、安全確認が済んでから合流させます。
- **もう少し詳しく**: Gitは変更をコミット単位で記録するバージョン管理の仕組みで、いつ誰が何を変えたかを追えます。ブランチは本線から分けた作業用の枝で、失敗しても本線は無傷です。プルリクエストはその枝を本線へ取り込む依頼で、差分の表示、レビューのやり取り、自動チェックの結果がここに集まります。IaCの価値の半分は、この履歴とレビューの流れから来ます。
- **この案件では**: `.github/workflows/validate.yml`はプルリクエストとmainへのpushで動くよう設定されています。つまり枝から本線へ入れる前に自動検査が回ります。
- **覚え方**: 動作イメージの3語で覚えます。**記録するのがコミット、分けるのがブランチ、頼むのがプルリクエスト**。記録・分岐・依頼の3拍子です。
- **つまずきポイント**: 1人開発ならブランチは不要と思いがちですが、実際は作業単位を分けると差分が読みやすくなり、後から自分で追いやすくなります。
- **関連**: CI/CD / コードレビューの観点 / シークレットをコミットしない

### 13.2.17 CI/CD(Continuous Integration / Continuous Delivery、GitHub Actions)

- **一言でいうと**: 変更を入れるたびに検査や配布を自動で走らせ、壊れた状態が本線に入るのを防ぐ仕組みです。
- **たとえると**: 工場のラインに置いた自動検品機です。人の目に頼らず、毎回同じ基準で全数を検査します。
- **もう少し詳しく**: CIは変更を頻繁に統合しながら毎回自動検査すること、CDはその成果物を継続的に届けることです。GitHub ActionsはGitHub上でこれを動かす機能で、`.github/workflows/`配下のYAMLに、いつ動くか(トリガー)と何をするか(ステップ)を書きます。インフラでは、実際にデプロイしない静的検査だけでも十分に効果があります。
- **この案件では**: `.github/workflows/validate.yml`が4つの検査を行います。`az bicep build`でBicepがJSONへ変換できるか、`az bicep build-params`でパラメーター例が本体の定義と合っているか、Markdownのリンクが暗号化された通信になっているか、`git diff --check`で行末の余分な空白がないか、です。実Azureへのデプロイは行いません。
- **覚え方**: 頭文字を素直に開きます。CIは**継続的に統合**、CDは**継続的に届ける**。continuousの「継続的に」が両方に共通する主役です。
- **つまずきポイント**: CIが通れば本番でも動くと思いがちですが、実際にこのCIが見ているのは書式と整合性だけで、Azure上での成否はWhat-Ifと実機確認の仕事です。
- **関連**: リンター / Git・ブランチ・プルリクエスト / What-If

### 13.2.18 シークレットをコミットしない(Secrets、.gitignoreの役割)

- **一言でいうと**: 秘密鍵やパスワード、実在のIPやIDをGitに入れないという鉄則と、それを機械的に守らせる仕組みです。
- **たとえると**: 合鍵をコピーして掲示板に貼るようなものです。あとで剥がしても、写真を撮られていれば意味がありません。
- **もう少し詳しく**: Gitは履歴を保存する道具なので、一度コミットした値はファイルを消しても過去のコミットに残ります。公開リポジトリなら流出と同義で、対応は鍵やパスワードの無効化と再発行です。`.gitignore`は「この条件に合うファイルはGitの管理対象にしない」という指定で、うっかりの持ち込みを事前に止めます。`!`で始まる行は除外の解除です。
- **この案件では**: `.gitignore`が`infra/parameters/*.bicepparam`を無視し、`!infra/parameters/*.example.bicepparam`で例だけを追跡対象に戻すため、自分用の`dev.bicepparam`は手元だけに残ります。さらに`scripts/deploy.ps1`は秘密鍵らしい文字列を見つけると処理を止めます。
- **覚え方**: 数字で覚えます。**取り消せない回数は1回**。送信ボタンと同じで、押したあとに戻す手段はありません。
- **つまずきポイント**: あとで削除すれば大丈夫と思いがちですが、実際は履歴に残るため、正解は「入れない」しかありません。入れてしまったら鍵の作り直しです。
- **関連**: パラメーターとパラメーターファイル / Git・ブランチ・プルリクエスト / コードレビューの観点

### 13.2.19 コードレビューの観点(Code Review Checklist)

- **一言でいうと**: 他人のインフラコードを見るとき、感想ではなく決まった軸で確認するための着眼点です。
- **たとえると**: 車の点検です。気になった所を眺めるのではなく、点検表の項目を順に見ていきます。
- **もう少し詳しく**: インフラのレビューは、動くかどうかより「危なくないか」を見ます。実務では次の6点が中心です。名前が命名規則に沿っているか、通信の穴が広すぎないか、秘密の値が混ざっていないか、パラメーターの既定値が安全側か、What-Ifに意図しない削除がないか、タグが揃っているか。指摘は「ここをこう変えると、こういう事故を防げます」という形で書くと通りやすくなります。
- **この案件では**: 見るべき具体例は、`adminCidr`が`/32`など十分に狭いか、`openHttp`が`false`のままか、`sshPublicKey`に公開鍵しか入っていないか、`commonTags`のタグが付いているかです。
- **覚え方**: 語呂で6点を並べます。**名前・穴・秘密・既定・消える・札**。「なあ、ひ・き・け・ふだ」と口に出すと順に出てきます。
- **つまずきポイント**: レビューは詳しい人の仕事と思いがちですが、実際は初心者が「ここが分からない」と書くだけでも、コードの読みにくさという実在の欠陥が見つかります。
- **関連**: What-If / シークレットをコミットしない / CI/CD

## 13.3 このセクションの覚え方まとめ

このセクションは、コードを書く順番でそのまま覚えられます。

```text
書く      : param で受ける → var で組む → resource で宣言 → module に任せる → output で返す
確かめる  : リンター → az bicep build(JSON化) → What-If → -Apply
守る      : 増分が既定 / べき等だから再実行できる / ドリフトはコードへ書き戻す
残す      : ブランチで作業 → プルリクエスト → CIが自動検査 → レビューで6点確認
```

覚える柱は3本だけです。1本目は**宣言型**、完成形を書けばAzureが差分を埋める。2本目は**べき等性**、だから何度でも安全に実行できる。3本目は**What-If**、それでも実行前に必ず予測を見る。この3本が繋がると、`infra/main.bicep`と`scripts/deploy.ps1`が何を守っている仕組みなのかが読めるようになります。

そして最後に、覚え方より優先する1行があります。**秘密の値はコミットしない**。他はやり直せますが、これだけはやり直せません。
