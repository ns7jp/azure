# 11. バックアップ・可用性・障害対応

[用語集トップ](../11-azure-glossary.md) ・ 前: [10. 監視と運用](10-monitoring.md) ・ 次: [12. コスト管理](12-cost.md)

この分野の主役は「取ること」ではなく「**戻せること**」です。バックアップが毎晩成功していても、戻す手順を誰も試していなければ、障害の日には何の役にも立ちません。本案件は基本設計にRPO 24時間と書きながら、バックアップも冗長化も未実装の発展課題という状態で、まさにその落とし穴の見本になっています。ここでは戻すための道具(Azure Backup)、戻す目標を測る指標(RPO/RTO)、壊れにくくする冗長化、そして壊れたときの切り分け順を、一続きの流れで覚えます。

## 11.2 用語解説

### 11.2.1 バックアップ(Backup)

- **一言でいうと**: 元のデータが消えたり壊れたりしても元の状態へ戻せるように、別の場所へ残しておく控えです。
- **たとえると**: 実家に預けた家の合鍵です。作っただけで満足し、どこに預けたか分からず取り出せなければ、鍵をなくした日には役に立ちません。
- **もう少し詳しく**: 守る相手は機器の故障だけでなく、誤操作による削除、設定ミス、ランサムウェアによる暗号化も含みます。だから控えは元データと同じ場所に置かず、消す権限も分けます。評価すべき指標は取得の成功率ではなく、**復元の成功率と所要時間**です。
- **この案件では**: バックアップは未実装の発展課題です。[不足点と学習ロードマップ](../09-gap-analysis-and-roadmap.md)では優先度「高」に置かれ、完了の証拠として設計・復元手順・隔離環境での復元試験の3点がそろうことを求めています。
- **覚え方**: 「バックアップを取る」ではなく「**戻せる状態を作る**」と言い換える癖をつけます。主語を復元側に置くだけで、試験の抜けに気づけます。
- **つまずきポイント**: ジョブが成功していれば安心と思いがちですが、実際は復元を試すまで戻せるかは不明です。取得成功は「戻せる見込み」までしか保証しません。
- **関連**: 復元試験 / RPO / スナップショット

### 11.2.2 Azure Backup

- **一言でいうと**: Azureのリソースを、決めた予定にそって自動でバックアップし、保持と復元まで面倒を見てくれるサービスです。
- **たとえると**: 宅配便の定期集荷です。曜日と時間を契約しておけば、こちらが忘れていても引き取りに来て、預かり期間まで管理してくれます。
- **もう少し詳しく**: 対象はAzure VMまるごと、Azure Files、VM内のSQL Serverなど複数あり、対象ごとに取得方式が違います。VMのバックアップはVM内に個別のソフトを入れる代わりにAzure側の拡張機能で動くため、設定量が少なくて済みます。取得データはコンテナーへ集約し、ポリシーで一括管理します。
- **この案件では**: 未実装です。[学習ロードマップ](../09-gap-analysis-and-roadmap.md)のStage 4に「Backupを追加し、別名VMまたは隔離環境への復元を試験する」が選択課題として並んでいます。
- **覚え方**: 名前のとおり「Azureが代わりに取る係」です。自作のcron運用との対比で、**予定表と保管庫を外に出したのがAzure Backup**と覚えます。
- **つまずきポイント**: 有効化すれば全リソースが対象になると思いがちですが、保護は対象ごとに個別に有効化する必要があります。作ったばかりのVMは何も保護されていません。
- **関連**: Recovery Servicesコンテナー / バックアップポリシー / Azure Site Recovery

### 11.2.3 Recovery Servicesコンテナー(Recovery Services vault、コンテナー)

- **一言でいうと**: バックアップの設定と、取得したデータ本体をまとめて入れておくAzure上の専用の保管庫です。
- **たとえると**: 銀行の貸金庫です。中身は自分のものですが、置き場所と鍵の管理は建物側の仕組みに任せます。
- **もう少し詳しく**: 保護対象、ポリシー、ジョブ履歴、復元ポイントがここに集まるため、バックアップの状態を見る入口になります。保管データの冗長性(同一リージョン内だけか、離れたリージョンへも複製するか)はコンテナーの設定で選びますが、**保護を開始する前に決める必要がある**項目があるため、作成時に方針を固めます。
- **この案件では**: 未作成です。Azure VMを保護するコンテナーは対象VMと同じリージョンに置く必要があるため、置き場所は`japaneast`で確定します。設計判断として記録するのは、保管データを同一リージョン内だけに置くのか、離れたリージョンへも複製する設定にするのかであり、これは保護を開始する前に決めます。
- **覚え方**: **vaultは金庫室**という意味です。「Recovery(復旧)のServices(部品)を入れるvault(金庫)」と3語に分解すれば、役割がそのまま出ます。
- **つまずきポイント**: VMを削除すればバックアップも消えると思いがちですが、コンテナー側に復元ポイントが残っている限りデータは保持され、課金も続きます。片付けはコンテナー側の確認までがセットです。
- **関連**: Azure Backup / 論理削除 / 世代管理

### 11.2.4 バックアップポリシー(Backup Policy)

- **一言でいうと**: いつバックアップを取り、いつまで残すかを書いた設定のひな型で、対象へ割り当てて使います。
- **たとえると**: 定期集荷の契約書です。集荷の曜日と時刻、そして預かり期間の2点が書かれていて、荷物ごとに契約を書き直さずに済みます。
- **もう少し詳しく**: 決める内容は大きく2つ、**スケジュール(取得の頻度と時刻)**と**保持期間(日次・週次・月次・年次をそれぞれ何回分残すか)**です。前者がRPOを決め、後者が「どこまで過去へ戻れるか」と保管コストを決めます。同じポリシーを複数の対象へ割り当てられるため、台数が増えても運用が散らばりません。
- **この案件では**: 未定義です。基本設計のRPO 24時間という仮置きに合わせるなら、少なくとも1日1回の取得が必要になる、という形で要件と設定を結びつけて考えます。
- **覚え方**: ポリシーで決めるのは「**いつ取る**」と「**いつまで残す**」の2つだけ、と数を固定して覚えます。3つ目を思い出せないときは、それはポリシーではなく復元側の話です。
- **つまずきポイント**: 保持期間を長くすればRPOも良くなると思いがちですが、RPOを決めるのは取得の頻度です。保持期間は過去のどこまで選べるかを決めるだけです。
- **関連**: RPO / 世代管理 / 復元ポイント

### 11.2.5 復元ポイントと世代管理(Recovery Point / Retention)

- **一言でいうと**: 復元ポイントは「その時点の状態へ戻せる保存済みの1回分」で、世代管理はそれを何回分どれだけ残すかの管理です。
- **たとえると**: 鉄道の停車駅です。列車は線路のどこへでも止まれるわけではなく、駅がある地点にしか戻れません。駅の数と間隔が、選べる戻り先を決めます。
- **もう少し詳しく**: 復元時はまず復元ポイントの一覧から時点を選び、次に戻し先(元の場所か、別名の新しいリソースか)を選びます。世代管理では日次を短期、週次・月次を長期という三段重ねで持つのが定石で、直近の誤削除には日次、数か月前の改ざん発覚には月次が効きます。世代が多いほど選択肢は増えますが、保管容量も増えます。
- **この案件では**: 未実装のため復元ポイントは存在しません。「1日1回の日次を何日分残すか」を決める作業が、そのまま世代設計になります。
- **覚え方**: 復元ポイント=駅、世代管理=時刻表に載っている駅の数と範囲。「駅がない時刻には戻れない」という一文で、RPOとの関係まで一度に思い出せます。
- **つまずきポイント**: 障害の直前に戻せると思いがちですが、戻せるのは最後の復元ポイントまでです。その先の更新は失われます。
- **関連**: バックアップポリシー / RPO / フルバックアップ

### 11.2.6 フルバックアップ / 増分バックアップ / 差分バックアップ

- **一言でいうと**: 毎回まるごと取るのがフル、直前からの変化分だけ取るのが増分、直近のフルからの変化分を毎回取るのが差分です。
- **たとえると**: 家計簿です。月初の残高がフル、毎日の増減の記録が増分、月初からの累計差額が差分にあたります。
- **もう少し詳しく**: 違いは取得の軽さと**復元手順の複雑さ**のトレードオフです。取得量はフルが最大、増分が最小、差分は日が進むほど増えます。増分は途中の1回が欠けると復元できません。Azure VMのバックアップは初回にフル相当を取得し、以降は変更ブロックだけを取得する方式で、復元時の組み立てはAzure側が行います。
- **覚え方**: 復元に必要な個数で覚えます。フルは1、差分は1+1、増分は1+日数。数字が小さいほど復元は楽で、取得は重いという対比です。
- **つまずきポイント**: 名前が似ているため逆に覚えがちです。**差分は基準が固定(いつもフル)**、増分は基準が移動(直前のもの)と、基準の位置で区別します。
- **関連**: 復元ポイント / RTO / バックアップポリシー

```text
月曜         火曜        水曜        木曜        復元に必要な数
フル : [全部]      [全部]      [全部]      [全部]       1個(最新のフル)
増分 : [全部] + [火の変化] + [水の変化] + [木の変化]    1個 + 経過日数分
差分 : [全部] +              [月からの変化(木時点)]     1個 + 最新の差分1個
```

### 11.2.7 RPO(Recovery Point Objective、目標復旧時点)

- **一言でいうと**: 障害が起きたとき、どの時点のデータまで戻せればよいかという目標で、許容できるデータの失われる量を表します。
- **たとえると**: 毎晩つける家計簿です。1日1回しか書かないなら、財布を落とした日に失う記録は最大1日分です。
- **もう少し詳しく**: RPOを決めるのは**バックアップの取得頻度**です。1日1回なら失うのは最大1日分、15分ごとなら最大15分分です。短くするほど処理負荷と保管コストが上がるため、「どこまでのデータ損失なら業務が耐えられるか」を業務側と合意してから頻度を決めます。
- **この案件では**: 基本設計でRPO 24時間を仮置きしていますが、バックアップが未実装のため**達成手段がありません**。要件に数値を書くこととそれを満たすことは別だという学習課題であり、「書いてあるが未達」と正直に言えることが評価点です。
- **覚え方**: **P**oint=点=時点。RPOは過去を向いた矢印で、「どこまで戻れるか」を指します。頻度を上げると矢印が短くなります。
- **つまずきポイント**: RPOはバックアップの所要時間だと思いがちですが、時間の長さではなく**戻れる時点**の目標です。所要時間側はRTOが担当します。
- **関連**: RTO / バックアップポリシー / 復元ポイント

### 11.2.8 RTO(Recovery Time Objective、目標復旧時間)

- **一言でいうと**: 障害の発生から、どれだけの時間で復旧させるかという目標で、業務が止まっていられる時間の上限を表します。
- **たとえると**: 電車が止まったあと、運転を再開するまでの時間です。線路が直っていても、点検と車両の手配が終わるまで乗客は動けません。
- **もう少し詳しく**: RTOを決めるのは復旧手順の複雑さと自動化の度合いです。バックアップから新しいVMを組み立てる手順が用意され、担当者が訓練済みならRTOは短くなり、OSの再インストールから手作業でやり直す方法では長くなります。だからRTOは机上で宣言する数値ではなく、**復元試験で計測して裏づける数値**です。
- **この案件では**: 基本設計ではRTO 4時間を仮置きしていますが、こちらも復元手順と復元試験がないため実測値がありません。時間を計るには、まず戻す手順書が必要になります。
- **覚え方**: **T**ime=時間。RTOは未来を向いた矢印で「どれだけ早く動き出せるか」を指します。RPOは過去向き、RTOは未来向きと、矢印の向きで対にして覚えます。
- **つまずきポイント**: 復元処理が終わればRTO達成と思いがちですが、業務が使える状態に戻るまでが対象です。アプリの起動確認や利用者への周知までを含めて計測します。
- **関連**: RPO / 復元試験 / DR

### 11.2.9 復元試験(リストアテスト)

- **一言でいうと**: 取得したバックアップから実際にデータやサーバーを戻せるかを、あらかじめ確かめておく試験です。
- **たとえると**: 消防訓練です。消火器を買って壁に掛けた事実と、いざ火が出たときに使える事実は別物です。
- **もう少し詳しく**: 確認するのは3点、**戻せるか**(手順の正しさ)、**どれだけかかるか**(RTOの実測)、**どの時点に戻れたか**(RPOの実測)です。本番へ上書きすると事故になるため、隔離した検証用リソースグループや別名リソースへ戻すのが基本です。バックアップの設計より先に、この復元側の手順を書き始めるほうが安全です。
- **この案件では**: [運用・障害対応Runbook](../07-operations-runbook.md)の毎月の確認に「復旧手順を机上または隔離環境で訓練」が入っています。実施していない項目を`PASS`と書かず、`NOT RUN`と正直に書くのが本教材の作法です。
- **覚え方**: 語呂で「**取ったら戻す、戻して計る**」。取得と復元は必ず対で数え、復元側に時計を持たせると覚えます。
- **つまずきポイント**: 復元試験は本番と同じ場所で行うと思いがちですが、それでは元データを壊しかねません。別名か隔離環境へ戻すのが原則です。
- **関連**: RTO / バックアップ / DR

### 11.2.10 スナップショットとバックアップの違い

- **一言でいうと**: スナップショットはディスクのある時点の姿を素早く写し取る仕組みで、バックアップは別に管理された保管庫へ残す運用の仕組みです。
- **たとえると**: スナップショットは同じ家の中の別の引き出しにしまった写真、バックアップは別の街の貸金庫へ預けた写真です。引き出しの写真は元のアルバムを捨てても残りますが、家ごと被災すれば一緒に失います。
- **もう少し詳しく**: スナップショットは取得が速く、変更作業の直前に取る一時的な安全網に向きます。一方で世代管理、保持期間の自動適用、削除保護、離れた場所への保全はバックアップ側の役割です。スナップショットは元のディスクとは別のリソースとして残るため、VMを削除しても自動では消えず課金が続きます。片付けではスナップショットの削除まで確認します。実務では「作業直前はスナップショット、日々の備えはバックアップ」と分けます。
- **この案件では**: どちらも未導入です。Bicepで再作成できる部分と、VMの中にしかないデータを分けて考えると、何を守るべきかが決めやすくなります。
- **覚え方**: 対比の一文で覚えます。「スナップショットは**同じ敷地内の控え**、バックアップは**別の建物で管理される控え**」。置き場所が同じか違うかが本質的な差です。
- **つまずきポイント**: スナップショットがあるからバックアップは不要と思いがちですが、元のリソースやサブスクリプションの事故には道連れになる場合があります。世代と保管場所の管理がある側がバックアップです。
- **関連**: バックアップ / 3-2-1ルール / 復元ポイント

### 11.2.11 論理削除(Soft Delete)

- **一言でいうと**: 削除の操作をしても一定期間はデータを残しておき、その間なら元に戻せるようにする保護の仕組みです。
- **たとえると**: パソコンのゴミ箱です。捨てたつもりでも、ゴミ箱を空にするまでは拾い直せます。
- **もう少し詳しく**: 狙いは誤操作と悪意ある削除の両方への備えです。バックアップは「最後に残る備え」なので、それ自体を消される攻撃への耐性が必要になります。保持期間や有効・無効の扱いはサービスと設定で変わるため、導入時に公式ドキュメントで確認します。片付けの観点では、論理削除の期間中は保持が続く点も押さえます。
- **覚え方**: 語を分解します。**soft=やわらかい削除**で、対になるのはhard delete(完全削除)です。「やわらかい削除はまだ戻せる」と一組で覚えます。
- **つまずきポイント**: 削除ボタンを押したら即座に消えると思いがちですが、論理削除が働く場面では見た目上消えても保持が続きます。学習後の片付けでは、残存を必ず確認します。
- **関連**: Recovery Servicesコンテナー / バックアップ / リソースロック

### 11.2.12 3-2-1ルール

- **一言でいうと**: 控えは合計3つ、保存する媒体は2種類、そのうち1つは離れた場所に置く、というバックアップ設計の古典的な原則です。
- **たとえると**: 大事な契約書を、手元に原本、事務所にコピー、実家にもう1部という形で分散させる考え方です。
- **もう少し詳しく**: 同じ場所と同じ仕組みに全部を置くと、火災や大規模障害、そして操作ミスで一度に全滅します。3-2-1は媒体と場所を意図的にずらすことで、同時に失う確率を下げます。クラウドでは「媒体を2種類」を、別のサービスや別リージョンなど**障害の原因を共有しない置き方**に読み替えて適用します。
- **この案件では**: 単一VMかつバックアップ未実装なので、控えの数は事実上0です。まず1つ作り、次に置き場所を離す、という順番で近づけます。
- **覚え方**: 数字がそのまま内容です。**3=控えの数、2=媒体の種類、1=別の場所**。声に出して「サン、ニー、イチ」と唱えれば3語を思い出せます。
- **つまずきポイント**: クラウドに置けば自動的に別の場所と思いがちですが、同一リージョン内の複製は地域全体の障害には効きません。「離れているか」は距離で確認します。
- **関連**: DR / Recovery Servicesコンテナー / 冗長化

### 11.2.13 DR(Disaster Recovery、災害復旧)

- **一言でいうと**: 地震や大規模障害でシステム全体が使えなくなったときに、どう業務を復旧させるかを定めた考え方と体制です。
- **たとえると**: 台風で本社が閉鎖したときに、支社へ移って業務を続ける段取りです。机と回線があるだけでは足りず、誰がいつ判断するかまで決めておく必要があります。
- **もう少し詳しく**: 規模が違う点が重要です。VM1台の故障は日常の障害対応で、DRが扱うのは`japaneast`のような**リージョン規模の被災**です。手段は費用の軽い順に、バックアップだけを離れた場所へ保全して被災後に建て直す、待機環境を用意する、常時複製して短時間で切り替える、の3段階です。
- **この案件では**: 単一リージョン・単一VMのため未対応の発展課題です。「採用しない」と決め、理由と見直し条件を残すことも設計成果になります。
- **覚え方**: **D**isaster=災害。「1台が壊れる話ではなく、地域が使えなくなる話」と規模で線を引くと、通常の障害対応と混ざりません。
- **つまずきポイント**: バックアップがあればDR対応済みと思いがちですが、バックアップが被災した地域の中にしかなければ一緒に失います。データの置き場所と復旧先の両方が必要です。
- **関連**: Azure Site Recovery / 3-2-1ルール / RTO

### 11.2.14 Azure Site Recovery(ASR)

- **一言でいうと**: VMを別のリージョンへ継続的に複製しておき、災害時にそちら側へ切り替えて業務を続けるためのサービスです。
- **たとえると**: 支社へ書類の写しを毎日送り続けておく体制です。本社が使えなくなった日でも、支社の写しから業務を再開できます。
- **もう少し詳しく**: 複製は常時動き続けるため、被災後にゼロから建て直すよりRTOを大きく短縮できます。反面、平常時から複製先のディスクなどストレージと、保護対象ごとの費用が継続して発生します(待機側のVM自体は切り替え時に作成されます)。金額はリージョン・契約・時期で変わるため、Azure Pricing CalculatorとCost Managementで確認します。実務で価値があるのは**テストフェイルオーバー**で、本番の複製を止めずに切り替えの手順と所要時間を確認できます。
- **この案件では**: 未導入です。導入を検討するときは「RTO 4時間の仮置きを本当に守る必要があるのか」を先に問い直し、費用対効果を比較したうえで採否を記録します。
- **覚え方**: 略語を分解します。**A**zure **S**ite **R**ecovery=「拠点(Site)ごと復旧する係」。バックアップが荷物単位、ASRが拠点単位という粒度の違いで覚えます。
- **つまずきポイント**: ASRがあればバックアップは不要と思いがちですが、役割が違います。複製は最新の状態を運びますが、誤って消したデータや暗号化されたデータも運んでしまうため、過去へ戻す手段はバックアップが担います。
- **関連**: DR / フェイルオーバー / 冗長化

### 11.2.15 冗長化(可用性セット / 可用性ゾーン / リージョン)

- **一言でいうと**: 同じ役割のものを複数用意して分散配置し、1つ壊れてもサービスを止めないようにする設計です。
- **たとえると**: 住まいの分散です。同じマンションの別の部屋(可用性セット)、別の棟(可用性ゾーン)、別の街(別リージョン)と、離れるほど広い災害に耐えます。
- **もう少し詳しく**: 可用性セットは、電源やネットワークを共有する単位とAzure側の計画メンテナンスの単位をずらして配置する仕組みです。可用性ゾーンは、リージョン内で電源・冷却・ネットワークが物理的に独立したデータセンター群への分散です。リージョンをまたげばさらに広い災害に備えられますが、遅延と運用の複雑さが増えます。**いずれも同じ役割のVMが2台以上あって初めて効きます**。
- **この案件では**: 学習費用を抑えるための単一VMで、冗長化は未実装の発展課題です。高可用性要件があれば可用性ゾーンやロードバランサーと複数VMへ変更する、と[README](../../README.md)に明示しています。
- **覚え方**: 3段階を距離の順に並べます。**部屋 → 棟 → 街**。守れる災害の大きさは、離れた距離に比例します。
- **つまずきポイント**: 冗長化すればバックアップは不要と思いがちですが、複数台に同じ誤削除が反映されれば全台が同時に壊れます。冗長化は予防、バックアップは事後の回復で、役割が別です。
- **関連**: SPOF / フェイルオーバー / DR

### 11.2.16 SPOF(Single Point of Failure、単一障害点)

- **一言でいうと**: そこ1か所が壊れると全体が止まってしまう、代わりのない箇所のことです。
- **たとえると**: 事務所の鍵を持っている人が1人だけの状態です。その人が休むと、誰も出勤できません。
- **もう少し詳しく**: 探し方は「1つしかないと止まるものを数える」です。VM、ディスク、Public IP、回線だけでなく、手順を知る担当者が1人という人の面もSPOFです。構成図の各部品に「これが落ちたら何が止まるか」を書き込むと見つかります。
- **この案件では**: 単一VMが最大のSPOFで、[学習ロードマップ](../09-gap-analysis-and-roadmap.md)では残存リスクとして説明できることが達成条件です。学習用として意図的に受け入れたと言えれば、弱点の指摘ではなく設計判断の説明になります。
- **覚え方**: 頭文字を分解します。**S**ingle **P**oint **O**f **F**ailure=単一の・点の・故障。積み木から1本抜くと全部倒れる絵を思い浮かべると、探す目線が定まります。
- **つまずきポイント**: サーバーを2台にすればSPOFは消えると思いがちですが、その前段の回線や振り分け役が1つなら、SPOFはそこへ移動しただけです。経路全体で数えます。
- **関連**: 冗長化 / 障害の切り分け / DR

### 11.2.17 フェイルオーバーとフェイルバック

- **一言でいうと**: 障害時に待機側へ切り替えるのがフェイルオーバー、復旧後に元の側へ戻すのがフェイルバックです。
- **たとえると**: 道路工事の迂回路です。通行止めの間は迂回路へ回し、工事が終わったら元の道へ戻します。戻す作業も段取りが必要な工程です。
- **もう少し詳しく**: 実務で難しいのは戻す側です。切り替えている間に待機側で更新されたデータを元へ反映しないと、業務データが食い違います。そのため手順書には切り替え条件、判断者、そして戻すときのデータ同期と業務停止のタイミングまで書きます。切り替えを事前に確かめる**テストフェイルオーバー**は、本番を止めずに手順を検証する手段です。
- **この案件では**: 待機側がないため、どちらも発生しません。単一VMでの復旧は、切り替えではなくバックアップからの復元という手段になります。
- **覚え方**: 前置詞で覚えます。over=**向こう側へ移る**、back=**元へ戻る**。fail(失敗)したときに向こうへ、直ったら元へ、と動きの向きで対にします。
- **つまずきポイント**: 切り替えれば復旧完了と思いがちですが、フェイルオーバー中は待機側の1系統だけで動く、冗長性のない状態です。戻すまでが対応です。
- **関連**: Azure Site Recovery / 冗長化 / RTO

### 11.2.18 障害の切り分け手順(切り分けの順番)

- **一言でいうと**: 症状から原因のある場所を、決めた順番で機械的に絞り込んでいく作業です。
- **たとえると**: 蛇口から水が出ないときの調べ方です。蛇口、屋内の配管、元栓、そして水道局からの供給と、手前から順に確かめます。当てずっぽうに壁を壊す人はいません。
- **もう少し詳しく**: 基本は**通信の順番を逆にたどる**ことです。本案件の経路は`管理者PC → Public IP → NSGの判定 → NIC → VM → Nginx`なので、調べる順は`Nginx → VM → NIC → NSG → Public IP → 管理者PCまでの経路`になります。分水嶺はVMの中から自分自身へアクセスできるかで、そこで成功するなら原因はVMの外側(NSGやIP)、失敗するならVMの内側(サービスや設定)に絞れます。初動の型は[Runbook](../07-operations-runbook.md)の「**止・見・守・戻・残**」です。
- **この案件では**: `docs/07-operations-runbook.md`に、Webに接続できない場合とSSHできない場合の確認コマンドと判断基準が用意されています。無計画な再起動は証拠を消してしまうため、まず影響を止め、記録を残してから復旧します。
- **覚え方**: 語呂で「**止・見・守・戻・残**」の5文字。順番は「作った順に調べず、**流れの終点から逆へ**」と覚えます。切り分けは推理ではなく順路です。
- **つまずきポイント**: 再起動で直れば解決と思いがちですが、原因が残っていれば再発します。復旧と原因除去は別の作業として記録します。
- **関連**: SPOF / 復元試験 / RTO

## 11.3 このセクションの覚え方まとめ

まずRPOとRTOを、障害の瞬間を挟んだ時間軸の左右で覚えます。左が失うデータ、右が止まる時間です。

```text
時間 ─────────────────────────────────────────────>
    最後のバックアップ        障害発生         復旧完了
          |                     |                  |
          |<------ RPO -------->|<------ RTO ----->|
          失うデータの量          業務が止まる時間
          頻度で短くする          手順と訓練で短くする
```

次に、この分野の全体像を1本の線で並べます。**予防(冗長化)→ 備え(バックアップ)→ 検証(復元試験)→ 発動(フェイルオーバー・復元)→ 記録(残す)**。壊れにくくするのが前半、壊れた後を短くするのが後半です。

最後に数字で締めます。復元に必要な個数は**フル1、差分1+1、増分1+日数**、控えの分散は**3-2-1**、冗長化の距離は**部屋・棟・街**の3段階。この3組を言えれば、この節はひととおり思い出せます。そして全体を貫く一文は「**バックアップは取ることではなく戻せること**」です。
