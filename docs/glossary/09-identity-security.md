# 9. ID・アクセス管理とセキュリティ

[用語集トップ](../11-azure-glossary.md) ・ 前: [8. ストレージとディスク](08-storage.md) ・ 次: [10. 監視と運用](10-monitoring.md)

このセクションは「誰がAzureに入れるか」と「入った人が何をしてよいか」を扱います。ネットワークの許可表がNSGなら、人と権限の許可表がここで登場するEntra IDとRBACです。本案件でSSHをパスワードではなく公開鍵だけに限定し、接続元を`adminCidr`に絞っているのも、この分野の考え方をそのまま形にしたものです。用語は多いですが、最初の1語「認証と認可の違い」が分かると残りは枝葉として並びます。

## 9.2 用語解説

### 9.2.1 認証と認可の違い(Authentication / Authorization)

- **一言でいうと**: 認証は「あなたが誰か」を確かめる手続き、認可は「その人が何をしてよいか」を決める手続きです。
- **たとえると**: 入館ゲートで社員証をかざすのが認証、その社員証で開くドアが所属部署だけなのが認可です。
- **もう少し詳しく**: Azureではこの2つを別の仕組みが担当します。認証はMicrosoft Entra ID、認可はAzure RBACです。サインインできることと操作できることは別問題で、「サインインは通るのにVMを作れない」なら認可側、「サインイン自体が弾かれる」なら認証側を疑います。切り分けの最初の分岐がここです。
- **この案件では**: `az login`が認証、リソースを作成する権限があるかどうかが認可です。基本設計では構築者に必要なロールだけを付与する方針としています。
- **覚え方**: 英語の綴りで対比します。AuthenticationとAuthorizationは先頭が同じなので、区別に使う文字を取って**AuthN**と**AuthZ**と書き分けます。NはAuthenticatioNの末尾の文字、ZはAuthoriZationのZです。意味は日本語で**認証=誰、認可=どこまで**の6文字で足ります。
- **つまずきポイント**: 「認証が通れば操作できる」と思いがちですが、実際は認可が別に必要で、権限がゼロでもサインインだけはできます。
- **関連**: Microsoft Entra ID / RBAC / 最小権限の原則

### 9.2.2 Microsoft Entra ID(旧Azure AD、エントラID)

- **一言でいうと**: 人やアプリの「誰か」を管理し、サインインを受け付けるMicrosoftのクラウドID基盤です。
- **たとえると**: 会社の人事名簿と受付を合わせたものです。名簿に載っていない人は受付を通れません。
- **もう少し詳しく**: ユーザー、グループ、アプリの登録情報を保持し、パスワードやMFAでサインインを検証します。Azure Active Directory(Azure AD)から名称が変更されたため、古い資料ではAzure ADと書かれていますが同じものです。Microsoft 365と同じIDでAzureポータルにもサインインできます。
- **覚え方**: Entraは英語の`enter`(入る)に近い語感です。**入口の担当がEntra ID**、中で何ができるかは次のRBACの担当、と役割で分けて覚えます。
- **つまずきポイント**: 「WindowsのActive Directory(AD DS)のクラウド版」と思いがちですが、実際は別の製品で、ドメイン参加やグループポリシーの仕組みをそのまま持ち込むことはできません。
- **関連**: テナントとディレクトリ / ユーザーとグループ / MFA

### 9.2.3 テナントとディレクトリ(Tenant / Directory)

- **一言でいうと**: テナントは組織ごとに割り当てられたEntra IDの専用区画で、その中身の名簿がディレクトリです。
- **たとえると**: マンション1棟がAzure全体、その中の1部屋が自社のテナント、部屋の中の住民台帳がディレクトリです。
- **もう少し詳しく**: サブスクリプションは必ず1つのテナントに紐づき、認証はそのテナントが行います。会社のアカウントと個人のアカウントで見えるサブスクリプションが違うのは、テナントが違うからです。テナントはテナントIDというGUIDで識別します。
- **この案件では**: `az account show`で、いま操作している対象がどのテナント・サブスクリプションかを確認します。テナントIDは証跡に残す際にマスクします。
- **覚え方**: 賃貸の「テナント」=借りている区画、ディレクトリ=電話帳。**区画と名簿**の2語だけで区別できます。
- **つまずきポイント**: 「サブスクリプションを切り替えれば同じ感覚で使える」と思いがちですが、実際は別テナントのサブスクリプションはそのアカウントでの認証から別扱いになります。
- **関連**: Microsoft Entra ID / 認証と認可の違い / 監査ログ

### 9.2.4 ユーザーとグループ(User / Group)

- **一言でいうと**: ユーザーは1人分のアカウント、グループは複数のユーザーをまとめて権限を渡すための束です。
- **たとえると**: 社員1人が「ユーザー」、「インフラ課」という部署名が「グループ」です。異動は部署の付け替えだけで済みます。
- **もう少し詳しく**: 権限はユーザーへ直接ではなく、グループへ割り当てるのが基本です。人が増えたらグループに入れるだけ、退職時は外すだけで権限が消えます。社外の協力者をゲストユーザーとして招くこともでき、その場合も権限はグループ経由で管理すると追跡しやすくなります。
- **覚え方**: 動作でイメージします。**人に鍵を直接渡さず、部署の鍵箱に入れる**。鍵箱=グループです。
- **つまずきポイント**: 「まず本人に権限を付ければ早い」と思いがちですが、実際は個別付与が積み重なると誰が何を持つか追えなくなり、権限の棚卸しができなくなります。
- **関連**: RBAC / ロール割り当て / 最小権限の原則

### 9.2.5 MFA(Multi-Factor Authentication、多要素認証)

- **一言でいうと**: パスワードだけに頼らず、種類の違う要素を2つ以上組み合わせて本人確認する認証方式です。
- **たとえると**: 銀行ATMのキャッシュカード(持ち物)と暗証番号(記憶)の2点セットです。
- **もう少し詳しく**: 要素は「知識(パスワード)」「所持(スマートフォンアプリ、トークン)」「生体(指紋、顔)」の3種類に分かれ、種類の違うものを2つ以上使うのがMFAです。パスワードが漏れても別の要素がなければサインインできないため、強い権限を持つ管理者アカウントほど効果が大きくなります。
- **覚え方**: 数字で覚えます。**要素は3種類、必要なのは違う種類が2つ以上**。「3種から2種」と唱えれば、パスワード2つがMFAにならない理由まで思い出せます。
- **つまずきポイント**: 「パスワードと秘密の質問の2段階だからMFA」と思いがちですが、実際はどちらも知識要素なので、多段階ではあっても多要素ではありません。
- **関連**: 条件付きアクセス / 認証と認可の違い / ゼロトラスト

### 9.2.6 条件付きアクセス(Conditional Access)

- **一言でいうと**: サインインの状況を見て、許可・ブロック・MFA要求などを自動で判定するEntra IDの仕組みです。
- **たとえると**: 空港の入国審査です。パスポートの真偽だけでなく、どこから来たか、何をしに来たかで対応が変わります。
- **もう少し詳しく**: ユーザー、利用するアプリ、接続元の場所、デバイスの状態などを条件に、アクセスの可否や追加の確認を決めます。「社外からの管理操作はMFA必須」といった規則を人ごとに設定せずまとめて適用できます。上位のライセンスプランを前提とする機能のため、利用可否は契約内容を確認します。
- **覚え方**: プログラムの`if`文だと考えます。**条件=誰・どこ・何・どの端末、判定=通す・止める・MFA**。この2行で構造が言えます。
- **つまずきポイント**: 「規則を作れば安全になる」と思いがちですが、実際は対象の指定を誤ると管理者自身が入れなくなるため、除外アカウントの用意と事前検証が欠かせません。
- **関連**: MFA / ゼロトラスト / PIM

### 9.2.7 RBAC(Role-Based Access Control、ロールベースのアクセス制御)

- **一言でいうと**: 誰に、どの範囲で、どんな役割を与えるかという形でAzureの操作権限を決める仕組みです。
- **たとえると**: 会社の役職です。部長という役職に権限が定義されていて、人はその役職に就くだけです。
- **もう少し詳しく**: 権限を人ごとに書くのではなく、あらかじめ定義された役割(ロール)を対象範囲(スコープ)へ割り当てます。認可の担当がRBACで、認証のEntra IDとは役割が分かれています。VMの作成、ネットワークの変更、参照だけなど、操作の粒度で制御できます。
- **この案件では**: 構築者にはBicepでリソースを作成できるロールを付与し、それ以上の権限は渡さない方針です。
- **覚え方**: 頭文字を分解します。R=Role(役割)、B=Based(基準)、AC=Access Control。**役割を基準にした通行管理**と読み替えます。
- **つまずきポイント**: 「RBACでサインインも止められる」と思いがちですが、実際にサインインを制御するのはEntra ID側で、RBACは操作できる範囲だけを決めます。
- **関連**: 認証と認可の違い / 組み込みロール / ロール割り当て

### 9.2.8 ロール定義・ロール割り当て・スコープ(Role Definition / Role Assignment / Scope)

- **一言でいうと**: 「何ができるか」「誰に渡すか」「どこまで効くか」の3点がそろって初めて権限が成立します。
- **たとえると**: ロール定義は合鍵の種類、ロール割り当ては誰に渡したかの台帳、スコープはその鍵が開けるフロアの範囲です。
- **もう少し詳しく**: ロール定義は許可される操作の一覧です。ロール割り当ては「対象者+ロール定義+スコープ」の組み合わせを登録する行為です。スコープは管理グループ、サブスクリプション、リソースグループ、個別リソースの4段階で、上位で割り当てた権限は下位へ**継承**されます。継承は下向きの一方通行です。
- **この案件では**: リソースグループ`rg-portfolio-dev-jpe-001`をスコープにすれば、その中のVNetやNSG、VMへまとめて権限が効きます。
- **覚え方**: 3語を日本語に置き換えます。**定義=何を、割り当て=誰に、スコープ=どこまで**。
- **つまずきポイント**: 「下位で狭く割り当て直せば上位の権限を打ち消せる」と思いがちですが、実際は継承された許可を下位の割り当てで減らすことはできず、狭めたいなら上位の割り当て自体を見直します。
- **関連**: RBAC / 組み込みロール / リソースグループ

```text
管理グループ                    ← ここで割り当てると
  └ サブスクリプション            配下すべてに効く
      └ リソースグループ            (rg-portfolio-dev-jpe-001)
          └ 個別リソース          ← ここで割り当てると
                                    そのリソースだけに効く

権限は上から下へ流れる。下から上へは流れない。
```

### 9.2.9 組み込みロール(Built-in roles、所有者 / 共同作成者 / 閲覧者 / ユーザーアクセス管理者)

- **一言でいうと**: Azureがあらかじめ用意している役割で、権限の広さが段階的に分かれています。
- **たとえると**: 社長、現場責任者、見学者、人事担当の4役です。できることの範囲がはっきり違います。
- **もう少し詳しく**: 所有者(Owner)はすべての操作に加えて他人への権限付与もできます。共同作成者(Contributor)はリソースの作成・変更・削除ができますが、権限付与はできません。閲覧者(Reader)は参照だけです。ユーザーアクセス管理者(User Access Administrator)は権限付与の管理に特化しています。ほかにサービス別のロールも多数あり、まずはこの4つを基準にします。
- **覚え方**: 「作れる/権限を配れる」の2軸で対比します。**所有者=両方、共同作成者=作れるだけ、閲覧者=どちらもなし、ユーザーアクセス管理者=配れるだけ**。
- **つまずきポイント**: 「共同作成者なら何でもできる」と思いがちですが、実際はロール割り当てができないため、他人に権限を渡す作業で必ず止まります。
- **関連**: RBAC / 最小権限の原則 / PIM

### 9.2.10 最小権限の原則(Principle of Least Privilege)

- **一言でいうと**: 業務に必要な最小限の権限だけを、必要な範囲と必要な期間に限って与える考え方です。
- **たとえると**: 宅配業者に自宅の合鍵を渡すのではなく、宅配ボックスの暗証番号だけを伝えるようなものです。
- **もう少し詳しく**: 権限を広く渡すと運用は楽ですが、アカウントが乗っ取られたときや操作ミスのときの被害が一気に広がります。まず閲覧者から始め、足りない操作が出たときに必要なロールを足す方向で設計します。ネットワーク側の最小許可と対になる、ID側の基本原則です。
- **この案件では**: SSHの許可元を`adminCidr`だけに絞り、HTTPを`openHttp=false`で閉じているのが通信面、構築者へ必要なロールだけを付与するのが権限面の実践です。
- **覚え方**: **まず全部禁止、必要な分だけ足す**と唱えます。引き算ではなく足し算で権限を組み立てます。
- **つまずきポイント**: 「あとで絞ればよい」と思いがちですが、実際は広い権限は動いている運用に組み込まれてしまい、後から外すほうが何倍も手間がかかります。
- **関連**: RBAC / 攻撃対象領域 / ゼロトラスト

### 9.2.11 PIM(Privileged Identity Management、特権ID管理)

- **一言でいうと**: 強い権限を常時持たせず、申請と承認を経て一時的にだけ有効化させるEntra IDの機能です。
- **たとえると**: 金庫の鍵を常に持ち歩かず、必要なときに台帳へ記入して受け取り、使い終えたら返す運用です。
- **もう少し詳しく**: 対象者を「資格あり(必要なときに有効化できる)」という状態にしておき、作業のたびに理由を入力して有効化します。有効期間が切れると権限は自動で外れ、誰がいつ何のために昇格したかが記録されます。上位のライセンスプランを前提とする機能です。
- **覚え方**: 頭文字はP=Privileged(特権)、I=Identity、M=Management。動作としては**特権を貸出制にする**と覚えます。
- **つまずきポイント**: 「PIMを入れれば権限が弱くなる」と思いがちですが、実際に減るのは権限を持っている時間で、有効化した後にできることの広さは変わりません。
- **関連**: 組み込みロール / Just-In-Timeアクセス / 監査ログ

### 9.2.12 Just-In-Time(JIT)アクセス

- **一言でいうと**: 必要な瞬間だけアクセスを開け、時間が来たら自動で閉じる考え方と、その実装機能です。
- **たとえると**: 通行止めの道を工事の時間だけ開ける規制です。作業が終われば自動でゲートが閉まります。
- **もう少し詳しく**: 常時開いている入口は、常時狙われている入口です。ID面では特権ロールの一時的な有効化(PIM)、ネットワーク面ではMicrosoft Defender for Cloudのjust-in-time VMアクセスのように、SSHやRDPの管理ポートを申請時だけ限定的に開ける機能があります。後者はDefenderの対象プランを前提とします。
- **この案件では**: 常時開放を避ける発想は同じですが、実装はNSGで`adminCidr`のみを許可する方式です。JITの導入自体は未実装の発展課題です。
- **覚え方**: Just In Time=**ちょうどその時だけ**。製造業のジャストインタイム(必要な分を必要な時に)と同じ発想を権限に当てます。
- **つまずきポイント**: 「JITなら接続元を絞らなくてよい」と思いがちですが、実際は開ける時間の短さと開ける範囲の狭さは別の話で、接続元の制限と併用します。
- **関連**: PIM / Microsoft Defender for Cloud / 攻撃対象領域

### 9.2.13 マネージドID(Managed Identity、システム割り当て / ユーザー割り当て)

- **一言でいうと**: AzureリソースがパスワードなしでAzureへ認証できるよう、Azureが自動で管理してくれるIDです。
- **たとえると**: 業務用の社員証を自分で作らず会社が発行し、退職時に自動で失効させる仕組みです。
- **もう少し詳しく**: VMやアプリにIDを持たせ、そのIDへRBACでロールを割り当てると、コードに接続情報を書かずにKey Vaultなどへアクセスできます。システム割り当ては対象リソースに1対1で付き、リソースを削除するとIDも消えます。ユーザー割り当ては独立したリソースとして作成し、複数のリソースで共有できます。資格情報の更新はAzure側が行います。
- **覚え方**: 対比で覚えます。**システム割り当て=リソースと一生を共にする専属、ユーザー割り当て=使い回せる派遣**。
- **つまずきポイント**: 「マネージドIDを有効にすればアクセスできる」と思いがちですが、実際は有効化とロール割り当ては別作業で、権限を与えるまで何もできません。
- **関連**: サービスプリンシパル / RBAC / Azure Key Vault

### 9.2.14 サービスプリンシパルとアプリ登録(Service Principal / App Registration)

- **一言でいうと**: 人ではなくアプリや自動処理のために用意する、アカウントに相当するAzure上の主体です。
- **たとえると**: 会社が業務ロボットに専用の社員証を発行するイメージです。人の社員証を使い回させません。
- **もう少し詳しく**: アプリ登録でアプリの定義を作り、そのテナント内で実際に認証に使われる主体がサービスプリンシパルです。クライアントシークレットまたは証明書で認証し、RBACでロールを割り当てて使います。CI/CDのパイプラインからAzureを操作するときの主体がこれになります。
- **この案件では**: 学習中は自分のアカウントで`az login`します。CIを`az bicep build`の静的検証から実デプロイまで広げる段階で、この仕組みが必要になります。
- **覚え方**: **アプリ登録=設計図、サービスプリンシパル=そのテナントでの実体**。設計図と現物の対比で覚えます。
- **つまずきポイント**: 「シークレットは一度作れば使い続けられる」と思いがちですが、実際は有効期限があり、期限切れで自動処理が突然失敗します。
- **関連**: マネージドID / RBAC / Azure Key Vault

### 9.2.15 Azure Key Vault(キーボルト)

- **一言でいうと**: パスワードや鍵、証明書といった秘密情報を安全に預け、権限のある相手だけに渡すサービスです。
- **たとえると**: 銀行の貸金庫です。中身は許可された人しか取り出せず、出入りの記録も残ります。
- **もう少し詳しく**: 設定ファイルやコードに秘密情報を直接書くと、共有やコミットのたびに漏えいの危険が増えます。Key Vaultへ集約してアクセスをRBACなどで制御すると、値を更新しても参照する側の設定を直さずに済みます。マネージドIDと組み合わせれば、取得側にパスワードを一切持たせずに済みます。
- **この案件では**: 基礎編ではKey Vaultを作成しません。SSHの秘密鍵は手元に保管し、AzureにもGitにも置かない運用で代替しています。
- **覚え方**: Vaultは金庫です。**鍵の金庫**と覚え、預けるものは次の3種類(シークレット、キー、証明書)と続けます。
- **つまずきポイント**: 「Key Vaultへ入れれば安全」と思いがちですが、実際は取り出せる権限を広く配ってしまえば、置き場所を変えただけになります。
- **関連**: シークレット・キー・証明書 / マネージドID / RBAC

### 9.2.16 シークレット・キー・証明書(Secret / Key / Certificate)

- **一言でいうと**: Key Vaultが預かる3種類の中身で、任意の文字列、暗号鍵、身元証明という役割の違いがあります。
- **たとえると**: シークレットはメモした暗証番号、キーは金庫を開ける鍵そのもの、証明書は写真付きの身分証です。
- **もう少し詳しく**: シークレットはパスワードや接続文字列などの任意の文字列を保管します。キーは暗号化や署名に使う鍵で、鍵そのものを取り出さずに「鍵を使った処理」を依頼できる点が特徴です。証明書は公開鍵と身元情報の組で、TLSのサーバー証明書などに使います。用途が違うので保管場所も分けて考えます。
- **覚え方**: 動作で3分割します。**シークレット=見せる値、キー=使う道具、証明書=名乗る書類**。
- **つまずきポイント**: 「証明書もただのファイルなので置いておけばよい」と思いがちですが、実際は有効期限があり、期限切れは通信断や認証失敗に直結します。
- **関連**: Azure Key Vault / TLSとサーバー証明書 / 保存時の暗号化と転送時の暗号化

### 9.2.17 SSH公開鍵認証と鍵ペア(SSH public key authentication / Key pair)

- **一言でいうと**: 対になった2つの鍵を使い、パスワードを送らずにLinuxサーバーへ本人確認を行う方式です。
- **たとえると**: 公開鍵は「自分専用の南京錠」、秘密鍵は「その南京錠を開けられる唯一の鍵」です。錠は配ってよく、鍵は誰にも渡しません。
- **もう少し詳しく**: `ssh-keygen`で公開鍵と秘密鍵を作り、公開鍵だけをサーバーの`~/.ssh/authorized_keys`へ置きます。接続時、サーバーはランダムな問いを出し、クライアントは秘密鍵で署名して返します。サーバーは公開鍵でその署名を検証します。つまり**秘密鍵はネットワークを流れない**ため、通信を盗聴されても鍵は盗まれません。だからこそ秘密鍵は他人に渡さず、ファイル自体にもパスフレーズを付けます。SSHは既定でTCPの`22`番を使います。
- **この案件では**: VM作成時に公開鍵をパラメーター`sshPublicKey`として渡し、VM内の`authorized_keys`へ配置します。秘密鍵はAzureにもリポジトリにも置きません。
- **覚え方**: 動作イメージで**錠を配って鍵は持つ**。ファイル名でも見分けられ、公開鍵は`.pub`が付く配ってよい側、秘密鍵は`.pub`が付かない出してはいけない側です。
- **つまずきポイント**: 「秘密鍵を相手へ送れば接続できる」と思いがちですが、実際に渡すのは公開鍵だけで、秘密鍵を渡した時点で誰でも自分になりすませます。
- **関連**: パスワード認証の無効化 / Azure Key Vault / 最小権限の原則

### 9.2.18 パスワード認証の無効化

- **一言でいうと**: SSHでのパスワードログインをそもそも受け付けない設定にして、鍵を持つ人だけに限定することです。
- **たとえると**: 玄関の暗証番号パネルを撤去し、物理鍵だけで開く扉にすることです。番号を当てる攻撃が成立しなくなります。
- **もう少し詳しく**: インターネットに面したSSHには、辞書攻撃や総当たり攻撃が絶え間なく届きます。パスワードは推測される余地がありますが、鍵は現実的な時間で当てられません。Azure VMのLinux構成には`disablePasswordAuthentication`という設定があり、OS側では`sshd`の設定で制御します。鍵認証を有効にしただけではパスワードの入口が残る場合があるため、閉じるところまでを1組の作業と考えます。
- **この案件では**: パスワード認証は無効で、SSHは公開鍵認証のみです。加えて接続元も`adminCidr`で指定したCIDRだけに限定しています。
- **覚え方**: **当てられる認証をやめる**。パスワードは当てられる、鍵は当てられない。この一言で理由まで説明できます。
- **つまずきポイント**: 「パスワードを長く複雑にすれば十分」と思いがちですが、実際は攻撃は24時間自動で続くため、受け付けない設定にするほうが確実です。
- **関連**: SSH公開鍵認証と鍵ペア / 攻撃対象領域 / 最小権限の原則

### 9.2.19 保存時の暗号化と転送時の暗号化(Encryption at rest / Encryption in transit)

- **一言でいうと**: 止まっているデータを守るのが保存時、流れているデータを守るのが転送時の暗号化です。
- **たとえると**: 保存時は書類を金庫に入れて保管すること、転送時は封をした封筒で宅配便に出すことです。
- **もう少し詳しく**: 保存時はディスクやバックアップ、ストレージ上のデータを暗号化します。Azureのマネージドディスクはプラットフォームが管理する鍵による保存時暗号化が行われ、要件に応じて顧客管理キーへ切り替えることもできます。転送時はTLSやSSHのように通信そのものを暗号化します。守る対象が違うため、片方だけでは不足します。
- **覚え方**: **棚と道**の対比です。棚に置いてあるとき=保存時、道を運んでいるとき=転送時。両方に鍵を掛けます。
- **つまずきポイント**: 「ディスクを暗号化したから通信も安全」と思いがちですが、実際は別物で、平文のHTTP通信は暗号化されたディスクの上でも盗聴されます。
- **関連**: TLSとサーバー証明書 / シークレット・キー・証明書 / 多層防御

### 9.2.20 TLSとサーバー証明書(Transport Layer Security / Server certificate)

- **一言でいうと**: 通信を暗号化しつつ相手が本物かも確かめる仕組みと、その身元を示す電子的な証明書です。
- **たとえると**: 証明書は宅配ドライバーの顔写真付き身分証、TLSは中身が見えない封筒です。両方そろって安心して渡せます。
- **もう少し詳しく**: HTTPSはHTTPをTLSで包んだもので、既定でTCPの`443`番を使います。サーバーは証明書を提示し、クライアントは信頼された認証局の署名か、ドメイン名が一致するか、有効期限内かを確認します。確認が済んでから鍵を共有し、以降の通信を暗号化します。SSLはTLSの旧称で、現在使われているのはTLSです。
- **この案件では**: HTTP(`80`番)は`openHttp=false`により既定で閉じており、HTTPS化を前提とした設計です。HTTPSの構成自体は未実装の発展課題です。
- **覚え方**: T=Transport(運ぶ)、L=Layer(層)、S=Security。**運ぶ層を安全にする**の頭文字です。ブラウザーの鍵マークは「封筒と身分証がそろった目印」と覚えます。
- **つまずきポイント**: 「証明書を入れればHTTPSになる」と思いがちですが、実際はWebサーバー側の設定、`443`番の許可、期限の更新運用まで含めて初めて成り立ちます。
- **関連**: 保存時の暗号化と転送時の暗号化 / シークレット・キー・証明書 / 攻撃対象領域

### 9.2.21 ゼロトラスト(Zero Trust)

- **一言でいうと**: 社内ネットワークだから安全という前提を捨て、アクセスのたびに検証するセキュリティの考え方です。
- **たとえると**: 全社員が顔パスで通れるオフィスをやめ、部屋ごとに毎回社員証をかざす運用へ変えることです。
- **もう少し詳しく**: 「明示的に検証する」「最小権限を使う」「侵害を前提とする」の3つが柱です。境界の内側を無条件に信頼する従来型に対し、ID、デバイス、通信のそれぞれで都度確認します。特定の製品を買えば実現するものではなく、MFA、条件付きアクセス、RBAC、通信の最小許可を積み上げて近づける設計方針です。
- **覚え方**: 名前どおり**信頼をゼロから始める**。3本柱は「検証する/絞る/破られる前提」の3語だけ覚えれば復元できます。
- **つまずきポイント**: 「誰も信頼しない極端な方式」と思いがちですが、実際は信頼を毎回確かめてから与える方式で、業務を止めるための考え方ではありません。
- **関連**: 多層防御 / 条件付きアクセス / 最小権限の原則

### 9.2.22 多層防御(Defense in Depth、深層防御)

- **一言でいうと**: 防御を1枚に頼らず何層も重ね、1つ破られても被害が広がらないようにする設計思想です。
- **たとえると**: 家の防犯を門扉、玄関の鍵、室内の金庫と重ねることです。門を越えられても金庫はすぐには開きません。
- **もう少し詳しく**: ネットワーク(NSGで最小許可)、ID(RBACで最小権限)、認証(鍵認証とMFA)、データ(暗号化)、監視(ログとアラート)のように層を分けて対策します。層ごとに守る対象が違うため、どこか1層に設定漏れがあってもただちに致命傷にはなりません。逆に、層が1枚しかない構成は設定ミス1件で崩れます。
- **この案件では**: NSGでの接続元制限、鍵認証のみのSSH、CPUアラートとLog Analytics Workspaceの受け皿という複数の層を重ねています。
- **覚え方**: **タマネギの皮**を思い出します。皮が何枚もあるほど中心まで届きにくい。英語のDepthは深さです。
- **つまずきポイント**: 「NSGで絞っているからOS側の対策は不要」と思いがちですが、実際は層が1枚減っただけで、NSGの1行の設定ミスがそのまま侵入経路になります。
- **関連**: ゼロトラスト / ラテラルムーブメント / 攻撃対象領域

### 9.2.23 攻撃対象領域(Attack Surface、アタックサーフェス)

- **一言でいうと**: 外から狙える入口の総量で、公開したIPやポート、権限を持つアカウントの数だけ増えていきます。
- **たとえると**: 建物の出入口や窓の数です。多いほど便利ですが、見張るべき場所も同じだけ増えます。
- **もう少し詳しく**: Public IP、開いているポート、公開しているサービス、強い権限を持つアカウント、使われていない古いシークレットなどがすべて対象領域に含まれます。使っていないものを閉じる、権限を持つ人を減らす、必要なときだけ開ける、という3手で小さくできます。減らせるものを減らす対策が、費用対効果では最も高くつきます。
- **この案件では**: HTTPを既定で閉じ、SSHは`adminCidr`のみに限定し、単一VMで公開面を最小にしています。Public IPを使う点は面がゼロでないことを意味し、基本設計で残る課題として明記しています。
- **覚え方**: **面積**で考えます。ポートを1つ開ければ面積が増え、閉じれば減る。ゼロにはできないが小さくはできます。
- **つまずきポイント**: 「使っていない機能は放置してよい」と思いがちですが、実際は使っていない入口ほど誰も見ていないため、狙われやすくなります。
- **関連**: 最小権限の原則 / Just-In-Timeアクセス / パスワード認証の無効化

### 9.2.24 ラテラルムーブメント(Lateral Movement、横方向移動)

- **一言でいうと**: 侵入された1台を足場に、攻撃者が同じ環境内の別のサーバーへ横へ広げていく動きです。
- **たとえると**: マンションの1室に入られたあと、共用廊下を通って隣の部屋も開けられてしまう状態です。
- **もう少し詳しく**: 最初の侵入口は本命ではないことが多く、そこで資格情報を集めて別のサーバーへ移り、最終的に重要なデータへ到達しようとします。対策はサブネットとNSGで通信を分ける、共有の管理者アカウントをやめる、強い権限を常時持たせないことです。ゼロトラストの「侵害を前提とする」が最も効く場面です。
- **覚え方**: Lateralは横。前進(縦)ではなく**横滑り**です。「横に滑らせない=通路を塞ぐ」まで続けて覚えると対策も出てきます。
- **つまずきポイント**: 「入口を守れば十分」と思いがちですが、実際は1台入られた後の広がりを止める内側の仕切りがないと、被害は環境全体に及びます。
- **関連**: 多層防御 / 最小権限の原則 / 攻撃対象領域

### 9.2.25 Microsoft Defender for Cloudとセキュアスコア(Secure Score)

- **一言でいうと**: Azure環境の設定を点検して改善案を出し、対策の進み具合を点数で示すサービスです。
- **たとえると**: 健康診断とその総合判定です。項目ごとの指摘と、全体としての状態が数値で分かります。
- **もう少し詳しく**: 構成の弱点を推奨事項として一覧にし、対応するとセキュアスコアが上がります。無償で使える基本のクラウド構成管理の機能と、サーバー保護などの有償プランに分かれ、有償プランを有効にすると脆弱性の評価やjust-in-time VMアクセスといった機能が使えます。点数を上げること自体を目的にせず、指摘の重要度が高いものから潰す使い方が実務的です。
- **この案件では**: 基礎編では有効化していません。基本設計の将来構成で、本番要件が加わった際の検討対象として挙げています。
- **覚え方**: 健康診断の連想でつなげます。**Defender=防御役、Secure Score=セキュリティの健康スコア**。生活習慣を直すと点数が上がる、という関係も同じです。
- **つまずきポイント**: 「スコアが満点なら安全」と思いがちですが、実際の評価対象は既知の推奨事項であり、アプリの脆弱性や運用手順の穴は別に確認する必要があります。
- **関連**: ゼロトラスト / Just-In-Timeアクセス / 監査ログ

### 9.2.26 監査ログ(Audit log、アクティビティログ)

- **一言でいうと**: 誰がいつ何をしたかを残す記録で、原因調査と社内への説明の両方の土台になります。
- **たとえると**: 建物の入退室記録です。何かあったときに「いつ誰が入ったか」をさかのぼれます。
- **もう少し詳しく**: Azureのアクティビティログはサブスクリプションに対する操作(作成、変更、削除)を記録します。Entra ID側には監査ログとサインインログがあり、ID関連の操作とサインインの結果を確認できます。プラットフォームでの保持期間には限りがあるため、長期間残して検索したい場合はLog Analyticsワークスペースなどへ送る設定が必要です。
- **この案件では**: VMの停止や割当解除に気付いたとき、アクティビティログで変更者と時刻を確認する初動を運用側で定めています。Log Analytics Workspaceは受け皿だけを作成し、OSログの収集に必要なAMAとDCRは未実装の発展課題です。
- **覚え方**: **記録がなければ説明できない**。種類は「操作の記録=監査・アクティビティログ、入室の記録=サインインログ」の2つに分けて覚えます。
- **つまずきポイント**: 「ログは自動で永久に残る」と思いがちですが、実際は保持期間があり、送り先を決めていないと必要な時期をさかのぼれません。
- **関連**: PIM / テナントとディレクトリ / Log Analytics Workspace

## 9.3 このセクションの覚え方まとめ

この分野は「入る」→「できる範囲」→「守り方」→「見える化」の4段で並べると迷いません。

```text
[入る]     Entra ID  → MFA → 条件付きアクセス       = 認証(誰か)
[範囲]     RBAC → ロール定義/割り当て/スコープ       = 認可(何ができるか)
           → 組み込みロール → 最小権限 → PIM/JIT
[守り方]   鍵認証とパスワード無効化 / Key Vault
           / 保存時と転送時の暗号化 / TLS
[見える化] Defender for Cloudとセキュアスコア / 監査ログ
```

- 迷ったら2語に戻ります。**認証=誰、認可=どこまで**。
- 権限は上から下へ流れます。管理グループ → サブスクリプション → リソースグループ → 個別リソース。
- 本案件の合言葉は**錠を配って鍵は持つ**。公開鍵はVMへ、秘密鍵は手元だけ、パスワードの入口は閉じる。
- 考え方の3語は「ゼロトラスト(毎回検証)」「多層防御(重ねる)」「最小権限(絞る)」。この3つで設計判断をほぼ説明できます。
