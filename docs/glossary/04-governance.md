# 4. 契約と管理階層・ガバナンス

[用語集トップ](../11-azure-glossary.md) ・ 前: [3. クラウドとAzureの基礎概念](03-cloud-basics.md) ・ 次: [5. ネットワークの基礎(Azure以前に必要な知識)](05-network-basics.md)

Azureで最初につまずくのは、機能の難しさではなく「このリソースは、どこに作られて、誰に請求されるのか」が分からないことです。Azureはテナント、管理グループ、サブスクリプション、リソースグループ、リソースという入れ子の階層でできており、課金が決まる階層とルールが決まる階層は別々です。このセクションではその地図と、名前・タグ・ポリシーで散らからないようにする道具、そしてAzureを操作する4つの入口をまとめます。本案件で `rg-portfolio-dev-jpe-001` という名前を決め、タグを全リソースへ付け、削除を安全に行えるのは、すべてこの階層の理解が土台です。

## 4.2 用語解説

### 4.2.1 Microsoft Entra IDテナント(Microsoft Entra ID tenant、旧Azure ADテナント)

- **一言でいうと**: 誰がAzureにログインできるかを管理する、組織ごとの人の名簿の入れ物です。
- **たとえると**: 会社の社員名簿と社員証を発行する部署。名簿に載っていない人は、そもそも入館できません。
- **もう少し詳しく**: テナントはユーザー、グループ、アプリの登録情報を持つ認証の単位です。Azureを操作するときは、まずテナントで本人確認(認証)が行われ、その後にサブスクリプション側で権限(認可)が確認されます。1つのサブスクリプションが信頼するテナントは、常に1つだけです。
- **この案件では**: `scripts/deploy.ps1` は実行前に `az account show` で対象の `tenantId` とサブスクリプションを表示します。テナントIDは公開しない値なので、証跡のスクリーンショットではマスクします。
- **覚え方**: テナント=入居者名簿。「入れるかどうか」を決める層で、「いくら払うか」は決めない層です。
- **つまずきポイント**: テナントを分ければ請求も分かれると思いがちですが、請求はサブスクリプション側の話です。逆に、ログインできても対象サブスクリプションの権限がなければ何も作れません。
- **関連**: サブスクリプション / 管理グループ / RBAC

### 4.2.2 サブスクリプション(Subscription)

- **一言でいうと**: 使った分の請求先と利用上限がひもづく、Azureの契約単位です。
- **たとえると**: 同じ家の中の電気メーター。建物(テナント)が同じでも、メーター(契約)が違えば請求書は別々に届きます。
- **もう少し詳しく**: すべてのリソースは必ずどれか1つのサブスクリプションの下に作られ、そこへ課金されます。リージョンごとの作成上限(クォータ)もサブスクリプション単位です。本番と検証を分けるのは、請求と上限を分けたいときです。
- **この案件では**: `infra/main.bicep` は `targetScope = 'subscription'` で、サブスクリプションを対象にリソースグループごと作成します。作成先を間違えると別の請求先にリソースができるため、実行前の `az account show` での確認が必須です。
- **覚え方**: Sub+scribe=「申し込む」。申し込んだ人に請求が行く単位、と語源から覚えます。請求と上限はセットです。
- **つまずきポイント**: `az login` すれば意図した契約が選ばれていると思いがちですが、複数持っていると既定が別のサブスクリプションになっていることがあります。毎回表示して確認します。
- **関連**: テナント / リソースグループ / クォータ

### 4.2.3 管理グループ(Management Group)

- **一言でいうと**: 複数のサブスクリプションをまとめて、同じルールを一度に効かせるための上位階層です。
- **たとえると**: 会社の事業部。事業部で決めた規程は、その下のすべての課に自動で適用されます。
- **もう少し詳しく**: テナントの直下にルート管理グループが1つあり、その下に管理グループを入れ子にしてサブスクリプションを所属させます。ここでAzure PolicyやRBACを割り当てると、配下のサブスクリプション全体へ継承されます。サブスクリプションが増えてから同じ設定を1つずつ入れる手間を、先に消すための層です。
- **この案件では**: 学習用の単一サブスクリプション構成のため、基礎編では管理グループを作りません。階層の名前と役割だけ知っておけば十分です。
- **覚え方**: 「まとめて上から」。上に付けたルールは下へ落ちる、傘の関係です。
- **つまずきポイント**: 課金がまとまる階層と思いがちですが、請求はサブスクリプション単位のままです。管理グループがまとめるのは、ルールと権限です。
- **関連**: サブスクリプション / Azure Policy / ランディングゾーン

### 4.2.4 リソースグループ(Resource Group)

- **一言でいうと**: 同じ案件のリソースをまとめて置き、まとめて消せるようにする箱です。
- **たとえると**: 引っ越し用の段ボール1箱。中身をまとめて運べて、要らなくなれば箱ごと捨てられます。
- **もう少し詳しく**: リソースは必ず1つのリソースグループに属します。作る時期と消す時期が同じものを1箱にまとめるのが基本で、削除も箱ごと行えます。リソースグループ自体にもリージョンがありますが、これは箱の管理情報を置く場所であり、中のリソースは別のリージョンでも構いません。
- **この案件では**: `rg-portfolio-dev-jpe-001` の中に、VNet、Subnet、NSG、Public IP、NIC、Linux VM、Log Analytics Workspace、CPU使用率のメトリックアラートをすべて入れています。`scripts/remove.ps1` はリソースグループ名を二重に指定して、箱ごと削除します。
- **覚え方**: 「捨てるタイミングが同じものを、同じ箱へ」。この一文で分け方の判断がつきます。
- **つまずきポイント**: 見た目を整えるフォルダーだと思いがちですが、削除すると中のリソースも消えます。削除前の対象名の確認が最重要です。
- **関連**: リソース / サブスクリプション / リソースロック

### 4.2.5 リソース(Resource)

- **一言でいうと**: Azure上に実際に作られる部品1つ1つのことです。
- **たとえると**: 段ボールの中に入っている家電1台1台。箱は入れ物で、値段が付くのは中身です。
- **もう少し詳しく**: VM、VNet、NSG、Public IP、Log Analytics Workspaceなど、作成・課金・監視の対象になる実体がリソースです。それぞれに種別、名前、リージョン、タグがあります。設計とは、必要なリソースを選び、その設定値を決める作業だと言い換えられます。
- **この案件では**: Bicepの `resource` ブロック1つが、原則としてリソース1つに対応します。`infra/modules/workload.bicep` にネットワークとVM側のリソースがまとまっています。
- **覚え方**: 「課金明細に名前が出るもの」がリソース。数を数えるときも明細の単位で数えます。
- **つまずきポイント**: VMを1台作れば1リソースだと思いがちですが、実際はNIC、ディスク、Public IPなどが別のリソースとして一緒に作られます。削除漏れが起きるのはこのためです。
- **関連**: リソースグループ / リソースID / リソースプロバイダー

### 4.2.6 リソースID(Resource ID)

- **一言でいうと**: リソース1つを世界で一意に指し示す、スラッシュ区切りの長い住所です。
- **たとえると**: 「都道府県/市区町村/番地/建物名/部屋番号」という住所表記。上から順に範囲を絞って1室にたどり着きます。
- **もう少し詳しく**: 形は `/subscriptions/<サブスクリプションID>/resourceGroups/<リソースグループ名>/providers/<リソースプロバイダー>/<リソース種別>/<リソース名>` です。ポータルのプロパティやCLIの出力に現れ、権限やアラートの適用範囲(スコープ)を指定するときにも使います。
- **覚え方**: 4.3の階層図をそのまま横に倒した形です。サブスクリプション → リソースグループ → 提供元 → 種別 → 名前の5段跳びと覚えます。
- **つまずきポイント**: 名前だけで一意に決まると思いがちですが、同じ名前のリソースは別のリソースグループに存在できます。特定にはIDまで必要です。
- **関連**: リソースプロバイダー / ARM / リソースグループ

### 4.2.7 リソースプロバイダー(Resource Provider)

- **一言でいうと**: リソースの種類ごとの担当部署で、`Microsoft.Compute` のような名前が付いています。
- **たとえると**: 役所の窓口。住民票は住民課、車の登録は運輸支局と、扱う書類ごとに受け付ける窓口が違います。
- **もう少し詳しく**: VMは `Microsoft.Compute`、VNetやNSGは `Microsoft.Network`、リソースグループは `Microsoft.Resources` が担当します。Bicepで書く `Microsoft.Network/virtualNetworks@2024-05-01` は「プロバイダー/種別@APIバージョン」の組み合わせです。使うプロバイダーはサブスクリプションで登録されている必要があり、未登録だと作成が失敗します。
- **覚え方**: `Microsoft.<担当>` の形。Compute=計算(VM)、Network=通信、Storage=保管、Resources=箱、と担当名を英語で読みます。
- **つまずきポイント**: プロバイダー未登録のエラーを権限不足と読み違えがちですが、こちらは「そのサービスの窓口がまだ開いていない」状態で、対処が別です。
- **関連**: リソースID / ARM / Bicep

### 4.2.8 ARM(Azure Resource Manager、Azureリソースマネージャー)

- **一言でいうと**: ポータルでもコマンドでも、Azureへの作成・変更依頼が必ず通る受付窓口です。
- **たとえると**: 会社の総務窓口。誰がどの申請書を出しても、最後は総務が受け付けて各部署へ回します。
- **もう少し詳しく**: ポータル、Azure CLI、Azure PowerShell、Bicepは入力方法が違うだけで、依頼はすべてARMへ届きます。ARMは権限とポリシーを確認したうえで、担当のリソースプロバイダーへ処理を渡します。だからどの手段で作っても結果は同じ形になり、Bicepは完成形だけ書けば差分の計算をARMに任せられます。
- **この案件では**: `az bicep build` でBicepをARMテンプレート(JSON)へ変換し、`az deployment sub what-if` でARMに変更予測を問い合わせます。
- **覚え方**: 頭文字がそのまま役割です。Azureの/Resource(資源)を/Manage(管理)する窓口。
- **つまずきポイント**: ARMをファイル形式の名前だと思いがちですが、本体はAzure側の管理サービスです。JSONのARMテンプレートは、その窓口へ出す申請書にあたります。
- **関連**: Bicep / リソースプロバイダー / コントロールプレーン

### 4.2.9 コントロールプレーンとデータプレーン(Control Plane / Data Plane)

- **一言でいうと**: リソースを「作る・変える」操作と、リソースを「使う」操作を分けて考える区別です。
- **たとえると**: マンションの管理会社に改装を頼むのがコントロールプレーン、自分の鍵で部屋に入って生活するのがデータプレーンです。
- **もう少し詳しく**: コントロールプレーンはARM経由の操作で、VMの作成やNSGルールの変更が該当します。データプレーンはリソース自体への操作で、VMへのSSHログインやNginxへのHTTPアクセスが該当します。権限も別系統で、Azure側のロールを持っていてもOSにログインできるわけではありません。
- **この案件では**: Bicepでの構築とNSGの設定変更はコントロールプレーン、SSHでのログインとNginxの表示確認はデータプレーンです。つながらないときは、どちら側の問題かをまず切り分けます。
- **覚え方**: 対比で覚えます。作る側は管制塔(control)、使う側は線路を走る列車(data)。管制塔の許可と、列車の運転は別の仕事です。
- **つまずきポイント**: Azureで強い権限を持てばVMにもログインできると思いがちですが、OSのユーザーとSSH鍵は別管理です。本案件はパスワード認証を無効化しているため、鍵がなければ入れません。
- **関連**: ARM / RBAC / NSG

### 4.2.10 タグ(Tag)

- **一言でいうと**: リソースに貼る「名前:値」の付箋で、後からの絞り込みや費用の集計に使います。
- **たとえると**: 宅配の荷物に貼る宛名シール。誰の荷物で、どの現場向けかが一目で分かります。
- **もう少し詳しく**: `Environment: dev` のようにキーと値の組を付け、コストの内訳表示、一括検索、棚卸しに使います。「持ち主」「環境」「管理方法」が分かるタグを最初に決めておくと、後から作った人を探す時間がなくなります。
- **この案件では**: `infra/main.bicep` の `commonTags` で `Environment` / `Project` / `Owner` / `ManagedBy` / `DataClassification` の5つを全リソースへ付けています。`Owner` はパラメーター `owner` で渡す、秘密情報を含まない識別子です。
- **覚え方**: 「誰が(Owner)・何を(Project)・どこで(Environment)」の3点から始めます。この3つがあれば追跡できます。
- **つまずきポイント**: リソースグループに付けたタグが中のリソースへ自動で引き継がれると思いがちですが、継承はされません。各リソースに付ける必要があるため、コードで一括付与するのが確実です。
- **関連**: 命名規則 / Azure Policy / リソースグループ

### 4.2.11 命名規則(CAF準拠のリソース名)

- **一言でいうと**: リソース名の並べ方を先に決めて、名前を見ただけで正体が分かるようにするルールです。
- **たとえると**: 学籍番号。「入学年度+学部+番号」と決めておけば、番号だけで所属が読めます。
- **もう少し詳しく**: Cloud Adoption Framework(CAF)は「種別の略称-ワークロード名-環境-リージョン-連番」という形を推奨しています。本リポジトリの `rg-portfolio-dev-jpe-001` は、`rg`=リソースグループ、`portfolio`=プロジェクト名、`dev`=開発環境、`jpe`=`japaneast`、`001`=連番、と5つの部品に分解できます。
- **この案件では**: Bicepが `<projectName>-<environment>-<regionCode>-001` という共通の接尾辞を組み立て、全リソース名で使い回します。
- **覚え方**: 前から「種類・仕事・環境・場所・番号」。この5語の順番だけ覚えれば、初見のリソース名も読み解けます。
- **つまずきポイント**: 名前は後から直せると思いがちですが、多くのリソースは作成後に改名できず、作り直しになります。ストレージアカウントのように全世界で一意かつ小文字英数字のみという制約を持つ種別もあります。
- **関連**: タグ / リソースグループ / CAF

### 4.2.12 Azure Policy

- **一言でいうと**: 決めたルールに合わない設定を、そもそも作らせないか、違反として一覧に出す仕組みです。
- **たとえると**: マンションの管理規約。ペット禁止と決まっていれば、入居の時点で許可されません。
- **もう少し詳しく**: 管理グループ、サブスクリプション、リソースグループのいずれかに割り当てると、配下のリソースが評価されます。効果には作成を拒否する `deny`、記録だけ残す `audit`、足りない設定を補う `deployIfNotExists` などがあります。「東日本以外にVMを作らせない」「タグのないリソースを監査する」といった統制に使います。
- **この案件では**: 単一サブスクリプションの学習環境のため、基礎編ではポリシーを割り当てていません。同じ目的を、Bicepでの設定固定とCIの静的検証で代替しています。
- **覚え方**: RBACとの対比で覚えます。RBACは「誰ができるか」、Azure Policyは「どんな設定が許されるか」。人か設定か、です。
- **つまずきポイント**: 権限があれば何でも作れると思いがちですが、`deny` のポリシーは強い権限を持つ人の操作でも止めます。作成が通らないときの調査先の1つです。
- **関連**: RBAC / 管理グループ / タグ

### 4.2.13 リソースロック(Resource Lock)

- **一言でいうと**: 消させない、または変更させないようにする、うっかり防止の南京錠です。
- **たとえると**: ブレーカーに貼る操作禁止の札。担当者が誰であっても、札を外さないと触れません。
- **もう少し詳しく**: 種類は削除だけを禁止する `CanNotDelete` と、変更も禁止する `ReadOnly` の2つです。サブスクリプション、リソースグループ、リソースのどこにも設定でき、下位のリソースへ継承されます。ロックの作成と解除には対応する権限が必要で、ロックがある間は強い権限を持つ人でも削除できません。
- **この案件では**: 学習用のため設定していません。誤削除の防止は、`scripts/remove.ps1` でリソースグループ名を二重に指定させる方法で代替しています。
- **覚え方**: 名前がそのまま動作です。`CanNotDelete`=消せない、`ReadOnly`=読むだけ。強いのは `ReadOnly` のほうです。
- **つまずきポイント**: ロックしておけば安心と思いがちですが、`ReadOnly` は正当な運用変更まで止めます。逆に、リソースグループが削除できない原因がロックであることも多く、削除手順の確認項目になります。
- **関連**: リソースグループ / RBAC / Azure Policy

### 4.2.14 クォータ(Quota、サブスクリプションの上限)

- **一言でいうと**: 1つのサブスクリプションでリージョンごとに作れる量の上限です。
- **たとえると**: 携帯回線のデータ上限。契約した枠を超えると、それ以上は使えません。
- **もう少し詳しく**: 代表例はVMのvCPU数で、サブスクリプションとリージョンとVMのシリーズの組み合わせごとに枠があります。上限に達すると、権限もコードも正しいのに作成が失敗します。多くの上限はサポート要求で引き上げを申請できます。具体的な値は契約の種類で異なり変更される場合があるため、ポータルの使用量と上限の表示で確認します。
- **覚え方**: 「箱の大きさ」ではなく「使える枠の大きさ」。数字の話で、料金の話ではないと区別します。
- **つまずきポイント**: 課金の上限設定だと思いがちですが、クォータは数量の上限で、支払額を止める仕組みではありません。費用の管理はCost Managementと予算アラートの役割です。
- **関連**: サブスクリプション / リージョン / VMサイズ

### 4.2.15 Azure Portal

- **一言でいうと**: ブラウザーからAzureを操作したり状態を確認したりできる管理画面です。
- **たとえると**: ネットバンキングの画面。残高照会も振り込みも、画面上の操作で1件ずつ行えます。
- **もう少し詳しく**: リソースの作成だけでなく、状態確認、メトリックやログの閲覧、権限やタグの確認に向きます。一方で同じ構成をもう一度作るときの再現が難しく、変更の記録も残りにくいのが弱点です。実務では「見るのはポータル、作るのはコード」という使い分けをします。
- **この案件では**: 構築はBicepで行い、ポータルは作成結果の確認と証跡のスクリーンショット取得に使います。スクリーンショットではテナントIDなどの機密値をマスクします。
- **覚え方**: Portal=入口。入口は分かりやすいけれど、毎回自分の手で開けなければならないと覚えます。
- **つまずきポイント**: ポータルで作るのが一番早いと思いがちですが、同じ環境を3回作る場面ではコードのほうが速く、間違いも減ります。
- **関連**: Azure CLI / Bicep / Azure Cloud Shell

### 4.2.16 Azure CLI

- **一言でいうと**: `az`で始まるコマンドを打ってAzureを操作する、コマンド行のツールです。
- **たとえると**: ポータルが自動販売機のボタンなら、Azure CLIは注文内容を1行で書いて渡す伝票です。
- **もう少し詳しく**: Windows、macOS、Linuxで同じコマンドが使え、`az login` で認証します。`az group create` のように「対象+動作」の順で書き、結果をJSONで受け取れるためスクリプトやCIとの相性がよいのが特徴です。
- **この案件では**: `scripts/deploy.ps1` が `az account show`、`az bicep build`、`az deployment sub what-if`、`az deployment sub create` を使います。CIでも `az bicep build` と `az bicep build-params` で構文を検証しています。
- **覚え方**: 語順は「`az`+名詞+動詞」。`az group create` を「グループを、作る」と英語の並びで読むと迷いません。
- **つまずきポイント**: `az`はPowerShell専用だと思いがちですが、BashでもWindowsのコマンドプロンプトでも同じように動きます。
- **関連**: Azure PowerShell / ARM / Bicep

### 4.2.17 Azure PowerShell

- **一言でいうと**: PowerShellからAzureを操作するための公式モジュール(`Az`モジュール)です。
- **たとえると**: 同じ目的地に着くバスと電車。Azure CLIとどちらでも行けますが、乗り方の作法が違います。
- **もう少し詳しく**: `Connect-AzAccount` で接続し、`New-AzResourceGroup` のように「動詞-Az名詞」の形でコマンドを書きます。結果がオブジェクトとして返るため、Windowsの運用で使い慣れたPowerShellの処理と組み合わせやすいのが強みです。
- **この案件では**: `scripts/deploy.ps1` などはPowerShellのスクリプトですが、Azureへの操作自体はAzure CLIの `az`コマンドで行っています。この2つは別物なので混同しないよう注意します。
- **覚え方**: 「動詞-Az名詞」。Get、New、Removeと動詞が先に来るのがPowerShell流、名詞が先に来るのがAzure CLI流です。
- **つまずきポイント**: 拡張子が `.ps1`ならAzure PowerShellを使っていると思いがちですが、本リポジトリのようにPowerShellからAzure CLIを呼ぶ構成もよくあります。中身のコマンドで判断します。
- **関連**: Azure CLI / Azure Cloud Shell / ARM

### 4.2.18 Azure Cloud Shell

- **一言でいうと**: ブラウザー上で使える、Azure用のコマンド実行環境です。
- **たとえると**: 図書館の共用パソコン。自分の端末に何も入れなくても、必要な道具がそろっています。
- **もう少し詳しく**: Azure CLI、Azure PowerShell、Bicep CLIなどがあらかじめ用意され、ログイン済みの状態から使い始められます。自分のPCに環境を作れないときや、共有端末から一時的に確認したいときに向きます。一定時間操作しないとセッションが切れるため、長時間の作業には向きません。
- **覚え方**: Cloud(雲の上)+Shell(コマンド画面)。「自分のPCにインストールしない`az`」と覚えます。
- **つまずきポイント**: 自分のPCと同じ環境だと思いがちですが、ファイルの残り方や使える範囲は環境の設定によって変わります。大事な作業ファイルはリポジトリで管理し、シェル側に置き続けないのが安全です。
- **関連**: Azure CLI / Azure PowerShell / Azure Portal

### 4.2.19 Azure Advisor

- **一言でいうと**: 現在の構成を見て、改善の推奨事項を分野別に挙げてくれる無料の助言サービスです。
- **たとえると**: 健康診断の結果表。数値の一覧と一緒に「ここを改善しましょう」という指摘が並びます。
- **もう少し詳しく**: 信頼性、セキュリティ、パフォーマンス、コスト、オペレーショナルエクセレンスの分野で推奨事項が示され、Azure Well-Architected Frameworkの柱と対応しています。実際の構成にもとづく指摘なので、設計レビューの出発点として使えます。
- **この案件では**: 単一VM構成のため、可用性や監視の強化に関する指摘が出る可能性があります。これは未実装の発展課題と重なる領域で、あえて受け入れている判断でもあります。
- **覚え方**: Advisor=助言者。「健康診断は受けるが、治療方針を決めるのは主治医である自分」と覚えます。
- **つまずきポイント**: 出た指摘はすべて直すべきだと思いがちですが、学習目的で単一VMにしている場合のように、要件上あえて残す判断も設計の一部です。理由を書いておくことが大切です。
- **関連**: Azure Well-Architected Framework / Azure Policy / メトリックアラート

### 4.2.20 CAF(Cloud Adoption Framework、クラウド導入フレームワーク)

- **一言でいうと**: クラウド導入を戦略づくりから運用まで順番に進めるための、Microsoftの手引きです。
- **たとえると**: 家を建てるときの工程表。土地探し、設計、着工、引き渡し、その後の点検までの順番が示されています。
- **もう少し詳しく**: 戦略、計画、準備、導入、統治、管理といった段階ごとに、決めるべきことと推奨手順がまとまっています。初心者が最初に出会うのは「準備」段階に含まれる命名規則とタグ付けの推奨で、本リポジトリの `rg-portfolio-dev-jpe-001` という名前もこの考え方に沿っています。
- **覚え方**: Cloudを/Adopt(採用)する/Framework(型)の頭文字です。CAFは「組織の進め方」担当、Well-Architected Frameworkは「設計品質」担当、と役割で区別します。
- **つまずきポイント**: Azureの機能名だと思いがちですが、CAFはドキュメントとして提供される指針で、画面上のサービスではありません。
- **関連**: Azure Well-Architected Framework / ランディングゾーン / 命名規則

### 4.2.21 Azure Well-Architected Framework(Azureアーキテクチャ設計の指針)

- **一言でいうと**: 設計の良し悪しを5つの柱で点検するための、Microsoftの設計指針です。
- **たとえると**: 車検の検査項目表。走れば合格ではなく、決められた観点ごとに1つずつ見ていきます。
- **もう少し詳しく**: 5つの柱は信頼性、セキュリティ、コスト最適化、オペレーショナルエクセレンス(運用性)、パフォーマンス効率です。柱は互いにぶつかることがあり、たとえば冗長化して信頼性を上げるとコストが上がります。設計とは、どの柱をどこまで優先するかを要件に合わせて決め、その理由を説明できる状態にすることです。
- **この案件では**: 「学習費用を抑えるため単一VMにする」という判断は、コスト最適化を優先して信頼性を割り切った例として説明できます。面接では柱の名前を使って理由を語れると強みになります。
- **覚え方**: 「信・セ・コ・運・パ」の5文字。信頼性/セキュリティ/コスト/運用性/パフォーマンスの頭文字を、この順で唱えます。
- **つまずきポイント**: WAFと略しがちですが、Web Application Firewallと紛らわしいため、Well-Architectedは略さずに書くのが安全です。
- **関連**: CAF / Azure Advisor / ランディングゾーン

### 4.2.22 ランディングゾーン(Landing Zone)

- **一言でいうと**: 本格的にリソースを載せる前に、ネットワークや権限、統制を整えておく受け入れ用の土台です。
- **たとえると**: 工場を建てる前の土地の造成と、道路や電気、水道の引き込み。土台が整っていれば、あとは建物を建てるだけです。
- **もう少し詳しく**: CAFの「準備」段階で用意する環境の型で、管理グループの階層、サブスクリプションの分け方、ネットワーク設計、RBAC、Azure Policy、命名規則とタグ、監視の受け皿などを先に決めます。後から直すと影響範囲が広くなる項目を、最初にまとめて用意する考え方です。
- **この案件では**: 単一サブスクリプションの学習環境なので、ランディングゾーンは構築しません。ただし命名規則とタグ、監視の受け皿としてのLog Analytics Workspaceを先に用意している点は、同じ考え方の縮小版といえます。
- **覚え方**: 飛行機が降りる滑走路(landing)を先に舗装するイメージ。舗装のないところに機体は降ろせません。
- **つまずきポイント**: 買ってくる製品名だと思いがちですが、設計と設定の集まりです。大企業向けの大きな型だけでなく、小さく始める形もあります。
- **関連**: CAF / 管理グループ / Azure Policy

## 4.3 このセクションの覚え方まとめ

```text
Microsoft Entra IDテナント        <- 誰が入れるか(認証)
  +- 管理グループ                 <- ルールと権限をまとめて継承
       +- サブスクリプション      <- 課金と数量上限(クォータ)
            +- リソースグループ   <- まとめて作り、まとめて消す箱
                 +- リソース      <- 課金明細に名前が出る部品
```

- 上から「人 → ルール → お金 → 箱 → 部品」の5段。この順番を口で言えれば、どこに何が作られるか迷いません。
- 決まる場所を混ぜないこと。請求はサブスクリプション、ルールの継承は管理グループ、削除の単位はリソースグループです。
- 名前は `rg-portfolio-dev-jpe-001` = 種類・仕事・環境・場所・番号。タグは「誰が・何を・どこで」の3点から。
- 操作の入口はポータル、Azure CLI、Azure PowerShell、Cloud Shellの4つでも、出口は必ずARMの1つです。
- 作れないときの調査順は、権限 → Azure Policy → クォータ → リソースロック。上から順に外していきます。
