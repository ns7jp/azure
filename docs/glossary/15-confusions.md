# 15. 混同しやすい用語の対比

[用語集トップ](../11-azure-glossary.md) ・ 前: [14. 現場でよく使う仕事の言葉](14-workplace.md)

用語は1語ずつ覚えるより、似た用語と並べて「どこが違うか」で覚えるほうが速く、そして忘れにくくなります。現場でのミスの多くは、知らない用語ではなく、知っているつもりの2語を取り違えたときに起きます。ここでは初心者が実際に取り違える34組を、一撃で違いが分かる形に並べます。まず表で全体を眺め、特に間違えやすい10組は後半で詳しく見ていきます。

## 15.2 特に間違えやすい10組の詳しい解説

### 15.2.1 テナント と サブスクリプション

- **違いを一言で**: テナントは「人とIDの世界」、サブスクリプションは「リソースと請求の世界」です。
- **なぜ混同するのか**: どちらもAzureの一番外側にある大きな箱に見えるうえ、サインイン画面でも管理画面でも隣り合って表示されるためです。
- **見分け方**: 「誰がサインインできるか」「どのグループに属するか」の話ならテナント、「どこにリソースを作るか」「請求はどこに行くか」の話ならサブスクリプションです。1つのテナントに複数のサブスクリプションをぶら下げられますが、逆はできません。
- **覚え方**: テナントは社員名簿、サブスクリプションは部門ごとの予算。人事と経理は別部署だと考えると混ざりません。

### 15.2.2 リソースグループのロケーション と リソースのロケーション

- **違いを一言で**: リソースグループのロケーションは管理情報の置き場所、リソースのロケーションは実体が動く場所です。
- **なぜ混同するのか**: 作成画面でリソースグループにも地域を選ばされるため、「ここで選んだ地域にリソースが建つ」と読めてしまうからです。
- **見分け方**: 実際にVMが動く地域を決めるのは各リソースの`location`です。リソースグループの地域は、そのグループ自身のメタデータをどこに保存するかを決めるものだと覚えてください。両者が違っていても構成としては成立します。
- **この案件では**: リソースグループ`rg-portfolio-dev-jpe-001`もその中のリソースも`japaneast`にそろえます。そろえておくと、後から読む人が地域を1つだけ覚えれば済みます。
- **覚え方**: リソースグループの地域は「住所録をしまってある場所」、リソースの地域は「本人が住んでいる場所」。住所録が東京にあっても、住人が大阪に住んでいることはありえます。

### 15.2.3 NSG と OSのファイアウォール(ufw / firewalld)

- **違いを一言で**: NSGはAzureのネットワーク側で通信を止め、`ufw`や`firewalld`はVMの中で通信を止めます。
- **なぜ混同するのか**: どちらも「ポートを開ける・閉じる」という同じ言葉で語られるため、片方を設定すればもう片方も追随すると思い込みやすいのです。
- **見分け方**: パケットは`Public IP → NSGの判定 → NIC → VM → OS内のファイアウォール → アプリ`の順に進みます。どこか1か所でも拒否があれば届きません。NSGで許可しても接続できない場合はOS側を、NSGのルール一覧に該当行がなければAzure側を疑います。
- **この案件では**: 通信の順番は`管理者PC → Public IP → NSGの判定 → NIC → VM → Nginx`です。SSHは`adminCidr`で指定したCIDRからのみ許可し、HTTPの`80`番は`openHttp=false`により既定で閉じています。
- **覚え方**: NSGはマンションのオートロック、OSのファイアウォールは部屋のドアの鍵。オートロックを開けてもらっても、部屋の鍵が閉まっていれば中には入れません。

### 15.2.4 サービスエンドポイント と プライベートエンドポイント

- **違いを一言で**: サービスエンドポイントは相手サービスに送信元サブネットを識別させる仕組みで、絞るのは相手サービス側の設定です。プライベートエンドポイントは相手を自分の中に引き込む仕組みです。
- **なぜ混同するのか**: どちらも「インターネットを通らずにAzureのサービスへ安全につなぐ」と説明されるため、目的が同じに見えるからです。
- **見分け方**: 接続先のアドレスを見ます。プライベートエンドポイントを作ると、相手サービス用のネットワークインターフェイスが自分のサブネットに現れ、サブネット内のプライベートIPで呼べるようになります。サービスエンドポイントではそうしたIPは生えず、あくまで対象サービス側で「このサブネットからのみ受け付ける」と絞る形になります。
- **覚え方**: サービスエンドポイントは通用口を関係者専用にする、プライベートエンドポイントは相手に自社ビルへ入居してもらう。後者だけが「自分の側の住所」を持ちます。

### 15.2.5 Load Balancer と Application Gateway

- **違いを一言で**: Load BalancerはIPとポートだけを見て振り分け、Application GatewayはURLやホスト名まで見て振り分けます。
- **なぜ混同するのか**: どちらも「複数のサーバーへ負荷を分散する装置」であり、構成図でも同じ位置に描かれるためです。
- **見分け方**: 「`/images`へのリクエストだけ別のサーバーへ送りたい」「証明書をここで終端したい」「WAFを入れたい」といった要望が出た時点で、レイヤー7を扱うApplication Gatewayの領域です。TCPやUDPをそのまま素早く分散したいだけならLoad Balancerで足ります。
- **この案件では**: 基礎編は単一VM構成のため、どちらも使いません。冗長化とHTTPS化は未実装の発展課題として扱います。
- **覚え方**: Load Balancerは封筒の宛名だけを見て仕分ける郵便局員、Application Gatewayは中の手紙を読んでから届け先を決める秘書。読む深さの差がレイヤーの差です。

### 15.2.6 可用性セット と 可用性ゾーン

- **違いを一言で**: 可用性セットは同じデータセンターの中で分散し、可用性ゾーンはデータセンターそのものを分けます。
- **なぜ混同するのか**: 名前がどちらも「可用性」で始まり、説明もどちらも「VMを分散して落ちにくくする」と書かれているためです。
- **見分け方**: 想定する障害の大きさで分けます。電源やスイッチを共有するラック単位の障害、Azure側の計画メンテナンスに備えるのが可用性セット。施設単位の停電や災害に備えるのが可用性ゾーンです。いずれも複数台あって初めて効果が出るため、1台構成では意味を持ちません。
- **この案件では**: 単一VM構成のため、どちらも採用していません。冗長化は未実装の発展課題です。
- **覚え方**: セットは「同じ建物の別ラック」、ゾーンは「別の建物」。守りたい範囲が建物の中か外かで選びます。

### 15.2.7 停止 と 停止(割り当て解除)

- **違いを一言で**: 「停止」はOSを止めただけ、「停止(割り当て解除)」は計算リソースの割り当てまで手放した状態です。
- **なぜ混同するのか**: VMの中で`shutdown`コマンドを実行すると画面上は止まって見えるのに、Azureから見ると計算リソースはVMのために確保されたままだからです。「止めたのに料金が続く」という相談の多くはこれが原因です。
- **見分け方**: 計算リソース分の課金が止まるのは割り当て解除のほうです。ただしディスクは残るためストレージ分の費用は続きます。また、動的に割り当てているパブリックIPは割り当て解除でアドレスが変わることがあります。実際の課金の扱いは契約や構成で変わるため、Cost Managementで実績を確認してください。
- **この案件では**: 学習が終わったら`scripts/remove.ps1`でリソースグループ名を二重指定して削除し、作りっぱなしを防ぎます。
- **覚え方**: 「停止」は部屋で寝ているだけ、「割り当て解除」は部屋を引き払うこと。寝ているだけなら家賃は続きます。

### 15.2.8 スナップショット と バックアップ

- **違いを一言で**: スナップショットは今の姿を1枚コピーすること、バックアップは世代と保持期間を決めて取り続ける仕組みです。
- **なぜ混同するのか**: どちらも「戻せるようにしておく」ための操作で、初心者からは同じ保険に見えるためです。
- **見分け方**: 「誰が、いつ、どこまで自動で取り、いつ捨てるか」が決まっているかどうかが境界です。作業前に手で1枚取るのはスナップショット、方針に沿って自動で回り続けるのがバックアップです。どちらも復元できて初めて価値があるため、復元手順を試していない保険は保険ではありません。
- **この案件では**: バックアップは未実装の発展課題です。定期取得も復元手順も用意していないため、この構成では「壊れたら作り直す」が前提になります。
- **覚え方**: スナップショットは写真1枚、バックアップはアルバムと撮影計画。計画があるほうがバックアップです。

### 15.2.9 認証 と 認可

- **違いを一言で**: 認証は「あなたが誰か」を確かめること、認可は「何をしてよいか」を決めることです。
- **なぜ混同するのか**: 日本語の見た目が1文字違いで、英語でもAuthentication(AuthN)とAuthorization(AuthZ)と似ているためです。実際の画面でも連続して起きるため、境目が意識されません。
- **見分け方**: エラーメッセージで切り分けます。そもそもサインインできない、鍵が合わないのは認証の問題。サインインはできているのに操作が拒否されるのは認可の問題です。認証は1回、認可は操作のたびに効きます。
- **この案件では**: SSHは公開鍵認証のみでパスワード認証を無効にしています。これは「鍵を持つ本人か」を確かめる認証側の対策で、Azure側で誰がリソースを操作してよいかを決めるRBACとは別の話です。
- **覚え方**: 認証は改札を通ること、認可は座席の等級。改札を通れても、グリーン車に座れるとは限りません。AuthNはauthe**N**tication、AuthZはauthori**Z**ationから1文字ずつ採った略記です。Nが付くほうが本人確認、Zが付くほうが権限、と対応させて覚えます。

### 15.2.10 Azure Monitor と Log Analyticsワークスペース

- **違いを一言で**: Azure Monitorは監視の仕組み全体を指す名前、Log Analyticsワークスペースはログを貯めて検索する場所の名前です。
- **なぜ混同するのか**: 監視の話題では常に一緒に登場し、画面上も行き来するため、同じものの別名だと感じてしまうからです。
- **見分け方**: 「メトリックを見る」「アラートを作る」といった監視の機能全般はAzure Monitorの傘の下にあります。そのうちログを保存して検索する受け皿として登場する具体的なリソースがLog Analyticsワークスペースです。ワークスペースは自分で作るリソースとして一覧に現れる、という点も見分けの手がかりになります。
- **この案件では**: CPU使用率のメトリックアラートはAzureプラットフォームメトリックを使います。Log Analyticsワークスペースは受け皿だけを作成し、OSログ収集に必要なAzure Monitor Agent(AMA)とData Collection Rule(DCR)は未実装の発展課題です。
- **覚え方**: Monitorは仕組みの名前、Workspaceは場所の名前。「モニターで見る、ワークスペースに貯める」と動作で区別します。

## 15.3 まぎらわしい略語の読み分け

3文字の略語は、先頭の1文字が同じだと一気に見分けがつかなくなります。「何の仲間か」を先に覚えると取り違えが減ります。

| 略語 | 読み方 | 正式名称 | 何の仲間か | 取り違えやすい相手 |
|---|---|---|---|---|
| NSG | エヌエスジー | Network Security Group | ネットワークの許可表 | ASG、Azure Firewall |
| ASG | エーエスジー | Application Security Group | NSGルールで使うNICのグループ名 | NSG、ASR |
| ASR | エーエスアール | Azure Site Recovery | 災害復旧のためのリージョン間の複製 | ASG、AKS |
| AKS | エーケーエス | Azure Kubernetes Service | コンテナを動かす基盤 | ACR、ASR |
| ACR | エーシーアール | Azure Container Registry | コンテナイメージの保管庫 | AKS |
| ARM | アーム | Azure Resource Manager | Azureの操作をすべて受け付ける土台 | ARMテンプレート、CPUのArm |
| AGW | エージーダブリュー | Application Gateway | レイヤー7のロードバランサー | Load Balancer、Azure Firewall |
| RBAC | アールバック | Role-Based Access Control | 操作権限の割り当て | NSG |
| AMA | エーエムエー | Azure Monitor Agent | VMからログなどを送るエージェント | DCR |
| DCR | ディーシーアール | Data Collection Rule | AMAが何を集めてどこへ送るかの設定 | AMA |
| VMSS | ブイエムエスエス | Virtual Machine Scale Sets | VMを台数で増減させる仕組み | 可用性セット |

読み分けのコツは3つです。まず`ASG`と`ASR`と`AKS`は用途が「NSGの部品」「災害復旧」「コンテナ」とまったく違うので、頭文字ではなく仲間で覚えます。次に`AMA`と`DCR`は必ずセットで登場する相棒で、`AMA`が運び屋、`DCR`が指示書です。最後に`AGW`はApplication Gatewayを指す現場の通称で、公式表記はApplication Gatewayです。文書では正式名称で書くほうが誤解が減ります。
