# 3. クラウドとAzureの基礎概念

[用語集トップ](../11-azure-glossary.md) ・ 次: [4. 契約と管理階層・ガバナンス](04-governance.md)

この用語集の出発点です。クラウドとは何を借りているのか、どこまでが自分の仕事なのかが分かると、この後に出てくるネットワークやセキュリティの用語が一気につながります。本案件で「なぜ`japaneast`に単一VMを建てるのか」「なぜ削除手順まで用意するのか」を説明できるようになる土台でもあります。難しい計算はありません。オンプレミスとの対比だけを軸に読み進めてください。

## 3.2 用語解説

### 3.2.1 クラウドコンピューティング(Cloud Computing)

- **一言でいうと**: サーバーやネットワークを買わずに、他社のデータセンターにある資源をインターネット越しに必要な分だけ借りて使う仕組みです。
- **たとえると**: 車を買わずにカーシェアを使う形です。乗りたいときに借り、降りたら返し、乗った分だけ払います。
- **もう少し詳しく**: 借りるのは物理的な機械そのものではなく、「使う権利と割り当てられた性能」です。申し込みから利用開始までが数分で済み、不要になれば削除して支払いを止められます。この「早く始められて、早くやめられる」点が、機器の購入と設置が前提だった従来との最大の違いです。
- **覚え方**: 昔からネットワーク図では、詳細を描かない相手側を雲の形で表してきました。その雲の中に計算資源を置いたのがクラウドです。
- **つまずきポイント**: 「クラウド=データをネットに置くこと」と思いがちですが、実際は保存だけでなく、計算、ネットワーク、認証まで含む資源の貸し借り全体を指します。
- **関連**: オンプレミス / データセンター / 従量課金

### 3.2.2 オンプレミス(On-Premises、自社所有環境)

- **一言でいうと**: サーバーやネットワーク機器を自分で購入し、自社の建物や借りたラックに設置して運用する、従来型のやり方です。
- **たとえると**: 持ち家です。自由に改造できますが、屋根の修理も固定資産税も自分持ちになります。
- **もう少し詳しく**: 機器の選定、見積もり、発注、納品、設置、配線、OS導入という工程が必要で、増設にも数週間から数か月かかります。一方で、機器の場所と設定を完全に自分で決められるため、法令や社内規定で設置場所が指定される場合に選ばれます。クラウドの用語はほぼすべて「オンプレミスなら何をしていたか」との対比で理解できます。
- **覚え方**: `on premises`は「敷地の上に」という意味です。敷地の上に置くからオンプレミス、と語源で覚えます。
- **つまずきポイント**: 「オンプレミスは古い」と思いがちですが、実際は要件次第で今も合理的な選択であり、クラウドと併用する構成も一般的です。
- **関連**: クラウドコンピューティング / ハイブリッドクラウド / CapExとOpEx

### 3.2.3 データセンター(Data Center)

- **一言でいうと**: 大量のサーバーを安定して動かすために、電源、空調、通信、入退室管理を強化した専用の建物です。
- **たとえると**: サーバー専用の高層マンションです。自家発電機という非常用電源があり、玄関にも各フロアにも入館チェックがあります。
- **もう少し詳しく**: サーバーはラックという棚に収められ、停電に備えた無停電電源装置と発電機、熱を逃がす冷却設備、複数経路の回線が用意されます。クラウド事業者はこうした建物を世界各地に持ち、その中の資源を切り分けて利用者へ貸し出しています。つまりクラウドを使うとは、この建物と設備の管理を丸ごと任せることでもあります。
- **覚え方**: 建物の写真を思い浮かべ、「電源、空調、回線、入退室」の4点セットが揃った箱と覚えます。この4つは自前で用意すると最も手間がかかる部分です。
- **つまずきポイント**: 「クラウドは実体がない」と思いがちですが、実際は必ずどこかの建物の中に物理サーバーがあり、その所在地の選択がリージョンの選択になります。
- **関連**: リージョン / 可用性ゾーン / 仮想化とハイパーバイザー

### 3.2.4 仮想化とハイパーバイザー(Virtualization / Hypervisor)

- **一言でいうと**: 1台の物理サーバーの中に、独立して動く複数の仮想サーバーを作る技術と、それらを取り仕切る管理ソフトのことです。
- **たとえると**: 1棟の建物を壁で仕切って複数の部屋にするのが仮想化、部屋の割り当てと共用設備を管理する管理人がハイパーバイザーです。
- **もう少し詳しく**: ハイパーバイザーは物理的なCPU時間、メモリ、ディスク、ネットワークを各仮想マシンへ配分し、隣の仮想マシンから中身が見えないように分離します。この仕組みがあるため、クラウド事業者は1台の高性能な物理サーバーを多数の利用者へ切り売りでき、利用者は数分で1台のサーバーを手に入れられます。VMを作るという操作は、この配分をお願いする操作です。
- **覚え方**: `hyper`+`visor`で、`supervisor`(監督者)のさらに上に立つ役という語の作りです。OSの上ではなく、OSの下から全体を監督すると覚えます。
- **つまずきポイント**: 「仮想だから性能が出ない」と思いがちですが、実際は物理資源を割り当てて動かしており、サイズを適切に選べば実用上の性能が得られます。
- **関連**: データセンター / IaaS / マルチテナント

### 3.2.5 パブリッククラウド / プライベートクラウド / ハイブリッドクラウド

- **一言でいうと**: 不特定多数と共用で借りるのがパブリック、自社専用に用意するのがプライベート、その両方を組み合わせて使うのがハイブリッドです。
- **たとえると**: 賃貸マンション、自社ビル、そして本社は自社ビルで支店は賃貸という二拠点体制の違いです。
- **もう少し詳しく**: パブリッククラウドはAzureのように事業者の設備を多数の利用者で分け合う形で、初期費用を抑えて即座に使えます。プライベートクラウドは自社または専用の設備でクラウド的な仕組みを構築する形で、統制はしやすい反面、費用と運用負荷が残ります。ハイブリッドは、既存の社内システムを残しつつクラウドを併用する現実的な選択で、両者を専用線やVPNでつなぎます。
- **覚え方**: 公衆浴場が`public`、自宅の風呂が`private`、両方使い分けるのが`hybrid`という3段で覚えます。
- **つまずきポイント**: 「ハイブリッドは中途半端な妥協」と思いがちですが、実際は移行期間中や規制対象データを抱える企業では標準的な構成です。
- **関連**: パブリッククラウド / オンプレミス / マルチテナント

### 3.2.6 マルチテナント(Multi-Tenant、マルチテナント方式)

- **一言でいうと**: 1つの設備やソフトを多数の利用者が共有しつつ、互いのデータや設定は見えないように分離する方式です。
- **たとえると**: 複数の会社が同じオフィスビルに入居している状態です。エレベーターや電気は共用ですが、各社の部屋の鍵は別々で、勝手に入ることはできません。
- **もう少し詳しく**: パブリッククラウドはこの方式で成り立っています。物理サーバーやネットワーク機器は共有しつつ、仮想化とアクセス制御によって利用者ごとの境界を作ります。共有によって単価が下がる一方、分離の設計と運用は事業者の重要な責務になります。対義語は、専用の物理資源を1利用者が占有するシングルテナントです。
- **覚え方**: `tenant`は不動産の「賃借人、入居者」です。入居者が多数だからマルチテナント、と不動産の語で覚えます。
- **つまずきポイント**: 「共用だから他人にデータを見られる」と思いがちですが、実際は仮想化と権限管理で論理的に分離されており、見えるかどうかは自分の権限設定にも左右されます。
- **関連**: 仮想化とハイパーバイザー / パブリッククラウド / 責任共有モデル

### 3.2.7 Microsoft Azure(マイクロソフトアジュール)

- **一言でいうと**: Microsoftが世界各地のデータセンターで提供する、多数のクラウドサービスをまとめた総称です。
- **たとえると**: 巨大なホームセンターです。サーバー、ネットワーク、データベース、監視といった部品が棚に並び、必要なものを選んで組み立てます。
- **もう少し詳しく**: 仮想マシンやネットワークのようなインフラ寄りのサービスから、アプリ実行基盤、データベース、監視、AIまでが同じ契約と管理画面の下に並んでいます。作った物はすべてリソースと呼ばれ、Resource Groupという箱にまとめて管理します。何を選ぶかより、要件に対して最小の部品で組む判断が実務では重視されます。
- **この案件では**: Sample Works社向けに、Resource Group、VNet、Subnet、NSG、Public IP、NIC、Linux VM、Log Analytics Workspace、CPU使用率のメトリックアラートという最小構成を組みます。
- **覚え方**: `azure`は「空色」を意味する英単語です。クラウド=雲、空色=Azureと、空つながりで結びつけます。
- **つまずきポイント**: 「Azureは1つの製品」と思いがちですが、実際は多数のサービスの集合体で、必要なサービスだけを選んで課金される仕組みです。
- **関連**: リージョン / IaaS / マネージドサービス

### 3.2.8 IaaS(Infrastructure as a Service、インフラ提供型)

- **一言でいうと**: サーバー、ネットワーク、ストレージという土台部分だけを借り、OSから上は自分で導入して管理する利用形態です。
- **たとえると**: 建物の躯体と配管だけができた状態で借りる、スケルトン物件です。内装も設備も自分で入れます。
- **もう少し詳しく**: Azure VMが代表例です。CPUやメモリのサイズ、ディスク、ネットワーク構成を細かく決められるため自由度が高く、既存の運用手順をほぼそのまま持ち込めます。その代わり、OSの更新、ミドルウェアの導入、バックアップ設計といった作業は利用者側に残ります。オンプレミスの知識がそのまま活きるため、最初に学ぶ形態として適しています。
- **この案件では**: Ubuntuと`Nginx`を載せたLinux VMを中心とする、IaaS中心の構成です。Nginxの設定やOSの更新は利用者側の作業になります。
- **覚え方**: 頭文字の`I`は`Infrastructure`=土台です。「土台だけ借りて、部屋は自分で作る」と最初の1文字で思い出します。
- **つまずきポイント**: 「VMを作れば運用も任せられる」と思いがちですが、実際はOSより上の管理責任は利用者に残ります。
- **関連**: PaaS / 仮想化とハイパーバイザー / 責任共有モデル

### 3.2.9 PaaS(Platform as a Service、実行基盤提供型)

- **一言でいうと**: OSやミドルウェアまで用意された実行環境を借り、自分のアプリケーションだけを載せて動かす利用形態です。
- **たとえると**: 内装と厨房設備まで整った居抜き店舗です。あとはメニューを持ち込めば開店できます。
- **もう少し詳しく**: 事業者側がOSの更新や基盤の面倒を見るため、運用の負担が大きく下がり、開発に集中できます。反面、使えるOSの設定やインストールできるソフトに制約があり、既存アプリをそのまま載せられない場合があります。IaaSからPaaSへ寄せるほど自由度は下がり、運用の楽さは上がるという交換関係を理解しておくと、設計の判断がぶれません。
- **覚え方**: 頭文字の`P`は`Platform`=床です。床まで張ってあるから、その上に自分の荷物を置くだけと覚えます。
- **つまずきポイント**: 「PaaSのほうが常に良い」と思いがちですが、実際は既存アプリの改修コストや細かい設定要件によってはIaaSが妥当な場合があります。
- **関連**: IaaS / SaaS / マネージドサービス

### 3.2.10 SaaS(Software as a Service、ソフト提供型)

- **一言でいうと**: 完成したソフトウェアをそのまま利用し、利用者は自分のデータと設定だけを管理する形態です。
- **たとえると**: 外食です。厨房も食材も気にせず、席に座って注文するだけで食事ができます。
- **もう少し詳しく**: ブラウザやアプリからログインして使うメールやオフィスソフト、業務システムがこれにあたります。サーバーの構築も更新も不要で、利用開始が最も早い一方、機能追加や仕様変更は提供者の裁量で行われます。利用者に残る仕事は、アカウント管理、権限設計、データの取り扱いといった運用ルールの部分です。
- **覚え方**: `IaaS`、`PaaS`、`SaaS`を「イー、パー、サー」の順に並べ、順に自由度が下がり、順に楽になると覚えます。
- **つまずきポイント**: 「SaaSなら自分の責任はない」と思いがちですが、実際はアカウントとデータの管理責任は常に利用者側に残ります。
- **関連**: PaaS / 責任共有モデル / マネージドサービス

### 3.2.11 マネージドサービス(Managed Service、管理提供型サービス)

- **一言でいうと**: 基盤の構築や保守をクラウド事業者が代わりに行い、利用者は設定と使用に集中できるサービスのことです。
- **たとえると**: 管理人常駐のマンションです。共用部の点検も設備の更新も管理人が行い、住人は自分の部屋の使い方だけを決めます。
- **もう少し詳しく**: データベース、監視、認証などに多く、サーバーの用意、更新適用、冗長化といった裏方作業が価格に含まれています。自分でVMに同じ機能を構築する方法と比べると、細かい調整の自由は減りますが、運用の手間と設定ミスの機会が減ります。どちらを選ぶかは、要件、必要な調整の細かさ、運用に割ける人手で決めます。
- **この案件では**: Log Analytics Workspaceは受け皿として作成しますが、OSログ収集に必要なAzure Monitor Agent(AMA)とData Collection Rule(DCR)は未実装の発展課題です。
- **覚え方**: `managed`は「管理された」という受け身の形です。誰が管理されているのかを考えると、「自分ではなく事業者が面倒を見る側」だと思い出せます。
- **つまずきポイント**: 「マネージドなら設定も不要」と思いがちですが、実際はアクセス権や保存期間などの設定は利用者が決めます。
- **関連**: PaaS / 責任共有モデル / SLA

### 3.2.12 責任共有モデル(Shared Responsibility Model)

- **一言でいうと**: クラウドの安全と稼働について、どこまでを事業者が受け持ち、どこからを利用者が受け持つかを定めた分担の考え方です。
- **たとえると**: 賃貸住宅です。建物の構造と共用設備の管理は大家、部屋の施錠と持ち物の管理は入居者という分担に似ています。
- **もう少し詳しく**: 建物、電源、物理サーバー、仮想化基盤は常に事業者側です。反対に、データ、アカウント、権限設定は、IaaSでもPaaSでもSaaSでも常に利用者側に残ります。その間にあるOSやミドルウェアの担当が、利用形態によって移動します。事故の多くは、この境界を勘違いして「誰かがやってくれているはず」と放置した場所で起きます。
- **この案件では**: SSHの公開鍵の管理、`adminCidr`で許可する接続元の決定、`openHttp=false`という既定の維持、Nginxの設定はすべて利用者側の責任範囲です。
- **覚え方**: 「建物は大家、鍵は自分」と唱えます。合鍵を誰に渡したかは大家の責任ではない、という感覚がそのままアカウント管理の責任にあたります。
- **つまずきポイント**: 「Azure上のVMはMicrosoftが守ってくれる」と思いがちですが、実際はOSの更新もNSGの設定も利用者の担当です。
- **関連**: IaaS / SaaS / マルチテナント

### 3.2.13 従量課金(Pay-As-You-Go)

- **一言でいうと**: 使った量と使った時間に応じて後から支払う課金方式で、資源を減らしたり削除したりすれば費用も下がる考え方です。
- **たとえると**: 電気や水道のメーターです。使った分だけ請求されますが、蛇口を閉めても、引いたままの配管にかかる基本料は残ります。
- **もう少し詳しく**: VMは稼働時間、ストレージは容量と読み書き、通信は送出量というように、サービスごとに数える単位が異なります。注意すべきは、VMを停止しても割り当てを解放しなければ費用が続く種類の資源や、削除するまで残り続けるディスクとPublic IPです。学習用途では「作ったら消す」を手順に組み込むことが、そのままコスト管理になります。
- **この案件では**: 学習後は`scripts/remove.ps1`でリソースグループ名を二重指定して削除します。料金はリージョン、契約、時期で変わるため、Azure Pricing CalculatorとCost Managementで実施直前に確認します。
- **覚え方**: 蛇口の絵を思い浮かべ、「閉め忘れ=課金継続」と結びつけます。停止ではなく削除で閉栓、と一段強く覚えます。
- **つまずきポイント**: 「VMを停止すれば費用はゼロ」と思いがちですが、実際はディスクやPublic IPなど、残っている資源に対する費用は続きます。
- **関連**: CapExとOpEx / 弾力性 / リージョン

### 3.2.14 CapExとOpEx(Capital Expenditure / Operating Expenditure、資本的支出と運用的支出)

- **一言でいうと**: 機器を買って資産として持つ支出がCapEx、使った分を毎月払い続ける支出がOpExです。
- **たとえると**: 車を一括購入するのがCapEx、カーシェアの利用料を毎月払うのがOpExです。
- **もう少し詳しく**: オンプレミスは購入時に大きな初期投資が必要で、数年かけて費用計上します。クラウドは初期投資を抑えられる代わりに、使い続ける限り毎月の費用が発生します。どちらが得かは利用期間と稼働率で変わり、常時フル稼働なら購入が有利になる場合もあります。クラウドの提案では「安くなる」ではなく「支出の形と増減のしやすさが変わる」と説明できると説得力が出ます。
- **覚え方**: `Cap`は`Capital`で資本、つまり買い物です。`Op`は`Operating`で運用、つまり毎月の支払いです。頭3文字で用途を分けます。
- **つまずきポイント**: 「クラウドは必ず安い」と思いがちですが、実際は使い方次第で高くなることもあり、比較は前提条件をそろえて行います。
- **関連**: 従量課金 / オンプレミス / 弾力性

### 3.2.15 リージョン(Region)

- **一言でいうと**: Azureのデータセンターが集まっている地理的な地域のことで、リソースを作るときにどこへ置くかを選びます。
- **たとえると**: 住所でいう都道府県です。同じ会社の荷物でも、東京の倉庫に置くか大阪の倉庫に置くかで、届く速さも災害時の影響も変わります。
- **もう少し詳しく**: 選ぶリージョンによって、利用者からの通信の速さ、提供されているサービスの種類、料金、データの保存場所が変わります。日本国内向けのシステムでは国内リージョンを選ぶのが基本で、法令や社内規定でデータの保存国が定められている場合は特に重要です。あとから別リージョンへ移すには作り直しが必要になるため、最初に決める項目です。
- **この案件では**: 既定のリージョンは`japaneast`(東日本)です。リソースグループ名`rg-portfolio-dev-jpe-001`の`jpe`もこのリージョンを表しています。
- **覚え方**: 名前の`east`や`west`は方角そのものです。`japaneast`=日本の東=東日本、と地図で覚えると命名規則も一緒に頭に入ります。
- **つまずきポイント**: 「近いリージョンなら何でも同じ」と思いがちですが、実際は提供サービスや対応機能がリージョンで異なる場合があります。
- **関連**: 可用性ゾーン / リージョンペア / データセンター

### 3.2.16 可用性ゾーン(Availability Zone、AZ)

- **一言でいうと**: 同じリージョンの中で、電源、冷却、ネットワークが物理的に分けられた区画のことです。
- **たとえると**: 同じ町内にある別棟の倉庫です。片方が停電しても、もう片方は電源系統が別なので動き続けます。
- **もう少し詳しく**: 対応しているリージョンでは複数のゾーンが用意され、同じシステムの構成要素を別々のゾーンへ分散させることで、1つの建物レベルの障害に耐えられるようになります。分散させるには複数台の構成と、前段で振り分ける仕組みが必要になり、その分の費用と設計の手間が増えます。可用性の要件がどれだけ厳しいかを確認してから採用を判断します。
- **この案件では**: 学習費用を抑えるため単一VM構成であり、可用性ゾーンによる冗長化は未実装の発展課題です。高可用性が必要になったら、可用性ゾーン、Load Balancer、複数VMへの変更を検討します。
- **覚え方**: リージョンが都道府県なら、ゾーンはその中の別々の建物です。「地域の中の別棟」と2段の入れ子で覚えます。
- **つまずきポイント**: 「ゾーンを分ければ自動で冗長になる」と思いがちですが、実際は複数台を配置して初めて効果が出ます。1台をゾーンに置いても、そのゾーンが止まれば停止します。
- **関連**: リージョン / スケールアウト / 可用性と停止時間の考え方

### 3.2.17 リージョンペア(Region Pair、ペアリージョン)

- **一言でいうと**: あらかじめ組み合わされた2つのリージョンで、大規模な災害への備えとして使われる関係のことです。
- **たとえると**: 本社と、離れた場所に置いた予備拠点です。片方が使えなくなっても、もう片方で業務を続けられるようにしておきます。
- **もう少し詳しく**: ペアは同じ地域内の離れた2つのリージョンで構成され、`japaneast`(東日本)と`japanwest`(西日本)が日本のペアにあたります。地理的に離れているため、地震や広域停電が同時に両方へ影響する可能性を下げられます。計画的な更新作業もペアの片側ずつ順に行われる運用がとられています。バックアップの保存先を選ぶ際などに、この関係を意識します。
- **覚え方**: ペアは二人一組です。「東日本の相棒は西日本」と、日本の組み合わせだけを最初に覚えます。
- **つまずきポイント**: 「ペアがあるから自動で切り替わる」と思いがちですが、実際に別リージョンへ切り替えるには、それを前提としたバックアップや構成の設計が必要です。
- **関連**: リージョン / 可用性ゾーン / リフト&シフト

### 3.2.18 SLA(Service Level Agreement、サービスレベルアグリーメント)

- **一言でいうと**: 提供するサービスの品質水準について、事業者が示す取り決めのことです。
- **たとえると**: 宅配便の「翌日までにお届けします」という約束です。守られなかったときの扱いも、あらかじめ定められています。
- **もう少し詳しく**: 稼働率などの指標と、その未達時の対応が定められます。数値はサービスごとに異なり、同じサービスでも構成によって変わるため、単一構成と冗長構成では扱いが違います。実務では「SLAが高いから安心」ではなく、自分の構成がその条件を満たしているかを確認することが重要です。具体的な数値は変更されるため、必ず公式のSLAページで最新を確認します。
- **この案件では**: 単一VM構成であり、冗長化は未実装の発展課題です。可用性の説明では、構成上の限界を隠さず伝えることが求められます。
- **覚え方**: 頭文字を`Service`(サービスの)、`Level`(水準についての)、`Agreement`(取り決め)と3語に開くと、意味がそのまま出てきます。
- **つまずきポイント**: 「SLAは絶対に止まらない保証」と思いがちですが、実際は品質水準の取り決めであり、停止が起きないという保証ではありません。
- **関連**: 可用性と停止時間の考え方 / マネージドサービス / 可用性ゾーン

### 3.2.19 可用性と停止時間の考え方(Availability / Downtime)

- **一言でいうと**: システムが使える状態でいられる割合を可用性と呼び、その裏返しとして許される停止時間を計算する考え方です。
- **たとえると**: 鉄道の運行です。年に何分止まってよいかを先に決めるからこそ、点検の頻度や予備車両の数が決まります。
- **もう少し詳しく**: 1年は約8,760時間なので、可用性が99%なら年間で約87.6時間、99.9%なら約8.76時間の停止に相当します。桁が1つ増えるたびに、許容される停止時間はおよそ10分の1になります。ここで挙げた数値はSLAではなく、割合から逆算した計算例です。重要なのは、必要な可用性を先に決め、その水準に見合った構成と費用を選ぶ順序です。
- **覚え方**: 「9が1つ増えるたびに停止時間は1桁減る」と数字の並びで覚えます。9の個数と桁数が連動する、と結びつけると忘れません。
- **つまずきポイント**: 「可用性は高いほど良い」と思いがちですが、実際は上げるほど構成が複雑になり費用も増えるため、要件との釣り合いで決めます。
- **関連**: SLA / 可用性ゾーン / スケールアウト

### 3.2.20 スケールアップ(Scale Up、垂直スケール)

- **一言でいうと**: 1台のサーバーのCPUやメモリを増やして、処理できる量を増やす方法です。
- **たとえると**: レジ係を1人のまま、より手際の良い人に交代してもらうやり方です。
- **もう少し詳しく**: Azure VMではサイズを変更することで実現でき、アプリケーションの作りを変えずに性能を上げられるのが利点です。一方で、サイズ変更には再起動を伴うことが多く、その間は停止します。また、1台で出せる性能には上限があり、台数が1台のままなので障害時に代わりがいないという弱点は解消されません。
- **この案件では**: 単一VM構成のため、性能不足の一次対応はスケールアップが基本になります。台数を増やす冗長化は未実装の発展課題です。
- **覚え方**: `up`は上向きです。同じ場所で背を伸ばすイメージで、1台を強くすると覚えます。
- **つまずきポイント**: 「スケールアップすれば可用性も上がる」と思いがちですが、実際は台数が1台のままなので、止まるときは止まります。
- **関連**: スケールアウト / 弾力性 / 可用性と停止時間の考え方

### 3.2.21 スケールアウト(Scale Out、水平スケール)

- **一言でいうと**: 同じ役割のサーバーを複数台に増やして、処理を分担させることで全体の処理量を増やす方法です。
- **たとえると**: 駅の改札機を増やす対応です。1台の処理速度を上げるより、通路そのものを増やすほうが混雑に効きます。
- **もう少し詳しく**: 前段に振り分ける仕組みを置き、複数台へ処理を分散させます。台数を後から増減しやすく、1台が故障しても残りで処理を続けられるため、可用性の向上にもつながります。ただし、セッション情報やファイルを1台の中に持つ作りだと分散できないため、アプリケーション側が複数台前提で作られている必要があります。
- **覚え方**: `out`は外向きです。横に並べて広げるイメージで、台数を増やすと覚えます。`up`は上、`out`は横、と方向で対比します。
- **つまずきポイント**: 「台数を増やせば必ず速くなる」と思いがちですが、実際は共有するデータベースなどが先に限界になる場合があります。
- **関連**: スケールアップ / 弾力性 / 可用性ゾーン

### 3.2.22 弾力性(Elasticity、エラスティック)

- **一言でいうと**: 負荷の増減に合わせて、資源の量を必要なときに増やし、不要になったら減らせる性質のことです。
- **たとえると**: ゴムです。引っ張れば伸び、力を抜けば元に戻ります。伸びたままにならないのが要点です。
- **もう少し詳しく**: クラウドの費用面の利点は、この「減らせる」側にあります。繁忙期だけ台数を増やし、終われば戻すことで、ピークに合わせて機器を買い揃える必要がなくなります。実現には、増減しても壊れない構成と、増減の条件を決めた設定が必要です。増やす設計だけを行い、減らす条件を決めないと費用が下がらないという失敗が起こります。
- **覚え方**: 輪ゴムを伸ばして戻す動きを思い浮かべます。増やすだけなら`scale`、戻せて初めて`elastic`と覚えます。
- **つまずきポイント**: 「クラウドなら自動で増減する」と思いがちですが、実際は自動化の設定を行わない限り、台数もサイズも手動のままです。
- **関連**: スケールアウト / 従量課金 / クラウドネイティブ

### 3.2.23 リフト&シフト(Lift and Shift)

- **一言でいうと**: 今動いているシステムの構成をほとんど変えずに、そのままクラウド上のサーバーへ移す移行のやり方です。
- **たとえると**: 引っ越しで、家具の配置をそのまま新居へ再現する方法です。片付けは後回しでも、まず生活は始められます。
- **もう少し詳しく**: 既存のサーバーをクラウドのVMへ置き換えるため、アプリケーションの改修が最小限で済み、移行の期間とリスクを抑えられます。IaaS中心の構成になりやすく、OSの運用負荷はそのまま残ります。まず移し、その後で段階的にマネージドサービスへ置き換えていくという二段構えが、現実の案件では広く採られています。
- **覚え方**: `lift`(持ち上げて)、`shift`(移す)という2つの動作をそのまま順に思い浮かべます。中身を作り替えないから2動作で終わる、と覚えます。
- **つまずきポイント**: 「クラウドへ移せば自動的に安く、強くなる」と思いがちですが、実際は構成が同じなら課題も一緒に移ります。
- **関連**: オンプレミス / IaaS / クラウドネイティブ

### 3.2.24 クラウドネイティブ(Cloud Native)

- **一言でいうと**: 最初からクラウドで動かす前提で設計され、増減や再作成に強い作り方や仕組みのことです。
- **たとえると**: 引っ越し前提で選んだ、分解して運べる組み立て家具です。移動や入れ替えを想定して作られています。
- **もう少し詳しく**: サーバー1台を大事に守り続けるのではなく、壊れたら作り直す、必要なら増やすという前提に立ちます。マネージドサービスの活用、構成をコードで管理する運用、自動化された配布などが典型的な要素です。移行の入口としてはリフト&シフトが現実的で、その後にクラウドネイティブへ寄せていくのが一般的な進み方です。
- **この案件では**: 構成をBicep(`infra/main.bicep`)で宣言し、同じ環境を再現できる形にしている点が、この考え方に沿った部分です。
- **覚え方**: `native`は「生まれつきの」です。クラウド生まれか、あとから引っ越してきたか、という出自の違いで覚えます。
- **つまずきポイント**: 「クラウドで動いていればクラウドネイティブ」と思いがちですが、実際は動く場所ではなく、作り方と運用の考え方を指します。
- **関連**: リフト&シフト / マネージドサービス / 弾力性

## 3.3 このセクションの覚え方まとめ

この章の骨格は「どこまで自分でやるか」の1本の軸です。下の表を書けるようになれば、IaaS、PaaS、SaaSと責任共有モデルを同時に説明できます。

| 層 | IaaS | PaaS | SaaS | 覚え方 |
|---|---|---|---|---|
| データ、アカウント、権限 | 自分 | 自分 | 自分 | 常に自分 |
| アプリケーション | 自分 | 自分 | Azure | 使う形ほどAzure側 |
| OS、ミドルウェア | 自分 | Azure | Azure | ここが動く境界 |
| 仮想化、物理サーバー、建物 | Azure | Azure | Azure | 常にAzure |

覚える順番は「借りる(クラウド、オンプレミス、仮想化)→ 形を選ぶ(IaaS、PaaS、SaaS、責任共有)→ 払う(従量課金、CapExとOpEx)→ 置く(リージョン、ゾーン、ペア)→ 守る(SLA、可用性)→ 増やす(アップ、アウト、弾力性)→ 移る(リフト&シフト、クラウドネイティブ)」の7段です。
方向の対比も1組で覚えます。`up`は上へ伸ばして1台を強く、`out`は横へ広げて台数を増やす。可用性を上げたいなら`out`側です。
最後に一言だけ持ち帰るなら、「建物は大家、鍵は自分」。この感覚が、この後のNSGやSSH鍵の章でそのまま効いてきます。
