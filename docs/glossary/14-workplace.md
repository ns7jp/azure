# 14. 現場でよく使う仕事の言葉

[用語集トップ](../11-azure-glossary.md) ・ 前: [13. IaCと開発ツール](13-iac.md) ・ 次: [15. 混同しやすい用語の対比](15-confusions.md)

ここに出てくる言葉はAzureの機能名ではありません。SIerや社内情シスの打ち合わせで毎日飛び交う、仕事の進め方そのものの言葉です。未経験者が初出社や面接で固まるのは、技術用語よりもこちら側であることが多いです。この節では24語すべてを、本リポジトリの「どのファイルが実物か」と対応づけます。言葉と成果物が結びつけば、面接で「何をしたか」を工程の名前で語れます。

## 14.2 用語解説

### 14.2.1 キックオフとレビュー(kick-off、review)

- **一言でいうと**: 案件の開始を関係者で合わせる最初の会議と、成果物を担当者以外の目で点検する場です。
- **たとえると**: 旅行の出発前の集合と、道中の乗り換え確認。行き先の合意が最初、経路の確認が途中です。
- **もう少し詳しく**: キックオフでは目的、範囲、体制、期限、連絡経路を共有します。レビューは設計書、手順書、コードを担当者以外が読み、抜けと危険を洗い出す工程です。未経験者が最初に任されるのは議事録とレビュー指摘の記録であることが多く、ここが評価の入口になります。
- **この案件では**: 顧客ヒアリングは`docs/01-project-brief.md`が担い、レビューはGitHubのPull Requestと、`az bicep build`やMarkdownリンク・空白チェックを行うGitHub ActionsのCIが担います。
- **覚え方**: キックオフ=球を蹴り出す動作、レビュー=re(再び)+view(見る)。始めに蹴り、途中で見直すと動作で覚えます。
- **つまずきポイント**: レビューは間違い探しの糾弾と思いがちですが、目的は成果物の品質を上げることです。指摘は人ではなく文書に向きます。
- **関連**: 要件定義 / 手戻り / 変更管理とリリース

### 14.2.2 要件定義(requirements definition)

- **一言でいうと**: 顧客の曖昧な要望を、合否を測れる「作るもの」の記述へ翻訳して文書にする工程です。
- **たとえると**: 「涼しい部屋にして」を「室温26度、静音、6畳用」に置き換える作業。数値になって初めて機種が選べます。
- **もう少し詳しく**: 要望のままでは合否を判定できません。要件定義では、何を作るか、どこからが範囲外か、前提と制約、完了条件を決めます。ここが曖昧だと設計と試験がすべて揺れます。直す費用は上流ほど安いため、最も丁寧に行う工程です。
- **この案件では**: `docs/01-project-brief.md`が要件定義書で、「Webページを置きたい」を「Ubuntu VMにNginxを導入」へ変換し、要件IDと確認方法を1行ずつ対応させています。
- **覚え方**: 要件=要(かなめ)+件(ことがら)。「かなめの事柄を決め、IDを振る」まで含めて1セットと語源から覚えます。
- **つまずきポイント**: 顧客の言葉をそのまま書けば要件定義と思いがちですが、確認方法が書けない文はまだ要件になっていません。
- **関連**: 機能要件と非機能要件 / 基本設計と詳細設計 / トレーサビリティ

### 14.2.3 機能要件と非機能要件(functional requirements / non-functional requirements)

- **一言でいうと**: 「何ができるか」が機能要件、「どのくらいの品質で動くか」が非機能要件です。
- **たとえると**: 宅配便で「荷物が届く」が機能要件、「翌日に届く、壊れない、追跡できる」が非機能要件です。
- **もう少し詳しく**: 機能要件はあるかないかで判定でき、非機能要件は性能、可用性、セキュリティ、運用性、コストなど程度で判定します。インフラエンジニアの仕事の大半は非機能要件側で、VMサイズ、冗長化、監視、バックアップの判断はすべてここから決まります。
- **この案件では**: `docs/01-project-brief.md`が`FR`(機能要件)と`NFR`(非機能要件)でIDを分けています。`FR-01`はNginx導入、`NFR-01`は費用抑制、`NFR-04`は共通タグ付与です。
- **覚え方**: 頭文字で分けます。FRのFはFunction(機能)、NFRのNはNon(非)。Nが付くほど構成が重く、費用も上がると紐づけます。
- **つまずきポイント**: 非機能要件はおまけと思いがちですが、費用と構成を決めるのはこちら側です。可用性の一行がVM1台と複数台を分けます。
- **関連**: 要件定義 / SLA / SLO / SLI / 基本設計と詳細設計

### 14.2.4 基本設計と詳細設計(basic design / detailed design)

- **一言でいうと**: 基本設計は「どんな構成にするかとその理由」、詳細設計は「実装にそのまま使える値」を決める工程です。
- **たとえると**: 家づくりの間取り図と、コンセント位置や品番まで書いた施工図。前者で暮らし方を決め、後者で工事ができます。
- **もう少し詳しく**: 基本設計では方針、構成図、選定理由、トレードオフを書いて顧客と合意します。詳細設計ではIPアドレス、名前、サイズ、ポート番号を確定させます。基本設計に「なぜ」、詳細設計に「いくつ」が入ると分けると迷いません。
- **この案件では**: `docs/03-basic-design.md`が設計方針と非機能設計、`docs/04-detailed-design.md`がVNet `10.20.0.0/16`、サーバー用サブネット`10.20.1.0/24`などの確定値を持ちます。
- **覚え方**: 対比で覚えます。基本設計=なぜ(Why)、詳細設計=いくつ(How many)。「なぜ」から「いくつ」へ降りていく順番です。
- **つまずきポイント**: 詳細設計だけあれば構築できると思いがちですが、理由が残っていないと後で変更の可否を判断できません。
- **関連**: 要件定義 / パラメーターシート / ADR

### 14.2.5 パラメーターシート(設計台帳、parameter sheet)

- **一言でいうと**: 構築時に入力する設定値を、項目名と値と理由の形で一覧にした台帳です。
- **たとえると**: 引っ越し先の住所や契約番号を1枚に書いた控え。作業者が変わっても同じ値を入れられます。
- **もう少し詳しく**: 理由の列があるおかげで、レビューで「なぜこの値か」に答えられ、変更時に影響範囲を追えます。設定値の正解は必ず1か所に置くのが原則で、台帳と実物が食い違った状態が事故の温床になります。
- **この案件では**: `docs/04-detailed-design.md`が詳細設計書(パラメーターシート)です。`location`は`japaneast`、リソースグループは`rg-portfolio-dev-jpe-001`、VM認証はSSH公開鍵のみといった値と理由が並び、実際の入力値は`infra/parameters/dev.example.bicepparam`が受け持ちます。
- **覚え方**: シート=1枚。「設定値は1枚に集める」という動作で覚えます。台帳が2枚あると、必ずどちらかが古くなります。
- **つまずきポイント**: 作ったら終わりと思いがちですが、構築中に変えた値をシートへ戻さないと、次の担当者が古い値で作業します。
- **関連**: 基本設計と詳細設計 / 構築手順書 / 棚卸し

### 14.2.6 ADR(Architecture Decision Record、設計判断記録)

- **一言でいうと**: なぜその案を選び、他の案を選ばなかったのかを1件1枚で残す記録です。
- **たとえると**: 家電を買うときの比較メモ。候補、決め手、諦めた点を残しておけば、買い替えのときに同じ調査をしなくて済みます。
- **もう少し詳しく**: 課題、制約、選択肢、判断、理由、影響、見直し条件を書きます。設計書は最終形しか語らないため、判断の経緯は別に残します。半年後に「この設定を変えてよいか」を判断できるのは、この記録があるときだけです。
- **この案件では**: `docs/09-gap-analysis-and-roadmap.md`にDecision Recordのテンプレートがあり、状態はProposed / Accepted / Rejected / Supersededから選びます。改善を1つ加えるときは採用理由をここへ残す運用です。
- **覚え方**: 頭文字を3語そのまま読みます。A=Architecture(構成)、D=Decision(判断)、R=Record(記録)。「構成の判断を記録する」です。
- **つまずきポイント**: 採用案だけ書けばよいと思いがちですが、価値があるのは却下した案とその理由です。
- **関連**: 基本設計と詳細設計 / 変更管理とリリース / 手戻り

### 14.2.7 構築手順書(build guide、作業手順書)

- **一言でいうと**: 誰が読んでも同じ結果になるように、作業をコマンド単位で順番に書いた文書です。
- **たとえると**: 料理のレシピ。分量と順番が書いてあれば、作る人が違っても同じ味になります。
- **もう少し詳しく**: 前提条件、作業手順、確認方法、失敗時の戻し方を含めます。手順の途中に「ここで何を確認するか」を書いてあるものが良い手順書で、確認のない手順書は事故をそのまま通過させます。作業当日に考える量をゼロに近づけるのが目的です。
- **この案件では**: `docs/05-build-guide.md`がフェーズA(事前確認)から順に進み、`scripts/deploy.ps1`を`-Apply`なしで実行して差分を確認してから構築へ移る順序になっています。
- **覚え方**: 語呂で「手・順・確」。手を動かす前に順番を決め、1手ごとに確認を挟む、と3文字で唱えます。
- **つまずきポイント**: 分かる人向けに短く書けばよいと思いがちですが、読者は初見の人と夜間の自分です。省略した1行がそのまま障害になります。
- **関連**: パラメーターシート / ドライラン / ロールバック

### 14.2.8 ドライラン(dry run、空打ち)

- **一言でいうと**: 実際に変更を加える前に、何が起きるかだけを確かめる練習実行です。
- **たとえると**: 引っ越し当日の前に、家具を運ぶ経路を手ぶらで歩いて確認すること。ぶつかる場所が先に分かります。
- **もう少し詳しく**: 削除や上書きは戻せないことが多いため、実行前に対象と件数を予測して照合します。結果を「予想」と「実測」に分けて記録すると、理解できていない箇所がその場で見えます。予想と一致しないまま本番実行しないのが原則です。
- **この案件では**: `scripts/deploy.ps1`は既定でWhat-If(変更予測)だけを表示し、実際に作成するには`-Apply`の明示が必要です。証跡テンプレートには、What-If実行前に予想を書いてから実測を転記する表があります。
- **覚え方**: dry(乾いた)+run(実行)。「水を通さずに配管だけ通す」。濡れない実行=何も変わらない実行と語源で結びます。
- **つまずきポイント**: 件数が少なければ安全と思いがちですが、見るべきは削除(`Delete`)の有無と、リソース名やリージョンが設計書と一致しているかです。
- **関連**: 構築手順書 / 変更管理とリリース / 手戻り

### 14.2.9 試験仕様書(test specification、テスト仕様書)

- **一言でいうと**: 何をどう試し、どうなれば合格かを、実施する前に決めておく文書です。
- **たとえると**: 健康診断の検査項目表。測る項目と基準値が先にあるから、結果を見て正常か異常かを判断できます。
- **もう少し詳しく**: 試験ID、分類、手順、期待結果を1行ずつ書き、実施時に実測、合否、証跡を追記します。期待結果を実施後に書くと、出た結果に合わせて基準が動いてしまうため、必ず先に確定させます。合否の言葉をそろえることも同じくらい重要です。
- **この案件では**: `docs/06-test-plan.md`が試験仕様書で、各試験に「日時、実施者、対象、期待値、実測、合否、証跡、備考」を残します。合否は`PASS` / `FAIL` / `BLOCKED` / `NOT RUN`の4語で、未実施を成功扱いしません。
- **覚え方**: 数字で「合否は4語だけ」。`PASS`、`FAIL`、`BLOCKED`、`NOT RUN`。4本の引き出しにすべての結果を入れる、と覚えます。
- **つまずきポイント**: 動いたかどうかを試すものと思いがちですが、試験は「設計どおりか」を確かめる作業です。設計に紐づかない期待値は判定の基準になりません。
- **関連**: 正常系と異常系 / エビデンス / トレーサビリティ

### 14.2.10 正常系と異常系(normal case / abnormal case)

- **一言でいうと**: 想定どおりに使ったときの試験が正常系、わざと間違えた条件で試す試験が異常系です。
- **たとえると**: 鍵と合鍵の確認。自分の鍵で開くかを見るのが正常系、他人の鍵では開かないことを見るのが異常系です。
- **もう少し詳しく**: 正常系だけでは「動くこと」しか示せません。セキュリティ要件は、拒否されるべき通信が実際に拒否されたという異常系でしか証明できません。異常系は自分を締め出す危険があるため、別経路か現在のセッションを確保して行います。
- **この案件では**: `NT-01`が許可CIDRからのSSH成功(正常系)、`NT-02`が非許可CIDRからのSSH失敗(異常系)です。`openHttp=false`のときに外部からのHTTPが失敗することを確かめる`NT-03`も、異常系側の証明に当たります。
- **覚え方**: 対比で1行ずつ。正常系=開くはずのものが開く。異常系=開かないはずのものが開かない。後者を忘れると要件の半分が未証明です。
- **つまずきポイント**: 異常系は失敗を記録する試験と思いがちですが、失敗することが期待値であり、そのとおりなら結果は`PASS`です。
- **関連**: 試験仕様書 / 単体試験・結合試験・総合試験 / エビデンス

### 14.2.11 単体試験・結合試験・総合試験(unit test / integration test / system test)

- **一言でいうと**: 部品ごと、つなぎ目、通し全体という3段階で試験の粒度を分ける考え方です。
- **たとえると**: 鉄道の点検。1駅ずつの設備確認が単体、駅と駅の接続確認が結合、始発から終点まで乗り通すのが総合です。
- **もう少し詳しく**: 小さい単位から順に確かめると、失敗したときの原因範囲が狭まります。全体から始めると、どこが悪いのか分かりません。インフラでは、リソース単体の設定確認から、経路をまたぐ通信確認、利用者の使い方をなぞる確認へと広げます。呼び方は現場ごとに違い、UT / IT / STと略すこともあります。
- **この案件では**: `docs/06-test-plan.md`はこの3語ではなく、静的、構成、ネットワーク、OS、監視、再現性、削除という分類を使っています。粒度の考え方は同じで、`ST-01`のBicepビルドが最も小さく、管理者PCからSSHで接続する`NT-01`が通しの確認に当たります。
- **覚え方**: 動作イメージで「点→線→面」。点が部品単体、線がつなぎ目、面が業務全体です。矢印の向きを逆にしないのが要点です。
- **つまずきポイント**: 総合試験が通れば単体は省けると思いがちですが、原因を切り分ける材料が残らないため、障害調査で時間を失います。
- **関連**: 試験仕様書 / 切り分け / 正常系と異常系

### 14.2.12 エビデンス(evidence、証跡)

- **一言でいうと**: 実施した事実を、第三者が後から追跡できる形で残した記録です。
- **たとえると**: 宅配便の受領印と追跡番号。届いたと言うだけでなく、いつ誰がどう受け取ったかが残ります。
- **もう少し詳しく**: コマンド、日時、終了コード、期待値と実測、合否をそろえて残します。見栄えのよい画面写真だけでは証跡になりません。秘密情報を残さないことも同じ重さで、鍵、トークン、未マスクのIDは記録しません。失敗と対処まで残すと、対応力の証明になります。
- **この案件では**: `evidence/README.md`が保存してよい情報と残してはいけない情報を定義し、`evidence/deployment-record.example.md`をコピーして使います。画像は`evidence/images/`へ、`ST-01-bicep-build-pass.png`のように意味の分かる名前で置きます。
- **覚え方**: 語源分解でe(外へ)+vid(見る)=「外から見える」。自分だけ分かるメモは、定義からして証跡になりません。
- **つまずきポイント**: 成功だけ残せばよいと思いがちですが、失敗と再試験の記録のほうが評価されます。未実施は`NOT RUN`と書き、静的検証で代用したと書きません。
- **関連**: 試験仕様書 / トレーサビリティ / インシデントと障害対応

### 14.2.13 トレーサビリティ(traceability、追跡性)

- **一言でいうと**: 要件から設計、実装、試験、証跡までを線でつなぎ、双方向にたどれる状態にしておく性質です。
- **たとえると**: 食品のロット番号。棚の商品から製造した工場まで、逆向きにたどれる状態です。
- **もう少し詳しく**: 要件IDを設計、コード、試験IDへ引き継ぐと、「この要件はどこで満たしたか」と「この設定は何のためか」の両方に答えられます。表にして、試験のない要件と要件のない実装を見つけるのが実務の使い方です。「作ったもの」ではなく「要件を満たしたもの」として語れるようになります。
- **この案件では**: `docs/09-gap-analysis-and-roadmap.md`の要件トレーサビリティ表が、`FR-01`から`NFR-04`までを設計、実装、試験ID、試験結果、状態の列でつないでいます。試験が`PASS`でも証跡がなければ未完了と判定します。
- **覚え方**: trace(たどる)+ability(できること)=「たどれること」。要件IDという1本の糸を、最後まで切らずに通す作業だと考えます。
- **つまずきポイント**: 資料がそろっていれば追跡できると思いがちですが、IDが引き継がれていない資料は束であって鎖ではありません。
- **関連**: 要件定義 / 試験仕様書 / エビデンス

### 14.2.14 本番環境・ステージング環境・開発環境(production / staging / development)

- **一言でいうと**: 利用者が実際に使う環境、本番に近い条件で最終確認する環境、壊して試してよい環境という役割分担です。
- **たとえると**: 舞台の本番、衣装と照明をそろえた通し稽古、稽古場の3段階。稽古場で通っても、本番の照明で初めて分かる問題があります。
- **もう少し詳しく**: 開発環境は失敗してよい場所、ステージング環境は本番相当の条件で確認する場所、本番環境は止めてはいけない場所です。環境名はリソース名やタグへ入れて、操作対象を取り違えないようにします。最も危険なのは、どの環境に接続しているか分からないまま作業することです。
- **この案件では**: 基礎編は学習用の`dev`環境だけを扱います。`environment`は`dev`、リソースグループ名も`rg-portfolio-dev-jpe-001`と環境名を含みます。本番相当やステージングは用意していません。
- **覚え方**: 名前の3文字で見分けます。開発は`dev`、ステージングは`stg`、本番は`prod`のように略す現場が多く、表記は現場ごとに違います。名前に環境が入っていれば誤操作の確率が下がります。
- **つまずきポイント**: 開発環境で通ったから本番でも通ると思いがちですが、権限、ネットワーク経路、データ量が違えば結果は変わります。
- **関連**: 変更管理とリリース / ドライラン / パラメーターシート

### 14.2.15 変更管理とリリース(change management / release)

- **一言でいうと**: 誰の承認で、いつ、何を変えるのかを決めて記録し、実環境へ反映する一連の手続きです。
- **たとえると**: マンションの共用部の工事。住民への告知、管理組合の承認、作業日時の掲示があってから着工します。
- **もう少し詳しく**: 内容、影響範囲、作業時間、戻し方、承認者を書いた申請を出し、承認後に実施して結果を記録します。緊急変更の扱いも先に決めます。手続きは遅くするためではなく、「誰も知らない変更」をなくすためにあります。障害調査で最初に見るのは直前の変更で、記録がなければそこから調べられません。
- **この案件では**: 証跡テンプレートに`変更承認`の欄があり、GitHubのIssueまたはPull RequestのURL、あるいは自己学習と記録します。IaCのため、変更内容はBicepの差分とWhat-Ifの結果で示せます。
- **覚え方**: 語呂で「申・承・実・記」。申請、承認、実施、記録の4拍子です。どれが抜けても後から追えなくなります。
- **つまずきポイント**: 小さい設定変更は申請不要と思いがちですが、判断基準は変更の大きさではなく、影響が届く範囲です。
- **関連**: ロールバック / ADR / ドライラン

### 14.2.16 ロールバック(rollback、切り戻し)

- **一言でいうと**: 変更後に問題が出たとき、変更前の状態へ戻して影響を止める操作です。
- **たとえると**: 書類の前の版を保存しておき、書き直しが失敗したら前の版を開くこと。前の版がなければ戻れません。
- **もう少し詳しく**: 肝心なのは、作業を始める前に戻し方を決めておくことです。設定の戻しは比較的容易ですが、削除したデータはバックアップがなければ戻りません。戻せない作業を「戻せない」と認識して始めるだけで、事故の重さが変わります。
- **この案件では**: 証跡テンプレートの事前確認に「ロールバック方法を確認」の項目があります。構成はBicepの前の版を再デプロイして戻す方針で、学習終了時は`scripts/remove.ps1`にリソースグループ名を二重指定して片付けます。バックアップは未実装の発展課題のため、データは戻せません。
- **覚え方**: roll(転がす)+back(後ろへ)。「前の版まで転がして戻す」。戻し道具のない作業は片道切符だと結びます。
- **つまずきポイント**: 失敗したら元に戻せると思いがちですが、戻せるのは戻す手段を先に用意した範囲だけです。
- **関連**: 変更管理とリリース / 構築手順書 / インシデントと障害対応

### 14.2.17 切り分け(fault isolation、原因の絞り込み)

- **一言でいうと**: 障害の原因がどこまでの範囲にあるかを、順番に確かめて狭めていく作業です。
- **たとえると**: 部屋の照明が点かないとき、電球、スイッチ、ブレーカー、地域の停電と順に見ていく手順です。
- **もう少し詳しく**: 経路がある構成では、通信の順番に沿って端から確かめると最短で絞れます。1回の確認で残る範囲が半分になる問いを選ぶのがコツです。思い込みで真ん中から手を付けると、確かめたはずの箇所を何度も見ることになります。確認した内容と結果を書き残すと、そのまま証跡になります。
- **この案件では**: 通信の順番は`管理者PC → Public IP → NSGの判定 → NIC → VM → Nginx`です。つながらないときはこの順番を逆にたどり、Nginxの稼働、OSの起動、NICとIP、NSGの許可元、手元の経路の順に確認します。
- **覚え方**: 動作イメージで「川を上る」。水が出ない蛇口から配管をさかのぼり、元栓まで1つずつ見ます。
- **つまずきポイント**: 詳しい人は勘で当てると思いがちですが、順番どおり確かめた人のほうが速く、しかも記録が残ります。
- **関連**: インシデントと障害対応 / 単体試験・結合試験・総合試験 / エスカレーション

### 14.2.18 エスカレーション(escalation)

- **一言でいうと**: 自分の権限や知識では解決できない案件を、判断できる上位の担当者や窓口へ引き上げることです。
- **たとえると**: 店頭で判断できない返品を店長へ回すこと。判断できる人へ渡すのが役割であり、放り投げるのとは違います。
- **もう少し詳しく**: 良いエスカレーションは、事象、影響範囲、実施済みの確認、判断してほしいことを添えます。上げる基準は事前に決めておくもので、経過時間や影響範囲で線を引きます。遅らせるほど選べる手が減るため、判断の速さがそのまま被害の大きさを左右します。
- **この案件では**: 基礎編は個人の学習構成で、社内の連絡経路は定義していません。通知(Action Group)も未実装の発展課題です。学習では、`docs/07-operations-runbook.md`の初動を実施した記録をそろえてから質問する練習に置き換えられます。
- **覚え方**: escalator(エスカレーター)と同じ語源で「上の階へ運ぶ」。手ぶらで乗らず、調べた材料を持って上がると覚えます。
- **つまずきポイント**: 自力で解決するほうが偉いと思いがちですが、影響が広がる前に上げる判断のほうが現場では評価されます。
- **関連**: インシデントと障害対応 / 切り分け / SLA / SLO / SLI

### 14.2.19 インシデントと障害対応(incident / incident response)

- **一言でいうと**: サービスに影響が出た出来事がインシデントで、その抑え込みから復旧と記録までの動きが障害対応です。
- **たとえると**: 鉄道の運転見合わせ。まず安全確保と案内、次に原因調査、最後に再発防止の報告という順番で進みます。
- **もう少し詳しく**: 最初にやるのは原因究明ではなく影響の抑え込みです。時刻、症状、範囲、直前の変更を押さえ、ログを保全してから復旧に進みます。復旧後に原因、対応、再発防止、時系列を残します。焦って再起動すると、原因の痕跡ごと消えることがあります。
- **この案件では**: `docs/07-operations-runbook.md`に初動の型「止・見・守・戻・残」があります。止は影響拡大を止める、見は時刻と症状と直前変更を見る、守はログと証跡を保全する、戻は承認済み手順で復旧する、残は原因と時系列を残す、です。
- **覚え方**: 5文字「止・見・守・戻・残」を声に出します。並びを入れ替えないことが要点で、特に3文字目の「守」を飛ばさないことです。
- **つまずきポイント**: 早く直すのが最優先と思いがちですが、記録のない復旧は再発防止につながらず、同じ障害を繰り返します。
- **関連**: 切り分け / エスカレーション / SLA / SLO / SLI

### 14.2.20 SLA / SLO / SLI(Service Level Agreement / Objective / Indicator)

- **一言でいうと**: 提供者と利用者が交わす約束がSLA、社内で狙う目標がSLO、それを測る実測値がSLIです。
- **たとえると**: 宅配便で「翌日までに届けます」が約束、社内で掲げる翌日到着率の目標が目標値、実際の到着時刻の集計が指標です。
- **もう少し詳しく**: SLIは可用率や応答時間などの測定値、SLOはその目標値、SLAは未達だった場合の取り扱いまで含む合意です。順番はSLI、SLO、SLAで、測れないものは目標にできず、目標にできないものは約束できません。AzureのサービスにもSLAがありますが、値はサービスと構成で変わるため、公式のSLA情報で確認します。
- **この案件では**: `docs/03-basic-design.md`に復旧目標を仮置きしていますが、バックアップと冗長化が未実装のため達成手段がありません。面接では、この差を「未実装として認識している」と説明できることが評価点になります。
- **覚え方**: 3語の最後の1文字で並べます。I=Indicator(指標)、O=Objective(目標)、A=Agreement(合意)。測る、狙う、約束するの順に積み上げます。
- **つまずきポイント**: SLAは高いほど良いと思いがちですが、上げるほど構成と運用が重くなります。要件に見合う水準を選ぶ判断こそが仕事です。
- **関連**: 機能要件と非機能要件 / インシデントと障害対応 / 運用引き継ぎ

### 14.2.21 運用引き継ぎ(handover、運用移行)

- **一言でいうと**: 構築した人が、日々動かす担当者へ手順と判断基準を渡し、任せられる状態にすることです。
- **たとえると**: 車を売るときに、鍵だけでなく取扱説明書と整備記録を一緒に渡すこと。鍵だけでは点検も修理もできません。
- **もう少し詳しく**: 渡すのは構成図、パラメーターシート、日次と月次の確認項目、障害時の初動、連絡経路、既知の制約です。とくに「まだできないこと」を明記するのが誠実な引き継ぎです。ここが甘いと、構築者へ問い合わせが戻り続け、次の案件に進めません。
- **この案件では**: `docs/07-operations-runbook.md`が引き継ぎ資料に当たり、毎日と毎月の確認、初動、調査コマンドをまとめています。通知、バックアップ、HTTPS、冗長化が未実装であることも、一緒に伝える対象です。
- **覚え方**: 対比で「作る人」と「回す人」。渡すのは鍵ではなく、鍵と説明書と点検記録の3点セットだと数で覚えます。
- **つまずきポイント**: 資料を渡せば引き継ぎ完了と思いがちですが、完了地点は相手が資料だけで手順を実施できたところです。
- **関連**: 構築手順書 / 属人化 / 棚卸し

### 14.2.22 属人化(その人しかできない状態)

- **一言でいうと**: 特定の人にしか作業や判断ができず、その人が不在だと業務が止まる状態です。
- **たとえると**: 合鍵を1本も作っていない家。持ち主が旅行に出ると、誰も中に入れません。
- **もう少し詳しく**: 手順が頭の中にある、設定が手作業で入っている、記録が個人の端末にある、という条件がそろうと起きます。対策は手順書、コード化、記録の共有場所への集約、レビューの4つです。属人化は能力の問題ではなく、記録と仕組みの問題として扱います。
- **この案件では**: 構成をBicep(`infra/main.bicep`とモジュール`infra/modules/workload.bicep`)で書き、手順を`docs/05-build-guide.md`、運用を`docs/07-operations-runbook.md`へ出しているのが対策です。GitHub ActionsのCIが自動で確認するのも、人に依存しない仕組みの一部です。
- **覚え方**: 属人=「人に属する」。その逆は「文書とコードに属する」。頭の中にある知識を外へ出す作業だと言い換えて覚えます。
- **つまずきポイント**: 詳しい人がいるうちは効率がよいと思いがちですが、休暇と異動と退職で必ず表面化します。
- **関連**: 構築手順書 / 運用引き継ぎ / 棚卸し

### 14.2.23 棚卸し(inventory、資産の洗い出し)

- **一言でいうと**: 今あるものを一覧化し、台帳と実物の差を突き合わせて確認する作業です。
- **たとえると**: 店の在庫確認。帳簿の数と棚の数を数え合わせ、合わない分の理由を追います。
- **もう少し詳しく**: クラウドは作るのが簡単なため、使われないリソースが残って課金され続けます。日を決めてリソース、権限、ログ量、費用を数え、要らないものを消し、要るものを台帳へ反映します。「気付いたら消す」では、気付かないものが残り続けます。
- **この案件では**: `docs/07-operations-runbook.md`の毎月の確認に、Cost Managementでの予算差異と不要リソースの確認、OS更新、容量、ログ量、アカウントとRBACの確認が入っています。学習終了後は`scripts/remove.ps1`で削除し、残った課金対象がないかを確かめます。費用はリージョン、契約、時期で変わるため、実施直前にAzure Pricing CalculatorとCost Managementで確認します。
- **覚え方**: 数字で「月1回、数える」。棚から下ろして数える動作をそのまま思い出せば、頻度と作業内容が一緒に出てきます。
- **つまずきポイント**: 消し忘れは目立つリソースだけと思いがちですが、VMを消してもディスクやPublic IPが残ることがあります。リソースグループ単位で確認します。
- **関連**: パラメーターシート / 属人化 / 運用引き継ぎ

### 14.2.24 手戻り(rework、やり直し)

- **一言でいうと**: 前の工程の抜けや誤りが後の工程で見つかり、そこまで戻って作り直しになることです。
- **たとえると**: 家が建ってから間取りを変える工事。図面の段階なら消しゴムで済んだ変更が、壁を壊す工事になります。
- **もう少し詳しく**: 手戻りの費用は、見つかる工程が後ろになるほど大きくなります。だから要件定義とレビューに時間をかけ、ドライランで先に差分を見て、試験の期待値を先に決めます。この節の用語はすべて手戻りを減らすための道具だと捉えると、24語が一本につながります。
- **この案件では**: `scripts/deploy.ps1`が既定でWhat-Ifだけを表示する設計、証跡テンプレートで予想を先に書く運用、GitHub ActionsのCIによる自動チェックが、いずれも手戻りを前工程で止める仕掛けです。
- **覚え方**: 動作イメージで「戻る距離が費用」。要件で気付けば1歩、構築後に気付けば全工程分。工程表の上を左へ戻る矢印を思い浮かべます。
- **つまずきポイント**: 手戻りは能力不足の証と思いがちですが、早い段階の手戻りは成果です。問題なのは、遅くまで見つからなかった仕組みのほうです。
- **関連**: 要件定義 / キックオフとレビュー / ドライラン

## 14.3 このセクションの覚え方まとめ

```text
要件定義 → 基本/詳細設計 → 構築手順書 → ドライラン → 構築 → 試験 → 証跡 → 引き継ぎ → 運用
   ^                                                                          |
   +--------------------- 手戻り(戻る距離がそのまま費用) ---------------------+
```

- 工程と文書は番号順に対応します。要件は`01`、設計は`03`と`04`、手順は`05`、試験は`06`、運用は`07`、追跡は`09`、証跡は`evidence/`です。ファイル番号を思い出せば工程名が出てきます。
- 暗記するのは2つだけです。障害時の5文字「止・見・守・戻・残」と、変更時の4拍子「申・承・実・記」。残りは工程の順番からたどれます。
- 3語セットは並び順で覚えます。SLI→SLO→SLA(測る→狙う→約束する)、開発→ステージング→本番(壊せる→似せる→守る)、単体→結合→総合(点→線→面)。
- 面接で効く一言は「未実施を`NOT RUN`と書き分けています」です。正常系と異常系、証跡、トレーサビリティの3語が、この一言の裏付けになります。
